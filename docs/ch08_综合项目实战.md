## 1. 概念讲解

### 1.1 什么样的项目才算"做完了"

初学者的项目通常停在"能跑出结果"。而工业界的标准是**别人能复现你的结果**。两者之间的差距，就是这一节要说的四份材料。

| 交付物 | 没有它会怎样 | 最低标准 |
|---|---|---|
| **README** | 别人（包括三个月后的你）不知道怎么编译 | 依赖列表 + 构建命令 + 运行命令 + 预期输出片段 |
| **性能报告** | "我的优化很快"变成一句无法验证的话 | 环境信息 + 基线 + 每一步的收益 + 最终指标 |
| **Profile 证据** | 无法证明瓶颈真的解决了 | ncu/nsys 的关键指标表或截图 |
| **正确性验证脚本** | 优化出错了也不知道 | 一条命令跑完全部对拍，失败时返回非零退出码 |

**一个残酷但真实的标准**：如果你把代码和报告发给一个陌生人（或用一台干净的机器），他能不能在 30 分钟内跑出和你一样的数字？如果不能，这个项目就还没做完。

### 1.2 性能报告怎么写才有说服力

先看一份**不合格**的写法：

> 我优化了矩阵乘法，从 50 GFLOPS 提升到了 5000 GFLOPS，提升了 100 倍。

问题在哪？

1. 没说在哪张卡上（换成一张 H100，起点就不一样）。
2. 没说矩阵形状（不同形状的优化效果差好几倍）。
3. 没说怎么计时的（有没有预热？测几次？含不含显存拷贝？）。
4. "100 倍"这个数字本身可疑：朴素版本之所以慢，很大一部分是访存比例问题，用对的基线会让倍数回归合理区间。

再看**合格**的写法：

> 环境：RTX 3060 12GB (CC 8.6, 28 SM)，驱动 535.104，CUDA 12.3，Ubuntu 22.04。
> 编译：`nvcc -O3 -arch=sm_86 -lineinfo`。
> 测试形状：M=N=K=1024，单精度，外存数据随机初始化（固定种子 1/2）。
> 计时：每组预热 3 次，正式测 20 次，取中位数；计时区间只包含 kernel，不含 H2D/D2H 拷贝。
> 正确性：与 CPU 的 i-k-j 分块实现对比，最大相对误差 4.7e-6，阈值 1e-3。
> 结果：v1 118 GFLOPS → v7 4110 GFLOPS，为 cuBLAS 的 68%。逐步数据见下表。

**记住三条**：

1. **环境 + 参数 + 计时口径必须写全。** 缺任何一个，数据都失去可比性。
2. **报告最小值，也报告中位数。** 噪声只会让耗时变大，所以最小值最接近"纯计算"时间；中位数代表典型表现。
3. **不要只报一个尺寸。** 至少测 4 个形状（比如 512³、1024³、2048³、4096³），并在报告里讨论"为什么某些形状下表现不同"。

### 1.3 为什么必须"从朴素到最优一步一步来"

你可能会想：直接抄一个最优版本不就行了？为什么要写 7 个版本？

因为**优化的价值只有在对比中才能被测量**。如果你只交出最终版本，你无法回答下面这些本报告必答的问题：

- 哪个优化手段贡献最大？（不知道 → 下次遇到别的问题你依然不会优化）
- 哪个手段其实没什么用，甚至有害？（不知道 → 你会一直带着错误的经验）
- 现在的瓶颈在哪？还有多少空间？（不知道 → 你无法判断"该收手了"还是"还差得远"）

而且，实践会告诉你一些"反直觉"的事实。比如在 SGEMM 的 7 个版本里，你大概率会观察到：

- **v6（双缓冲）在 K 很小的时候会比 v5 慢。** 因为流水线的序言/尾声开销占比变高了。
- **v7 的占用率只有 25% 左右，却比高占用率的 v4 快得多。** 因为每个线程有 64 个独立的 FMA 可以发射，指令级并行（ILP）已经足够填满流水线了。
- **某些版本在 1024³ 上排名 A>B，在 512³ 上就变成 B>A。** 因为固定开销（启动、序言）在小规模下占比高。

**这些"反直觉"才是这个项目真正的收获。**

### 1.4 SGEMM 的理论基础：算术强度与 Roofline

在动手之前，先算清楚"理论上能有多快"。这决定了你的优化目标是"合理"还是"妄想"。

**算术强度**（Arithmetic Intensity, AI）定义为：

```
AI = 浮点运算次数 / 访存字节数   （单位：FLOP/Byte）
```

对 `C(M×N) = A(M×K) · B(K×N)`：

- 浮点运算次数 = `2·M·N·K`（一次乘 + 一次加）
- **朴素做法**的访存：每个输出元素读 K 个 A 值 + K 个 B 值，共 `4·M·N·K` 字节读 + `4·M·N` 字节写
  → `AI_naive ≈ 2·M·N·K / (4·M·N·K) ≈ 0.5 FLOP/Byte`
- **理想分块做法**的访存：每个输入元素只从显存读一次，输出只写一次
  → 字节数 = `4·(M·K + K·N + M·N)`，`AI_optimal ≈ 2·M·N·K / (4·(M·K+K·N+M·N))`

对 `M=N=K=1024`：`AI_optimal ≈ 2·1024³ / (4·3·1024²) ≈ 170 FLOP/Byte`。

**Roofline 模型**说：程序能达到的性能上限是

```
性能上限 = min( 峰值算力, AI × 峰值带宽 )
```

一个具体的例子（数字用于说明方法，不代表任何特定型号）：假设某卡峰值单精度算力 13 TFLOPS，峰值带宽 360 GB/s，那么"算力/带宽 = 36 FLOP/Byte"。也就是说：

- `AI < 36` 的程序是**带宽受限**的（Roofline 的斜线段）；
- `AI > 36` 的程序是**算力受限**的（Roofline 的平段）。

因为 `AI_optimal ≈ 170 > 36`，所以**一个充分分块的 SGEMM 是算力受限的** —— 这也是为什么分块能带来巨大收益：它把程序从"带宽受限"搬到了"算力受限"。

**你在报告里应该做的事情**：

1. 查出你显卡的峰值 FP32 算力和峰值带宽（`nvidia-smi -q` + 官网规格，或 `ncu` 的 Speed Of Light 面板）。
2. 算出交叉点 `峰值算力 / 峰值带宽`。
3. 算出你的实现在各形状下的实测 GFLOPS，除以峰值算力，得到"占峰值百分比"。
4. 如果占比 < 20% 而 `AI > 交叉点`，说明还有大量优化空间；如果占比已经 60%~80%，基本可以收手了。

### 1.5 其他项目的领域背景

#### 1.5.1 光线追踪

**核心问题**：屏幕上有 W×H 个像素，每个像素独立地发射一条光线，找它与场景中最近的交点，然后根据材质着色。

**为什么适合练 CUDA**：
- 线程映射极其简单（一个线程 = 一个像素），没有线程间通信，不需要同步；
- 但**工作量非常不均匀**：打到空背景的像素只需要几次求交，打到镜面球的像素可能递归好几层、每条反射光线还要再发一条阴影光线。这会导致 warp 内的线程完成时间差异巨大（**负载不均**），SM 大量时间在等最慢的那个线程。
- 优化手段：把"每个线程一个像素"改成"每个线程一组像素"（提高访存规整度），或者用**工作队列 / 动态调度**（把光线打包成任务，让先完成的线程领新任务）。

**关键概念**：
- **自交（shadow acne）**：光线从表面出发时，如果 `tMin` 取 0，会立刻打中自己。所以 `tMin` 要取一个小正数（本项目的代码里用 `1e-3`）。
- **gamma 校正**：显示器是非线性的，线性颜色要开 2.2 次方（常用平方近似）才能看起来正确。
- **抗锯齿**：每个像素内做多次随机采样再平均（本项目用 xorshift 生成抖动）。

#### 1.5.2 N 体模拟

**核心问题**：N 个质点，两两之间受引力作用，用数值积分推进时间。

**为什么适合练 CUDA**：
- 计算量 `O(N²)`，N=4096 时单步就有 800 万对相互作用，天然适合 GPU；
- 访存模式是"每个线程要读全部 N 个粒子的位置"→ **N 倍的重复读取**，是共享内存分块的经典适用场景（和矩阵乘法 V3 版一模一样的思路）；
- **验证手段特别好**：物理系统有能量守恒，可以量化地验证数值正确性。

**关键概念**：
- **软化因子 ε**：两个粒子距离趋近 0 时引力趋于无穷，程序会算出 Inf/NaN。标准做法是把分母改成 `r² + ε²`。
- **辛积分器**：蛙跳法（Leapfrog / Kick-Drift-Kick）不会让能量单调漂移，而是有界振荡。用欧拉法你会看到能量一直增加，系统"自发升温"。

#### 1.5.3 CNN 推理核

**核心问题**：实现卷积 → 池化 → 全连接的完整前向，并与 PyTorch 对拍。

**为什么适合练 CUDA**：
- 卷积是访存和计算都极重的算子，优化空间巨大；
- 有明确的工业参照（cuDNN / TensorRT），你知道"上限"在哪；
- 能直接对接就业市场。

**实现路线（推荐顺序）**：
1. 直接卷积（naive）：7 层循环，正确但慢；
2. 共享内存 tiling：把输入 tile 和权重 tile 装进共享内存；
3. `im2col + GEMM`：把卷积变成矩阵乘法，直接调用 cuBLAS —— 这是很多框架的实际做法；
4. Winograd F(2x2, 3x3)：把 3x3 卷积的乘法次数减少 2.25 倍；
5. FP16 / TF32 / INT8，配合 [第 6 章](ch06_CUDA高级特性.md) 的张量核心。

#### 1.5.4 SpMV + 共轭梯度

**核心问题**：稀疏矩阵向量乘 + 迭代求解线性方程组 `Ax = b`。

**为什么适合练 CUDA**：
- SpMV 是典型的**带宽受限**算法（每个非零元只有 2 次 FLOP），性能指标是 GB/s 而不是 GFLOPS；
- CG 方法每一步都要做 SpMV + 两次点积 + 两次 axpy，是"多个带宽受限算子串联"的典型，非常适合练习**kernel 融合**；
- 收敛判据、残差计算这些"数值细节"会逼你把工程做严谨。

#### 1.5.5 实时图像处理管线

**核心问题**：把一串图像处理算子（去噪 → 灰度 → 边缘 → 缩放）串成管线，对视频帧持续处理，要求**端到端延迟**低且稳定。

**为什么适合练 CUDA**：
- 单帧的计算量往往很小，**kernel 启动开销成为主要矛盾** → 逼你学 CUDA Graph、多流并发、`cudaMemcpyAsync` + 页锁定内存；
- "延迟"和"吞吐"是两回事：多流能提高吞吐，但可能增加单帧延迟，你要在报告里讨论清楚。

#### 2.1.0 公共基础设施 `sgemm_common.h`

完整文件：[`code/projects/sgemm/sgemm_common.h`](../code/projects/sgemm/sgemm_common.h)

```cpp
#include <vector>
#include <random>
#include <functional>
#include <algorithm>
#include "../common/cuda_check.h"

namespace sgemm {

// GPU 事件计时器
class CudaTimer {
public:
    CudaTimer() {
        CUDA_CHECK(cudaEventCreate(&s_));
        CUDA_CHECK(cudaEventCreate(&e_));
    }
    ~CudaTimer() { cudaEventDestroy(s_); cudaEventDestroy(e_); }
    void start() { CUDA_CHECK(cudaEventRecord(s_, 0)); }
    float stop() {
        CUDA_CHECK(cudaEventRecord(e_, 0));
        CUDA_CHECK(cudaEventSynchronize(e_));
        float ms = 0.f;
        CUDA_CHECK(cudaEventElapsedTime(&ms, s_, e_));
        return ms;
    }
private:
    cudaEvent_t s_{}, e_{};
};

struct Result {
    float ms = 0.f;        // 中位数耗时
    float msMin = 0.f;     // 最小值（最接近"纯计算"的时间）
    double gflops = 0.0;
    double gbps = 0.0;     // 有效带宽：只统计"必须从全局内存读/写"的字节
};

// CPU 参考实现：i-k-j 循环顺序 + 分块。
// 比 i-j-k 快很多：内层写 C 是连续的，读 A[i][k] 是标量广播。
// 注意它只是"参考"，但也不能慢到让验证本身成为瓶颈。
inline void cpuSgemm(int M, int N, int K,
                     const float* __restrict A, const float* __restrict B,
                     float* __restrict C) {
    const int MC = 64, KC = 256, NC = 64;
    std::memset(C, 0, sizeof(float) * (size_t)M * N);
    for (int k0 = 0; k0 < K; k0 += KC) {
        const int kmax = std::min(k0 + KC, K);
        for (int i0 = 0; i0 < M; i0 += MC) {
            const int imax = std::min(i0 + MC, M);
            for (int j0 = 0; j0 < N; j0 += NC) {
                const int jmax = std::min(j0 + NC, N);
                for (int i = i0; i < imax; ++i) {
                    float* cRow = C + (size_t)i * N;
                    const float* aRow = A + (size_t)i * K;
                    for (int k = k0; k < kmax; ++k) {
                        const float aik = aRow[k];
                        const float* bRow = B + (size_t)k * N;
                        for (int j = j0; j < jmax; ++j) cRow[j] += aik * bRow[j];
                    }
                }
            }
        }
    }
}

// 正确性验证：必须用相对误差，浮点结果永远不能直接比 ==
inline bool verify(const std::vector<float>& ref, const std::vector<float>& got,
                   float tol = 1e-3f, bool print = true) {
    double maxAbs = 0.0, maxRel = 0.0;
    size_t worst = 0;
    for (size_t i = 0; i < ref.size(); ++i) {
        double d = std::fabs((double)ref[i] - (double)got[i]);
        double rel = d / std::fmax(1.0, std::fabs((double)ref[i]));
        if (rel > maxRel) { maxRel = rel; worst = i; }
        maxAbs = std::fmax(maxAbs, d);
    }
    // ... 打印 ...
    return maxRel < tol;
}

// 基准测试：预热 + 多次 + 取中位数
inline Result benchmark(const std::function<void()>& launch,
                        int M, int N, int K, int repeat = 20, int warmup = 3) {
    for (int i = 0; i < warmup; ++i) launch();
    CUDA_CHECK(cudaDeviceSynchronize());

    std::vector<float> times;
    CudaTimer timer;
    for (int i = 0; i < repeat; ++i) {
        timer.start();
        launch();
        times.push_back(timer.stop());
    }
    std::sort(times.begin(), times.end());

    Result r;
    r.ms = times[times.size() / 2];       // 中位数：抗离群点
    r.msMin = times.front();              // 最小值：最接近"纯计算"
    const double flops = 2.0 * (double)M * N * K;
    r.gflops = flops / (r.ms * 1e-3) / 1e9;
    const double bytes = 4.0 * ((double)M * K + (double)K * N + (double)M * N);
    r.gbps = bytes / (r.ms * 1e-3) / 1e9;
    return r;
}

}  // namespace sgemm
```

**为什么把 `launch` 做成闭包参数？** 因为这样所有版本共用同一套测量代码。如果每个版本自己写一遍计时逻辑，"v3 比 v4 快"这个结论就可能只是两套计时代码的差异 —— 这种错误在真实项目里非常常见。

#### 2.1.1 v1 —— 朴素三重循环（建立基线）

完整文件：[`code/projects/sgemm/v1_naive.cu`](../code/projects/sgemm/v1_naive.cu)

```cpp
// 每个线程算 C 的一个元素。
// 慢在哪：算 C[i][j] 需要读 A 的第 i 行（K 个 float）和 B 的第 j 列（K 个 float），
// 也就是一次浮点运算配两次全局内存读取。
__global__ void sgemmNaive(int M, int N, int K,
                           const float* __restrict__ A,
                           const float* __restrict__ B,
                           float* __restrict__ C) {
    const int col = blockIdx.x * blockDim.x + threadIdx.x;
    const int row = blockIdx.y * blockDim.y + threadIdx.y;

    // 网格比数据大时线程会越界，必须挡住
    if (row >= M || col >= N) return;

    float acc = 0.f;
    for (int k = 0; k < K; ++k) {
        // A[row][k] 和 B[k][col]：同一个 warp 内 col 连续，
        // 所以 B 的读取是合并的，A 的读取是"广播"（所有线程同地址）。
        // 但这两次读取的比例仍然是 2:1，远高于硬件能承受的水平。
        acc += A[(size_t)row * K + k] * B[(size_t)k * N + col];
    }
    C[(size_t)row * N + col] = acc;
}

// 启动配置：16x16 的线程块
const dim3 block(16, 16);
const dim3 grid((N + block.x - 1) / block.x, (M + block.y - 1) / block.y);
```

**这一版的使命是建立基线，不是快。** 后面的每一版都要和它比，同时确认"优化没有把结果算错"。

#### 2.1.2 v2 —— 寄存器分块（thread tiling）

完整文件：[`code/projects/sgemm/v2_global_tile.cu`](../code/projects/sgemm/v2_global_tile.cu)

**三个问题**：
1. **原来慢在哪？** v1 每算 1 个输出要读 K 个 A 和 K 个 B，访存/计算比是 8 字节 : 2 FLOP。
2. **为什么能变快？** 让每个线程一次算 `TS×TS` 个输出。读 1 个 A 值可以被 TS 个输出复用，读 1 个 B 值同理，访存/计算比降为原来的 1/TS。
3. **怎么证明？** 同一台机器、同一组数据，比 GFLOPS。

```cpp
constexpr int TS = 4;   // 每个线程计算的输出块边长

__global__ void sgemmGlobalTile(int M, int N, int K,
                                const float* __restrict__ A,
                                const float* __restrict__ B,
                                float* __restrict__ C) {
    const int rowStart = (blockIdx.y * blockDim.y + threadIdx.y) * TS;
    const int colStart = (blockIdx.x * blockDim.x + threadIdx.x) * TS;
    if (rowStart >= M || colStart >= N) return;

    // 累加器放在寄存器里：整个 K 循环期间只有它被反复读写，
    // 寄存器访问是零延迟的，这是"用寄存器换访存"的核心。
    float acc[TS][TS];
#pragma unroll
    for (int i = 0; i < TS; ++i)
#pragma unroll
        for (int j = 0; j < TS; ++j) acc[i][j] = 0.f;

    for (int k = 0; k < K; ++k) {
        // 先把这一轮 k 需要的 A 列 和 B 行 一次性读进寄存器数组
        float aReg[TS], bReg[TS];
#pragma unroll
        for (int i = 0; i < TS; ++i)
            aReg[i] = A[(size_t)(rowStart + i) * K + k];
#pragma unroll
        for (int j = 0; j < TS; ++j)
            bReg[j] = B[(size_t)k * N + colStart + j];

        // 每个读进来的值都被用了 TS 次
#pragma unroll
        for (int i = 0; i < TS; ++i)
#pragma unroll
            for (int j = 0; j < TS; ++j) acc[i][j] += aReg[i] * bReg[j];
    }
    // ... 写回，带边界检查 ...
}
```

**这一版仍然从全局内存读**，只是读的次数少了。它留下的两个问题：

1. `B` 的读取模式是 `[k][colStart..colStart+3]`，相邻线程跨了 4 个 float，一个 warp 的访存被拆成更多内存事务；
2. `A` 的同一行数据被块内 16 个不同线程各读了一遍 —— 纯粹的重复劳动。

#### 2.1.3 v3 —— 共享内存分块

完整文件：[`code/projects/sgemm/v3_shared_tile.cu`](../code/projects/sgemm/v3_shared_tile.cu)

```cpp
constexpr int TILE = 32;   // 32x32 的块，正好一个 warp 覆盖一行

__global__ void sgemmSharedTile(int M, int N, int K,
                                const float* __restrict__ A,
                                const float* __restrict__ B,
                                float* __restrict__ C) {
    // [TILE][TILE + 1]：多出来的那一列是经典的"错位填充"，用来打散 bank。
    // 没有它，读 Bs[k][tx] 时一个 warp 内 tx=0..31 会落在 stride=32 的地址上，
    // 全部撞到同一个 bank（32 路冲突），共享内存的优势会被完全吃掉。
    __shared__ float As[TILE][TILE + 1];
    __shared__ float Bs[TILE][TILE + 1];

    const int tx = threadIdx.x;
    const int ty = threadIdx.y;
    const int row = blockIdx.y * TILE + ty;
    const int col = blockIdx.x * TILE + tx;

    float acc = 0.f;
    const int numTiles = (K + TILE - 1) / TILE;
    for (int t = 0; t < numTiles; ++t) {
        // ---- 装载阶段：相邻 tx 读相邻地址，全局访存完全合并 ----
        // 越界填 0 而不是 return：块内所有线程都必须走到 __syncthreads。
        const int aCol = t * TILE + tx;
        As[ty][tx] = (row < M && aCol < K) ? A[(size_t)row * K + aCol] : 0.f;

        const int bRow = t * TILE + ty;
        Bs[ty][tx] = (bRow < K && col < N) ? B[(size_t)bRow * N + col] : 0.f;

        // 屏障 1（生产者-消费者）：保证共享内存写完了，所有人才能开始读
        __syncthreads();

        // ---- 计算阶段：全部数据来自共享内存 ----
#pragma unroll
        for (int k = 0; k < TILE; ++k) acc += As[ty][k] * Bs[k][tx];

        // 屏障 2（防覆盖）：保证所有人都读完了，下一轮才能覆盖共享内存
        __syncthreads();
    }

    if (row < M && col < N) C[(size_t)row * N + col] = acc;
}

// 启动配置：32x32 = 1024 线程（这是每块最大线程数）
const dim3 block(TILE, TILE);
const dim3 grid((N + TILE - 1) / TILE, (M + TILE - 1) / TILE);
```

**为什么输出仍然是每个线程一个元素？** 因为这一版的目标是单独验证"共享内存"这一个手段的收益。一次只改一个变量，收益才可归因 —— 这是优化实验的基本纪律。

**这一版的新瓶颈**：每做 1 次乘加要读 2 次共享内存。共享内存虽快，但 LDS 指令的吞吐也是有限的。瓶颈从全局内存转移到了共享内存。

#### 2.1.4 v4 —— 共享内存 + 4×4 线程级分块

完整文件：[`code/projects/sgemm/v4_thread_tile.cu`](../code/projects/sgemm/v4_thread_tile.cu)

```cpp
constexpr int BM = 64, BN = 64, BK = 16;   // 块级分块
constexpr int TM = 4,  TN = 4;             // 线程级分块
constexpr int THREADS_X = BN / TN;         // 16
constexpr int THREADS_Y = BM / TM;         // 16

__global__ void sgemmThreadTile(int M, int N, int K,
                                const float* __restrict__ A,
                                const float* __restrict__ B,
                                float* __restrict__ C) {
    __shared__ float As[BM][BK + 1];       // padding 1 列，作用同 v3
    __shared__ float Bs[BK][BN + 1];

    const int tx = threadIdx.x;
    const int ty = threadIdx.y;
    const int tid = ty * blockDim.x + tx;

    const int blockRow = blockIdx.y * BM;
    const int blockCol = blockIdx.x * BN;
    const int rowStart = blockRow + ty * TM;   // 本线程负责的 4x4 子块左上角
    const int colStart = blockCol + tx * TN;

    float acc[TM][TN];
#pragma unroll
    for (int i = 0; i < TM; ++i)
#pragma unroll
        for (int j = 0; j < TN; ++j) acc[i][j] = 0.f;

    const int numTiles = (K + BK - 1) / BK;
    for (int t = 0; t < numTiles; ++t) {
        // 装载 As：BM x BK = 64 x 16 = 1024 个元素，256 线程 -> 每人 4 个。
        // 用 一维编号 -> 二维坐标 的展开方式，保证相邻线程访问的全局地址连续。
#pragma unroll
        for (int i = 0; i < BM * BK / (THREADS_X * THREADS_Y); ++i) {
            const int idx = tid + i * (THREADS_X * THREADS_Y);
            const int r = idx / BK, c = idx % BK;
            const int gr = blockRow + r, gc = t * BK + c;
            As[r][c] = (gr < M && gc < K) ? A[(size_t)gr * K + gc] : 0.f;
        }
        // 装载 Bs：BK x BN = 16 x 64，同样每人 4 个。Bs 的行是 K 方向，
        // 列是 N 方向，和 B 在全局内存里的布局一致，所以也是合并访存。
#pragma unroll
        for (int i = 0; i < BK * BN / (THREADS_X * THREADS_Y); ++i) {
            const int idx = tid + i * (THREADS_X * THREADS_Y);
            const int r = idx / BN, c = idx % BN;
            const int gr = t * BK + r, gc = blockCol + c;
            Bs[r][c] = (gr < K && gc < N) ? B[(size_t)gr * N + gc] : 0.f;
        }
        __syncthreads();

        // 每次 k 只读 TM + TN = 8 个共享内存值，却做了 TM * TN = 16 次乘加。
        // 这就是线程级分块的全部价值：访存/计算比从 2:1 降到 0.5:1。
#pragma unroll
        for (int k = 0; k < BK; ++k) {
            float aReg[TM], bReg[TN];
#pragma unroll
            for (int i = 0; i < TM; ++i) aReg[i] = As[ty * TM + i][k];
#pragma unroll
            for (int j = 0; j < TN; ++j) bReg[j] = Bs[k][tx * TN + j];
#pragma unroll
            for (int i = 0; i < TM; ++i)
#pragma unroll
                for (int j = 0; j < TN; ++j) acc[i][j] += aReg[i] * bReg[j];
        }
        __syncthreads();
    }
    // ... 写回 4x4 子块，带边界检查 ...
}
```

**这一版是后面所有高级版本的布局基础。** 从这里开始，"分块"这个词有了两层含义：块级分块（决定共享内存用多大）和线程级分块（决定寄存器里的复用倍数）。

#### 2.1.5 v5 —— float4 向量化访存

完整文件：[`code/projects/sgemm/v5_float4.cu`](../code/projects/sgemm/v5_float4.cu)

**三个问题**：
1. **原来慢在哪？** v4 装载共享内存时每个线程发 4 条 32 位读指令。硬件搬运数据是按"内存事务"（32/64/128 字节）来的，指令条数多意味着更多指令周期、更多地址计算、更高的 LSU 占用。
2. **为什么 float4 会快？** 一条 `LDG.E.128` 指令能搬 16 字节，同样搬 1024 个 float，指令数变成 1/4。
3. **怎么证明？** `ncu` 里 "L1/TEX Load Throughput" 和指令数会明显下降。

```cpp
constexpr int BM = 64, BN = 64, BK = 16;
constexpr int TM = 4, TN = 4;
constexpr int LD_A = BK + 4;    // 20：既保持 16 字节对齐（float4 需要），
constexpr int LD_B = BN + 4;    // 68：又能顺带缓解 bank conflict

__global__ __launch_bounds__(256) void sgemmFloat4(
    int M, int N, int K,
    const float* __restrict__ A, const float* __restrict__ B,
    float* __restrict__ C) {
    // __align__(16)：float4 的读写要求 16 字节对齐。
    // 声明成 __shared__ float 时编译器不保证 16 字节对齐，必须显式声明。
    __shared__ __align__(16) float As[BM * LD_A];
    __shared__ __align__(16) float Bs[BK * LD_B];

    const int tx = threadIdx.x, ty = threadIdx.y;
    const int tid = ty * blockDim.x + tx;
    const int blockRow = blockIdx.y * BM, blockCol = blockIdx.x * BN;

    // 每个线程负责 1 个 float4。
    //   As 是 64x16 = 1024 个 float = 256 个 float4 -> 正好每人一个
    const int aRow  = tid / (BK / 4);              // 0..63
    const int aCol4 = (tid % (BK / 4)) * 4;        // 0,4,8,12
    //   Bs 是 16x64 = 1024 个 float = 256 个 float4
    const int bRow  = tid / (BN / 4);              // 0..15
    const int bCol4 = (tid % (BN / 4)) * 4;        // 0,4,...,60

    float acc[TM][TN];
#pragma unroll
    for (int i = 0; i < TM; ++i)
#pragma unroll
        for (int j = 0; j < TN; ++j) acc[i][j] = 0.f;

    const int numTiles = (K + BK - 1) / BK;
    for (int t = 0; t < numTiles; ++t) {
        {
            const int gr = blockRow + aRow, gc = t * BK + aCol4;
            float4 v = make_float4(0.f, 0.f, 0.f, 0.f);
            // 先判断"整个 float4 都在界内"再读，既安全又能保住向量化指令。
            // 如果改成逐元素判断，编译器会退化成 4 条标量读，白忙一场。
            if (gr < M && gc + 3 < K)
                v = *reinterpret_cast<const float4*>(A + (size_t)gr * K + gc);
            *reinterpret_cast<float4*>(As + aRow * LD_A + aCol4) = v;
        }
        {
            const int gr = t * BK + bRow, gc = blockCol + bCol4;
            float4 v = make_float4(0.f, 0.f, 0.f, 0.f);
            if (gr < K && gc + 3 < N)
                v = *reinterpret_cast<const float4*>(B + (size_t)gr * N + gc);
            *reinterpret_cast<float4*>(Bs + bRow * LD_B + bCol4) = v;
        }
        __syncthreads();

        // 计算部分和 v4 完全一样：访存优化不该改动计算逻辑
#pragma unroll
        for (int k = 0; k < BK; ++k) {
            float aReg[TM], bReg[TN];
#pragma unroll
            for (int i = 0; i < TM; ++i) aReg[i] = As[(ty * TM + i) * LD_A + k];
#pragma unroll
            for (int j = 0; j < TN; ++j) bReg[j] = Bs[k * LD_B + tx * TN + j];
#pragma unroll
            for (int i = 0; i < TM; ++i)
#pragma unroll
                for (int j = 0; j < TN; ++j) acc[i][j] += aReg[i] * bReg[j];
        }
        __syncthreads();
    }
    // ... 写回 ...
}
```

**这一版引入的新代价**：数据必须 16 字节对齐，且尺寸要能整除分块大小，否则要写边界处理代码。生产代码里这一步最容易出隐藏 bug。

#### 2.1.6 v6 —— 双缓冲软件流水线

完整文件：[`code/projects/sgemm/v6_double_buffer.cu`](../code/projects/sgemm/v6_double_buffer.cu)

**三个问题**：
1. **原来慢在哪？** v5 的循环体里三件事严格串行：发起全局读 → `__syncthreads` 等待 → 用共享内存计算。在"等待"那一段，所有线程都闲着。全局内存延迟几百个时钟周期，而一个 BK 块的计算只有几十个周期。
2. **双缓冲怎么解决？** 准备两份共享缓冲，把下一块数据**提前读到寄存器里**（这一步不必等数据到达），然后用当前缓冲做计算 —— 计算的这几十个周期正好用来掩盖寄存器装载的几百周期延迟。
3. **怎么证明？** `ncu` 里 "Warp Stall Reasons" 中的 Long Scoreboard（等全局内存）占比下降。

```cpp
__global__ __launch_bounds__(256) void sgemmDoubleBuffer(
    int M, int N, int K,
    const float* __restrict__ A, const float* __restrict__ B,
    float* __restrict__ C) {
    // 两份缓冲：As[0]/Bs[0] 和 As[1]/Bs[1] 轮流当"当前块"
    __shared__ __align__(16) float As[2][BM * LD_A];
    __shared__ __align__(16) float Bs[2][BK * LD_B];
    // ... 索引计算同 v5 ...

    // ---- 序言：先把第 0 块装进缓冲 0 ----
    // 流水线总要有一次"填不满"的启动过程，这是软件流水线的固有开销。
    { /* 同步加载 tile 0 到 As[0]/Bs[0] */ }
    __syncthreads();

    for (int t = 0; t < numTiles; ++t) {
        const int cur = t & 1;
        const int nxt = (t + 1) & 1;

        // 第 1 步：预取下一块到寄存器。
        // 关键点：这里只是"发射"读指令，线程不会停在原地等数据；
        // 真正使用寄存器里的值是在第 3 步，中间隔着整个计算过程，
        // 几百周期的全局内存延迟就被这段计算盖住了。
        float4 va = make_float4(0.f, 0.f, 0.f, 0.f);
        float4 vb = make_float4(0.f, 0.f, 0.f, 0.f);
        if (t + 1 < numTiles) { /* 发射下一步的 float4 读 */ }

        // 第 2 步：用"当前"缓冲做计算 —— 这段时间就是预取的隐藏期
#pragma unroll
        for (int k = 0; k < BK; ++k) {
            float aReg[TM], bReg[TN];
#pragma unroll
            for (int i = 0; i < TM; ++i) aReg[i] = As[cur][(ty * TM + i) * LD_A + k];
#pragma unroll
            for (int j = 0; j < TN; ++j) bReg[j] = Bs[cur][k * LD_B + tx * TN + j];
#pragma unroll
            for (int i = 0; i < TM; ++i)
#pragma unroll
                for (int j = 0; j < TN; ++j) acc[i][j] += aReg[i] * bReg[j];
        }

        // 第 3 步：等所有人都算完（屏障 A），再把预取的数据写进另一份缓冲，
        // 然后再一次壁垒（屏障 B）保证下一轮所有人都能看到新数据。
        // 屏障 A 必须在写之前：否则会覆盖别人还没读完的旧缓冲。
        __syncthreads();
        if (t + 1 < numTiles) {
            *reinterpret_cast<float4*>(As[nxt] + aRow * LD_A + aCol4) = va;
            *reinterpret_cast<float4*>(Bs[nxt] + bRow * LD_B + bCol4) = vb;
        }
        __syncthreads();
    }
    // ... 写回 ...
}
```

**为什么用"寄存器中转"而不是 `cp.async`？** 因为 `cp.async` 需要 CC ≥ 8.0，而寄存器中转在所有架构上都能用，也更能帮你看清"预取"这件事的本质。[第 6 章](ch06_CUDA高级特性.md) 讲过的 `cuda::pipeline` 是同一思想的库化版本。

**注意：双缓冲不一定总是更快。** K 很小时（循环次数少），序言/尾声开销占比高，可能变慢。这就是为什么"优化"必须用数据说话。

#### 2.1.7 v7 —— 128×128 大块 + 8×8 寄存器分块

完整文件：[`code/projects/sgemm/v7_reg_tile_8x8.cu`](../code/projects/sgemm/v7_reg_tile_8x8.cu)

**三个问题**：
1. **v4~v6 慢在哪？** 线程级分块只有 4×4，每次 k 读 8 个共享内存值只做 16 次乘加，访存/计算比还不够低，C 的数据复用次数也不够。
2. **这一版做了什么？** 线程级分块放大到 8×8（读 16 个值做 64 次乘加）；块级分块放大到 128×128；用 `__launch_bounds__` 告诉编译器"我要 256 线程/块"，让它敢用更多寄存器。
3. **怎么证明？** `ncu` 里 "Compute (SM) Throughput" 应该接近 100%，而 "Memory Throughput" 不再是瓶颈。

```cpp
constexpr int BM = 128, BN = 128, BK = 8;
constexpr int TM = 8, TN = 8;
constexpr int LD_A = BK + 4;    // 12
constexpr int LD_B = BN + 4;    // 132
constexpr int NUM_THREADS = (BM / TM) * (BN / TN);   // 256

__global__ __launch_bounds__(NUM_THREADS, 1) void sgemmRegTile(
    int M, int N, int K,
    const float* __restrict__ A, const float* __restrict__ B,
    float* __restrict__ C) {
    __shared__ __align__(16) float As[BM * LD_A];   // 128 x 12
    __shared__ __align__(16) float Bs[BK * LD_B];   // 8 x 132

    const int tx = threadIdx.x, ty = threadIdx.y;
    const int tid = ty * blockDim.x + tx;
    const int blockRow = blockIdx.y * BM, blockCol = blockIdx.x * BN;
    const int threadRow = ty * TM;   // 0..120
    const int threadCol = tx * TN;   // 0..120

    // 装载索引：As = 128x8 = 1024 float = 256 个 float4 -> 每线程 1 个
    const int aRow  = tid / (BK / 4);              // tid/2  -> 0..127
    const int aCol4 = (tid % (BK / 4)) * 4;
    // Bs = 8x128 = 1024 float = 256 个 float4 -> 每线程 1 个
    const int bRow  = tid / (BN / 4);              // tid/32 -> 0..7
    const int bCol4 = (tid % (BN / 4)) * 4;

    // 64 个累加器全在寄存器里。这是这一版的核心资产，
    // 也是为什么必须用 __launch_bounds__ 保证编译器不去 spill。
    float acc[TM][TN];
#pragma unroll
    for (int i = 0; i < TM; ++i)
#pragma unroll
        for (int j = 0; j < TN; ++j) acc[i][j] = 0.f;

    const int numTiles = (K + BK - 1) / BK;
    for (int t = 0; t < numTiles; ++t) {
        // 装载：每线程恰好 1 个 float4，完美分摊（代码同 v5 的两段）
        { /* As 装载 */ }
        { /* Bs 装载 */ }
        __syncthreads();

        // 计算：8 次 A 读 + 2 次 128 位 B 读，换来 64 次 FMA
#pragma unroll
        for (int k = 0; k < BK; ++k) {
            float a[TM];
#pragma unroll
            for (int i = 0; i < TM; ++i) a[i] = As[(threadRow + i) * LD_A + k];

            // 用 float4 读 B 的一行：一条 LDS.128 指令拿 4 个值。
            // 如果改成逐元素读 b[j] = Bs[k*LD_B + threadCol + j]，
            // 相邻线程的地址间隔是 8 个 float，会撞成 4 路 bank conflict，
            // 共享内存吞吐直接掉到 1/4。
            const float4 b0 = *reinterpret_cast<const float4*>(&Bs[k * LD_B + threadCol]);
            const float4 b1 = *reinterpret_cast<const float4*>(&Bs[k * LD_B + threadCol + 4]);
            const float b[TN] = {b0.x, b0.y, b0.z, b0.w, b1.x, b1.y, b1.z, b1.w};

#pragma unroll
            for (int i = 0; i < TM; ++i)
#pragma unroll
                for (int j = 0; j < TN; ++j) acc[i][j] += a[i] * b[j];
        }
        __syncthreads();
    }
    // ... 写回 8x8 子块 ...
}

// 启动配置：（N/BN, M/BM）= 8x8 个块，每块 256 线程
const dim3 block(THREADS_X, THREADS_Y);   // 16 x 16
const dim3 grid((N + BN - 1) / BN, (M + BM - 1) / BM);
```

**这一版有一个反直觉但重要的现象**：寄存器用量大幅上升（累加器就占 64 个），占用率会降到 25% 左右，但性能反而最好。原因是每个线程有 64 个独立的 FMA 可以发射，**指令级并行（ILP）已经足够填满流水线**了，不再需要靠"更多线程"来隐藏延迟。

**这正是"高寄存器用量 + 低占用率 + 高 ILP"成为现代 GEMM 常态的原因。**

用 `-Xptxas -v` 编译时你应该看到类似输出：

```
ptxas info    : Used 98 registers, 4864 bytes smem, ...
ptxas info    : 0 bytes spill stores, 0 bytes spill loads
```

**`spill stores` 必须是 0！** 出现 spill 说明寄存器不够，累加器被丢到了本地内存（物理上就是全局内存），性能会暴跌。

```cpp
// ---------- 基础数学类型 ----------
struct Vec3 { float x, y, z; };

__host__ __device__ inline Vec3 makeVec(float x, float y, float z) {
    return Vec3{x, y, z};
}
__host__ __device__ inline float dot(const Vec3& a, const Vec3& b) {
    return a.x * b.x + a.y * b.y + a.z * b.z;
}
__host__ __device__ inline Vec3 normalize(const Vec3& a) {
    // 刻意用 1/sqrtf 而不是 rsqrtf：rsqrtf 是设备端专用内在函数，
    // 而这个函数被 CPU 参考实现复用，写成 1/sqrtf 两边都能编译。
    const float len = sqrtf(dot(a, a));
    return a * (1.f / len);
}

// ---------- 场景放在常量内存里 ----------
// 所有线程在每个像素上读的都是同一份数据，
// 常量内存的广播机制正是为这种访问模式设计的。
constexpr int MAX_SPHERES = 16;
__constant__ Sphere c_spheres[MAX_SPHERES];
__constant__ int c_numSpheres;

// ---------- 光线与球求交 ----------
// 解 |o + t*d - c|^2 = r^2，化简成 at^2 + 2*(b/2)t + c0 = 0，取最小的正根。
// 用 b 的一半能省一次乘法，是图形学里的标准写法。
__device__ bool hitSphere(const Sphere& s, const Ray& r,
                          float tMin, float tMax, float& tOut) {
    const Vec3 oc = r.origin - s.center;
    const float a = dot(r.dir, r.dir);
    const float halfB = dot(oc, r.dir);
    const float cc = dot(oc, oc) - s.radius * s.radius;
    const float disc = halfB * halfB - a * cc;
    if (disc < 0.f) return false;              // 判别式小于 0：光线没打中球

    const float sq = sqrtf(disc);
    float t = (-halfB - sq) / a;
    if (t < tMin || t > tMax) {
        t = (-halfB + sq) / a;                 // 近端不在范围里，试远端
        if (t < tMin || t > tMax) return false;
    }
    tOut = t;
    return true;
}

// ---------- 着色：把"递归"展开成循环 ----------
// ★ GPU 上的函数调用栈很浅，递归会带来巨大开销（甚至编译不过），
//   而光线反弹本质上就是一个可以迭代的循环。这个技巧在并行代码里非常常见。
__device__ Vec3 shade(const Ray& r0, int maxDepth) {
    const Vec3 lightDir = normalize(makeVec(0.6f, 1.0f, 0.4f));
    const Vec3 lightColor = makeVec(1.0f, 0.98f, 0.92f);

    Vec3 acc = makeVec(0.f, 0.f, 0.f);          // 已经累积到的颜色
    Vec3 throughput = makeVec(1.f, 1.f, 1.f);   // 当前路径还剩多少能量
    Ray r = r0;

    for (int depth = 0; depth <= maxDepth; ++depth) {
        Hit hit;
        if (!traceScene(r, 1e-3f, 1e30f, hit)) {
            // 背景也要乘 throughput，否则透过镜面球看到的天空会亮得不合理
            const float t = 0.5f * (r.dir.y + 1.f);
            const Vec3 bg = makeVec(1.f, 1.f, 1.f) * (1.f - t)
                          + makeVec(0.5f, 0.7f, 1.0f) * t;
            acc = acc + throughput * bg;
            break;
        }

        float ndotl = fmaxf(dot(hit.n, lightDir), 0.f);
        // 只有朝向光源的面才需要发阴影射线 —— 省掉大约一半的求交
        float shadowFactor = 1.f;
        if (ndotl > 0.f && inShadow(hit.p, lightDir)) shadowFactor = 0.f;

        const Vec3 local = hit.color * lightColor * (ndotl * shadowFactor)
                         + hit.color * AMBIENT;
        // 漫反射部分被吸收掉 (1 - refl)，其余能量进入反射路径
        acc = acc + throughput * local * (1.f - hit.refl);

        if (depth == maxDepth || hit.refl <= 0.f) break;
        throughput = throughput * hit.refl;
        // 反射方向：d - 2(d·n)n
        const Vec3 reflDir = normalize(r.dir - hit.n * (2.f * dot(r.dir, hit.n)));
        r = Ray{hit.p, reflDir};

        // 能量衰减到可以忽略时提前退出：这是最重要的性能优化之一
        if (throughput.x + throughput.y + throughput.z < 0.02f) break;
    }
    return acc;
}

// ---------- 主核函数：一个线程负责一个像素 ----------
__global__ void renderKernel(unsigned char* out, int width, int height,
                             Vec3 camPos, Vec3 camForward, Vec3 camRight, Vec3 camUp,
                             float fovScaleX, float fovScaleY,
                             int samplesPerPixel, int maxDepth, unsigned int seed) {
    const int x = blockIdx.x * blockDim.x + threadIdx.x;
    const int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x >= width || y >= height) return;   // 尺寸不是块的整数倍时必须有

    // 每个线程一个独立的伪随机状态。这里不引入 cuRAND，
    // 用最轻量的 xorshift 就够了 —— 抗锯齿只要求"看起来随机"。
    unsigned int rng = seed + (unsigned int)y * 1973u + (unsigned int)x * 9277u;

    Vec3 accum = makeVec(0.f, 0.f, 0.f);
    for (int s = 0; s < samplesPerPixel; ++s) {
        float jx = 0.f, jy = 0.f;
        if (samplesPerPixel > 1) {
            // ... xorshift 生成亚像素抖动 ...
        }
        // 归一化设备坐标：x 向右为正，y 向上为正
        const float u = ((x + 0.5f + jx) / width * 2.f - 1.f) * fovScaleX;
        const float v = (1.f - (y + 0.5f + jy) / height * 2.f) * fovScaleY;
        const Ray ray{camPos, normalize(camForward + camRight * u + camUp * v)};
        accum = accum + shade(ray, maxDepth);
    }
    Vec3 color = accum * (1.0f / samplesPerPixel);

    // gamma 校正（gamma 2.2 的常用近似：开平方）。
    // 不做这一步图像会明显偏暗。
    color.x = sqrtf(fminf(fmaxf(color.x, 0.f), 1.f));
    color.y = sqrtf(fminf(fmaxf(color.y, 0.f), 1.f));
    color.z = sqrtf(fminf(fmaxf(color.z, 0.f), 1.f));

    const size_t idx = ((size_t)y * width + x) * 3;
    out[idx + 0] = (unsigned char)(color.x * 255.f + 0.5f);
    out[idx + 1] = (unsigned char)(color.y * 255.f + 0.5f);
    out[idx + 2] = (unsigned char)(color.z * 255.f + 0.5f);
}
```

```cpp
// 用 float4 存位置和质量：数组结构体（AoS）里如果只读 pos，
// 却因为结构体对齐把 mass 也一起搬进缓存行，会浪费带宽。
// 把"每次都要一起用的 4 个 float"打包成 float4，一次 16 字节对齐读取就能拿到。
struct Body {
    float4 pos;   // xyz = 位置，w = 质量
    float4 vel;   // xyz = 速度，w = 未使用（留作 padding，保持 16 字节对齐）
};

__constant__ float c_G;
__constant__ float c_softening2;   // eps^2，避免两个粒子距离趋零时力发散

// ★ 这是全程序的热点。朴素写法的访存模式是：
//      每个线程读一遍全部 N 个粒子的位置
//   => 总读取量 N * N * 16 字节，而实际只需要 N * 16 字节。
//   也就是说有 N 倍的重复读取 —— 这正是共享内存分块要解决的问题。
//
// TODO 1（基础）：把 j 循环改写成"块内分块 + 共享内存"。
//   思路：一个 block 负责 BM 个粒子（i 方向），
//         每次从全局内存装载 BTILE 个粒子到共享内存（j 方向），
//         然后块内所有线程用这份共享数据算力，循环覆盖全部 j。
//         这样全局读取量降为 N * N / BM * 16 字节。
// TODO 2（进阶）：加上双缓冲（第 2 章技巧），让下一块 j 的装载与当前块的计算重叠。
__global__ void computeAccel(const Body* __restrict__ bodies,
                             float4* __restrict__ acc, int n) {
    const int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    const float4 pi = bodies[i].pos;
    float ax = 0.f, ay = 0.f, az = 0.f;

    for (int j = 0; j < n; ++j) {
        // TODO 3（基础）：这里跳过 i == j。写成分支会造成 warp divergence，
        //   更好的做法是让 (r_j - r_i) 在 i==j 时天然为 0（分母有 eps 保护）。
        if (j == i) continue;

        const float4 pj = bodies[j].pos;
        const float dx = pj.x - pi.x;
        const float dy = pj.y - pi.y;
        const float dz = pj.z - pi.z;
        const float r2 = dx * dx + dy * dy + dz * dz + c_softening2;

        // rsqrtf 是设备端专用内在函数：硬件近似倒数平方根，比 1/sqrtf 快得多，
        // 物理模拟对这点精度损失完全不敏感。
        const float invR = rsqrtf(r2);
        const float invR3 = invR * invR * invR;
        const float f = c_G * pj.w * invR3;
        ax += f * dx;  ay += f * dy;  az += f * dz;
    }
    acc[i] = make_float4(ax, ay, az, 0.f);
}

// TODO 4（进阶）：把两个核函数用 CUDA Graph 串起来，消除每步的启动开销。
__global__ void integrate(Body* __restrict__ bodies,
                          const float4* __restrict__ acc, int n, float dt) {
    const int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    const float4 a = acc[i];
    float4 v = bodies[i].vel, p = bodies[i].pos;
    v.x += a.x * (0.5f * dt);   // 半步踢
    v.y += a.y * (0.5f * dt);
    v.z += a.z * (0.5f * dt);
    p.x += v.x * dt;            // 漂移
    p.y += v.y * dt;
    p.z += v.z * dt;
    bodies[i].vel = v;
    bodies[i].pos = p;
}
```

**验证手段**：程序会检查所有粒子坐标是否有限（NaN/Inf 检测），并计算总能量。蛙跳法是辛积分器，总能量应当**有界振荡**而不是单调漂移。这是检验物理正确性最有力的工具。

#### 2.4.1 项目四：CNN 推理核

**目标**：手写 Conv2d + ReLU + MaxPool + Linear 的完整前向，并与 PyTorch 逐层对拍。

**架构**：

```
输入图像 (N=8, C=3, H=32, W=32)
   │
   ▼
Conv1: 3→16, 3x3, pad=1  ──► ReLU ──► MaxPool 2x2
   │                                        (8, 16, 16, 16)
   ▼
Conv2: 16→32, 3x3, pad=1 ──► ReLU ──► MaxPool 2x2
   │                                        (8, 32, 8, 8)
   ▼
Flatten ──► Linear 2048→10
   │
   ▼
输出 logits (8, 10)
```

**数据结构**：

```cpp
// NCHW 连续布局（和 PyTorch 默认一致，方便对拍）
struct Tensor {
    float* data;
    int N, C, H, W;
    size_t numel() const { return (size_t)N * C * H * W; }
};
```

**分步实现清单**：

1. **朴素卷积**（必需）：一个线程算一个输出元素，7 层循环。先用它验证正确性。
2. **共享内存 tiling**（必需）：把输入 tile 和权重 tile 装进共享内存；输出按 `(N, K, H_out, W_out)` 四维展开到线程。
   - 注意：3×3 卷积的输入 tile 是 `(TILE_H + 2) × (TILE_W + 2)`，比输出 tile 大一圈（halo 区）。
3. **im2col + GEMM**（推荐）：把输入展开成 `(K·R·S) × (N·H_out·W_out)` 的矩阵，卷积变成一次大 GEMM，直接调 cuBLAS。
   - 优点：几乎立刻能达到 cuBLAS 的性能；缺点：im2col 的中间矩阵可能非常大（显存换性能）。
4. **池化与全连接**（必需）：MaxPool 用"一个线程一个输出 + 局部循环"；全连接直接调 cuBLAS 或用 `sgemm` 的批处理形式。
5. **与原框架对拍**（必需）：逐层对比，而不是只比最终输出 —— 逐层对比能精确定位是哪一层出错。

#### 2.4.2 项目五：SpMV + 共轭梯度求解器

**目标**：用 CSR 格式实现 SpMV，再在其上实现共轭梯度法，求解 `Ax = b`，与 CPU 参考解对比收敛性和精度。

**数据结构**：

```cpp
struct CsrMatrix {

};
```

**CG 算法的每一步**（这决定了你要写哪些 kernel）：

```
r = b - A*x            ← SpMV + axpy
p = r                  ← copy
rsold = dot(r, r)      ← 点积（归约）
for i in 1..maxIter:
    Ap = A*p           ← SpMV
    alpha = rsold / dot(p, Ap)        ← 点积
    x = x + alpha*p                   ← axpy
    r = r - alpha*Ap                  ← axpy
    rsnew = dot(r, r)                 ← 点积
    if sqrt(rsnew) < tol: break       ← 收敛判据（注意用相对残差更稳）
    p = r + (rsnew/rsold)*p           ← axpy
    rsold = rsnew
```

**分步实现清单**：

1. **CSR SpMV 的朴素实现**：一个线程一行（或一个 warp 一行），按行循环累加。
   - **关键问题**：每行的非零元数量差异很大（行长度不均），"一个线程一行"会导致严重的负载不均。
2. **优化一：warp 级合并访存**。同一个 warp 的线程协作处理一行中的多个非零元，用 `__shfl_down_sync` 做归约（[第 3 章](ch03_同步通信与原子操作.md)）。
3. **优化二：向量化**。把 `values`/`colInd` 按 4 个一组处理，用 `float4`/`int4` 降低指令数。
4. **优化三：把两次点积合并**。CG 每轮要做 2~3 次点积，每次点积都是一次归约 kernel + 一趟显存。可以用 CUB 的 `DeviceReduce` 并考虑**融合**（[第 7 章](ch07_生态库与工程化.md) 2.6 节）。
5. **收敛性验证**：对同一个矩阵，与 CPU 的 CG 实现对比每次迭代的残差 2-范数。

**验证方法**：

```cpp
// 相对残差是比"迭代了多少次"更可靠的收敛判据：
//   ||b - Ax||_2 / ||b||_2 < tol
double relRes = sqrt(dotResidual) / sqrt(dotBB);
printf("iter %d: 相对残差 = %.3e\n", iter, relRes);
```

**性能指标**：SpMV 部分只看 **GB/s**（有效带宽 = `(nnz*(4+4) + 2*rows*4) / 时间`），不要看 GFLOPS —— 这就是个带宽受限的算子。

#### 2.4.3 项目六：实时图像处理管线

**目标**：把"高斯去噪 → 灰度化 → Sobel 边缘 → 缩放"串成管线，对连续多帧做处理，优化**端到端延迟**和**帧率**。

**架构**：

```
帧源 (host, 页锁定内存)
   │ cudaMemcpyAsync (流 S1)
   ▼
Stage 1 去噪 (kernel, 流 S1)
   │ 事件 event1
   ▼
Stage 2 灰度 (kernel, 流 S1)
   │
   ▼
Stage 3 Sobel (kernel, 流 S1)
   │
   ▼
Stage 4 缩放 (kernel, 流 S1)
   │ cudaMemcpyAsync (流 S1)
   ▼
输出帧
```

**分步实现清单**：

1. **先把单帧管线跑通**（顺序执行，一段一段来）。测出单帧延迟，作为基线。
2. **用 `cudaMemcpyAsync` + 页锁定内存**（`cudaHostAlloc` 加 `cudaHostAllocDefault`）替换同步拷贝。这一步通常能砍掉相当一部分延迟。
3. **合并 kernel**：灰度化和去噪可以融合成一个 kernel（去噪在灰度图上做效果一样，但少读一次显存）。**这是收益最大的一步。**
4. **引入多流流水**：把帧分成两三个段，不同段在不同流上并发（帧 i 在做 Sobel 时，帧 i+1 在做去噪）。**注意：多流提高的是吞吐（帧率），不一定会降低单帧延迟，甚至可能因为资源竞争而略微增加。** 报告里要把这两个指标分开讨论。
5. **用 CUDA Graph 捕获整个 DAG**，然后重放。这能消除每帧几十次的 kernel 启动开销，对"帧很小、调用很多"的场景收益非常明显。

**验证方法**：
- **正确性**：每一级 Stage 的输出都和 CPU 版本逐像素对拍（相对误差阈值 1e-4）。
- **延迟**：`nsys profile` 看完整个时间线，量出"第一帧输入 → 第一帧输出"的时间。
- **帧率**：稳态下处理 N 帧的总时间 / N。
- **抖动**：报告延迟的 P50 / P95 / P99。实时系统里，**P99 比平均值重要得多**。

## 3. 代码逐行解析

### 3.1 SGEMM 里"为什么每一步都要改对地方"

**v2 → v3 的关键改动**：v2 从全局内存读 `aReg`/`bReg`，v3 改成从共享内存 `As`/`Bs` 读。

```cpp
// v2：
for (int i = 0; i < TS; ++i) aReg[i] = A[(size_t)(rowStart + i) * K + k];
for (int j = 0; j < TS; ++j) bReg[j] = B[(size_t)k * N + colStart + j];

// v3：
__shared__ float As[TILE][TILE + 1];   // 先集中装载
...
for (int k = 0; k < TILE; ++k) acc += As[ty][k] * Bs[k][tx];   // 再从共享内存读
```

**为什么这样改就快了？** 全局内存的延迟是几百个时钟周期，共享内存是二三十个。更关键的是**访问次数**：v2 里 `A` 的同一行被块内 16 个线程各读了一遍，v3 里每个元素只被从全局内存读**一次**，之后 16 个线程共享它。

**v4 的关键改动**：把"一个线程一个输出"改成"一个线程 4×4 个输出"。

```cpp
// v3（每线程 1 个输出）：
float acc = 0.f;
for (int k = 0; k < TILE; ++k) acc += As[ty][k] * Bs[k][tx];
// → 每次 k 读 2 个共享内存值，做 1 次乘加，比值 2:1

// v4（每线程 4x4 个输出）：
float acc[TM][TN];
for (int k = 0; k < BK; ++k) {
    float aReg[TM], bReg[TN];
    for (int i = 0; i < TM; ++i) aReg[i] = As[ty * TM + i][k];   // 4 次读
    for (int j = 0; j < TN; ++j) bReg[j] = Bs[k][tx * TN + j];   // 4 次读
    for (int i = 0; i < TM; ++i)
        for (int j = 0; j < TN; ++j) acc[i][j] += aReg[i] * bReg[j];  // 16 次乘加
}
// → 每次 k 读 8 个共享内存值，做 16 次乘加，比值 0.5:1
```

**这就是 ALL of 优化的本质**：不是让某一步变快，而是**让每次访存服务于更多计算**。

### 3.2 `__syncthreads()` 的两个位置为什么不能搞错

```cpp
// 装载共享内存 ...
__syncthreads();    // 屏障 1：生产者-消费者
// 计算 ...
__syncthreads();    // 屏障 2：防覆盖
```

- **屏障 1 的作用**：保证所有线程都把数据写进共享内存了，才开始读。少了它，某个线程可能读到另一个线程还没写完的脏数据。
- **屏障 2 的作用**：保证所有线程都把当前这块数据读完了，下一轮才能覆盖它。少了它，某个线程可能刚把新数据写进去，另一个线程还在读旧数据。
- **越界填 0 而不是 `return`**：因为 `__syncthreads()` 要求块内**所有**线程都执行到同一行。如果你在边界处提前 `return`，那些线程就不会参与屏障，其他线程会永远等下去（死锁或未定义行为）。这是 [第 3 章](ch03_同步通信与原子操作.md) 最重要的一条纪律。

### 3.3 双缓冲里顺序为什么必须是"计算 → 屏障 → 写入 → 屏障"

```cpp
for (int t = 0; t < numTiles; ++t) {
    const int cur = t & 1, nxt = (t + 1) & 1;

    float4 va = ...;  /* 预取 t+1 到寄存器 */
    /* 用 As[cur] 计算 */          // ← 此时 As[nxt] 里放的是 t-1 轮的数据，没人读
    __syncthreads();                // ← 必须：确认所有人都算完了
    /* 把寄存器写进 As[nxt] */
    __syncthreads();                // ← 必须：确认所有人都写完了，下一轮才能读
}
```

**如果第一个屏障放到"写"后面会怎样？** 会出现这种情况：线程 A 已经算完了，直接把 `va` 写进 `As[nxt]`；而线程 B 还在读 `As[nxt]`（它是 B 的 `cur`）—— 数据被覆盖，结果错误。

**这也是为什么"双缓冲"看起来只多了一份共享内存，实际难点全在同步顺序上。**

### 3.4 光线追踪器里两个容易忽略的细节

**细节一：`tMin` 不能取 0。**

```cpp
if (!traceScene(r, 1e-3f, 1e30f, hit)) { ... }
```

如果 `tMin = 0`，从球面出发的光线会立刻和这个球自己求交（数学上 `t = 0` 是一个合法解），于是整个画面会出现"表面上一块块的黑色斑纹"，这叫 **shadow acne**。标准解法就是把 `tMin` 取一个小正数。

**细节二：背景也要乘 `throughput`。**

```cpp
const Vec3 bg = makeVec(1.f, 1.f, 1.f) * (1.f - t) + makeVec(0.5f, 0.7f, 1.0f) * t;
acc = acc + throughput * bg;      // ← 这个 throughput 不能漏
```

漏掉它的话，透过镜面球看到的天空会和直接看到的天空一样亮 —— 物理上不对（光线被反射一次就衰减了一次）。

### 3.5 CMake 工程里"CPU 回退"的实现要点

```cpp
#ifdef __CUDACC__
// GPU 实现
bool gpuAvailable() {
    int count = 0;
    if (cudaGetDeviceCount(&count) != cudaSuccess) return false;
    return count > 0;
}
#else
void sgemmGPU(...) {
    // 静默退化会让人误以为"GPU 跑了但很慢"，所以这里必须给出提示
    fprintf(stderr, "[提示] 本二进制未编译 CUDA 支持，sgemmGPU 退回 CPU 实现\n");
    sgemmCPU(M, N, K, A, B, C);
}
bool gpuAvailable() { return false; }
#endif
```

**"必须打印提示"这一条是血泪教训。** 如果回退时静默执行，用户看到"GPU 版"和"CPU 版"耗时一样，会得出完全错误的结论（有个同学就曾经因此花了一天排查"为什么我的 GPU 一点没加速"）。

### [挑战] 练习 5：消除 v7 里的 2 路共享内存 bank conflict

1. 用 `ncu` 的 "Shared Memory" 面板确认冲突存在（看 `l1tex__data_bank_conflicts_pipe_lsu_mem_shared` 指标）；
2. 用**共享内存 swizzle**（异或打散）或者**改变 Bs 的存储布局**（比如转置存储）消除它；
3. 证明冲突消除了（指标下降）并且性能提升了。

**提示**：常见的 swizzle 是 `index ^= (index >> 5) & mask` 这类。如果改了之后性能没提升，说明瓶颈已经不在共享内存上了 —— 这也是一个有效结论。

### [挑战] 练习 6：完成 N 体模拟的 5 个 TODO

打开 [`code/projects/nbody/nbody_starter.cu`](../code/projects/nbody/nbody_starter.cu)，按顺序完成 5 个 TODO。每完成一个：

1. 跑正确性（无 NaN + 能量守恒）；
2. 记录性能；
3. 写一句话说明"这一步为什么有效/无效"。

**注意**：TODO 3（消除 `if (j == i)`）可能会让你**变慢**，因为去掉分支之后每个线程多算了一次自身相互作用（虽然力为 0），但省掉了分支开销。到底哪个快取决于架构 —— 这正是需要实测的地方。

## 6. 常见错误与排查

### 6.1 SGEMM 项目

| 错误信息 / 现象 | 原因 | 解决办法 |
|---|---|---|
| 结果全对但性能极差（和 v1 差不多） | 用 Debug 模式编译，或者 `-G` 开着 | 用 `-O3`，去掉 `-G`；确认 `CMAKE_BUILD_TYPE=Release` |
| `spill stores` 不为 0 | 寄存器不够，累加器被丢到本地内存 | 减小 TM/TN，或用 `__launch_bounds__` 调整；不要盲目追求大分块 |
| 结果全 0 | 共享内存装载后忘了 `__syncthreads()` | 检查是否有"装载后立刻读"的路径 |
| 结果偶尔错、偶尔对 | 缺了第二个 `__syncthreads()`（防覆盖） | 在每个 tile 循环末尾补上屏障 |
| 程序挂死 / 卡住不返回 | `__syncthreads()` 在分支里，或者越界时 `return` 了 | 越界一律填 0，不要 return；屏障不能放在条件分支内 |
| `CUDA error: an illegal memory access` | float4 的对齐/边界判断写错 | 确认 `__align__(16)`；确认"整个 float4 都在界内"再读 |
| 性能随矩阵变大而急剧下降 | 分块大小不适合大矩阵（缓存/TLB 压力） | 测多个形状，找到拐点，必要时按形状切换配置 |
| 换成 `float4` 后反而变慢 | 尺寸不是 4 的倍数，编译器退化成逐元素循环 | 确认边界判断是"整个向量在界内"，而不是逐元素判断 |
| 与 cuBLAS 比，误差到了 1e-3 | Ampere 及更新的卡上 cuBLAS 可能启用 TF32 | 这不影响你自己的 kernel；对比正确性时各自和自己的参考比 |
| `-arch=native` 报错 | nvcc 版本低于 11.5 | 换成 `-arch=sm_XX`（查 `nvidia-smi --query-gpu=compute_cap`） |

### 6.2 光线追踪器

| 错误信息 / 现象 | 原因 | 解决办法 |

| 写出的 PPM 打不开 | 文件头写错（P6 必须是 `P6\n宽 高\n255\n`） | 用文本编辑器看一下文件头的前 15 个字节 |

## 7. 本章小结

### 7.1 要点清单

1. **一个项目的完成标准是"别人能复现"**，不是"我这儿能跑"。四份材料：README、性能报告、profile 证据、验证脚本。
2. **性能报告必须写全环境 + 形状 + 计时口径**，否则数据没有意义。
3. **从朴素到最优要一步一步来**，因为每一步的收益必须可归因；而且你会遇到一堆反直觉现象。
4. **先算 Roofline**：`AI × 带宽` 和 `峰值算力` 谁小谁就是上限。SGEMM 充分分块后是算力受限。
5. **SGEMM 的优化主线只有一句话**：让每次访存服务于更多计算。7 个版本分别对应：寄存器复用 → 共享内存复用 → 线程级复用 → 访存指令效率 → 延迟隐藏 → 极致复用。
6. **占用率低不一定慢**。现代 GEMM 是"高寄存器 + 低占用率 + 高 ILP"。
7. **`spill stores` 必须为 0**，否则累加器被丢到本地内存，性能暴跌。
8. **`__syncthreads()` 的两个位置**：装载后（生产者-消费者）、计算后（防覆盖）。越界要填 0，不能 `return`。
9. **双缓冲的顺序**是"预取寄存器 → 计算 → 屏障 → 写入 → 屏障"，顺序错了会覆盖别人正在读的数据。
10. **光线追踪器里 `tMin` 不能为 0**（shadow acne），而且要把递归展开成循环。
11. **N 体的验证靠能量守恒**，不是靠"看起来转得挺圆"。
12. **不同项目有不同的核心指标**：SGEMM/CNN 看 GFLOPS，SpMV/CG 看 GB/s，图像管线看延迟分布（P50/P99）。

### 7.2 自检问题（附答案要点）

**Q1：为什么 v7 的占用率只有 25% 却最快？**
A：因为每个线程持有 64 个独立的累加器，可以连续发射大量互不依赖的 FMA 指令。指令级并行（ILP）已经足够填满 FMA 流水线，不再需要靠"更多并行线程"来隐藏延迟。

**Q2：v4 到 v5 引入 `float4` 收益来自哪里？**
A：装载共享内存时指令数降为 1/4，减少了 LSU 占用和地址计算；同时 128 位的访存让内存事务利用率更高。

**Q3：v6 的双缓冲为什么在 K 很小时可能变慢？**
A：流水线有固定的序言（加载第 0 块）和尾声，K 小时循环次数少，这些固定开销的占比就高；另外多一份共享内存和额外的寄存器会略微降低可并发块数。

**Q4：`__syncthreads()` 少写一个会怎样？**
A：少"装载后"那个，可能读到未写完的数据（结果随机出错）；少"计算后"那个，下一轮装载会覆盖别人正在读的数据（同样随机出错）。这类 bug 往往在小矩阵上不复现，在大矩阵上才出现。

**Q5：为什么光线追踪里要避免递归？**
A：CUDA 的设备端函数调用栈很浅，递归开销大且可能编译不过；而反射路径的展开本质上是可迭代的，写成循环既省栈又更快。

**Q6：`shadow acne` 是什么，怎么解决？**
A：从物体表面出发的光线立刻与自身相交（`t ≈ 0`），导致表面出现黑色斑点。解决办法是把光线求交的 `tMin` 设为一个小的正数（如 1e-3）。

**Q7：N 体模拟怎么验证正确性？**
A：检查所有坐标是否为有限值（NaN/Inf 检测），并计算总能量。使用辛积分器（蛙跳法）时总能量应当有界振荡，而不是单调漂移。

**Q8：做一个 CNN 推理核，第一步应该实现哪个版本？**
A：朴素直接卷积（7 层循环）。先保证正确性，再逐层优化（共享内存 tiling → im2col + GEMM → Winograd → 低精度）。

**Q9：为什么 SpMV 的性能指标是 GB/s 而不是 GFLOPS？**
A：每个非零元只贡献约 2 次浮点运算，但需要读取 4 字节的值 + 4 字节的列号。算术强度极低（< 0.5 FLOP/Byte），远低于 Roofline 的交叉点，所以必然带宽受限。

**Q10：什么样的性能报告是不合格的？**
A：只有一句"提升了 N 倍"而没有环境、形状、计时口径、正确性验证和 profile 证据的报告。任何一项缺失，数据都无法被复现或验证。

这是全书的最后一节。我们不预告"下一章"，而是回答一个问题：**从这里出发，往哪走？**

### 8.1 全书路线回顾

```
第 0 章  环境搭建       ── 能把程序跑起来
   │
第 1 章  编程模型       ── 知道"谁在算什么"（线程索引、SIMT、warp）
   │
第 2 章  内存层次       ── 知道"数据放在哪、怎么搬最省"（这是全书最重要的一章）
   │
第 3 章  同步与原子     ── 知道"多线程怎么协作"（屏障、shuffle、原子、流）
   │
第 4 章  性能方法论     ── 知道"怎么测、怎么找瓶颈、怎么证明变快了"
   │
第 5 章  算法模式       ── 拿到一个新问题能往 Map/Reduce/Scan/Stencil 上靠
   │
第 6 章  高级特性       ── 动态并行、张量核心、异步流水线、集群、多 GPU
   │

   │
```

**回过头看，你会发现一个规律**：真正难的不是语法（`<<<>>>` 一天就能学会），而是三件事：

1. **数据怎么摆放**（行主序/列主序、AoS/SoA、padding、对齐）；
2. **线程怎么映射**（一维/二维、线程级分块的大小、warp 内的访存模式）；
3. **瓶颈在哪里**（访存受限还是计算受限，是延迟问题还是吞吐问题）。

这三件事，你在第 2、4 章和第 8 章反复练过。如果现在让你面对一个全新的算子，你能在半小时内说出"数据怎么摆、线程怎么映射、大概会卡在哪"，那这门课就真的学完了。

### 8.2 四条进阶路线

#### 路线 A：源码级优化（性能工程师方向）

**目标**：把 kernel 性能压到硬件的 80% 以上。

**要学的东西**：
- **SASS 汇编**：`cuobjdump -sass ./app`、`nvdisasm`。看编译器到底生成了什么指令，有没有意外的 spill、有没有把 FMA 拆开、访存是不是向量化的。
- **PTX 与内联汇编**：`asm volatile("mma.sync.aligned...")`，直接控制张量核心指令。
- **架构细节**：每一代 SM 的寄存器文件大小、共享内存/SM 的上限、L2 大小与分区、访存合并的粒度、`cp.async` 的 batch 语义。
- **高级技巧**：寄存器双缓冲、swizzle 消除 bank conflict、CUTLASS 的 warp-level MMA 抽象、persistent kernel（一个常驻 kernel 处理全部工作，消除反复启动）。

**练习建议**：拿本项目的 SGEMM，用 CUTLASS 的文档对照，一个模块一个模块地看它比你多做了什么。**不要直接抄 CUTLASS**，而是"看懂它为什么这么做，然后自己实现一遍"。

**参考**：NVIDIA 的 `cuda-samples`、CUTLASS 仓库与其文档、GPU MODE 的 online 课程、各代架构的 tuning guide。

#### 路线 B：生态库与框架内部（深度学习系统方向）

**目标**：理解 PyTorch / TensorRT / vLLM 这些系统内部是怎么调用 GPU 的。

**要学的东西**：
- **cuDNN / cuBLASLt 的算法选择与 autotune 机制**：为什么同一个卷积在不同形状下会选不同算法。
- **PyTorch 的 ATen / Dispatcher**：一个 `torch.matmul` 从 Python 到 cuBLAS 的完整调用链。
- **算子融合与图优化**：TorchInductor、TensorRT 的 layer fusion 是怎么做的。
- **推理系统**：KV Cache 管理、PagedAttention、Continuous Batching（vLLM 的核心思想）。
- **量化**：INT8/FP8 的量化方案、校准、精度恢复。

**练习建议**：写一个 PyTorch 自定义算子（练习 5 的 softmax），然后对比 `torch.compile` 生成的 Triton kernel，看它的策略和你的有什么不同。

#### 路线 C：跨平台与异构（系统/可移植性方向）

**目标**：让同一套计算代码能跑在 NVIDIA / AMD / Intel / 国产卡上。

**要学的东西**：
- **HIP/ROCm**：用 `hipify-perl` 把你的 CUDA 项目转成 HIP，跑在 AMD 卡上，对比两边性能差异。
- **SYCL/oneAPI**：用 `parallel_for` 重写一个 kernel，体会模板化的 kernel 表达方式。
- **抽象层设计**：怎么设计接口让后端可插拔（第 7 章 1.7 节的原则）。
- **性能可移植性**：同一个 kernel 在不同架构上的最优配置完全不同，怎么做到"自动调优"。

#### 路线 D：AI 编译器与 DSL（编译方向）

**目标**：从"手写 kernel"提升到"写生成 kernel 的编译器"。

**要学的东西**：
- **TVM / MLIR / Triton 的 IR 与调度**：`tile`、`bind`、`vectorize`、`unroll` 这些原语对应到 CUDA 的什么东西。
- **自动调度与搜索**：AutoTVM、Ansor 是怎么搜索最优分块参数的。
- **Polyhedral 编译**：循环变换的数学基础。

**面试里最常考的五个问题**（几乎每一轮都会遇到一个）：

1. 一个 kernel 的线程是怎么映射到数据的？grid/block/thread 三个维度分别用在什么场景？
2. 什么是合并访存？一段代码里怎么判断有没有合并？怎么改？
3. 什么时候用共享内存？怎么消除 bank conflict？`__syncthreads()` 要放在哪？
4. 一个 kernel 慢，你怎么定位？说一个你实际优化过的例子，用了什么指标，提升了多少。
5. 什么情况下你会用 cuBLAS/Thrust，什么情况下自己写 kernel？为什么？

**第 4 题是最重要的。** 面试官想听的不是"我用了共享内存所以变快了"，而是"我先用 ncu 测出是 Long Scoreboard 停顿占主导，判断是全局内存延迟没被掩盖，加了双缓冲做了软件流水线，停顿占比从 X% 降到 Y%，GFLOPS 从 A 提升到 B"。**这正是第 8 章逼你练的那套流程。**

### 8.4 最后三个建议

**第一，把项目放到一个别人能访问的地方。**
放进 GitHub（哪怕是私有仓库），写好 README。面试时能直接打开给面试官看，比"我做过"有说服力得多。

**第二，养成为每一次优化记录"三个问题"的习惯。**
- 原来慢在哪？
- 这个手段为什么能变快？
- 怎么用数据证明它变快了？

这个习惯贯穿了本书的每一章。它不只是写作要求，而是**性能工程师的思维方式**。

**第三，不要停止测量。**
GPU 编程里最容易出现的就是"我觉得这样会更快"。你在这本书里已经见过好几个反例了（双缓冲在小 K 时更慢、低占用率反而最快、自己写的 SAXPY 不会比 PyTorch 快）。**相信数据，不相信直觉 —— 但要先保证你的数据是可信的。**
