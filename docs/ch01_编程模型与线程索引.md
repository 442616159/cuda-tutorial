## 1. 概念讲解

### 1.1 异构计算：谁干活，谁指挥

#### 🍽️ 场景：一家餐厅，经理和后厨

**生活化比喻**：把一个 CUDA 程序想象成**一家餐厅**。

- **Host（CPU）是餐厅经理**。他下单（分配内存）、把原料搬到后厨（拷贝数据）、喊一声"开始做"（启动 kernel），然后就去干别的事了。
- **Device（GPU）是后厨的几百个厨师**。他们拿到同一份菜谱（核函数），每个厨师负责做一道菜的某一部分。
- **kernel 就是那份菜谱**。经理喊"开始做"，厨房里**所有厨师**都同时开始按菜谱做自己的那份。

这里有个初学者最容易崴脚的细节：

> **经理喊完"开始做"就走了（异步），他并不知道菜做完没有。**

这就是为什么你必须在需要结果时加 `cudaDeviceSynchronize()`。

> 🎯 **用餐厅的比喻理解"异步"的后果**：
> 经理喊完"开始做"，**立刻转身去接下一桌客人**（host 继续执行）。
> 如果他这时候就跑去问客人"菜好吃吗"（读结果）——**菜可能还没下锅**。
>
> 所以：**要么等（`cudaDeviceSynchronize()`），要么别急着看结果。**

**严谨定义**：CUDA 采用**异构执行模型**。主机端代码（host code）在 CPU 上串行执行，负责资源管理与任务调度；设备端代码（device code，即核函数）在 GPU 上由大量并行线程执行。两者通过显式或隐式数据搬运协作。

**一个重要推论**：既然 kernel 是"所有线程都执行一遍同样的函数体"——那么**每个线程怎么知道该处理哪一部分数据？**

答案就是本章的主角：**内建变量（built-in variables）**。

> 🎯 **这个问题贯穿整章**。请带着它读 1.2 ~ 1.6 节：
> "如果我是第 12345 号线程，我怎么算出'我该处理第几个数据'？"

### 1.2 三层线程结构：grid / block / thread

#### 🏢 场景：一栋大楼，楼层，办公室，座位

这是 CUDA 编程模型最核心的结构。请先看图：

```text
  Grid（网格）—— 一次 kernel 启动产生的全部线程
  ┌───────────────────────────────────────────────────────────────┐
  │  Block(0,0)     Block(1,0)     Block(2,0)     Block(3,0)      │
  │  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐     │
  │  │ t t t t │    │ t t t t │    │ t t t t │    │ t t t t │     │
  │  │ t t t t │    │ t t t t │    │ t t t t │    │ t t t t │     │
  │  └─────────┘    └─────────┘    └─────────┘    └─────────┘     │
  │     16 个线程     16 个线程      16 个线程      16 个线程        │
  │                                                               │
  │  Block(0,1)     Block(1,1)     Block(2,1)     Block(3,1)      │
  │  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐     │
  │  │ t t t t │    │ t t t t │    │ t t t t │    │ t t t t │     │
  │  │ t t t t │    │ t t t t │    │ t t t t │    │ t t t t │     │
  │  └─────────┘    └─────────┘    └─────────┘    └─────────┘     │
  └───────────────────────────────────────────────────────────────┘
            gridDim  = (4, 2)            一共 8 个块
            blockDim = (4, 4)            每块 16 个线程
            总线程数 = 4*2 * 4*4 = 128
```

**生活化比喻**：把 grid 想象成**一栋大楼**。

- **grid = 整栋楼**。`gridDim.x` 是"每层有几间办公室"，`gridDim.y` 是"有几层"。
- **block = 一间办公室**。`blockDim.x` 是"办公室里横向有几个座位"，`blockDim.y` 是"有几排"。
- **thread = 一个人**。`blockIdx` 是"我在哪间办公室"，`threadIdx` 是"我在办公室里的哪个座位"。

> 🎯 **这个比喻能解释一个关键性质**：
> **"同一间办公室里的人可以互相说话、共用一块白板（共享内存）；但不同办公室的人不行。"**
> 这就是为什么 `__syncthreads()` 和 `__shared__` 的作用范围**只能是块内**（第 2、3 章）。

**三层结构的三个关键性质**：

| 性质                                   | 含义                            | 你要注意什么                                                              |
| -------------------------------------- | ------------------------------- | ------------------------------------------------------------------------- |
| **同一个块内的线程可以同步和共享内存** | 块是最小的"协作单元"            | 需要 `__syncthreads()` 或 `__shared__` 时，协作范围不能跨块（第 2、3 章） |
| **不同块的执行顺序完全不确定**         | 硬件想先跑哪个块就跑到哪个块    | **绝不能**假设 Block 0 比 Block 1 先完成                                  |
| **块与块之间相互独立**                 | 这让 GPU 能在不同 SM 上自由调度 | 这也是 GPU 能扩展到几千核心的原因                                         |

> ⚠️ **第 2 条是新手最容易犯的错**，用大楼的比喻说：
> **"你没法规定'3 楼必须先于 2 楼完成'。"** 物业管理（硬件调度器）想先扫哪层就扫哪层。
> 所以任何"等别的块算完"的代码都是错的——**这是第 3 章"块间同步"要解决的问题**。

**严谨定义**：

- **Grid（网格）**：一次核函数启动对应一个网格，包含 `gridDim.x × gridDim.y × gridDim.z` 个线程块。
- **Block（线程块）**：一组可以互相协作的线程，包含 `blockDim.x × blockDim.y × blockDim.z` 个线程。**同一个块一定被调度在同一个 SM 上**（这保证块内共享内存和同步是可行的）。
- **Thread（线程）**：最小的执行单元，拥有自己的寄存器和程序计数器。
- **Warp**：32 个连续编号的线程组成的硬件调度单位（[1.9 节](#19-simt-与-warp)详讲）。

**尺寸限制**（用 [第 0 章](ch00_环境搭建与第一个程序.md) 的 `device_query` 查到的实际值）：

| 维度         | 常见上限 | 说明                                        |
| ------------ | -------- | ------------------------------------------- |
| `blockDim.x` | 1024     | 三个方向乘积 ≤ 1024（`maxThreadsPerBlock`） |
| `blockDim.y` | 1024     | 老卡（CC 2.x）只有 64                       |
| `blockDim.z` | 64       | 老卡只有 4                                  |
| `gridDim.x`  | 2^31-1   | 大约 21 亿，够用                            |
| `gridDim.y`  | 65535    | **注意：只有 65535！**                      |
| `gridDim.z`  | 65535    | 同上                                        |

> 🧠 每个线程块（Block）的最大线程数**<u>硬性限制</u>**就是 1024，超过会报错 ⚠️

**`gridDim.y` 只有 65535 是个常见的踩坑点**。如果你的矩阵有 100000 行、每块处理 32 行，那 `gridDim.y` 需要 3125，没问题；但如果你每块只处理 1 行，`gridDim.y = 100000` 就会**启动失败**，报 `invalid configuration argument`。

> 💡 **记住这个"数量级"就够用了**：
> - `blockDim` 上限是 **1024**（三位数）
> - `gridDim.x` 上限是 **21 亿**（基本用不完）
> - `gridDim.y/z` 上限是 **65535**（**六万多，容易撞**）
>
> **只有 y/z 方向需要留意**——这就是为什么处理大矩阵时，大家常把它"展平成一维"（[1.6 节](#16-三维索引什么时候真的需要)结尾会讲）。

### 1.3 四个内建变量

#### 🎫 场景：四个"我是谁"的答案

这是本章要背得滚瓜烂熟的东西。它们**不需要声明、不能赋值**，由硬件在核函数开始执行时填好。

> 🎫 **用"公司"的比喻理解这四个变量**：
> - **`gridDim`**：**公司一共几个部门、每个部门几排座位** → "公司有多大"
> - **`blockDim`**：**我这个部门有几排几列** → "我们部门多大"
> - **`blockIdx`**：**我在第几个部门** → "我在哪儿"
> - **`threadIdx`**：**我在部门里的第几号座位** → "我坐哪儿"
>
> **前两个是"规模"（所有线程看到的值都一样），后两个是"位置"（每个线程不同）。**

| 变量        | 类型   | 含义                         | 取值范围                   | 每个线程相同？ |
| ----------- | :----: | ---------------------------- | -------------------------- | -------------- |
| `gridDim`   | `dim3` | 网格的维度（几个块）         | 由 `<<<>>>` 第一个参数决定 | ✅ 都相同      |
| `blockDim`  | `dim3` | 线程块的维度（每块几个线程） | 由 `<<<>>>` 第二个参数决定 | ✅ 都相同      |
| `blockIdx`  | `dim3` | **我在哪个块**（块编号）     | `[0, gridDim)`             | ❌ 各不同      |
| `threadIdx` | `dim3` | **我在本块内是第几号线程**   | `[0, blockDim)`            | ❌ 各不同      |

> 🎯 **最后这一列非常重要**：
> **`gridDim` / `blockDim` 对块内所有线程都一样**——所以在 kernel 里用它们做循环上界、做边界判断是安全的（不会造成 warp 内部分歧）。
> 而 **`blockIdx` / `threadIdx` 每个线程不同**——**用它们做 `if` 判断就可能造成 warp 发散**（[1.9 节](#19-simt-与-warp)）。

**`dim3` 是什么？** 一个含 `x`、`y`、`z` 三个 `unsigned int` 的小结构体。它有两个构造函数：

```cpp
dim3 a;            // a = (1, 1, 1)   —— 默认值是 1，不是 0！
dim3 b(4);         // b = (4, 1, 1)
dim3 c(4, 8);      // c = (4, 8, 1)
dim3 d(4, 8, 16);  // d = (4, 8, 16)
```

> 🧠 **`dim3 a;` 的三个分量都是 1**，不是 0。

这个"默认 1"的设计是为了让一维和二维的写法自然退化：`dim3 b(4)` 等价于 `(4,1,1)`，而 `blockIdx.x * blockDim.x + threadIdx.x` 在 `blockDim.y == 1` 时依然正确。

> 💡 **为什么 `<<<>>>` 里可以直接写数字？**
>
> 因为 `dim3` 有隐式转换：`<<<3, 4>>>` 等价于 `<<<dim3(3), dim3(4)>>>`，也就是 `<<<dim3(3,1,1), dim3(4,1,1)>>>`。
>
> **这就是为什么你可以写 `<<<N, 256>>>` 而不用写 `<<<dim3(N), dim3(256)>>>`**——一维的情况太常见了，所以允许简写。

### 1.4 一维索引：为什么是这个公式

#### 🎫 场景：给全公司员工编一个工号

**问题**：公司有若干**部门**（block），每个部门有若干**员工**（thread）。现在要给**每个员工一个全公司唯一的工号**，怎么编最简单？

**✅ 最自然的编法**：**按部门顺序，一个部门接一个部门地编号**。

```text
   部门 0：[0][1][2][3]        ← 编号 0~3
   部门 1：[4][5][6][7]        ← 编号 4~7
   部门 2：[8][9][10][11]      ← 编号 8~11
```

**这个编法就是公式的来源**：

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
//      └────┬────┘   └───┬───┘   └────┬────┘
//      我在第几个部门   每个部门几人   我在部门内第几号
//      （前面有几个部门，就有几个部门的员工排在我前面）
```

> 🎯 **公式的"人话翻译"**：
> **"我前面的所有部门都排满了人，再加上我在本部门的序号，就是我的工号。"**

**⚠️ 这不是规定，是自然推导。** 请跟着下面的思路走一遍：

**推导**：

1. 一共有 `gridDim.x` 个块，每个块 `blockDim.x` 个线程。
2. 一个块的**起始编号**应该落在它前面所有块之后：

   ```text
   Block 0 的起始编号 = 0
   Block 1 的起始编号 = blockDim.x
   Block 2 的起始编号 = 2 * blockDim.x
   ...
   Block k 的起始编号 = k * blockDim.x
   ```
3. 块内的第 `t` 号线程，编号就是"块的起始编号 + t"：

   ```text
   全局编号 = blockIdx.x * blockDim.x + threadIdx.x
   ```

**验证**（`<<<3, 4>>>`，共 12 个线程）：

| blockIdx.x | threadIdx.x | `blockIdx.x*4 + threadIdx.x` |
| ---------- | ----------- | ---------------------------- |
| 0          | 0           | 0                            |
| 0          | 1           | 1                            |
| 0          | 2           | 2                            |
| 0          | 3           | 3                            |
| 1          | 0           | 4                            |
| 1          | 1           | 5                            |
| 1          | 2           | 6                            |
| 1          | 3           | 7                            |
| 2          | 0           | 8                            |
| 2          | 1           | 9                            |
| 2          | 2           | 10                           |
| 2          | 3           | 11                           |

完美：0 到 11 每个值恰好出现一次。**这个性质叫"双射"（bijection），是索引公式正确的判据。**

> 🎯 **"双射"是检验索引公式对不对的万能办法**：
> **把每个线程算出的编号列出来，看是不是"不重不漏"地覆盖了 0 ~ N-1。**
> 以后你自己写索引公式（尤其是二维、三维、分块的时候），**用这个方法一验就知道对不对**。

**💡 一个关键问题：这个公式是什么顺序？**

注意 `blockIdx.x` 乘的是 `blockDim.x`，也就是"块"是**外层循环**、"线程"是**内层循环**：

```text
for (int blk = 0; blk < gridDim.x; ++blk)      // 外层：块
    for (int t = 0; t < blockDim.x; ++t)       // 内层：块内的线程
        index = blk * blockDim.x + t;
```

这就是编程里最常见的**行主序（row-major）展开**：最右边的下标变化最快。

**为什么要关心这个顺序？** 因为**同一时刻，硬件是把"连续的 32 个线程"（一个 warp）放在一起执行的**。如果你让"全局编号连续的线程访问地址连续的内存"，访存就是最高效的（合并访存，[第 2 章](ch02_内存层次与访存优化.md) 详讲）。上面的公式保证了这一点。

> 🎯 **这里埋下了整本书最重要的一条伏笔**：
> **"线程编号连续" 天然对应 "访问地址连续"——只要你用这个标准公式。**
> 这就是为什么第 2 章反复强调"要让相邻线程访问相邻地址"——**因为默认写法本来就满足，你只要别自己写歪**。

### 1.5 二维索引：C 的数组怎么摆，线程就怎么摆

#### 🪑 场景：用"第几排第几列"找人

**生活化比喻**：一维索引是"给全班同学排一个学号"。二维索引是"用座位号（第几排、第几列）来定位"。

> 🪑 **为什么有了学号还要座位号？**
> 因为**数据本身就是二维的**（一张图片、一个矩阵）。
> 硬把它们压成一维，你就得自己算"第 5 行第 3 列是第几个"——**还不如让线程也用二维坐标，直接对上**。

CUDA 的二维索引用的是和 C 语言数组**完全一致的行主序约定**：

```text
C 里的 float A[HEIGHT][WIDTH]：
    A[r][c] 的线性地址 = r * WIDTH + c
                │         │            │
                │         │            └── 列号，变化最快
                │         └── 每行有多少元素
                └── 行号，变化慢

CUDA 二维线程：
    blockIdx.y = 块的行号（块在 y 方向的第几格）
    blockIdx.x = 块的列号（块在 x 方向的第几格）
    threadIdx.y = 线程在块内的行号
    threadIdx.x = 线程在块内的列号
```

> 🎯 **注意这里的对应关系——这是本章最容易搞混的地方**：
>
> | | C 数组 | CUDA 线程 |
> |---|---|---|
> | **行**（变化慢） | 第一个下标 `r` | **`.y`** |
> | **列**（变化快） | 第二个下标 `c` | **`.x`** |
>
> **`x` 对应"列"（变化最快），`y` 对应"行"。**
> 这和数学上的 `(row, col)` 直觉**是反的**，所以特别容易写错。

**推导全局二维坐标**：

```text
把 grid 看成一个大矩阵，其中：
    每个"格子"是一个 block
    block 内部的坐标是 (threadIdx.x, threadIdx.y)

全局列号（x 方向）：
    我左边有多少个块？blockIdx.x 个，每个块 blockDim.x 列
    所以我的起始列号 = blockIdx.x * blockDim.x
    加上我在块内的列偏移 threadIdx.x：
    col = blockIdx.x * blockDim.x + threadIdx.x

全局行号（y 方向）：
    同理，row = blockIdx.y * blockDim.y + threadIdx.y
```

> 💡 **看出来了吗？它和一维公式长得一模一样，只是"各算各的"。**
> `col` 只用 `.x` 方向的信息，`row` 只用 `.y` 方向的信息——**两个方向完全独立**。
> 这就是为什么二维索引**不需要背新公式**，只需要"把一维公式写两遍"。

**验证**（`grid(3,2)`, `block(2,2)`，共 3×2×2×2 = 24 个线程）：

| blockIdx | threadIdx | row 计算  | col 计算  |
| -------- | --------- | --------- | --------- |
| (0,0)    | (0,0)     | 0*2+0 = 0 | 0*2+0 = 0 |
| (0,0)    | (1,0)     | 0*2+0 = 0 | 0*2+1 = 1 |
| (0,0)    | (0,1)     | 0*2+1 = 1 | 0*2+0 = 0 |
| (0,0)    | (1,1)     | 0*2+1 = 1 | 0*2+1 = 1 |
| (1,0)    | (0,0)     | 0*2+0 = 0 | 1*2+0 = 2 |
| (1,0)    | (1,1)     | 0*2+1 = 1 | 1*2+1 = 3 |
| (2,1)    | (1,1)     | 1*2+1 = 3 | 2*2+1 = 5 |

`row ∈ [0,4)`、`col ∈ [0,6)`，每个 (row, col) 组合恰好被覆盖一次。**还是双射。**

**二维块的尺寸怎么选？** 这是本章最实用的经验之一：

```text
经验规则：blockDim.x 应该是 32 的倍数，blockDim.y 取 4 / 8 / 16。
常见配置：block(32, 8) = 256 线程
          block(32, 16) = 512 线程
          block(64, 4)  = 256 线程
          block(32, 32) = 1024 线程
```

原因：**warp 是沿着 x 方向切的**（`threadIdx.x` 连续变化构成一个 warp）。如果 `blockDim.x` 是 32 的倍数，那么一个 warp 恰好覆盖一整行，这一行的 32 个线程访问的内存是连续的 → 合并访存。

如果 `blockDim.x` 不是 32 的倍数（比如 24），那么一个 warp 会横跨两行，访问就断开了，产生额外的事务。

> 🎯 **这就是"为什么 `blockDim.x` 要是 32 的倍数"的完整理由**：
> **一个 warp 是"按 x 方向连续的 32 个线程"。**
> 所以 **x 方向是"内存连续"的那个方向**（对应数组的最后一维），**必须凑够 32**。
> 而 y 方向随便取，因为它本来就不在 warp 的切分方向上。

### 1.6 三维索引：什么时候真的需要

#### 🧊 场景：一个立方体，用 x/y/z 定位

三维索引的公式就是把上面的思路再套一层——**每个方向各算各的**：

```text
x = blockIdx.x * blockDim.x + threadIdx.x
y = blockIdx.y * blockDim.y + threadIdx.y
z = blockIdx.z * blockDim.z + threadIdx.z
```

**展平成一维线性地址**（比如 `float data[D][H][W]` 的 `data[z][y][x]`）：

```text
线性地址 = (z * H + y) * W + x
         = z * H * W + y * W + x
```

**推导**：在 C 的行主序里，最右边的维度变化最快。所以：

1. 每增加一个 `z`，要跨过整整一个 `H × W` 的平面 → `z * H * W`
2. 每增加一个 `y`，要跨过一整行 `W` → `y * W`
3. `x` 是最后的偏移 → `+ x`

> 🎯 **这个"嵌套"结构要记住**：
> ```text
> (最外层 * 中层大小 + 中层) * 内层大小 + 内层
> ```
> 二维是 `(z) ... ` 的退化版：`r * W + c`
> 四维就是再套一层：`((n * C + c) * H + h) * W + w`
> **看懂这个模式，任意维度你都会算。**

**三维块的展平**（块内 `(tx, ty, tz)` 的线性编号）：

```text
块内编号 = (tz * blockDim.y + ty) * blockDim.x + tx
```

**什么时候真的用三维？**

| 场景                           | 用三维的理由                                           |
| ------------------------------ | ------------------------------------------------------ |
| 3D 体数据（医学 CT、流体模拟） | 数据结构本身就是 3D 的，用三维索引可以省掉手工除法取模 |
| 深度学习里 (N, C, H, W) 张量   | 通常把 `x` 给 W、`y` 给 H、`z` 给 N×C（合并前两维）    |
| 视频处理 (帧, 行, 列)          | `z` 给帧号                                             |

> ⚠️ **但要注意**：三维以上的索引会让"合并访存"变复杂，而且 `blockDim.z` 上限只有 64。
>
> **能用一维展平解决的，就别硬上三维**——手工算线性地址虽然啰嗦，但更容易控制访存模式。
> 这也是为什么真正的高性能 kernel（矩阵乘法、卷积）几乎都是"一维或二维线程块 + 手工展平"。

> 💡 **一句话判断标准**：
> **"这个三维结构，我真的需要让硬件知道它是三维的吗？"**
> 如果只是"我自己算地址方便"，那**展平成一维更灵活**——你还能自由决定哪个维度连续（决定了访存效率）。

### 1.7 越界保护：为什么必须有 `if (i < n)`

#### 🚌 场景：租了一辆 40 座大巴，却只来了 37 个人

假设你要处理 `n = 1000` 个元素，块大小取 256：

```cpp
int gridSize = (n + 255) / 256;   // (1000 + 255)/256 = 4 个块
// 4 个块 × 256 线程 = 1024 个线程，但只有 1000 个元素！
```

启动了 1024 个线程，但数组只有 1000 个元素。

> 🚌 **用大巴的比喻**：
> 你**只能整块整块地租车**（线程数必须是块大小的整数倍），
> 但实际只有 1000 个人要坐车，于是**多出了 24 个空座位**。
>
> **空座位没关系**——但如果你让第 1001 号"乘客"去坐**不存在的座位**（`a[1000]`），那就出事了。

⚠️ **最后 24 个线程算出来的编号是 1000~1023，它们不能去访问 `a[1000]`**。

所以必须加保护：

```cpp
if (i < n) {  // 如果索引到1000了就不允许访问数组的内容了
    out[i] = ...;
}
```

`(n + B - 1) / B` 是**向上取整除法**，用整数运算实现 `ceil(n / B)`。这个写法你会看到成千上万次，请记住。

> 🎯 **向上取整除法的记忆窍门**：
> ```text
> (n + B - 1) / B        ← "先加一个 B-1，再整除"
>
> 直觉：整数除法是"向下取整"，所以先加一点，把它"顶上去"。
> 验算：n=1000, B=256 → (1000+255)/256 = 1255/256 = 4 ✅
>       n=1024, B=256 → (1024+255)/256 = 1279/256 = 4 ✅（刚好整除，不浪费）
>       n=1025, B=256 → (1025+255)/256 = 1280/256 = 5 ✅（多一个，需要第 5 块）
> ```

**❓ 常见疑问：被"浪费"的那 24 个线程，会不会拖慢性能？**

**💡 一个反直觉的真相**：**并不会。**

因为 1024 个线程 = 32 个 warp，硬件本来就是按 warp 调度的：第 31 个 warp（线程 992~1023）里只有 8 个线程真干活，但它本来也只能算一个 warp 的调度单位。所以浪费很小。

**但确实有一种情况很浪费**：

| 情况 | 浪费率 | 说明 |
| ---- | ------ | ---- |
| `n = 1000`，块 256 → 开 4 块 = 1024 线程 | **2.4%** | 几乎无感 ✅ |
| `n = 257`，块 256 → 开 2 块 = 512 线程 | **50%** | 一半线程白跑 ❌ |

> 🎯 **规律：`n` 越接近块大小的整数倍，浪费越小。**
> 当 `n` 比块大小的整数倍"刚好多一点点"时，浪费最严重。
>
> **最极端的例子**：`n = 257`、块 256 → 开了 512 个线程，**255 个白跑**。
> 这种情况怎么办？用 [1.8 节](#18-grid-stride-loop本章最重要的一个模式) 的 **Grid-Stride Loop**——它能让线程数**完全不受数据量影响**。

### 1.8 Grid-Stride Loop：本章最重要的一个模式

#### 📬 场景：10000 封信，只能雇 8 个邮递员

**生活化比喻**：你要把 10000 封信投进 1000 个信箱，但只有 8 个邮递员。

- **❌ 方案 A（朴素版）**：雇 10000 个邮递员，每人投一封信。
  问题是要管 10000 个人的考勤、发工资，**管理成本爆炸**。
- **✅ 方案 B（Grid-Stride）**：雇 8 个邮递员，每人负责一段，**送完自己的就往下走**。

**GPU 上"雇佣线程"的代价**：虽然硬件创建线程几乎免费，但**每多一个线程，它的寄存器、调度状态都要占用资源**。而且当线程数远超 SM 的容量时，多出来的线程只是排队等待——不会带来任何并行度提升，反而增加了被反复换入换出的开销。

> 🎯 **"线程数超过硬件容量"意味着什么？**
> 你的卡每 SM 最多挂 1536 个线程（[第 0 章](ch00_环境搭建与第一个程序.md) 查过），假设有 30 个 SM，那**同时最多只能有 46080 个线程在跑**。
> 如果你启动了 100 万个线程——**多出来的 95 万个只是在排队**。
> **排队本身不慢，但你得为它们准备"上下文"（寄存器），这挤占了真正在跑的线程的资源。**

**Grid-Stride Loop 的标准写法**：

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;      // 起始位置：全局编号
int stride = blockDim.x * gridDim.x;                 // 步长：整个网格的线程总数
for (; i < n; i += stride) {
    out[i] = in[i] + 1.0f;
}
```

**步长为什么是 `blockDim.x * gridDim.x`？** 因为这是"整个网格一次能覆盖多少个元素"。每次循环，所有线程一起往后推进"一整个网格的宽度"，直到越过数组末尾。

**跟着走一遍**（`n = 10`，2 个块 × 4 线程 = 8 个线程，`stride = 8`）：

```text
   第 1 轮： 线程编号 0 1 2 3 4 5 6 7   → 处理 data[0..7]
   第 2 轮： 线程编号 0 1 2 3 4 5 6 7   → 处理 data[8..15]
                     ↑ 但只有 i<10 的会真的执行
                     → 实际处理 data[8]、data[9]
   第 3 轮： i = 16 ≥ 10，所有线程退出循环
```

| 线程 | 第 1 轮 i | 第 2 轮 i | 第 3 轮 i | 共处理 |
| ---- | --------- | --------- | --------- | ------ |
| 0 | 0 ✅ | 8 ✅ | 16 ❌ | 2 个 |
| 1 | 1 ✅ | 9 ✅ | 17 ❌ | 2 个 |
| 2 | 2 ✅ | 10 ❌ | — | 1 个 |
| … | … | … | … | … |
| 7 | 7 ✅ | 15 ❌ | — | 1 个 |

**总数 = 2+2+1+1+1+1+1+1 = 10** ✅ **不重不漏**。

这保证了：

- 每个元素**恰好**被处理一次（不重不漏）；
- 循环条件 `i < n` 天然完成了越界保护，**不需要额外的 `if`**。

> 🎯 **注意最后这一条有多漂亮**：
> **朴素版需要 `if (i < n)` 来挡越界；Grid-Stride 版不需要——因为循环条件本身就是那个保护。**
> 少一个分支，代码更干净，也不会因为分支发散损失性能（[1.9 节](#19-simt-与-warp)）。

**为什么这样更快？** 三个理由：

| # | 理由 | 说明 |
| - | ---- | ---- |
| 1 | **网格规模稳定** | 无论 `n` 是 1000 还是 10 亿，网格大小都固定（比如 1024 个块）。这让"每次启动的开销"可预测 |
| 2 | **更好的缓存局部性** | 同一时刻所有线程访问的是一段连续的地址（因为线程编号连续），天然合并访存；同时"时间局部性"好——下一轮循环访问的地址紧接着上一轮 |
| 3 | **可调优** | 网格大小变成一个**可以调的性能旋钮**。你可以试 `SM数×4`、`SM数×8`、`SM数×16`，找出最快的那一个 |

**网格开多大？** 一个可靠的起点：

```cpp
int deviceId = 0;
cudaDeviceProp prop;
cudaGetDeviceProperties(&prop, deviceId);
int blockSize = 256;
// 每个 SM 挂 4~32 个块都能跑得好；从 "SM数 * 每SM最大块数" 起步
int gridSize = prop.multiProcessorCount * (prop.maxThreadsPerMultiProcessor / blockSize);
// 别超过"按 n 算出来的块数"，否则会启动一堆空块
gridSize = min(gridSize, (n + blockSize - 1) / blockSize);
```

**所有现代 CUDA 程序都应该优先用 Grid-Stride Loop。** 它已经成为事实上的标准写法，你在 CUB、Thrust、cuBLAS 的源码里到处能看到它。

> 💡 **一句话记住 Grid-Stride 的价值**：
> **它把"线程数"和"数据量"彻底解耦了。**
> 数据量是 1000 还是 10 亿，**你的 kernel 代码一模一样，网格大小都在一个合理的范围内**。

### 1.9 SIMT 与 Warp

#### 🎖️ 场景：一个教官带 32 个士兵

**SIMT = Single Instruction, Multiple Threads（单指令多线程）**。

**生活化比喻**：想象一个教官带着 32 个士兵。

- 教官只会喊一条命令，32 个士兵**同时执行同一条命令**（这就是 SIMD 的部分）。
- 但每个士兵可以有自己的"数据"（比如各自的枪口朝向）。
- 如果教官喊"左撇子向左转、右撇子向右转"，那这个队伍就必须**先让左撇子转（右撇子干等），再让右撇子转（左撇子干等）**——这就叫**分支发散（Warp Divergence）**，性能直接减半。

**严谨定义**：**Warp** 是 GPU 硬件调度的基本单位，由 **32 个连续编号的线程**组成。

- 同一个 block 内，`threadIdx` 连续的线程按 32 个一组切分成 warp。
- **同一个 warp 内的 32 个线程共享同一个程序计数器（PC）**，所以它们**必须执行相同的指令**。
- 一个 block 有 `blockDim.x * blockDim.y * blockDim.z / 32` 个 warp（如果不能整除，最后一个 warp 里有多余的线程，它们也是"活的"，只是不干活——所以块大小取 32 的倍数不会有半个 warp 被浪费）。

> 🎯 **"共享同一个程序计数器"是理解 warp 的钥匙**：
> 32 个士兵**共用一张嘴报数**——他们**只能同时走同一步**。
> 谁想走不同的路，就得等别人先走完。

#### 🅰️ 关键推论 1：块大小应当是 32 的倍数

在 `code/lessons/ch01_indices/print_index.cu` 里我用了 `block=4`、`block=6` 这种小尺寸，纯粹是为了让打印输出短一点好读。**真实程序里请用 128/256/512**。

> 💡 **为什么？** 用教官的比喻：
> 一个班**编制就是 32 人**。你派 33 个人，就得开两个班——**第二个班只有 1 个人，但教官照样得到场**。
> 所以 **33 人 = 2 个 warp 的成本**，跟派 64 人一样贵。

#### 🅱️ 关键推论 2：分支发散

看这段代码：

```cpp
// ❌ 坏例子：同一个 warp 内的线程走了不同分支
if (threadIdx.x % 2 == 0) {
    // 偶数号线程走这里
    result = a * b;
} else {
    // 奇数号线程走这里
    result = c + d;
}
```

同一个 warp 里，线程 0、2、4、… 走 if 分支，线程 1、3、5、… 走 else 分支。硬件做不到"同时执行两条指令"，只能：

```text
   时间轴 ──────────────────────────────────────►

   第 1 步：  [偶数线程执行 a*b]  [奇数线程：干等 😐]
   第 2 步：  [偶数线程：干等 😐]  [奇数线程执行 c+d]

   ⇒ 总共花了 2 步。如果所有线程走同一条路，只需 1 步。
```

**执行时间变成两倍。**

**怎么避免？**

| 手段                                     | 说明                                                                                            |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 让分支"整块统一"                         | 如果条件只依赖 `blockIdx`，那整个块要么都走 if、要么都走 else，没有发散                         |
| 把分支改成算术                           | 用 `result = cond ? a*b : c+d;` 这种形式，编译器往往能生成无分支的选择指令（SEL）               |
| 调整数据布局，让同一 warp 的线程走同一路 | 比如排序后再执行                                                                                |
| 尽量让**边界判断**只影响最后一个 warp    | `if (i < n) return;` 里，`i < n` 对大多数 warp 是全部为真，只有边界那个 warp 可能发散——影响很小 |

> ⚠️ **但不要过度恐慌发散。** `if (i < n)` 这种保护几乎是零代价的（最多影响一个 warp）。
>
> 🎯 **真正致命的是"热循环内部、warp 内几乎必然不同"的分支**——比如在一个跑 100 万次的循环里，每次都根据 `threadIdx.x % 2` 分岔。
> **判断严重程度的方法**：看这个分支**被执行多少次**，以及**每次有多少线程走不同路**。

#### 🅾️ 关键推论 3：占用率（Occupancy）初步

```text
占用率 = 每个 SM 上实际驻留的线程数 / 每 SM 支持的最大线程数
```

比如你的卡每 SM 支持 1536 个线程，某个 kernel 加上寄存器和共享内存的限制后，每个 SM 只能挂 768 个线程，那占用率就是 50%。

**占用率为什么重要？** 因为 GPU 隐藏内存延迟的办法就是"切换到别的 warp 去干活"。

> 🎖️ **用教官的比喻**：如果只有一个班在操场上，教官喊"向右转"之后**全班都在等**（内存延迟），教官**没人可换**，只能干等。
> 但如果有 6 个班在场，一班在等的时候，教官可以**转去训练另一个班**——**等待就被藏起来了**。

如果驻留的 warp 太少，一旦所有 warp 都在等内存，SM 就空转了。

**但占用率高 ≠ 性能好**。寄存器用得多（占用率低）往往意味着每个线程在干更多的活、复用了更多数据，可能反而更快。[第 2 章](ch02_内存层次与访存优化.md) 会用矩阵乘法展示这个权衡。

### 1.10 一次 kernel 启动到底发生了什么

#### 🎬 场景：从"经理下令"到"菜端上桌"的完整链条

把上面的概念串起来：

```text
   主机端                             设备端
   ──────                             ──────
   kernel<<<gridDim, blockDim>>>(args)
        │
        ├─ 1. 检查参数合法性（线程数是否超限、共享内存是否超限）
        │     不合法 → 记录错误，host 端拿 cudaGetLastError 能读到
        │
        ├─ 2. 把参数按值打包成一份"内核参数"放进常量内存
        │
        ├─ 3. 把这次启动命令放进流的队列里，host 立即返回
        │
        ▼
                                     ┌─ 4. GPU 的前端从队列里取出任务
                                     │
                                     ├─ 5. 按 SM 的可用资源，把 block 分派下去
                                     │     一个 block 一定整体落在同一个 SM 上
                                     │
                                     ├─ 6. 每个 block 内的线程按 32 个一组切成 warp
                                     │
                                     ├─ 7. warp 调度器每个时钟周期挑一个"就绪"的
                                     │     warp，让它的 32 个线程一起执行一条指令
                                     │
                                     ├─ 8. 遇到长延迟（比如读全局内存），
                                     │     调度器立刻切到另一个 warp（这就是隐藏延迟）
                                     │
                                     └─ 9. 所有 block 完成后，任务的完成事件被标记
```

**理解第 7、8 步，你就理解了 GPU 性能的全部秘密**：GPU 不是让单个线程跑得快，而是**用"很多个 warp 轮流上"来把长延迟藏起来**。

> 🎬 **用"餐厅"的比喻串一遍**（接 [1.1 节](#11-异构计算谁干活谁指挥)）：
>
> | 步骤 | 厨房里发生了什么 |
> | ---- | ---------------- |
> | 1 | 经理检查订单合不合理（参数合法性） |
> | 2 | 把订单内容抄在公告板上（参数放常量内存） |
> | 3 | 经理把订单**贴在出餐口就走了**（异步，host 立即返回） |
> | 4-5 | 后厨主管看到订单，**按各灶台的空闲情况分配任务**（分派 block 到 SM） |
> | 6 | **每 32 个厨师编成一个班组**（切 warp） |
> | 7 | 班组长每次只喊**一条指令**，全班组一起做 |
> | 8 | 张三要等锅烧热（内存延迟），班组长**立刻转头去指挥李四那组** ← **这就是"隐藏延迟"** |
> | 9 | 所有班组做完，这单完成 |
>
> **第 8 步是整个 GPU 设计的精髓**：它不是"让一个人干得快"，而是"**永远不让人闲着**"。

所以：

- 想让程序快 → 让每个 warp 的活干得有价值（合并访存、共享内存复用）；
- 想让延迟藏得住 → 有足够的 warp 可切换（合理的占用率）。

> 🎯 **这两条就是后面第 2 章的两条主线**：
> **"让每次访存更有价值"** 和 **"让 SM 始终有活可干"**。

```cpp
#include <cstdio>

#include "../common/cuda_check.h"

// ------------------------------------------------------------
// 核函数一：打印一维索引的分解与合成
// ------------------------------------------------------------
__global__ void printLinearIndex() {
    int gi = blockIdx.x * blockDim.x + threadIdx.x;  // 全局编号

    // 打印时把"我是谁"和"我算出的全局编号"一起打出来，
    // 这样你就能亲眼看到：不同的 (blockIdx, threadIdx) 组合
    // 被唯一地映射成了一个连续的全局编号。
    printf("块 %2d/%-2d 内线程 %2d/%-2d  ->  全局编号 = %2d*%2d + %2d = %2d\n",
           blockIdx.x, gridDim.x - 1,
           threadIdx.x, blockDim.x - 1,
           blockIdx.x, blockDim.x, threadIdx.x, gi);
}

// ------------------------------------------------------------
// 核函数二：二维线程块，打印二维索引是怎么"展平"的
// ------------------------------------------------------------
__global__ void print2DIndex() {
    // blockDim.x 是每行的线程数，也是二维数组的"列数"
    int flatInBlock = threadIdx.y * blockDim.x + threadIdx.x;
    // 全局二维坐标 = 块坐标 * 块尺寸 + 块内坐标
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;

    printf("  (bx=%d, by=%d) (tx=%d, ty=%d)  块内展平=%2d  全局(row=%d, col=%d)\n",
           blockIdx.x, blockIdx.y, threadIdx.x, threadIdx.y,
           flatInBlock, row, col);
}

// ------------------------------------------------------------
// 核函数三：三维线程块。三维以上 CUDA 不再支持。
// 展平公式：(((z * dim.y) + y) * dim.x) + x
// ------------------------------------------------------------
__global__ void print3DIndex() {
    int flat = (threadIdx.z * blockDim.y + threadIdx.y) * blockDim.x + threadIdx.x;

    int gx = blockIdx.x * blockDim.x + threadIdx.x;
    int gy = blockIdx.y * blockDim.y + threadIdx.y;
    int gz = blockIdx.z * blockDim.z + threadIdx.z;

    printf("  线程(3D) (tx=%d,ty=%d,tz=%d)  块内展平=%2d  全局(x=%d,y=%d,z=%d)\n",
           threadIdx.x, threadIdx.y, threadIdx.z,
           flat, gx, gy, gz);
}

int main() {
    printDeviceInfo();

    // 问一下这台设备的网格维度上限，免得为了演示而超过硬件限制
    int maxGridX = 0, maxGridY = 0, maxGridZ = 0;
    CUDA_CHECK(cudaDeviceGetAttribute(&maxGridX, cudaDevAttrMaxGridDimX, 0));
    CUDA_CHECK(cudaDeviceGetAttribute(&maxGridY, cudaDevAttrMaxGridDimY, 0));
    CUDA_CHECK(cudaDeviceGetAttribute(&maxGridZ, cudaDevAttrMaxGridDimZ, 0));
    printf("本设备网格维度上限: x=%d, y=%d, z=%d\n\n", maxGridX, maxGridY, maxGridZ);

    // ================= 演示 1：一维索引 =================
    // 3 个块 × 4 个线程 = 12 个线程。
    // 故意用非 32 倍数的 4，是为了让打印出来的 12 行短一点。
    printf("========== 演示 1：一维索引 (grid=3, block=4) ==========\n");
    printLinearIndex<<<3, 4>>>();
    CUDA_CHECK_KERNEL();
    CUDA_CHECK_SYNC();      // 必须同步：printf 的输出是异步的

    printf("\n========== 演示 1b：一维索引 (grid=2, block=6) ==========\n");
    printLinearIndex<<<2, 6>>>();
    CUDA_CHECK_KERNEL();
    CUDA_CHECK_SYNC();

    // ================= 演示 2：二维索引 =================
    printf("\n========== 演示 2：二维索引 grid(2,2) block(4,2) ==========\n");
    print2DIndex<<<dim3(2, 2), dim3(4, 2)>>>();
    CUDA_CHECK_KERNEL();
    CUDA_CHECK_SYNC();

    // ================= 演示 3：三维索引 =================
    if (maxGridZ >= 1) {
        printf("\n========== 演示 3：三维索引 grid(1,1,2) block(2,2,2) ==========\n");
        print3DIndex<<<dim3(1, 1, 2), dim3(2, 2, 2)>>>();
        CUDA_CHECK_KERNEL();
        CUDA_CHECK_SYNC();
    }

    printf("\n观察结论：\n");
    printf("  1. printf 的顺序不是按线程编号排的，因为多线程并发写同一个缓冲。\n");
    printf("  2. 但 (blockIdx, threadIdx) 与全局编号的映射是一一对应的、连续的。\n");
    printf("  3. 二维索引的展平等价于行主序数组下标，两者可以放心互相换算。\n");

    return 0;
}
```

### 2.2 `code/lessons/ch01_indices/vector_add.cu` —— 向量加法（本章主菜）

```cpp
// vector_add.cu（完整代码）
#include <cmath>
#include <cstdio>
#include <cstdlib>
#include <vector>

#include "../common/cuda_check.h"
#include "../common/cuda_timer.h"

// ------------------------------------------------------------
// 版本一：最朴素的写法 —— 一个线程一个元素
// ------------------------------------------------------------
__global__ void vectorAddNaive(const float* __restrict__ A,
                               const float* __restrict__ B,
                               float* __restrict__ C,
                               int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;  // 我的全局编号

    // 关键保护：启动的线程数通常是块大小的整数倍，一般会多于 n。
    // 多出来的线程必须直接返回，否则就会越界写坏别人的内存。
    if (i < n) {
        C[i] = A[i] + B[i];
    }
}

// ------------------------------------------------------------
// 版本二：Grid-Stride Loop —— 让"线程数"和"数据量"彻底解耦
// ------------------------------------------------------------
__global__ void vectorAddStrided(const float* __restrict__ A,
                                 const float* __restrict__ B,
                                 float* __restrict__ C,
                                 int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;  // 起始位置
    int stride = blockDim.x * gridDim.x;            // 步长 = 整个网格的线程数

    // 循环条件 i < n 同时完成了"覆盖全部数据"和"越界保护"两件事
    for (; i < n; i += stride) {
        C[i] = A[i] + B[i];
    }
}

// ------------------------------------------------------------
// CPU 参考实现：任何 GPU 程序都必须有可信的 CPU 版本做对拍
// ------------------------------------------------------------
static void vectorAddCPU(const std::vector<float>& A,
                         const std::vector<float>& B,
                         std::vector<float>& C) {
    for (size_t i = 0; i < A.size(); ++i) {
        C[i] = A[i] + B[i];
    }
}

// 逐元素比较，浮点必须用容差而不是 ==
static bool verify(const std::vector<float>& got,
                   const std::vector<float>& ref,
                   float tol = 1e-5f) {
    for (size_t i = 0; i < ref.size(); ++i) {
        if (fabs(got[i] - ref[i]) > tol) {
            fprintf(stderr, "结果不一致 @ i=%zu: got=%f ref=%f\n", i, got[i], ref[i]);
            return false;
        }
    }
    return true;
}

int main() {
    printDeviceInfo();

    // N 取 1<<20 = 1048576（约 100 万）。三个数组各 4 MB，
    // 远低于任何现代显卡的显存，保证小白机器也能跑。
    const int N = 1 << 20;
    const size_t bytes = (size_t)N * sizeof(float);

    // ---- 1. 主机端准备数据 ----
    std::vector<float> hA(N), hB(N), hC(N, 0.0f), hRef(N, 0.0f);
    for (int i = 0; i < N; ++i) {
        hA[i] = 1.0f * i;
        hB[i] = 2.0f * i;
    }
    vectorAddCPU(hA, hB, hRef);

    // ---- 2. 申请设备内存 ----
    float *dA = nullptr, *dB = nullptr, *dC = nullptr;
    CUDA_CHECK(cudaMalloc(&dA, bytes));
    CUDA_CHECK(cudaMalloc(&dB, bytes));
    CUDA_CHECK(cudaMalloc(&dC, bytes));

    // ---- 3. 主机 → 设备 拷贝 ----
    CUDA_CHECK(cudaMemcpy(dA, hA.data(), bytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(dB, hB.data(), bytes, cudaMemcpyHostToDevice));

    // ---- 4. 决定执行配置 ----
    const int blockSize = 256;   // 32 的倍数，通用的安全选择
    // (N + blockSize - 1) / blockSize 是"向上取整除法"
    const int gridSizeNaive = (N + blockSize - 1) / blockSize;

    printf("\n[朴素版]   N = %d, 块大小 = %d, 网格 = %d 个块, 共启动 %d 个线程\n",
           N, blockSize, gridSizeNaive, gridSizeNaive * blockSize);
    printf("          注意：启动了 %d 个线程，但只有 %d 个真干活，浪费了 %.2f%%\n",
           gridSizeNaive * blockSize, N,
           100.0 * (gridSizeNaive * blockSize - N) / (gridSizeNaive * blockSize));

    // ---- 5. 跑朴素版并计时 ----
    double msNaive = CudaTimer::measure([&](double& ms, int) {
        CudaTimer t;
        t.start();
        vectorAddNaive<<<gridSizeNaive, blockSize>>>(dA, dB, dC, N);
        CUDA_CHECK_KERNEL();
        ms = t.stopMs();  // stopMs 内部已经同步，测到的是真实的设备耗时
    }, 10, 2);

    CUDA_CHECK(cudaMemcpy(hC.data(), dC, bytes, cudaMemcpyDeviceToHost));
    bool okNaive = verify(hC, hRef);
    printf("          正确性: %s,  实测中位耗时: %.4f ms\n",
           okNaive ? "通过" : "失败", msNaive);

    // ---- 6. 跑 Grid-Stride 版并计时 ----
    cudaDeviceProp prop{};
    CUDA_CHECK(cudaGetDeviceProperties(&prop, 0));
    int maxBlocksPerSm = prop.maxThreadsPerMultiProcessor / blockSize;
    int gridSizeStrided = prop.multiProcessorCount * maxBlocksPerSm;
    // 再和"按 N 算出来的块数"取小，避免数据量很小时启动一堆空块
    if (gridSizeStrided > gridSizeNaive) gridSizeStrided = gridSizeNaive;
    if (gridSizeStrided < 1) gridSizeStrided = 1;

    printf("\n[Grid-Stride 版] 块大小 = %d, 网格 = %d 个块 (%d SM * %d 块/SM), 共 %d 个线程\n",
           blockSize, gridSizeStrided, prop.multiProcessorCount, maxBlocksPerSm,
           gridSizeStrided * blockSize);
    printf("          每个线程大约要循环 %d 次\n",
           (N + gridSizeStrided * blockSize - 1) / (gridSizeStrided * blockSize));

    std::fill(hC.begin(), hC.end(), 0.0f);
    CUDA_CHECK(cudaMemset(dC, 0, bytes));

    double msStrided = CudaTimer::measure([&](double& ms, int) {
        CudaTimer t;
        t.start();
        vectorAddStrided<<<gridSizeStrided, blockSize>>>(dA, dB, dC, N);
        CUDA_CHECK_KERNEL();
        ms = t.stopMs();
    }, 10, 2);

    CUDA_CHECK(cudaMemcpy(hC.data(), dC, bytes, cudaMemcpyDeviceToHost));
    bool okStrided = verify(hC, hRef);
    printf("          正确性: %s,  实测中位耗时: %.4f ms\n",
           okStrided ? "通过" : "失败", msStrided);

    // ---- 7. 计算有效带宽 ----
    // 一次加法要读 A、读 B、写 C，共 3 * N * 4 字节。
    double bytesMoved = 3.0 * bytes;
    printf("\n[有效性指标] 本次共搬运 %.1f MB\n", bytesMoved / 1024.0 / 1024.0);
    printf("  朴素版      有效带宽: %.1f GB/s\n",
           CudaTimer::bandwidthGBs(bytesMoved, msNaive));
    printf("  Grid-Stride 有效带宽: %.1f GB/s\n",
           CudaTimer::bandwidthGBs(bytesMoved, msStrided));
    printf("  （对比一下你的显卡理论带宽，能到 60%%~85%% 就算正常；\n");
    printf("    在哪张卡上实测约为多少，你的机器可能不同。）\n");

    // ---- 8. 释放设备内存 ----
    CUDA_CHECK(cudaFree(dA));
    CUDA_CHECK(cudaFree(dB));
    CUDA_CHECK(cudaFree(dC));

    printf("\n全部完成。\n");
    return 0;
}
```

### 2.3 `code/lessons/ch01_indices/matrix_add.cu` —— 二维矩阵加法

```cpp
// matrix_add.cu（完整代码）
#include <cmath>
#include <cstdio>
#include <vector>

#include "../common/cuda_check.h"
#include "../common/cuda_timer.h"

// 每块 32x8 = 256 个线程。
// 32 列宽让一个 warp 恰好覆盖一整行，同一 warp 内 32 个线程
// 访问的是矩阵同一行的 32 个连续元素 —— 完美的合并访存。
#define TILE_X 32
#define TILE_Y 8

__global__ void matrixAdd2D(const float* __restrict__ A,
                            const float* __restrict__ B,
                            float* __restrict__ C,
                            int width, int height) {
    // 本线程负责的列下标
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    // 本线程负责的行下标
    int row = blockIdx.y * blockDim.y + threadIdx.y;

    // 两个方向都要检查！只检查一个方向是新手常见的错误。
    if (row < height && col < width) {
        int idx = row * width + col;   // 展平成一维地址
        C[idx] = A[idx] + B[idx];
    }
}

// 对照组：用一维网格做同一件事
__global__ void matrixAdd1D(const float* __restrict__ A,
                            const float* __restrict__ B,
                            float* __restrict__ C,
                            int total) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < total) {
        C[i] = A[i] + B[i];
    }
}

int main() {
    printDeviceInfo();

    const int WIDTH = 1024;
    const int HEIGHT = 1024;
    const size_t count = (size_t)WIDTH * HEIGHT;
    const size_t bytes = count * sizeof(float);

    std::vector<float> hA(count), hB(count), hC(count, 0.0f), hRef(count, 0.0f);
    for (int r = 0; r < HEIGHT; ++r) {
        for (int c = 0; c < WIDTH; ++c) {
            size_t idx = (size_t)r * WIDTH + c;
            hA[idx] = (float)(r + c);
            hB[idx] = (float)(r * 2 - c);
        }
    }
    for (size_t i = 0; i < count; ++i) hRef[i] = hA[i] + hB[i];

    float *dA = nullptr, *dB = nullptr, *dC = nullptr;
    CUDA_CHECK(cudaMalloc(&dA, bytes));
    CUDA_CHECK(cudaMalloc(&dB, bytes));
    CUDA_CHECK(cudaMalloc(&dC, bytes));
    CUDA_CHECK(cudaMemcpy(dA, hA.data(), bytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(dB, hB.data(), bytes, cudaMemcpyHostToDevice));

    // ---------- 二维网格方案 ----------
    dim3 block(TILE_X, TILE_Y);                    // 32 x 8 = 256 线程
    dim3 grid((WIDTH + TILE_X - 1) / TILE_X,       // 列方向向上取整
              (HEIGHT + TILE_Y - 1) / TILE_Y);     // 行方向向上取整

    printf("\n[二维网格] block=(%d,%d)=%d 线程, grid=(%d,%d)=%d 块, 共 %d 线程\n",
           block.x, block.y, block.x * block.y,
           grid.x, grid.y, grid.x * grid.y,
           block.x * block.y * grid.x * grid.y);
    printf("           矩阵 %d x %d = %zu 个元素，启动的线程比元素多 %zu 个（靠 if 保护）\n",
           WIDTH, HEIGHT, count,
           (size_t)block.x * block.y * grid.x * grid.y - count);

    double ms2D = CudaTimer::measure([&](double& ms, int) {
        CudaTimer t;
        t.start();
        matrixAdd2D<<<grid, block>>>(dA, dB, dC, WIDTH, HEIGHT);
        CUDA_CHECK_KERNEL();
        ms = t.stopMs();
    }, 10, 2);

    CUDA_CHECK(cudaMemcpy(hC.data(), dC, bytes, cudaMemcpyDeviceToHost));
    bool ok2D = true;
    for (size_t i = 0; i < count; ++i) {
        if (fabs(hC[i] - hRef[i]) > 1e-5f) { ok2D = false; break; }
    }
    printf("           正确性: %s,  实测中位耗时: %.4f ms,  有效带宽: %.1f GB/s\n",
           ok2D ? "通过" : "失败", ms2D,
           CudaTimer::bandwidthGBs(3.0 * bytes, ms2D));

    // ---------- 一维网格方案（同一份数据） ----------
    const int blockSize1D = 256;
    int gridSize1D = (int)((count + blockSize1D - 1) / blockSize1D);

    printf("\n[一维网格] block=%d, grid=%d, 共 %d 线程\n",
           blockSize1D, gridSize1D, blockSize1D * gridSize1D);

    std::fill(hC.begin(), hC.end(), 0.0f);
    CUDA_CHECK(cudaMemset(dC, 0, bytes));

    double ms1D = CudaTimer::measure([&](double& ms, int) {
        CudaTimer t;
        t.start();
        matrixAdd1D<<<gridSize1D, blockSize1D>>>(dA, dB, dC, (int)count);
        CUDA_CHECK_KERNEL();
        ms = t.stopMs();
    }, 10, 2);

    CUDA_CHECK(cudaMemcpy(hC.data(), dC, bytes, cudaMemcpyDeviceToHost));
    bool ok1D = true;
    for (size_t i = 0; i < count; ++i) {
        if (fabs(hC[i] - hRef[i]) > 1e-5f) { ok1D = false; break; }
    }
    printf("           正确性: %s,  实测中位耗时: %.4f ms,  有效带宽: %.1f GB/s\n",
           ok1D ? "通过" : "失败", ms1D,
           CudaTimer::bandwidthGBs(3.0 * bytes, ms1D));

    printf("\n结论提示：\n");
    printf("  对逐元素这种访存密集、计算极少的操作，两种映射的带宽往往很接近，\n");
```

## 3. 代码逐行解析

### 3.1 `__restrict__` 是什么，为什么要加

```cpp
__global__ void vectorAddNaive(const float* __restrict__ A,
                               const float* __restrict__ B,
                               float* __restrict__ C,
                               int n)
```

`__restrict__` 是对编译器的**承诺**：这个指针是访问它所指内存的**唯一途径**，不存在其他指针指向同一块内存。

**为什么这个承诺值钱？** 看这段代码：

```cpp
C[i] = A[i] + B[i];
```

如果没有 `__restrict__`，编译器必须考虑一种可能：**`C` 和 `A` 指向同一块内存**（别名，aliasing）。那么写 `C[i]` 就可能改变 `A[i]` 的值，于是它**不敢**把 `A[i]`、`B[i]` 的加载提前、不敢做向量化合并、不敢重排指令。

加上 `__restrict__` 之后，编译器知道三个数组互不重叠，就可以放开手脚：把 `A[i]` 和 `B[i]` 的读取合并成一次 128 位的加载、把写回提前、做更激进的调度。

**实测差异**：在一个纯拷贝 kernel 上，加不加 `__restrict__` 常常有 5%~30% 的差别（取决于编译器和架构）。**这是性价比最高的一行注释式优化**，请养成习惯。

⚠️ **但它是"承诺"，不是"检查"**。如果你真的传了两个重叠的指针进去，程序会出错，而且编译器不会告诉你。

### 3.2 `if (i < n)` 的位置很关键

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) {
    C[i] = A[i] + B[i];
}
```

对比一下"不好的写法"：

```cpp
// ❌ 让所有线程都进循环，再在循环里判断
for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n + 1000; i += blockDim.x * gridDim.x) {
    if (i < n) {
        C[i] = A[i] + B[i];
    }
}
```

区别在哪？

- **好写法**：越界判断在 kernel 的最外层。**绝大多数线程只执行 1 次比较就进入主体**，只有边界那个 warp 里可能有部分线程被屏蔽。
- **坏写法**：判断在循环内部，**每次迭代都要判断一次**，白白增加指令数。

所以原则是：**越界保护放在最外层，让"没有越界风险"的路径尽量短。**

### 3.3 Grid-Stride Loop 的步长计算

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
int stride = blockDim.x * gridDim.x;
for (; i < n; i += stride) { ... }
```

**`stride` 为什么是 `blockDim.x * gridDim.x`（只算 x 方向）？**

因为我们的网格是纯一维的：`gridDim.y = gridDim.z = 1`。所以 grid 里的线程总数就是 `blockDim.x * gridDim.x`。

如果你用了二维块，那就得小心：`blockDim.x * blockDim.y * blockDim.z * gridDim.x * gridDim.y * gridDim.z` 才是真正的"网格线程总数"。但**步长取整个网格的线程总数是唯一正确的选择**——如果取少了，就会漏掉元素；取多了，就会重复处理。

**为什么循环开头是 `for (; ...)` 而不是 `for (int i = ...; ...)`？** 因为 `i` 已经在循环外初始化好了（就是全局编号）。这样写只是省一次赋值，同时语义更清晰："从我的全局编号出发，一步一步往前走"。

### 3.4 计时为什么必须"预热 + 取中位数"

```cpp
double msNaive = CudaTimer::measure([&](double& ms, int) {
    CudaTimer t;
    t.start();
    vectorAddNaive<<<gridSizeNaive, blockSize>>>(dA, dB, dC, N);
    CUDA_CHECK_KERNEL();
    ms = t.stopMs();
}, 10, 2);   // 预热 2 次，采样 10 次，取中位数
```

**三个理由**：

1. **必须预热**：第一次执行要经历 GPU 升频（从空闲的低频爬到高频）、指令缓存冷启动、驱动与分配器的懒初始化。第一次往往比后续慢几十个百分点。
2. **必须多次采样**：单次测量充满噪声（操作系统调度、别的进程抢显存、显存刷新）。
3. **取中位数而不是平均值**：偶发的长尾（比如某次被中断打断）会把平均值拉高，中位数更能代表"典型性能"。

**为什么计时用的 `cudaEvent` 而不是 host 的 `clock()`？** 因为 kernel 是异步的：

```cpp
// ❌ 错误示范：这个计时会严重低估
auto t0 = std::chrono::high_resolution_clock::now();
myKernel<<<g, b>>>(...);
auto t1 = std::chrono::high_resolution_clock::now();
// t1 - t0 测到的只是"把启动命令写进队列"的时间，可能只有几微秒！
```

`cudaEventRecord` 把事件记录在 **GPU 的时间线**上，`cudaEventElapsedTime` 得到的是真实的设备端耗时。`CudaTimer::stopMs()` 内部做了 `cudaEventSynchronize`，所以调用它时就自动完成了同步，不会漏掉。

### 3.5 有效带宽：判断"离峰值还有多远"

```cpp
double bytesMoved = 3.0 * bytes;   // 读 A + 读 B + 写 C
printf("有效带宽: %.1f GB/s\n", CudaTimer::bandwidthGBs(bytesMoved, msNaive));
```

**有效带宽（Effective Bandwidth）** = 实际搬运的字节数 ÷ 耗时。

**这个指标为什么重要？** 因为向量加法是一个**算术强度极低**的操作：每搬运 12 字节（读 8 写 4）只做 1 次浮点加法。这种程序**绝不可能**被计算能力限制，只可能被**显存带宽**限制。

所以判断标准很简单：

```text
有效带宽 / 显卡理论带宽 ≥ 60%   → 已经做得不错了
有效带宽 / 显卡理论带宽 < 30%   → 访存模式一定有问题（见第 2 章合并访存）
```

**显卡理论带宽怎么算？** 用 `device_query` 里的两个字段：

```text
理论带宽 (GB/s) ≈ 显存频率(MHz) × 2 (DDR) × 总线宽度(bit) / 8 / 1000
```

以 RTX 3060 笔记本版为例：6001 MHz × 2 × 192 bit / 8 / 1000 ≈ 288 GB/s。（这是粗略估算，实际以厂商规格为准。）

**注意**：`CudaTimer::bandwidthGBs` 里的 `1e9` 是十进制 GB（10^9 字节），和厂商规格一致。不要再乘以 1024 的三次方，否则数字会偏小。

### 3.6 `matrixAdd2D` 的两个边界检查

```cpp
if (row < height && col < width) {
    int idx = row * width + col;
    C[idx] = A[idx] + B[idx];
}
```

**为什么两个都要检查？** 因为二维网格的"越界"有两个独立来源：

```text
WIDTH  = 1000, TILE_X = 32  →  ceil(1000/32) = 32 个块
                        32 * 32 = 1024 列，多出 24 列 → col 越界
HEIGHT = 1000, TILE_Y = 8   →  ceil(1000/8)  = 125 个块
                        125 * 8 = 1000 行，恰好不越界
```

所以经常是"一个方向正好的、另一个方向越界"。**不要假设两个方向对称。**

**这个判断对 warp divergence 有影响吗？** 有一点，但可以接受：

- 对绝大多数块，`row < height && col < width` 全为真；
- 只有**最右列的那些块**（`col` 越界）和**最下面那些块**（`row` 越界）会发散；
- 即使发散，被屏蔽的也是"本来就不该干活"的线程，不是有效工作。

**更优的写法**是用"零填充"思路（把 C 也分配成 pad 后的尺寸），但那样会浪费显存。对"逐元素"操作而言，加判断是最简单也足够好的做法。

### 3.7 关于 `matrixAdd1D` 与 `matrixAdd2D` 的性能对比

我在 `matrix_add.cu` 里特意保留了两个版本，但**预期它们的性能非常接近**。这不是我偷懒，而是一个重要的思维训练：

> **如果有人告诉你"二维网格比一维网格快"，你应该反问他："为什么？"**

推理一下：两个 kernel 都实现了合并访存——`matrixAdd2D` 里同一个 warp 的 32 个线程 `threadIdx.x` 是 0~31（同一个 `threadIdx.y`），`col` 连续，访问 `A[row*width + col]` 是连续的 32 个 float。`matrixAdd1D` 里同一个 warp 的 32 个线程全局编号连续，访问也是连续的 32 个 float。**同样的访存模式，凭什么有性能差异？**

真正的差异只可能来自：

- 索引计算的指令数（二维多几次乘加，但在带宽受限时会被完全掩盖）；
- 越界判断的复杂度；
- 寄存器压力（二维版本多用了 2 个寄存器保存 row/col）。

**结论**：二维网格的价值在**可读性**和**表达能力**（能自然描述"每个线程处理一个 (row, col) 位置"以及邻域关系），而不是性能。**性能优化要用数据说话，不要用直觉说话**——这是 [第 4 章](ch04_性能分析与优化方法论.md) 的全部主题。

```text
 3     7       31
```

编号从 0 到 31 恰好一次。**一般结论**：对任意 `G = gridDim.x`、`B = blockDim.x`，编号 `k = b*B + t`（其中 `b ∈ [0,G)`、`t ∈ [0,B)`）是 `[0, G*B)` 上的双射。证明思路：把 `k` 做整除和取模——`b = k / B`、`t = k % B`，唯一确定。

</details>

### 练习 1.2 [基础] 把二维索引换算成线性地址

有一个 `float A[64][96]`（行主序），线程 `blockIdx=(2,1)`、`threadIdx=(5,3)`、`blockDim=(16,4)`。

**要求**：算出该线程应处理的 `(row, col)`，以及 `A[row][col]` 的线性地址。

<details>
<summary>参考做法</summary>

```text
row = blockIdx.y * blockDim.y + threadIdx.y = 1*4 + 3 = 7
col = blockIdx.x * blockDim.x + threadIdx.x = 2*16 + 5 = 37

线性地址 = row * 96 + col = 7*96 + 37 = 672 + 37 = 709
```

验证边界：`row=7 < 64` ✓，`col=37 < 96` ✓，所以不需要保护。另外注意 `block(16,4)` 的 `blockDim.x = 16` **不是 32 的倍数**，会导致一个 warp 横跨两行（性能隐患）。改成 `block(32,4)` 更好。

</details>

### 练习 1.3 [基础] 块大小必须是 32 的倍数吗？

**要求**：写一个 kernel，用 `blockSize = 100` 处理 N = 10000 个元素，观察：

1. 一共启动多少个线程？浪费多少？
2. 一共产生多少个 warp？（提示：`ceil(100/32) = 4`，第 4 个 warp 只有 4 个有效线程）
3. 换成 `blockSize = 128` 再算一遍，浪费率从多少降到多少？

<details>
<summary>参考做法</summary>

```text
blockSize = 100：
    网格 = ceil(10000/100) = 100 个块
    总线程 = 100 * 100 = 10000 —— 恰好，没浪费
    但每个块有 ceil(100/32) = 4 个 warp，共 100*4 = 400 个 warp
    有效线程 = (3*32 + 4) * 100 = 10000，warp 槽位 = 400*32 = 12800
    warp 利用率 = 10000/12800 = 78.1%   ← 浪费了 22% 的 warp 槽位！

blockSize = 128：
    网格 = ceil(10000/128) = 79 个块
    总线程 = 79 * 128 = 10112，浪费 112 个（1.1%）
    每块 4 个 warp，共 316 个 warp，槽位 = 10112
    warp 利用率 = 10000/10112 = 98.9%
```

**结论**：`blockSize` 不是 32 的倍数时，**每个块最后一个 warp 都有空槽**。块越小、块数越多，这个浪费被放大的倍数越大。这就是"块大小取 32 的倍数"的真正原因——**不是硬性规定，而是效率考虑**。

</details>

### 练习 1.4 [进阶] 写一个处理任意长度的向量加法

**要求**：不用 Grid-Stride Loop，用一个**固定块大小 256** 的朴素 kernel 处理 N = 1000003（一个质数，故意让它和 256 不整除）的数组，并：

2. 用 `compute-sanitizer` 确认没有越界；
3. 把 `if (i < n)` 去掉再跑一次 `compute-sanitizer`，记录错误信息。

<details>
<summary>参考做法</summary>

```cpp
const int N = 1000003;                 // 质数，保证不是 256 的倍数
const int blockSize = 256;
const int gridSize = (N + blockSize - 1) / blockSize;   // 3907
// 总线程 = 3907 * 256 = 1000192，浪费 189 个（约 0.019%）
```

去保护后的 sanitizer 错误：

注意 "thread (189,0,0)" —— 正好是第一个越界的线程编号（`3906*256 + 189 = 1000181 > 1000002`）。**sanitizer 会把越界的线程和块都告诉你**，这就是它的价值。

### 练习 1.5 [进阶] 调优 Grid-Stride 的网格大小

**要求**：修改 `vector_add.cu`，让 Grid-Stride 版本的网格大小变成一个可调参数，并测试下面几组配置，做一张表格记录耗时和有效带宽：

```text
网格 = SM数 × {1, 2, 4, 8, 16, 32, 64}
```

**要求**：找出你这台机器上最快的那一档，并解释为什么再往上加网格就不涨了。

<details>
<summary>参考做法</summary>

核心代码：

```cpp
auto runWithGrid = [&](int g) {
    return CudaTimer::measure([&](double& ms, int) {
        CudaTimer t; t.start();
        vectorAddStrided<<<g, blockSize>>>(dA, dB, dC, N);
        CUDA_CHECK_KERNEL();
        ms = t.stopMs();
    }, 20, 3);
};

for (int mult : {1, 2, 4, 8, 16, 32, 64}) {
    int g = prop.multiProcessorCount * mult;
    if (g > gridSizeNaive) continue;
    double ms = runWithGrid(g);
    printf("SM x %2d  ->  %5d 块  %7.4f ms  %6.1f GB/s\n",
           mult, g, ms, CudaTimer::bandwidthGBs(3.0 * bytes, ms));
}
```

**典型曲线的形状**（具体数值你的机器上会不同）：

```text
SM x 1   ->  30 块   0.0900 ms   133 GB/s     ← 线程太少，延迟藏不住
SM x 2   ->  60 块   0.0600 ms   200 GB/s
SM x 4   -> 120 块   0.0450 ms   267 GB/s
SM x 8   -> 240 块   0.0400 ms   300 GB/s
SM x 16  -> 480 块   0.0395 ms   304 GB/s     ← 已经接近峰值
SM x 32  -> 960 块   0.0392 ms   306 GB/s     ← 基本到顶
SM x 64  -> 1920 块  0.0390 ms   308 GB/s     ← 收益停滞，只有噪声级差别
```

**解释**：

- 网格太小（SM×1、×2）时，每个 SM 上驻留的 warp 数不足，一旦所有 warp 都在等内存，SM 就没活可干 → **延迟藏不住**。
- 随着网格增大，驻留 warp 变多，"切换对象"变多，延迟逐渐被填满。
- 到某个点之后，**显存带宽本身成了硬上限**，再多的线程也只能排队 → 曲线变平。

**经验结论**：网格取 `SM数 × 8` 到 `SM数 × 32` 通常是一个很好的区间。但**不要背这个数字**——你应该在自己的卡上、用自己的真实数据测一遍。

</details>

### 练习 1.6 [进阶] 制造并观察 warp 发散

**要求**：写一个 kernel，用两种方式做 `if/else`，并计时对比：

```cpp
// 版本 A：条件依赖 threadIdx（同一 warp 内部分线程走 if，部分走 else）
// 版本 B：条件依赖 blockIdx（整个块统一走一条路）
```

两个版本必须做同样多的"有效工作"（比如都在内层做 1000 次乘加）。

<details>
<summary>参考做法</summary>

```cpp
__global__ void divergeKernel(const float* __restrict__ in,
                              float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    float v = in[i];
    // 条件依赖 threadIdx：同一个 warp 里一半走 if、一半走 else -> 发散
    if (threadIdx.x % 2 == 0) {
        for (int k = 0; k < 1000; ++k) v = v * 1.0001f + 0.5f;
    } else {
        for (int k = 0; k < 1000; ++k) v = v * 1.0001f - 0.5f;
    }
    out[i] = v;
}

__global__ void uniformKernel(const float* __restrict__ in,
                              float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    float v = in[i];
    // 条件依赖 blockIdx：整个块要么全走 if、要么全走 else -> 无发散
    if (blockIdx.x % 2 == 0) {
        for (int k = 0; k < 1000; ++k) v = v * 1.0001f + 0.5f;
    } else {
        for (int k = 0; k < 1000; ++k) v = v * 1.0001f - 0.5f;
    }
    out[i] = v;
}
```

**预期**：`divergeKernel` 比 `uniformKernel` 慢。原因是同一个 warp 要串行执行两条路径。**具体慢多少取决于每条路径的长度**：如果两条路径长度相同，理论上会接近 2 倍（每条路径都要执行一遍，各有一半线程空转）。

**注意**：现代编译器很聪明，如果两个分支的代码几乎一样（只有常量不同），它可能把分支优化掉或者用谓词执行。所以**一定要用 `-Xptxas -v` 和实际计时验证，别靠猜**。

</details>

### 练习 1.7 [挑战] 实现一个二维的 Grid-Stride Loop

**要求**：把 `matrixAdd2D` 改成二维 Grid-Stride 形式，使得：

- 网格大小固定（不随矩阵尺寸增长）；
- 每个线程用两层循环处理多个 `(row, col)` 位置；
- 支持任意 `WIDTH`/`HEIGHT`（不要求是 32 或 8 的倍数）。

提示：x 和 y 方向各有一个 stride。

<details>
<summary>参考做法</summary>

```cpp
__global__ void matrixAdd2DStrided(const float* __restrict__ A,
                                   const float* __restrict__ B,
                                   float* __restrict__ C,
                                   int width, int height) {
    // x 方向的起点与步长
    int col    = blockIdx.x * blockDim.x + threadIdx.x;
    int strideX = blockDim.x * gridDim.x;
    // y 方向的起点与步长
    int row    = blockIdx.y * blockDim.y + threadIdx.y;
    int strideY = blockDim.y * gridDim.y;

    // 两层循环：外层走行，内层走列
    for (; row < height; row += strideY) {
        for (int c = col; c < width; c += strideX) {
            size_t idx = (size_t)row * width + c;
            C[idx] = A[idx] + B[idx];
        }
    }
}
```

主机端网格：

```cpp
dim3 block(32, 8);
// 让二维网格的总块数大致等于 "SM数 * 每SM块数"，并按 x:y = 4:1 分配
int totalBlocks = prop.multiProcessorCount * 8;
dim3 grid(std::min((width  + block.x - 1) / block.x, (unsigned)(totalBlocks * 4 / 5)),
          std::min((height + block.y - 1) / block.y, (unsigned)(totalBlocks / 5)));
if (grid.x == 0) grid.x = 1;
if (grid.y == 0) grid.y = 1;
```

**关键点**：内层循环保证了**同一个 warp 内线程的 `col` 连续**（因为 `threadIdx.x` 连续），所以每次迭代的访存仍然是合并的。这是二维 Grid-Stride 必须守住的性质。

**进阶思考**：为什么把"列"放在内层、"行"放在外层？因为 C 数组是行主序的，同一行内的地址连续。如果反过来（外层走列、内层走行），同一 warp 内的线程会访问相距 `width` 个 float 的地址，**访存就彻底废了**。这个例子很好地说明了："循环的顺序要服务于访存模式，而不是服务于直觉"。

</details>

## 6. 常见错误与排查

| 错误信息 / 现象                             | 原因                                                                                    | 解决办法                                                                      |
| ------------------------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `invalid configuration argument`            | `<<<>>>` 参数非法：块线程数 > 1024、`gridDim.y`/`gridDim.z` > 65535、请求的共享内存超限 | 打印 `prop.maxThreadsPerBlock` 和 `prop.maxGridSize[]` 对照；减小块大小       |
| 结果全靠前几个元素正确、后面全是 0 或垃圾   | 忘记 `if (i < n)` 保护，后面的线程越界写或者根本没被调度到                              | 加边界判断；用 `compute-sanitizer` 定位                                       |
| `illegal memory access was encountered`     | 索引算错，访问了数组之外                                                                | 打印 `i` 的最大值核对；用 `compute-sanitizer --tool memcheck`                 |
| 结果时对时错                                | 用了未初始化的内存，或者忘了 `__syncthreads`                                            | 用 `cudaMemset` 初始化；检查同步（[第 3 章](ch03_同步通信与原子操作.md)）     |
| kernel 跑完了但结果没变                     | 忘记 `cudaMemcpy` 拷回，或者方向写反了                                                  | 检查 `cudaMemcpyDeviceToHost`；测试时先 `cudaMemset` 成哨兵值                 |
| 计时结果极小（几微秒）或为 0                | 没同步就计时，测到的是"启动耗时"                                                        | 用 `cudaEvent` + `cudaEventSynchronize`，或直接用 `CudaTimer`                 |
| Grid-Stride 版本比朴素版**更慢**            | 网格开得太小（比如 `SM数 × 1`），驻留 warp 不足                                         | 网格取 `SM数 × 8` 以上；或者数据量很小时直接用朴素版                          |
| `printf` 输出顺序每次都不同                 | 正常现象：设备端 printf 走共享缓冲，不保证顺序                                          | 别依赖顺序；用 `blockIdx`/`threadIdx` 排序后再输出                            |
| `printf` 完全没有输出                       | 忘了 `cudaDeviceSynchronize()`，或 kernel 启动失败                                      | 加 `CUDA_CHECK_SYNC()`；加 `CUDA_CHECK_KERNEL()`                              |
| 换台机器（或换个 `-arch`）结果就不对了      | 大概率是**代码里本来就有竞态或越界**，只是恰好在这台机器上没暴露                        | 用 `compute-sanitizer --tool racecheck` 检查；别把"能跑"当成"正确"            |
| `cudaErrorLaunchOutOfResources`             | 每块线程数 × 每线程寄存器数超过了 SM 的寄存器总量                                       | 减小块大小；或加 `__launch_bounds__`（[第 2 章](ch02_内存层次与访存优化.md)） |
| 网格开成二维但 kernel 里只用了 `blockIdx.x` | 一半的块在做重复工作（或者一半数据没被处理）                                            | 检查是否漏了 `blockIdx.y`；数一数网格覆盖的总范围                             |

**一个必须养成的调试习惯**：在 kernel 里加"边界打印"，只让边界线程输出：

```cpp
// 只在最边界的几个线程上打印，避免输出爆炸
if (blockIdx.x == 0 && threadIdx.x < 4) {
    printf("blk=%d tid=%d -> i=%d (n=%d)\n", blockIdx.x, threadIdx.x, i, n);
}
if (blockIdx.x == gridDim.x - 1 && threadIdx.x < 4) {
    printf("LAST blk=%d tid=%d -> i=%d (n=%d)\n", blockIdx.x, threadIdx.x, i, n);
}
```

**看第一个和最后一个块的索引，就能立刻判断出是"少算了"还是"多算了"。** 这个技巧能帮你省下大量时间。

## 7. 本章小结

### 7.1 要点清单

- **三层结构**：grid（块）→ block（线程）→ thread。`gridDim`/`blockDim` 描述尺寸，`blockIdx`/`threadIdx` 描述"我是谁"。
- **四个内建变量**都是 `dim3` 类型（含 `x`/`y`/`z`）。`dim3 a;` 默认是 `(1,1,1)`。
- **一维索引**：`i = blockIdx.x * blockDim.x + threadIdx.x`，它是 `[0, G*B)` 上的双射。
- **二维索引**：`row = blockIdx.y*blockDim.y + threadIdx.y`，`col = blockIdx.x*blockDim.x + threadIdx.x`。**x 是列（变化快），y 是行（变化慢）**，和 C 的行主序一致。
- **三维展平**：`((z*H + y)*W) + x`。
- **越界保护**：`if (row < height && col < width)`，两个方向都要检查。向上取整除法 `(n + B - 1) / B`。
- **Grid-Stride Loop**：`for (i = 全局编号; i < n; i += 网格总线程数)`。这是处理任意长度的标准写法，也是调优网格大小的基础。
- **warp = 32 个连续线程**，是硬件调度单位。块大小取 32 的倍数能避免 warp 槽位浪费。
- **SIMT 与发散**：同一 warp 内线程走不同分支时，硬件必须串行执行两条路径 → 性能减半。让分支条件依赖 `blockIdx` 而不是 `threadIdx` 可以避免。
- **占用率**：每 SM 驻留线程数 / 每 SM 最大线程数。它决定了"能不能藏住延迟"，但**高占用率不等于高性能**。
- **计时规范**：`cudaEvent` + 预热 + 多次采样 + 取中位数。
- **有效带宽** = 搬运字节数 / 耗时，拿它和显卡理论带宽对比，判断访存效率。

### 7.2 自检问题

**Q1：`<<<dim3(64,64), dim3(16,16)>>>` 一共启动多少个线程？**

<details>
<summary>答案要点</summary>

```text
网格：64 × 64 × 1 = 4096 个块
每块：16 × 16 × 1 = 256 个线程
总计：4096 × 256 = 1,048,576 个线程 = 2^20
```

另外可以算：每个块 256 线程 = 8 个 warp，一共 4096×8 = 32768 个 warp。

</details>

**Q2：写出二维索引公式，并解释为什么 `blockIdx.x` 对应"列"。**

<details>
<summary>答案要点</summary>

```text
col = blockIdx.x * blockDim.x + threadIdx.x
row = blockIdx.y * blockDim.y + threadIdx.y
```

**x 对应列**是 CUDA 的约定（也是 C 行主序的约定）：最右边的分量变化最快。因为 C 的 `A[row][col]` 里 `col` 是最右边的下标、地址连续，而 warp 是沿 `threadIdx.x` 切的，所以把"连续变化的 `threadIdx.x`"映射到"连续的列地址"上，就能得到合并访存。如果反着来（x 给行、y 给列），同一个 warp 的线程会访问相距 `width` 个 float 的地址，访存效率会崩。

</details>

**Q3：Grid-Stride Loop 的步长为什么是 `blockDim.x * gridDim.x`？**

<details>
<summary>答案要点</summary>

因为这是**整个网格一次能覆盖的元素个数**（一维网格情况下）。每次循环所有线程整体向后推进"一整个网格宽度"，保证：

- 每个元素恰好被处理一次（不重不漏）；
- `i < n` 天然完成越界保护；
- 无论 n 多大，网格大小都是固定的，启动开销可预测。

  </details>

**Q4：为什么块大小要取 32 的倍数？**

<details>
<summary>答案要点</summary>

两个层面：

1. **warp 槽位浪费**：一个 block 被切成 `ceil(blockDim/32)` 个 warp。如果 `blockDim = 100`，第 4 个 warp 只有 4 个有效线程，但占满 32 个槽位 → 浪费 28/128 = 22% 的槽位。
2. **便于合并访存**：`blockDim.x` 是 32 的倍数时，一个 warp 恰好覆盖二维块的一整行，这一行的内存地址连续。

   </details>

**Q5：什么是 warp divergence？怎么避免？**

<details>
<summary>答案要点</summary>

同一个 warp 内的 32 个线程共享同一个程序计数器，必须执行相同的指令。当它们遇到依赖 `threadIdx` 的分支时，硬件只能串行执行各条路径，其他线程空转。这就是 divergence。

避免方式：

- 让分支条件依赖 `blockIdx`（整块统一）；
- 用算术或三元运算符替代分支（编译器常能生成 SEL 指令）；
- 调整数据布局，让同一 warp 的线程走同一条路；
- 边界判断（`if (i < n)`）的影响很小，可以放心用。

  </details>

**Q6：写一个把 `float A[1024][2048]` 全部置零的 kernel，块用 `(32,8)`，写出完整代码（含边界保护）。**

<details>
<summary>答案要点</summary>

```cpp
constexpr int ROWS = 1024;
constexpr int COLS = 2048;

__global__ void zeroMatrix(float* __restrict__ A) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (row < ROWS && col < COLS) {
        A[row * COLS + col] = 0.0f;
    }
}

// 主机端：
dim3 block(32, 8);
dim3 grid((COLS + block.x - 1) / block.x,   // 2048/32 = 64
          (ROWS + block.y - 1) / block.y);  // 1024/8  = 128
zeroMatrix<<<grid, block>>>(dA);
CUDA_CHECK_KERNEL();
```

注意本题的尺寸恰好整除（2048/32 = 64，1024/8 = 128），所以 `if` 实际上从不生效；但**仍然要写**——因为将来有人把 `COLS` 改成 2000 时，这个保护就是救命稻草。**边界保护是纪律，不是可选项。**

</details>

## 8. 下一章预告

你现在能回答"一个 kernel 启动了多少线程、它们如何映射到数据下标"了。这是 [第 1 阶段](CUDA学习步骤与教程大纲.md) 的验收标准。

但你会发现一个尴尬的事实：**向量加法的 GPU 版本，相对 CPU 版本并没有快得离谱**——因为它的瓶颈根本不是计算，而是**显存带宽**。也就是说，你还有大约 10 倍到 100 倍的性能被浪费在"数据怎么搬运"上。

[第 2 章 内存层次与访存优化](ch02_内存层次与访存优化.md) 就是全书第一个真正的分水岭。你会学到：

1. **内存金字塔**：寄存器 → 共享内存 → 全局内存，各自的延迟差了几个数量级。
2. **合并访存（Coalesced Access）**：为什么"相邻线程访问相邻地址"能让有效带宽差一个数量级。你会亲手写出反例并量化它的代价。
3. **共享内存分块（Tiling）**：矩阵乘法从朴素版到共享内存版，性能提升几倍到十几倍；再加寄存器分块，还能再提。
4. **Bank Conflict**：共享内存也有自己的"坑"，以及一个 padding 就能解决它的原理。
5. **寄存器压力与占用率**：为什么"每线程干更多活"有时反而更快。

学完第 2 章，你写出的矩阵乘法会比朴素版快一个数量级——**这是你第一次真正感受到 GPU 的威力**。
