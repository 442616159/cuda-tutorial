## 1. 概念讲解

### 1.1 一个比喻：仓库、工作台和你的手

先说一个故事。

你是**一个木匠**（一个线程），要加工 1000 块木头（1000 个数据）。

- **你的手**——能立刻拿起、立刻放下。但一次只能拿两三块。这就是**寄存器（Register）**。
- **你旁边的工作台**——伸手就能拿到，能放几十块木头。但只有你和**同一个工位上的几个同事**能用它。这就是**共享内存（Shared Memory）**。
- **仓库**——能放几百万块木头，所有工位的人都能去取。但走一趟要几分钟。这就是**全局内存（Global Memory）**。

**现在问题来了**：如果你每加工一块木头都要跑去仓库取一次、加工完再送回仓库，你的效率会有多低？

答案是：**低到 CPU 都打不过**。

那怎么办？**从仓库一次性搬一箱木头到工作台**（共享内存分块），然后从工作台上快速取用。这就是本章的主线。

**还有个细节**：仓库是货架式的（一排一排），**一次搬运能拿走"一整排放着的连续箱子"**。如果你要的箱子正好是连续的，能一趟拿走 32 个（这叫**合并访存**）；如果你要的箱子分散在 32 个不同的货架上，那就得跑 32 趟（这叫**不合并**）。

这两种情况的效率差**一个数量级**——而你的代码里可能只是把 `data[i]` 改成了 `data[i * 32]`。

### 1.2 内存金字塔：完整表格

| 内存类型              | 作用域      | 生命周期 | 典型容量                                 | 典型延迟                     | 带宽           | 声明方式            |
| --------------------- | ----------- | -------- | ---------------------------------------- | ---------------------------- | -------------- | ------------------- |
| **寄存器 Register**   | 单个线程    | 线程     | 每 SM 64K 个 32-bit（每线程最多 255 个） | ~1 个时钟周期                | 极高           | 普通的局部变量      |
| **共享内存 Shared**   | 线程块      | 块       | 每块 48~227 KB（视架构）                 | ~20~30 周期                  | 很高           | `__shared__`        |
| **常量内存 Constant** | 全设备      | 应用     | 每设备 64 KB                             | ~20 周期（命中缓存，且广播） | 广播时极高     | `__constant__`      |
| **纹理/只读缓存**     | 全设备      | 应用     | 依赖 L1/L2                               | 类似 L1                      | 高             | 纹理对象 / `__ldg`  |
| **L1 缓存**           | 每 SM       | 自动     | 通常 128~256 KB（与共享内存共享）        | ~30 周期                     | 高             | 由硬件自动管理      |
| **L2 缓存**           | 全设备      | 自动     | 数 MB（如 4~50 MB）                      | ~200 周期                    | 中             | 由硬件自动管理      |
| **全局内存 Global**   | 全设备      | 应用     | 显存大小（几 GB~几十 GB）                | ~400~800 周期                | 高（但延迟大） | `cudaMalloc`        |
| **本地内存 Local**    | 单个线程    | 线程     | 溢出时才用                               | 同全局内存                   | 同全局内存     | 寄存器溢出时自动    |
| **固定内存 Pinned**   | 主机        | 应用     | 受主机内存限制                           | 主机侧                       | 拷贝极快       | `cudaMallocHost`    |
| **统一内存 Unified**  | 全设备+主机 | 应用     | 显存 + 主机内存                          | 视位置                       | 视位置         | `cudaMallocManaged` |

**读这张表的正确姿势**：不要背数字，要抓住三个**数量级**：

```text
延迟：  寄存器 (1) << 共享内存 (20) < 常量(20) < L1 (30) << L2 (200) << 全局 (400+)
容量：  寄存器 (KB 级) << 共享内存 (百 KB 级) << L2 (MB 级) << 全局 (GB 级)
```

**这两条数量级差就是所有 GPU 优化的来源**：

> **🎯 优化的本质：把"频繁访问的数据"从"慢而大"的层级搬到"快而小"的层级上。**

**为什么全局内存"慢但带宽大"？** 这个组合很关键，别搞混：

- **延迟（Latency）大**：一次访问要等 400+ 个时钟周期。
- **带宽（Bandwidth）大**：如果**很多线程同时访问连续的地址**，硬件的吞吐量极高（几百 GB/s 到几 TB/s）。

所以 GPU 的办法是：**用"海量的并发线程"来把"单次访问的高延迟"藏起来**。这就是为什么：

- 我们强调"要开足够多的线程 / warp"（否则藏不住延迟）；
- 我们强调"要让访问合并"（否则带宽用不满）。

**这两件事是本章的两条主线。**

### 1.3 全局内存管理：四个 API、两个方向

#### 📦 场景：仓库的"租用、进货、出货、退租"

用仓库的比喻，这四个 API 就是四件事：

| API           | 干的事           | 仓库里的类比                     |
| ------------- | ---------------- | -------------------------------- |
| `cudaMalloc`  | 在显存里**租**一块地方 | 跟仓库管理员租一排货架           |
| `cudaMemcpy`  | **搬**数据       | 进货（主机→设备）/ 出货（设备→主机） |
| `cudaFree`    | **退租**         | 把货架还给仓库                   |

```cpp
// 1) 申请
cudaMalloc(&d_ptr, bytes);
// 2) 主机 → 设备
cudaMemcpy(d_ptr, h_ptr, bytes, cudaMemcpyHostToDevice);
// 3) 设备 → 主机
cudaMemcpy(h_ptr, d_ptr, bytes, cudaMemcpyDeviceToHost);
// 4) 释放
cudaFree(d_ptr);
```

**几个必须记住的细节**：

1. **`cudaMalloc` 的返回值和指针参数**：`cudaMalloc` 返回 `cudaError_t`（错误码），真正的地址通过**二级指针** `void**` 传出。所以必须写成 `&d_ptr`，且 `d_ptr` 必须是 `void*` 或能被隐式转换的类型：

   ```cpp
   float* d_a = nullptr;
   CUDA_CHECK(cudaMalloc(&d_a, bytes));   // 注意 &，别漏
   ```

2. **`cudaMalloc` 分配的对齐**：现代 CUDA 至少给 256 字节对齐。这对"向量化加载"（`float4`）很重要。

3. **四个拷贝方向的枚举**：

   | 枚值                       | 含义        | 常见用途                           |
   | -------------------------- | ----------- | ---------------------------------- |
   | `cudaMemcpyHostToDevice`   | 主机 → 设备 | 准备输入                           |
   | `cudaMemcpyDeviceToHost`   | 设备 → 主机 | 取回结果                           |
   | `cudaMemcpyDeviceToDevice` | 设备 → 设备 | 在显存内搬数据                     |
   | `cudaMemcpyDefault`        | 由指针判断  | 用统一内存时方便，但有一点额外开销 |

4. **必须 `cudaFree`**，否则多次运行会耗尽显存。**注意**：`cudaFree` 是**同步**的（它会等设备上所有相关的操作完成）。

5. **忘记拷贝就启动 kernel** 是最常见的 bug 之一。表现是"输出全是 0 或垃圾值"。

   > 🏭 **用仓库的话说**：你**租好了货架**（`cudaMalloc`），也**写好了生产计划**（kernel），
   > **但忘了把原料从总部运过来**（`cudaMemcpy`）。工人打开货架一看——**空的**。
   >
   > **防范习惯**：分配之后**立刻** `cudaMemset` 成一个哨兵值（比如全填 `-999`）。
   > 这样如果结果里出现 `-999`，你就知道"这块压根没被写过"，而不是去猜"是不是算法错了"。

**页锁定内存（Pinned Memory）**：

```cpp
float* h_pinned = nullptr;
CUDA_CHECK(cudaMallocHost(&h_pinned, bytes));   // 分配
...
CUDA_CHECK(cudaFreeHost(h_pinned));             // 释放
```

#### 🚚 场景：为什么"从总部运货"有时特别慢？

要理解页锁定内存，得先知道一个操作系统的小动作。

**普通的 `malloc` 内存是"可分页的"**：操作系统随时可能把它**换到磁盘上**（因为你内存不够用了）。

> 🏢 于是运货的卡车（DMA 引擎）**不敢直接去仓库拉货**——它怕拉到一半，货被系统搬到别的地方去了。

所以流程变成：

```text
❌ 普通 malloc 内存（可分页）：
   [你的内存] --先抄一份--> [临时缓冲区] --再装车--> [显卡]
                    ↑
              多了一次搬运！这就是慢的来源
```

**`cudaMallocHost` 分配的内存永远不会被换出**（页锁定 = 钉在物理内存里），卡车可以**直接开进去装货**：

```text
✅ cudaMallocHost 内存（页锁定）：
   [你的内存] ---------------------装车----> [显卡]
                    ↑
              直达，少一次搬运
```

所以：

- 拷贝速度快得多（在 PCIe 3.0 上常常能差 1.5~2 倍）；
- 是**异步拷贝 `cudaMemcpyAsync` 生效的前提**（[第 3 章](ch03_同步通信与原子操作.md)）；
- **代价**：占用真实物理内存，分配/释放慢，分配太多会拖慢整个系统。**用多少分配多少**。

> ⚠️ **一个常见的坑**：不要为了"图快"就把所有主机数组都改成 `cudaMallocHost`。
> 页锁定内存**是钉死的物理内存**——你钉了 8 GB，系统就少了 8 GB 可用内存，**整台机器都会变卡**。
> **正确姿势：只把真正要频繁传输的那几块改成页锁定。**

### 1.4 统一内存：一个指针，两边都能用

#### 🧳 场景：从"两地分居"到"共享一个衣柜"

传统方式的问题是"你必须在脑子里维护两份数据"：

```cpp
// 传统方式：两份数据，四次 API
float* h_a = (float*)malloc(bytes);      // CPU 侧
float* d_a; cudaMalloc(&d_a, bytes);     // GPU 侧
fill(h_a);
cudaMemcpy(d_a, h_a, bytes, cudaMemcpyHostToDevice);
myKernel<<<g, b>>>(d_a);
// 忘了 cudaFree 或者忘了拷回来，就出 bug
```

> 🧳 **用搬家的比喻**：这就像你**在两个城市各有一个衣柜**。
> 每天上班前要把衣服从 A 城衣柜搬到 B 城衣柜，下班再搬回来。
> **忘了搬 → 穿错衣服（结果错误）；忘了退租 → 两个衣柜一直占着（显存泄漏）。**

统一内存把它变成一份：

```cpp
// 统一内存：一份数据
float* a;
CUDA_CHECK(cudaMallocManaged(&a, bytes));
fill(a);                       // CPU 直接写
myKernel<<<g, b>>>(a);         // GPU 直接读
cudaDeviceSynchronize();
printf("%f\n", a[0]);          // CPU 直接读结果
CUDA_CHECK(cudaFree(a));       // 只用 free 一次
```

> 🧳 **现在只有一个衣柜了**，两个城市的人都能用同一个地址去拿。
> **代码短了一倍，心智负担小了很多——这才是统一内存最大的价值。**

**原理**：`cudaMallocManaged` 在**统一虚拟地址空间**里分配内存。CPU 和 GPU 的指针值相同。驱动在背后把页面在主机内存和显存之间迁移：

- CPU 访问时，页面在主机内存；
- GPU 访问时，页面被迁到显存（**按需、逐页**）。

**⚠️ 性能陷阱**：**"按需"听起来很美，但代价很大。**

> 🧳 想象一下：你有一个共享衣柜，但**衣服只能一件一件地搬**。
> CPU 想穿衬衫 → 把衬衫搬到 A 城；GPU 想用衬衫 → 又搬回 B 城；CPU 又要用 → 再搬回去……
> **这就是"抖动（thrashing）"：CPU 和 GPU 抢同一页数据，来回搬，比老老实实搬一次还慢。**

所以"裸"的统一内存往往比显式拷贝**慢**。

#### ✅ 解法：`cudaMemPrefetchAsync`（提前把货备好）

> 🧳 **思路很简单**：与其"一件一件按需搬"，不如**提前说一句**："我接下来要用这批衣服，先整箱搬过去。"

```cpp
int dev = 0;
cudaGetDevice(&dev);
// 告诉驱动："这块数据接下来在设备 0 上用，先搬过去"
#if CUDART_VERSION >= 13000
// CUDA 13 起第 3 个参数是 cudaMemLocation，另加一个 flags 参数（传 0）
cudaMemLocation loc{};
loc.type = cudaMemLocationTypeDevice;   // 搬到设备
loc.id   = dev;
CUDA_CHECK(cudaMemPrefetchAsync(a, bytes, loc, 0, /*stream=*/nullptr));
#else
CUDA_CHECK(cudaMemPrefetchAsync(a, bytes, dev, /*stream=*/nullptr));
#endif
// 搬完再启动 kernel —— 实际上它是异步的，会与后面的 kernel 在同一流里排队
myKernel<<<g, b>>>(a);
```

因为预取是**一次可调度的大块传输**，效率远高于"缺页时一页一页搬"。实测中，加预取之后统一内存能追平甚至超过显式拷贝的版本。

> 🎯 **这是一个反复出现的主题**：
> **"自动"的机制往往在"批量、可预测"的场景下输给"手动、提前规划"。**
> 缺页驱动是"被动响应"，预取是"主动调度"——**后者能让硬件做更大的连续传输**。

**`cudaMemAdvise`：给驱动的建议（不是命令）**

> ⚠️ **CUDA 版本差异**：CUDA 13 起 `cudaMemAdvise` 的第 4 个参数由 device id 改为 `cudaMemLocation`。完整兼容写法见 `code/lessons/ch02_memory/unified_memory.cu`。

```cpp
// CUDA 13 起第 4 个参数是 cudaMemLocation；旧版本直接传 device id
#if CUDART_VERSION >= 13000
cudaMemLocation loc{};
loc.type = cudaMemLocationTypeDevice;   // 设备
loc.id   = 0;                           // 设备 0
const cudaMemLocation target = loc;
#else
const int target = 0;                   // 设备 0
#endif

// 这块内存基本只读，可以建立只读副本提高命中率
CUDA_CHECK(cudaMemAdvise(a, bytes, cudaMemAdviseSetReadMostly, target));
// 优先放在设备 0 上
CUDA_CHECK(cudaMemAdvise(a, bytes, cudaMemAdviseSetPreferredLocation, target));
// 允许设备 0 直接访问（避免反复建立映射）
CUDA_CHECK(cudaMemAdvise(a, bytes, cudaMemAdviseSetAccessedBy, target));
```

> 🧳 **`cudaMemAdvise` 是"建议"，不是"命令"**——名字里的 "Advise"（建议）是认真的。
> 你在告诉驱动："根据我的经验，这块数据大概是这样的用途。"
> 驱动**可以采纳，也可以忽略**。
>
> 也别指望它包治百病：这些建议对"**只读大数组**"、"**多 GPU 共享**"等场景有实际收益，
> 对"**单卡单次访问的小数组**"几乎没用。

**什么时候用统一内存？**

| 场景                         | 建议                                       | 为什么                              |
| ---------------------------- | ------------------------------------------ | ----------------------------------- |
| 原型验证、教学代码           | 用，代码短一倍，心智负担小                 | 先跑通，再优化                      |
| 数据结构复杂（链表、树、图） | 用，因为显式拷贝这种结构极其痛苦           | 指针在两边都能用，不用"翻译"地址    |
| 数据量超过显存               | 用（会自动分页）                           | 显式拷贝这时候根本做不到            |
| 追求极致性能                 | 用，但**必须**配合预取；或者干脆用显式拷贝 | 裸用会因抖动变慢                    |
| 多 GPU                       | 用 + `cudaMemAdvise`，这是它的主战场       | 数据在哪块卡上由驱动协调            |

### 1.5 合并访存：本章最重要的一个概念

#### 🏦 场景：32 个人去银行取钱

想象 GPU 是一个银行，**一个 warp 就是 32 个窗口同时服务**，但它们共用一条“运钞通道”。每次运钞车从金库开过来，都是**一整箱一整箱**地搬钱，不能只搬一张。

✅ **合并访存 = 大家排队取连号的钱**

32 个人要取的钱是**连号的**：

- 第 1 个人取第 1 张

- 第 2 个人取第 2 张

- …

- 第 32 个人取第 32 张

运钞车一看：这 32 张钱都在同一个箱子里！**搬一箱就够了**。效率拉满 💯

这就是**合并访存**：warp 里 32 个线程访问的地址是**连续的**，硬件一次就把整段数据搬来了。

**❌ 非合并访存 = 每个人要的钱隔了十万八千里**

现在换一种情况，32 个人要的钱是这样的：

- 第 1 个人要第 1 张

- 第 2 个人要第 100 张

- 第 3 个人要第 200 张

- …

运钞车傻眼了：每张钱都在**不同的箱子**里！只能**跑 32 趟**，每次只拿一张回来。

钱是搬够了，但**运钞车跑了 32 趟**，累死，效率极低 🐢

这就是**非合并访存**：地址分散，硬件被迫发起很多次内存事务，带宽全浪费在“路上”了。

---

**🧩 关键点：为什么是 32 个一起？**

因为 GPU 执行指令是 **“warp（32 线程）一起走”** 的。硬件不是一个个线程单独处理，而是**一批 32 个一起**。

所以判断标准很简单：

> **同一个 warp 里，32 个线程要的地址是不是连续的？**

- 连续 → 合并 → 一趟搞定 ✅

- 跳着来 → 不合并 → 跑很多趟 ❌

---

**🚚 再加一层：运钞车按“固定大小”装箱**

运钞车不是想搬多少搬多少，它一次固定搬 **32 字节 / 64 字节 / 128 字节**（这叫做内存事务 / Cache Line）。

所以有两个坑：

1. **地址不连续**：钱散在不同箱子 → 跑很多趟。

2. **地址连续但没对齐**：比如从箱子中间开始取，跨了两个箱子 → 本来一趟变两趟。

这也是为什么 CUDA 里 `cudaMalloc` 分配的内存会自动对齐？

答：就是为了让你取钱时“刚好从箱子边开始”。

**判断合并的实操规则**：

> **看同一个 warp 内，相邻线程（`threadIdx.x` 相邻）访问的地址是否也相邻。**

🏦 **回到银行：关键是"这箱钱有没有被浪费"**

先明确一个核心事实：

> 运钞车搬钱，是**按箱子搬**的，不是按人搬的。  
> 它关心的是：**这一趟搬来的箱子里，钱是不是都被用上了。**

至于"哪张钱给哪个人"，运钞车**根本不管**。

---

✅ 例子1：正着取

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
float v = a[i];
```

32 个线程：

| 线程     | 0   | 1   | 2   | ... | 31  |
| -------- | --- | --- | --- | --- | --- |
| 取第几张 | 0   | 1   | 2   | ... | 31  |

运钞车一看：第 0~31 张，**正好一箱**。搬一趟，32 张全用上。✅

---

❌ 例子2：跳着取

```cpp
int i = (blockIdx.x * blockDim.x + threadIdx.x) * 32;
float v = a[i];
```

32 个线程：

| 线程     | 0   | 1   | 2   | ... | 31  |
| -------- | --- | --- | --- | --- | --- |
| 取第几张 | 0   | 32  | 64  | ... | 992 |

运钞车：第 0 张在第 1 箱，第 32 张在第 2 箱，第 64 张在第 3 箱……

**搬了 32 箱，每箱只用 1 张**。浪费 31/32。❌

---

✅ 例子3：倒着取

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
float v = a[n - 1 - i];
```

假设 `n = 32`，32 个线程：

| 线程     | 0   | 1   | 2   | ... | 31  |
| -------- | --- | --- | --- | --- | --- |
| 取第几张 | 31  | 30  | 29  | ... | 0   |

运钞车一看：**第 0~31 张，还是同一箱！**

它把这一箱搬过来，然后：

- 第 31 张给线程 0

- 第 30 张给线程 1

- …

- 第 0 张给线程 31

**一箱钱，32 张全用上了。** ✅

---

🎯 **关键区别在哪？**

对比例子2和例子3：

|                     | 例子2（跳着取）     | 例子3（倒着取）    |
| ------------------- | ------------------- | ------------------ |
| 线程 0 取           | 第 0 张             | 第 31 张           |
| 线程 31 取          | 第 992 张           | 第 0 张            |
| warp 覆盖的地址范围 | 0 ~ 992，**很分散** | 0 ~ 31，**很集中** |
| 需要搬几箱          | 32 箱               | 1 箱               |
| 每箱利用率          | 1/32                | 32/32              |

- **例子2**：线程编号和地址都是"递增"的，但**跳得太远**，warp 覆盖的范围被拉得巨大。

- **例子3**：线程编号递增，地址递减，但**所有地址仍然挤在同一小段区间里**。

运钞车只问一句：

> **"这 32 个人要的钱，是不是都挤在少数几个箱子里？"**

是 → 合并 ✅  
不是 → 不合并 ❌

#### 📌 总结

> **合并访存看的是"warp 覆盖的地址区间紧不紧凑"，不是"线程号小的地址也小"。**

只要 32 个线程要的数据**挤在一小段连续内存里**，不管谁拿哪张，运钞车都能一趟搬完。

反过来，哪怕线程号是递增的，只要地址**散得太开**，就得跑很多趟。

**内存事务的大小（经验值）**：

| 架构           | 典型事务粒度      | 说明                         |
| -------------- | ----------------- | ---------------------------- |
| Fermi/Kepler   | 128 字节          | 按 128 字节段合并            |
| Maxwell 及以后 | 32 字节（sector） | 更细粒度，但连续访问仍然最优 |

现代 GPU 用 32 字节的 sector 作为最小单位。也就是说：

- 一个 warp 访问连续的 128 字节 → 4 个 sector，全部用满 → **100% 利用率**；
- 一个 warp 访问跨步 32 个 float 的地址 → 32 个不同 sector，每个只用 4 字节 → **12.5% 利用率**。

**再强调一次**：访问的元素个数完全一样，慢就慢在"事务里有多少字节是有用的"。

**AoS vs SoA：一个真实世界的例子**

```cpp
// AoS（Array of Structs）：每个粒子 12 字节
struct ParticleAoS { float x, y, z; };
ParticleAoS* p;
// 线程 t 读 p[t].x，地址差是 12 字节
// warp 覆盖 32*12 = 384 字节，但只用其中 1/3（只取 x）→ 利用率 33%

// SoA（Struct of Arrays）：拆成三个独立数组
struct ParticleSoA { float *x, *y, *z; };
// 线程 t 读 x[t]，地址差 4 字节
// warp 覆盖 128 字节，全部用满 → 利用率 100%
```

**怎么选？**

| 访问模式                       | 推荐                                        |
| ------------------------------ | ------------------------------------------- |
| 总是同时访问 x/y/z             | AoS（一次事务拿全，虽然浪费但省了三次访问） |
| 大部分时候只访问其中一两个分量 | **SoA**（这是 GPU 上的常规选择）            |
| 需要随机构建/删除              | AoS 更容易管理，或用 SoA + 索引数组         |

**关键洞察**：`coalescing.cu` 会给你实测数据。你会看到 AoS 的"有用带宽"只有 SoA 的约 1/3。

### 1.6 共享内存：块内的"高速工作台"

#### 🍳 场景：8 个人做一桌菜

还是接着仓库那个故事。这回你是**厨师长**，手下有 **256 个厨师**（一个线程块的 256 个线程），要给客人做一桌 256 道菜。

- **每个人的手** = 寄存器。只能同时拿两三样东西，但拿了就能立刻用。
- **厨房中间那张大操作台** = 共享内存。整个后厨的人都能往上面放东西、也能从上面拿东西。伸手就到，比跑去仓库快 **10~20 倍**。
- **仓库** = 全局内存。什么都有，但走一趟要几分钟（400+ 个时钟周期）。

**问题**：做菜需要"胡萝卜"这一样食材，而且**256 道菜全都要用**。

**❌ 笨办法**：256 个厨师每人跑一趟仓库，各拿一根胡萝卜回来。

👉 跑了 **256 趟**，拿了 256 根，**其实只需要 1 根**。

**✅ 聪明办法**：派 **1 个厨师**跑一趟，抱回**一筐**胡萝卜倒在操作台上；喊一声"都拿好了！"（这就是 `__syncthreads()`）；然后 256 个人**从操作台上各拿一根**。

👉 跑了 **1 趟仓库**，操作台上拿 256 次（几乎不花时间）。

**这就是共享内存的全部意义**：

> **共享内存的作用，是把"每个线程都要单独跑一趟全局内存"变成"块内派人跑一趟，大家分着用"。**

---

**🧩 关键点：为什么共享内存能"分着用"？**

因为共享内存的**作用域是一个线程块**——同一个块里的所有线程，看到的是**同一块内存、同一批数据**。这和寄存器完全不同：

| 对比项                     | 寄存器                     | 共享内存                       |
| -------------------------- | -------------------------- | ------------------------------ |
| 谁能看见                   | **只有我自己**（线程私有） | **同块所有线程**（块内共享）   |
| 换个线程访问别人的寄存器   | ❌ 做不到                  | ✅ 随便读                      |

所以共享内存天生就是用来"**当一个块内的公共白板 / 公共操作台**"的。

---

#### 🔪 共享内存的两个"坑"：不喊话就乱套

共享内存虽然快，但它带来了两个在全局内存里**不存在**的新问题。这是本章后面所有复杂性的根源。

**🕳️ 坑 1：读写不同步（你需要 `__syncthreads()`）**

想象这个画面：

```text
厨师 A：把胡萝卜放到操作台上            ← 还没放稳
厨师 B：伸手去操作台拿胡萝卜            ← 抓了个空！
```

共享内存的读写**没有自动的顺序保证**。厨师 A 写了，不代表厨师 B 能立刻看见。所以必须**喊一声口令**：

```cpp
sdata[tid] = value;      // 我放好了
__syncthreads();         // 📢 全体注意！都停下来，等所有人放完
float v = sdata[tid+1];  // 现在再拿，一定能拿到
```

**这个口令就是 `__syncthreads()`**：块内所有线程都必须在这里集合，**等大家都到了才放行**。

⚠️ 注意一个反直觉的点：**它不是"快的人等慢的人"，而是"所有人互相等"**。它保证的是"口令之前的所有写操作，口令之后对所有线程可见"。

**🕳️ 坑 2：操作台就那么大（容量有限）**

操作台的面积有上限：老卡每块 **48 KB**，新卡（H100）最多 **227 KB**。

- 256 个人共用 48 KB → 平均每人 **192 字节**，也就是 **48 个 float**。
- 如果你想一次把整个 512×512 的矩阵搬上来（1 MB），**放不下**。

所以共享内存的用法永远是"**搬一小块 → 用完 → 再搬下一小块**"，这就是 1.7 节的**分块（Tiling）**。

---

#### 📋 共享内存的完整性质表

| 性质         | 说明                                                                          | 类比                         |
| ------------ | ----------------------------------------------------------------------------- | ---------------------------- |
| **作用域**   | 单个线程块。块外的线程看不到                                                  | 只有本后厨的人能用这张台子   |
| **生命周期** | 从块启动到块结束                                                              | 这一桌菜做完就收摊           |
| **速度**     | 约 20~30 个时钟周期延迟，比全局内存快 10~20 倍                                | 伸手就能拿 vs 跑一趟仓库     |
| **容量**     | 每块 48 KB（老卡）到 227 KB（H100）。用 `device_query` 查 `sharedMemPerBlock` | 操作台就那么大               |
| **访问模式** | 任何线程可以读任何位置（不像寄存器有归属）                                    | 谁都能上台子拿东西           |
| **需要同步** | 一个线程写了，别的线程要**显式** `__syncthreads()` 才能安全读到               | 必须喊口令"都拿好了！"       |
| **还有内斗** | 同一时刻太多人抢台子的同一块地方 → Bank Conflict（见 1.8 节）                 | 32 个人同时挤同一个抽屉      |

---

#### ✅ 正反例对照：同一个归约，写两遍

看一个具体的例子，就知道共享内存"该怎么用"和"不该怎么用"。

**任务**：把 256 个数加起来（块内归约）。

**❌ 错误示范：所有人都去仓库取**

```cpp
__global__ void reduceBad(const float* in, float* out, int n) {
    int tid = threadIdx.x;
    float sum = 0.0f;
    // 256 个线程，每个线程都遍历一遍完整数据 → 数据被读了 256 遍
    for (int i = 0; i < n; ++i) sum += in[i];
    // 还要"互相交换"才能合并 —— 但线程之间没法直接通信！
    // 只能靠 atomicAdd，串行化，极慢
    atomicAdd(out, sum);
}
```

👉 病根：**数据被重复读了 256 遍**，而且**线程间没有公共白板可以交换部分结果**。

**✅ 正确示范：先在各自手里攒，再上台子汇总**

```cpp
__global__ void reduceGood(const float* in, float* out, int n) {
    // ⚠️ volatile 的详细原因见 2.5 节，这里先记住"少了它可能读到旧值"
    __shared__ volatile float sdata[256];   // ← 操作台！块内共享
    int tid = threadIdx.x;

    // 阶段 1：每个线程先在"自己手里"（寄存器）累加自己负责的部分
    float sum = 0.0f;
    for (int i = blockIdx.x * blockDim.x + tid; i < n; i += blockDim.x * gridDim.x)
        sum += in[i];                    // 合并访存，每人只读自己的那一份

    // 阶段 2：把各自的局部和放到操作台上
    sdata[tid] = sum;
    __syncthreads();                     // 📢 等大家都放好

    // 阶段 3：在操作台上做"树形归约"，规模每轮减半：256 → 128 → 64 → ... → 1
    for (int s = blockDim.x / 2; s > 0; s >>= 1) {
        if (tid < s) sdata[tid] = sdata[tid] + sdata[tid + s];
        __syncthreads();                 // 每一轮都要喊一次
    }

    if (tid == 0) out[blockIdx.x] = sdata[0];
}
```

> ⚠️ **这里有个"魔鬼细节"：`volatile` 是必须的。**
> 编译器有权假设"共享内存里的值不会被别的线程悄悄改掉"（除非碰到同步原语），
> 于是它可能把 `sdata[tid + s]` 缓存进寄存器，下一轮**直接用旧值**——**结果就错了**。
> `volatile` 就是告诉编译器："这块内存随时会变，每次都真的去读。"
> **完整解释见 2.5 节**，这里只要先记住：**共享内存 + 循环 + 同步 = 想一想要不要 `volatile`。**

👉 好处：**数据只从仓库搬了一次**，剩下的 255 次"合并"都发生在操作台上（快 10~20 倍），而且**全局内存写入只有 1 次**。

**对照总结**：

|                    | ❌ 错误示范            | ✅ 正确示范              |
| ------------------ | ---------------------- | ------------------------ |
| 全局内存读取量     | n × 256 次             | n 次（每人一次）         |
| 线程间怎么交换数据 | 不能交换，只能 atomic  | 共享内存当白板           |
| 需要几次同步       | 0（但结果错/极慢）     | 每轮归约 1 次            |
| 谁写全局内存       | 256 个线程都在 atomicAdd | 只有 tid==0 写         |
| 共享内存要不要 volatile | 不涉及            | **要**（见 2.5 节）      |

---

#### 📌 共享内存的用法口诀

> **"全局内存搬一次，共享内存用多次；搬完喊一声，用完喊一声。"**

- **搬一次**：块内协作，把这一小块数据从全局内存搬到共享内存（记得**合并访存**，见 1.5 节）。
- **用多次**：块内每个线程反复从共享内存里取自己需要的那部分。
- **搬完喊一声**：`__syncthreads()`——等大家把数据放好，你再读。
- **用完喊一声**：`__syncthreads()`——等大家都读完，再放下一批（**防覆盖**）。

第三、四条在 1.7 节的矩阵乘法里会变成"**两个屏障**"，请务必对照理解。

---

**两种声明方式**：

```cpp
// 方式一：静态分配 —— 大小在编译期确定
__shared__ float tile[32][33];
// 优点：编译器知道大小，能更好地安排布局和优化
// 缺点：大小写死在代码里

// 方式二：动态分配 —— 大小在启动时确定
extern __shared__ float smem[];
// 启动时用第三个参数指定字节数：
//   myKernel<<<grid, block, sharedBytes>>>(...);
// 优点：灵活，能根据运行期参数决定
// 缺点：只有一个"起点"，要用指针手工切分多块
```

**动态分配的实战写法**（需要多块不同大小的共享内存时）：

```cpp
extern __shared__ float smem[];
float* a = smem;                    // 第一段
float* b = smem + aSize;            // 第二段
float* c = smem + aSize + bSize;    // 第三段
// 启动：myKernel<<<g, b, (aSize + bSize + cSize) * sizeof(float)>>>(...)
```

⚠️ **动态共享内存的对齐**：`extern __shared__` 声明的数组是按元素类型对齐的。如果你要先放 `float` 再放 `double`，记得手动对齐（把 `b` 的偏移向上取整到 8 的倍数）。

**`__syncthreads()` 的语义规则**

```cpp
sdata[tid] = value;      // 写共享内存
__syncthreads();         // 屏障：块内所有线程都必须到这里
float v = sdata[tid + 1]; // 现在再读，才能保证读到别人写的值
```

**三条必须记住的规则**：

1. **它是块内的屏障**：所有线程都必须到达同一条 `__syncthreads()`。**它不跨越块**。

   > 🍳 用厨房的话说：这是**一个后厨内部的口令**。隔壁后厨听不见，也不需要听。所以"块与块之间怎么同步"完全是另一个问题（[第 3 章](ch03_同步通信与原子操作.md)的协作组）。

2. **不能放在"只有部分线程能到达"的分支里**：

   ```cpp
   // ❌ 死锁：只有 tid < 16 的线程到达屏障，其他线程永远出不来
   if (tid < 16) {
       sdata[tid] = f(tid);
       __syncthreads();
   }
   ```

   想象一下：**厨师长只让前 16 号灶台的人举手报到，却要求全后厨 256 个人一起等**。剩下的 240 个人没被通知要举手，于是——**所有人永远等下去，程序卡死**。

   但**如果条件对整块统一**（比如依赖 `blockIdx` 或一个全块相同的变量），就是安全的：

   ```cpp
   // ✅ 安全：s 对所有线程都一样
   for (int s = blockDim.x / 2; s > 0; s >>= 1) {
       if (tid < s) { sdata[tid] += sdata[tid + s]; }
       __syncthreads();     // 所有线程都会到达
   }
   ```

   **为什么这个是安全的？** 因为**屏障在 `if` 外面**。`if (tid < s)` 只决定"谁干活"，但**所有线程都会走到 `__syncthreads()`**。

   > 🎯 **判断口诀：看"屏障这一行"在不在分支里面。屏障本身在所有线程都必经的路上，就安全。**

3. **它同时是"编译器屏障"和"内存屏障"**：不仅保证执行顺序，还保证共享内存的写在屏障之后对所有线程可见。但**它不保证全局内存的可见性**（那需要 `__threadfence()`，见 [第 3 章](ch03_同步通信与原子操作.md)）。

   > 🍳 换句话说：`__syncthreads()` 保证的是"**操作台上的东西**大家都看得到"，**不保证**"**仓库里的东西**大家都看得到"。这两个是不同的承诺——这一点在第 3 章会展开。

**Volta 及以后的一个重要变化**：`__syncthreads()` 只同步同一个块内**实际存在**的线程。如果你用了"提前退出"的线程（`if (i >= n) return;`），它们不会参与屏障——这没问题，因为 CUDA 的屏障语义只针对"还没退出的线程"。但**别在屏障前 return 而让剩下的线程等一个永远不来的同伴**。

### 1.7 分块（Tiling）：共享内存最经典的应用

#### 🏭 场景：装配线上的"零件重复搬运"

先讲一个工厂的故事，你就明白分块到底在解决什么。

假设工厂要生产 **512×512 = 262144 个零件**（输出矩阵 C 的每个元素）。

- **每个零件**需要用到 **512 个 A 零件 + 512 个 B 零件**（对应矩阵乘法的 K 次累加）。
- 总共需要 `262144 × 512 × 2 ≈ 2.7 亿` 次零件取用。

听起来没什么？**但整条产线上其实只有 512×512 + 512×512 ≈ 52 万个不同的零件**。

也就是说：**每个零件平均被取用了 512 次！**

**❌ 笨办法（朴素实现）**：

> 每个工人**每装一个零件就跑一趟仓库**，取一个 A、取一个 B。
> 结果：跑了 2.7 亿趟仓库，而仓库里只有 52 万种零件——**每个零件被反复搬了 512 遍**。

**✅ 聪明办法（分块）**：

> 把产线分成 **16×16 = 256 个班组**，每个班组负责生产 **32×32 = 1024 个零件**。
> 每个班组**只跑一趟仓库**，把"我需要的 A 原料"和"我需要的 B 原料"各搬一箱（32×32）到**自己的工作台**上。
> 然后这 1024 个零件**全部从工作台上取料**。

👉 结果：仓库只跑了 **1/32 的趟数**（因为每箱原料被 32 个零件共用），速度直接起飞。

**这就是 Tiling（分块）**：**把"每个元素单独取料"改成"一批元素共用一箱料"。**

---

#### 🔢 先算清楚账：到底重复了多少倍

看数学。`C[M][N] = A[M][K] * B[K][N]`，朴素实现里每个线程的算法：

```cpp
float acc = 0.0f;
for (int k = 0; k < K; ++k) {
    acc += A[row * K + k] * B[k * N + col];   // 每次迭代读 2 个 float
}
C[row * N + col] = acc;
```

**数一数全局内存的访问量**：

| 项目                     | 数量                                   |
| ------------------------ | -------------------------------------- |
| 每个线程读 A 的 K 个元素 | K 次                                   |
| 每个线程读 B 的 K 个元素 | K 次                                   |
| 每线程合计               | **2K 次全局读取**                      |
| 总线程数                 | M × N                                  |
| **全局读取总次数**       | `2 × M × N × K`                        |

**而实际需要的数据只有多少？**

| 项目             | 数量                       |
| ---------------- | -------------------------- |
| A 矩阵           | M × K 个元素               |
| B 矩阵           | K × N 个元素               |
| **真正不同的数据** | `M*K + K*N` 个元素       |

**重复率**：

```text
重复率 = 2MNK / (MK + KN)

对 M = N = K = 512：
        = 2 × 512 × 512 × 512 / (512×512 + 512×512)
        = 268435456 / 524288
        ≈ 512 倍
```

> **翻译成人话**：仓库里只有 **52 万个**不同的零件，你的程序却去取了 **2.7 亿次**。
> **你从仓库取了 512 倍于实际需要的木头。**

而这 512 倍**全部**是纯浪费——因为每次取到的都是**同一个东西**。

---

**🧩 关键点：为什么会有这么大的重复？**

因为**同一份数据被很多不同的线程需要**：

```text
A 的第 r 行，被 C 的第 r 行的所有 N 个元素用到    → 每个 A 元素被用 N 次
B 的第 c 列，被 C 的第 c 列的所有 M 个元素用到    → 每个 B 元素被用 M 次
```

对 M=N=512：**每个 A 元素被 512 个线程读，每个 B 元素也被 512 个线程读**。而这 512 个线程之间**互相不知道对方也读了**，于是各自又跑了一趟仓库。

> 🎯 **这就是 1.5 节说的"合并访存"解决不了的问题**：
> 朴素 GEMM 的访存**其实是合并的**（`B[k*N+col]` 里 col 连续），带宽利用率并不差。
> **它的病根不是"访问不连续"，而是"同一份数据被反复访问了 512 遍"。**
>
> **合并访存解决"这一趟有没有浪费"，分块解决"要不要跑这么多趟"。这是两个不同层面的优化。**

---

#### 🧱 分块（Tiling）的思想

```text
把输出矩阵 C 切成 TILE×TILE 的小块，每个线程块负责一块。
对 K 方向也切成 TILE 一段，逐段推进。

   ┌───────┐         ┌───────┐         ┌───────┐
   │  A 的  │   ×     │  B 的  │   =     │  C 的  │
   │ 一块   │         │ 一块   │         │ 一块   │
   └───────┘         └───────┘         └───────┘
    32×32             32×32             32×32
   （搬进共享内存）   （搬进共享内存）     （每个线程负责一个元素）
```

**每一段（一个 k0）的流程**：

```text
阶段 1：块内 1024 个线程协作，把 A 的 32×32 块和 B 的 32×32 块
        从全局内存搬进共享内存。
        → 全局内存访问量：2 * 32 * 32 = 2048 个 float（一次）
阶段 2：__syncthreads()  等大家都搬完
阶段 3：每个线程在自己的 32 次内层循环里，从共享内存读数据累加。
        → 共享内存访问：每线程 2 * 32 = 64 次（很快）
阶段 4：__syncthreads()  等大家都算完，才能写下一轮数据
```

**全局内存访问量的变化**：

```text
朴素版：每线程 2K 次全局读
分块版：每线程 2 * (K / TILE) 次全局读   ← 因为每轮只搬了 2*TILE*TILE 个，
                                          但被 TILE*TILE 个线程共享
减少倍数 ≈ TILE / 1 = 32 倍（用 32×32 的块）
```

**🧮 把 512×512×512 的账算一遍（感受一下 32 倍意味着什么）**：

|                       | 朴素版 v1                | 分块版 v2（TILE=32）     | 改善       |
| --------------------- | ------------------------ | ------------------------ | ---------- |
| 每线程全局读次数       | `2K = 1024` 次           | `2 × K/TILE = 32` 次     | **32 倍**  |
| 全局内存总读取量       | 约 `8·M·N·K` = **1 GB** | 约 `8·M·N·K/32` = **32 MB** | **32 倍**  |
| 共享内存读取量         | 0                        | 每线程 `2×TILE = 64` 次  | 用快的换慢的 |
| 算术强度（flops/byte） | **0.25**                 | **8**                    | **32 倍**  |

> 🏭 用工厂的话说：从"每个零件都跑一趟仓库"变成"**每 32 个零件共用一趟仓库**"。
> 搬运量直接掉到 **1/32**，而少搬的全是**纯粹重复的**东西。

**算术强度变化**：

```text
v2 的全局内存访问量 ≈ (2 * M*N*K / TILE) 次读取
算术强度 = 2*M*N*K / (8 * M*N*K / TILE) = TILE/4 = 8 flops/byte（TILE=32）
```

从 0.25 涨到 8，接近了机器平衡点 12.5。所以 v2 通常会比 v1 快**数倍到十几倍**（具体取决于卡）。

**一个细节提醒**：`As[ty][tx]` 和 `Bs[ty][tx]` 的加载是**合并访存**的（`tx` 连续 → 地址连续）。这是 v2 快的前提之一。如果你的 tile 加载写成 `As[tx][ty]`，加载就变成跨步的，v2 的收益会被吃掉一大半。

> 🎯 **看这里，两个概念联动了**：分块负责"少搬几趟"，合并访存负责"每趟都搬满"。
> **前者是 1.7 节，后者是 1.5 节。两个都做对，才是 v2 的真实收益。**

---

**🔪 现在回头看：`__syncthreads` 为什么需要两次？**

还是用操作台的比喻。一个块内有 256 个厨师，操作台只有 32×32 那么大，**这一轮的菜做完，台子要腾出来放下一批料**。于是：

```text
时间轴：

  ① 大家把这一批料搬上台子        ← 有人在放
     ────────────────────────
  ② 📢 "都放好了吗？"  __syncthreads()   【屏障 A】
     ────────────────────────
  ③ 大家从台子上取料做菜          ← 有人在读
     ────────────────────────
  ④ 📢 "都做完了吗？"  __syncthreads()   【屏障 B】
     ────────────────────────
  ⑤ 把台子上的旧料清掉，放新料 → 回到 ①
```

- **屏障 A（搬完之后）= 生产者-消费者屏障**：保证所有线程都**写完了**共享内存，才能开始**读**。没放稳就去拿，会抓到空气（垃圾数据）。
- **屏障 B（算完之后）= 防覆盖屏障**：保证所有线程都**读完了**当前这块，才能往里**写**下一块。别人还没做完菜，你就把料倒了换成新的——他那道菜就毁了。

**🧩 为什么两个屏障都要，而且不能合并成一个？**

因为它们保护的是**两个不同的依赖方向**：

```text
屏障 A：写（加载）→ 读（计算）     生产者-消费者
屏障 B：读（计算）→ 写（加载）     防覆盖
```

一个是"**先放后取**"，一个是"**先取后倒**"。方向相反，**一个屏障管不了两头**。

**❌ 漏掉屏障 B 会怎样？**

```text
轮 0: 加载 -> syncA -> 计算 -> [无屏障] -> 轮 1 加载 -> syncA -> 计算
                    ↑                        ↑
             快线程算完了直接跑去加载轮 1，覆盖了慢线程正在读的数据
```

结果会得到"**有时对有时错**"的答案——快的线程已经把下一轮数据写进去了，慢的线程还在读上一轮的数据。

**这种 bug 最难查**，因为它的表现依赖于硬件调度和时序：换个卡、换个块大小、甚至换个编译器版本，可能就"好了"。**它在你的机器上可能从来没出过错，然后在别人的机器上炸。**

> 💡 一个实用的自查方法：**每次写"加载→计算→加载"的循环，先在心里默数"我这里有几个屏障"。数出来是 2，才对。**

**这就是为什么 [第 3 章](ch03_同步通信与原子操作.md) 要专门讲同步**：内存和同步是分不开的。

### 1.8 Bank Conflict：共享内存自己的坑

#### 🗄️ 场景：操作台被切成了 32 个抽屉

还记得 1.6 节那张操作台吗？现在告诉你一个**硬件细节**：

> **那张操作台不是一整块大平面，而是被切成了 32 个并排的抽屉（bank），每个抽屉宽 4 字节。**

```text
  抽屉号:  0     1     2     3    ...    30    31
        ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐
        │ 0-3 │ 4-7 │ 8-11│12-15│ ... │     │     │  字节地址
        └─────┴─────┴─────┴─────┴─────┴─────┴─────┘
          ↑
        字节地址 0~3 在抽屉 0，4~7 在抽屉 1，8~11 在抽屉 2 ...

   抽屉号 = (字节地址 / 4) % 32
```

**关键规则：一个抽屉一个周期只能被一个人拉开。**

于是，1.6 节我们只说了"喊口令"的问题（时间上的冲突），现在遇到的是**空间上的冲突**：

> **一个 warp 的 32 个线程同时伸手，如果它们要的东西落在 32 个不同的抽屉里（且地址不同）→ 一瞬间全拿到，完美。**
> **如果好几个人抢同一个抽屉 → 只能排队，一个一个来。**

**这就叫 Bank Conflict（存储体冲突）。**

---

#### 🍽️ 三个场景对照：一眼看懂冲突

用一个自助餐台来对照。**32 个抽屉 = 32 个菜格**，**32 个线程 = 32 个客人同时伸手**。

**✅ 场景 A：每人要自己面前那一格（stride = 1）**

```cpp
int idx = threadIdx.x;
float v = buf[idx];
```

| 线程     | 0   | 1   | 2   | ... | 31  |
| -------- | --- | --- | --- | --- | --- |
| 要的地址 | 0   | 1   | 2   | ... | 31  |
| 落在抽屉 | 0   | 1   | 2   | ... | 31  |

👉 **32 个人，32 个不同的抽屉，一人一格，互不干扰。一个周期全部拿到。** ✅

**❌ 场景 B：所有人都要"第 0、32、64...格"（stride = 32）**

```cpp
int idx = threadIdx.x * 32;
float v = buf[idx];
```

| 线程     | 0   | 1   | 2   | ... | 31   |
| -------- | --- | --- | --- | --- | ---- |
| 要的地址 | 0   | 32  | 64  | ... | 992  |
| 落在抽屉 | 0   | 0   | 0   | ... | 0    |

算一下：`(32t) % 32 = 0`，**所有人都在抽屉 0**！

👉 **32 个人挤在同一个抽屉前，只能排队，一个一个拿。** ❌
**这就是 32 路冲突**：本来 1 个周期的事，变成 **32 个周期**。

**✅ 场景 C：每人要"第 0、33、66...格"（stride = 33）**

```cpp
int idx = threadIdx.x * 33;
float v = buf[idx];
```

| 线程     | 0   | 1   | 2   | ... | 31   |
| -------- | --- | --- | --- | --- | ---- |
| 要的地址 | 0   | 33  | 66  | ... | 1023 |
| 落在抽屉 | 0   | 1   | 2   | ... | 31   |

算一下：`(33t) % 32 = t % 32`，**完美散开在 32 个抽屉**！

👉 **虽然地址"跳着走"，但抽屉分得开，还是一个周期全部拿到。** ✅

**🎯 看出规律了吗？**

|              | 场景 A          | 场景 B          | 场景 C           |
| ------------ | --------------- | --------------- | ---------------- |
| 相邻线程地址差 | 1               | 32              | 33               |
| 落在几个抽屉 | 32 个           | **1 个**        | 32 个            |
| 结论         | 无冲突 ✅       | **32 路冲突** ❌ | 无冲突 ✅        |

> **判断口诀：看"相邻线程的地址差"和 32 的关系。**
> **互质（最大公约数是 1）→ 一定散得开，无冲突。**
> **是 32 的倍数 → 全挤在一起，最惨。**

---

#### 🎁 一个例外：广播不算冲突

如果 32 个线程要的是**完全相同的地址**呢？

```cpp
float v = buf[0];    // 所有线程都读 buf[0]
```

👉 硬件一看："哦，大家要的是**一模一样**的东西。" 于是掏出**一份**，**复制 32 份**发给所有人。

**这叫广播（Broadcast），只算 1 次访问，不算冲突。** ✅

> 🍽️ 类比：32 个人都要"今天的主菜是什么"这个信息。厨师喊一嗓子就完事了，**不用 32 个人排队去问**。

**⚠️ 但要注意区别**：

| 情况                                 | 结果                     |
| ------------------------------------ | ------------------------ |
| 32 个线程读**同一个地址**            | **广播**，1 次访问 ✅    |
| 32 个线程读**同一个 bank 的不同地址** | **冲突**，排队 ❌        |

> 📌 **"同一个抽屉"和"同一件东西"是两回事。** 同一个抽屉里的不同东西，还是要排队拿。

---

#### 💥 冲突代价有多大？

如果是 **N 路冲突**，这次访存要**串行 N 次**。

最坏情况：**32 路冲突 → 共享内存慢 32 倍**。

而共享内存本来就只比全局内存快 10~20 倍。所以：

> **32 路冲突的共享内存，比全局内存还慢！**
> 你精心设计的"用共享内存加速"，可能反而把你坑了。

---

#### 🔍 怎么算出冲突？看地址差与 32 的关系

> 一个 warp 内相邻线程的地址差（以"字"为单位）如果与 32 **互质**，就一定无冲突；
> 如果是 32 的倍数，就是 32 路全冲突。

**三个典型的冲突场景**：

```cpp
// 场景 1：stride = 32 的一维访问 —— 32 路冲突
int idx = threadIdx.x * 32;
float v = buf[idx];
// 线程 t 的地址是 32t，bank = (32t) % 32 = 0
// 所有线程都落在 bank 0 —— 32 路冲突！

// 场景 2：stride = 1 —— 无冲突
int idx = threadIdx.x;
float v = buf[idx];
// 线程 t 的地址是 t，bank = t % 32
// 32 个线程落在 32 个不同 bank —— 完美

// 场景 3：stride = 33 —— 无冲突（因为 33 与 32 互质）
int idx = threadIdx.x * 33;
float v = buf[idx];
// bank = (33t) % 32 = t % 32 —— 又是完美
```

**❓ 那 stride = 2 呢？** 2 与 32 **不互质**（公约数 2）。

```text
线程 t 的地址 = 2t，bank = (2t) % 32 = 2t mod 32
线程 0  → bank 0      线程 16 → bank 0     ← 撞了！
线程 1  → bank 2      线程 17 → bank 2     ← 撞了！
...
```

👉 只有 **16 个**不同的 bank 被用到，每个 bank 有 2 个线程要拿 → **2 路冲突**。

**所以更完整的规律是**：

```text
设相邻线程地址差 = d
冲突路数 = gcd(d, 32)        （gcd = 最大公约数）

d = 1  → gcd = 1  → 1 路  → 无冲突 ✅
d = 2  → gcd = 2  → 2 路  → 轻微冲突
d = 4  → gcd = 4  → 4 路  → 中等冲突
d = 8  → gcd = 8  → 8 路  → 严重
d = 16 → gcd = 16 → 16 路 → 非常严重
d = 32 → gcd = 32 → 32 路 → 最惨 ❌
d = 33 → gcd = 1  → 1 路  → 无冲突 ✅
```

> **这才是完整的判断法则**：不看"地址差是不是 32 的倍数"，而看 **`gcd(地址差, 32)`**。
> 上一句"互质就无冲突"是它的特例（gcd = 1）。

**二维 tile 的情况**：`tile[32][32]` 里的 `tile[i][j]` 地址是 `i*32 + j`。

```cpp
// 按行访问（warp 内 tx 变、ty 固定）：
tile[ty][tx]      // 地址 = ty*32 + tx，bank = (ty*32 + tx) % 32 = tx  → 无冲突 ✅
tile[ty][tx+1]    // 同理，无冲突

// 按列访问（warp 内 ty 变、tx 固定）—— 二维块的 warp 只沿 x 切，
// 所以严格说这种情况在二维块里不会出现；但如果你用一维块手工算索引，
// 就可能构造出来：
tile[i][fixed]    // 地址 = i*32 + fixed，bank = fixed % 32 恒定 → 32 路冲突 ❌
```

---

#### 🔧 消除方法一：Padding（填充）—— 本章的"魔法一招"

**做法**：把 `tile[32][32]` 改成 `tile[32][33]`。

**就多了一列。** 为什么这样就能解决问题？

**推导（跟着算一遍就懂了）**：

```text
改之前：tile[i][j] 的地址 = i*32 + j
        列访问时 i 变、j 固定 → bank = (i*32 + j) % 32 = j % 32  ← 恒定！全撞一起 ❌

改之后：tile[i][j] 的地址 = i*33 + j
        列访问时 i 变、j 固定 → bank = (i*33 + j) % 32
                                     = (i*32 + i + j) % 32
                                     = (i + j) % 32        ← 随 i 变化！
```

**看最后一行**：对固定的 `j`、变化的 `i = 0..31`，`(i + j) % 32` 会取遍 **0~31 全部 32 个值**——**每个抽屉正好一个人**！✅

> 🎯 **用抽屉的话说**：本来每一行的开头都对齐在抽屉 0，所以"同一列"的元素全都落在同一个抽屉里。
> **每行多塞一个空位（padding），就把每一行整体"错开"了一格**，于是同一列的元素被推到了 32 个不同的抽屉里。

**代价**：共享内存用量从 4096 字节变成 4224 字节（**多 3.1%**）。

**收益**：如果原本存在 32 路冲突，理论上能快很多倍（实际受限于其他瓶颈，通常能快 1.5~3 倍）。

---

#### ⚠️ 关键提醒：padding 不是万能药！

**这是本章最想让你记住的一条。** padding 只对**特定**的访问方向有效：

```text
按行访问（相邻线程地址差 1）        → 32 列本来就没冲突，加 padding 反而引入冲突！
按列访问（相邻线程地址差 32/33）    → 32 列会 32 路冲突，padding 到 33 消除
```

**为什么按行访问时 padding 反而有害？** 因为：

1. 它**没解决任何问题**（本来就没冲突）；
2. 每行多一个空位，**缓存行的利用率下降**（搬上来的数据里有 1/33 是没用的空洞）；
3. 索引计算变复杂（`i*33` 比 `i*32` 难算，编译器也不好做移位优化）。

**这正是 `bank_conflict.cu` 里第二个实验要演示的**：对"按行访问"的 kernel 加 padding，性能反而**变差**。

> 💡 **这个反例比正面例子更有教育意义——优化一定要看数据，不要照抄套路。**
> 别人说"padding 能治 bank conflict"，那是**在别人的访问模式下**。你的模式可能压根不冲突。

---

#### 🔧 消除方法二：错位访问（Staggered Access）

**思路**：不打乱布局，而是**让每个线程的起始位置错开**，从而把 bank 打散。

```cpp
// 不用 padding，改成"每行起始位置偏移 row 个元素"
// 索引变成 tile[ty][(tx + ty) % 32]
int j = (tx + ty) % 32;
float v = tile[ty][j];
```

**为什么有效？** 因为地址里**混入了 `ty`**，和 padding 的效果类似，把固定的 bank 打散成随行变化的 bank。

**❌ 缺点**：

- 索引计算多了取模，**每次访问都要算**（而 padding 是编译期就定好的）；
- 可能引入**新的**冲突模式（取决于具体的 `tx`/`ty` 组合）；
- 代码可读性变差。

现代实践里 **padding 更常用**——因为它零运行时开销。

---

#### 🔧 消除方法三：利用广播（Broadcast）

如果所有线程都需要**同一个值**，那么让它们**读同一个地址**，而不是"各自读一份副本"：

```cpp
// ❌ 每个线程读自己的一份（可能冲突）
float scale = s_scale[threadIdx.x % 4];   // 4 个地址，但 bank 分布取决于布局

// ✅ 用 __shfl_sync 从 lane 0 广播（见第 3 章）
float scale = __shfl_sync(0xffffffffu, s_scale[0], 0);
```

**思路对比**：

| 做法                       | 发生了什么                                       |
| -------------------------- | ------------------------------------------------ |
| ❌ 每人读自己的副本        | 4 个不同地址，可能落在同一个 bank → 冲突         |
| ✅ 大家读同一个地址        | 触发**广播**，1 次访问搞定                       |
| ✅ 用 `__shfl_sync` 广播   | 连共享内存都不用了，直接在寄存器之间传（第 3 章） |

> 🎯 **核心思想：能广播就广播。** 让 32 个线程读**同一个地址**，比让它们读"32 个内容相同的地址"要快得多——因为前者硬件认得出，后者硬件认不出。

---

#### 📌 Bank Conflict 总结

> **共享内存的"内斗"：抽屉有 32 个，一个周期一个抽屉只能服务一个人。**
> **散得开 → 一个周期全拿到；挤一起 → 排队，最惨慢 32 倍（比全局内存还慢）。**

| 你要判断的               | 怎么判断                                        |
| ------------------------ | ----------------------------------------------- |
| 有没有冲突               | 算 `gcd(相邻线程地址差, 32)`，等于 1 就无冲突   |
| 32 个线程读同一地址      | 不算冲突，是**广播** ✅                         |
| 加 padding 有用吗        | **只在"按列访问"时有用**；按行访问加它会更慢 ❌ |
| 不确定怎么办             | **用 `ncu` 测**，别靠推理（第 4 章）            |

**三种消除手段对比**：

| 手段         | 做法                        | 运行时开销 | 适用场景                     |
| ------------ | --------------------------- | ---------- | ---------------------------- |
| **Padding**  | `[32][32]` → `[32][33]`     | **零**     | 按列访问（最常用）           |
| **错位访问** | 索引加 `ty` 偏移            | 有（取模） | 不方便改数组大小时           |
| **广播**     | 让线程读同一地址 / `__shfl` | 零         | 所有线程需要同一个标量值时   |

### 1.9 矩阵乘法三级演进：本章的核心案例

这是把前面所有概念串起来的地方。请务必亲手跑一遍 `matrix_mul.cu`。

#### 🎬 场景：同一个任务，三次"换工具"

先看全局：三个版本，各自在解决什么问题。

| 版本 | 用什么工具            | 解决了什么                                 | 类比                             |
| ---- | --------------------- | ------------------------------------------ | -------------------------------- |
| v1   | 什么都没有            | （基准）                                   | 每个零件都跑一趟仓库 🐢          |
| v2   | **共享内存（分块）**  | 消除**重复访问**：512 倍 → 16 倍           | 一组人合搬一箱料，共用工作台 🚗  |
| v3   | **寄存器（分块）**    | 减少**共享内存访问**：每个值多用几次       | 料拿到手边，一次抓一把 🏃        |

> 🎯 **关键认知：v1 → v2 → v3 不是"把同一个东西改快一点"，而是三次"换用更好的工具"。**
> 每一次都要付出代价（v2 要同步、v3 要寄存器），每一次都要**实测**才知道值不值。

---

#### 🍳 v1：朴素版 —— "每个零件都跑一趟仓库"

```cpp
__global__ void gemmNaive(const float* A, const float* B, float* C,
                          int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < M && col < N) {
        float acc = 0.0f;
        for (int k = 0; k < K; ++k) {
            acc += A[row * K + k] * B[k * N + col];
        }
        C[row * N + col] = acc;
    }
}
```

**🧩 这个 kernel 到底慢在哪？很多人第一反应是错的**

大多数人的第一反应是："`A[row*K+k]` 里 `k` 在变，地址跨了 K 个 float，所以是**不合并**的！"

**❌ 这个判断是错的。** 我们来仔细看：

| 访问                       | 模式                                                                  | 评价                                            |
| -------------------------- | --------------------------------------------------------------------- | ----------------------------------------------- |
| `A[row*K + k]`             | 同一 warp 内 `col` 变、`row` 不变，所以**所有 32 个线程读同一个地址** | **广播**！其实一点不慢                          |
| `B[k*N + col]`             | 同一 warp 内 `col` 连续（0~31）                                       | **合并访存**！也是好的                          |

> **所以 v1 的访存模式其实是"合并的 + 广播的"，单看每一次访问都不算差。**
> 那它为什么慢？**因为访问的"次数"太多了。**

**真正的问题不是"不合并"，而是"重复访问太多"。** 这就是 1.7 节算出来的"512 倍重复"。

> 💡 **这个认知非常重要**：性能优化里，**"每次访问快不快"**和**"要访问多少次"**是两个独立的维度。
> 很多人只盯着第一个（合并访存），却完全忽略了第二个（数据复用）。**而 GEMM 的问题 100% 在第二个上。**

**算术强度（Arithmetic Intensity）**：

```text
算术强度 = 浮点运算次数 / 搬运字节数
         = 2*M*N*K / (8*M*N*K)      （朴素的全局内存访问量）
         = 0.25 flops/byte
```

极低。而 GPU 的算力/带宽比（在 A100 上）大约是 19.5 TFLOPS / 1555 GB/s ≈ 12.5 flops/byte。**算术强度 < 这个比值 → 访存受限**。

> 🍳 用大白话说：**GPU 是个超级大厨，刀快得吓人，但你每切一刀都要跑一趟仓库。**
> 结果就是——**大厨 99% 的时间都在走路，刀根本没机会快起来。**

#### 🚗 v2：共享内存分块 —— "一组人合搬一箱料"

```cpp
__global__ void gemmTiled(const float* A, const float* B, float* C,
                          int M, int N, int K) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;
    float acc = 0.0f;

    for (int k0 = 0; k0 < K; k0 += TILE) {
        // 阶段 1：协作加载（越界填 0，避免热循环里加判断）
        int aCol = k0 + tx, bRow = k0 + ty;
        As[ty][tx] = (row < M && aCol < K) ? A[row * K + aCol] : 0.0f;
        Bs[ty][tx] = (bRow < K && col < N) ? B[bRow * N + col] : 0.0f;

        __syncthreads();     // 阶段 2：等加载完

        // 阶段 3：在共享内存上累加
        #pragma unroll
        for (int k = 0; k < TILE; ++k) {
            acc += As[ty][k] * Bs[k][tx];
        }

        __syncthreads();     // 阶段 4：等算完，防覆盖
    }
    if (row < M && col < N) C[row * N + col] = acc;
}
```

**🔍 逐行看懂这四步**

把这四步和 1.6 节的厨房比喻对起来：

| 阶段 | 代码                            | 厨房里发生了什么                         |
| ---- | ------------------------------- | ---------------------------------------- |
| 1    | `As[ty][tx] = A[...]`           | 256 个厨师**一起**跑一趟仓库，各搬一样料 |
| 2    | `__syncthreads()`               | 📢 "都放好了吗？" —— 等大家搬完          |
| 3    | `acc += As[ty][k] * Bs[k][tx]`  | 每个人从**台子上**取料做菜               |
| 4    | `__syncthreads()`               | 📢 "都做完了吗？" —— 才能腾台子          |

**⚠️ 注意一个容易忽略的细节：为什么越界要填 0？**

```cpp
As[ty][tx] = (row < M && aCol < K) ? A[row * K + aCol] : 0.0f;
//                                       ^^^^^^^^^^^^^^^   ^^^^^^
//                                       正常取料           越界了，填 0
```

因为矩阵尺寸（比如 513）往往**不是 TILE（32）的整数倍**，tile 会伸出边界。

**为什么填 0 是安全的？** 因为矩阵乘法的内层是 `acc += As[ty][k] * Bs[k][tx]`——**0 乘任何数都是 0，加进去等于没加**。

> 🎯 **更重要的原因：把判断"挪出热循环"。**
> 如果写成"每次内层循环都检查 `if (合法) acc += ...`"，那这个判断要执行 `K × TILE` 次；
> 而填 0 只在**加载时判断一次**，内层循环干干净净——**这是用一点点多余的加载，换掉了海量的分支判断。**

**为什么变快（回答"这个手段为什么能变快"）**：

| 指标                          | v1      | v2           |
| ----------------------------- | ------- | ------------ |
| 每线程全局内存读取次数        | `2K`    | `2 * K/TILE` |
| 以 K=512、TILE=32 计          | 1024 次 | 32 次        |
| 减少倍数                      | —       | **32 倍**    |
| 全局内存总字节数（M=N=K=512） | 约 1 GB | 约 32 MB     |

**算术强度变化**：

```text
v2 的全局内存访问量 ≈ (2 * M*N*K / TILE) 次读取
算术强度 = 2*M*N*K / (8 * M*N*K / TILE) = TILE/4 = 8 flops/byte（TILE=32）
```

从 0.25 涨到 8，接近了机器平衡点 12.5。所以 v2 通常会比 v1 快**数倍到十几倍**（具体取决于卡）。

> 🍳 大厨现在切 32 刀才跑一趟仓库。虽然还是要跑，但**刀刃终于有时间发挥作用了**。

**一个细节提醒**：`As[ty][tx]` 和 `Bs[ty][tx]` 的加载是**合并访存**的（`tx` 连续 → 地址连续）。这是 v2 快的前提之一。如果你的 tile 加载写成 `As[tx][ty]`，加载就变成跨步的，v2 的收益会被吃掉一大半。

#### 🏃 v3：寄存器分块 —— "料拿到手边，一次抓一把"

v2 已经很快了，但还有优化空间。看 v2 的内层循环：

```cpp
for (int k = 0; k < TILE; ++k) {
    acc += As[ty][k] * Bs[k][tx];    // 每次迭代从共享内存读 2 个值，只用一次
}
```

**🧩 问题在哪？**

每个线程从共享内存读了 `2*TILE = 64` 个值，只做了 `TILE = 32` 次乘加。**每个读进来的值只用了一次。**

> 🍳 类比：厨师走到操作台前，**拿起一根胡萝卜**，切一刀，**放回去**；再拿起另一根，切一刀，放回去……
> **每次往返操作台都只切一刀。** 而操作台虽然近，来回跑 64 趟也是要时间的。

**寄存器分块（Register Tiling）的思想**：让每个线程**一次算多个输出**，这样读进来的 `A` 值能被多个输出复用、读进来的 `B` 值也能被多个输出复用。

```text
假设每线程算 TM×TN = 4×4 = 16 个输出：

  for each k:
      从共享内存读 aReg[0..TM-1]      → 4 次读
      从共享内存读 bReg[0..TN-1]      → 4 次读
      for i in 0..TM-1:
          for j in 0..TN-1:
              acc[i][j] += aReg[i] * bReg[j];    → 16 次乘加

  共享内存读取 / 乘加 = 8 / 16 = 0.5   （v2 是 2 / 1 = 2）
  复用率提升 4 倍
```

> 🍳 **换成厨房的说法**：厨师**一把抓起 4 根胡萝卜 + 4 个土豆**（8 次取料），回到案板前**一口气切 16 刀**（4×4 种搭配）。
> **往返次数没变，但每次往返干的活多了 4 倍。**

**代码结构**（以块覆盖 64×64、每线程 4×4、块 16×16 线程为例）：

```cpp
__global__ void gemmRegTiled(const float* A, const float* B, float* C,
                             int M, int N, int K) {
    constexpr int TM = 4, TN = 4;
    __shared__ float As[BM][BK];    // 64 x 16
    __shared__ float Bs[BK][BN];    // 16 x 64

    int tx = threadIdx.x, ty = threadIdx.y;
    int threadRowBase = ty * TM;
    int threadColBase = tx * TN;

    float acc[TM][TN];
    // ... 初始化为 0

    int blockRow = blockIdx.y * BM;
    int blockCol = blockIdx.x * BN;

    for (int k0 = 0; k0 < K; k0 += BK) {
        // 协作加载 BM*BK 和 BK*BN 的 tile
        // ...
        __syncthreads();

        #pragma unroll
        for (int k = 0; k < BK; ++k) {
            float aReg[TM], bReg[TN];
            #pragma unroll
            for (int i = 0; i < TM; ++i) aReg[i] = As[threadRowBase + i][k];
            #pragma unroll
            for (int j = 0; j < TN; ++j) bReg[j] = Bs[k][threadColBase + j];

            #pragma unroll
            for (int i = 0; i < TM; ++i)
                #pragma unroll
                for (int j = 0; j < TN; ++j)
                    acc[i][j] += aReg[i] * bReg[j];
        }
        __syncthreads();
    }

    // 写回
    // ...
}
```

**🔍 关键的三层结构（这张图值得盯一分钟）**

```text
   全局内存 (仓库)                          ← 最慢、最大
        │  协作加载，合并访存
        ▼
   共享内存 As/Bs (操作台)                  ← 快 10~20 倍
        │  aReg[4] + bReg[4]：每人一次抓 8 个
        ▼
   寄存器 acc[4][4] + aReg + bReg (手边)    ← 最快
        │  16 次乘加，零内存访问
        ▼
   累加结果
```

> 🎯 **这就是"内存金字塔"的实际运用（1.2 节）**：
> **把频繁访问的数据从"慢而大"的层级搬到"快而小"的层级。**
> v1 什么都直接在仓库干；v2 搬到了操作台；v3 进一步搬到了手边。
> **三级演进，就是沿金字塔往上爬了两层。**

**为什么变快**：

1. **共享内存访问量减半到 1/4**（复用率提高）；
2. **累加器全在寄存器里**，内层的 16 次乘加不需要任何内存访问；
3. 编译器可以对 `acc[i][j] += aReg[i] * bReg[j]` 这个模式做**指令级并行**（16 个独立的乘加可以流水起来）。

**代价**：

- **寄存器用量上升**：`TM * TN = 16` 个累加器 + `TM + TN = 8` 个操作数 + 索引变量。这会**降低占用率**。
- **写回时的访存模式**：如果每线程写 4×4 个连续的元素，需要小心保证"相邻线程写相邻地址"（否则写就不合并了）。

**三者的权衡正是 GPU 优化的核心张力**：

```text
更多共享内存 / 更多寄存器  →  每个线程干活更多、复用更高
                          →  但占用率下降、可能有 spill
                          →  必须实测找平衡点
```

> 💡 **手边的东西是有限的**：寄存器是"手"，一个人手上能拿的东西就那么几样。
> `TM×TN` 从 4×4 涨到 8×8，手上的东西从 16 样涨到 64 样——**手拿不下了，就得往地上放（spill，见 1.11 节），反而更慢。**

---

#### 📊 三级演进一览（把这一节的账收个尾）

|                        | v1 朴素       | v2 共享内存分块 | v3 寄存器分块        |
| ---------------------- | ------------- | --------------- | -------------------- |
| **每线程全局读**       | 2K = 1024     | K/16 = 32       | 32（同 v2）          |
| **每线程共享内存读**   | 0             | 2K = 64         | 64 / 4 = 16          |
| **每线程寄存器乘加**   | 0             | 0               | **256（零访存）**    |
| **算术强度**           | 0.25          | 8               | 8（但访存层次更高）  |
| **寄存器用量**         | 16            | 32              | 64                   |
| **共享内存用量**       | 0             | 8192 B          | 2048 B               |
| **相对速度（实测）**   | 1×            | **3~10×**       | **5~20×**            |
| **主要解决的问题**     | （基准）      | 重复读取        | 共享内存往返次数     |
| **付出的代价**         | 慢            | 要两次同步      | 寄存器压力、可能 spill |

> **注意最后一行的对照**：v2 的代价是"**必须严格同步**"（漏一个屏障就时对时错），v3 的代价是"**寄存器压力**"（可能 spill）。
> **没有免费的优化。每一个收益后面都站着一个代价。**

### 1.10 常量内存与只读缓存

#### 📢 场景：32 个工人问同一个问题

接着工厂的故事。这次的情况有点不一样：

> 产线上 32 个工人（一个 warp），**每个人都要看同一份"工艺参数表"**——
> 比如"这批零件的温度设成多少度"。

有两种做法：

**❌ 做法一：一人发一份参数表**

32 个人每人手里发一份，各自低头查。

👉 听起来没问题？**但硬件不这么看。** 如果这 32 份表**放在不同的地址**，硬件就得**跑 32 趟**去取——因为它不知道这 32 个地址里的内容其实一样。

**✅ 做法二：挂一块公告板，大家一起看**

工人不用低头查自己的，而是**抬头看墙上同一块公告板**。

👉 硬件一看："哦，**32 个人问的是同一个问题**。" 于是**只跑一趟**，把答案**喊给所有人听**。

**这就是广播（Broadcast）——常量内存就是为它而生的。**

> 🎯 **关键认知：常量内存快不快，不取决于"数据量小"，而取决于"32 个人问的是不是同一个问题"。**
> 32 个人问同一个 → **飞速**；32 个人各问各的 → **比全局内存还慢**。

---

#### 💾 `__constant__`：为广播而生的内存

```cpp
__constant__ float c_coeff[64];   // 文件作用域声明

// 主机端写入：注意是"符号"，不加 &
CUDA_CHECK(cudaMemcpyToSymbol(c_coeff, h_coeff, sizeof(h_coeff)));

// 核函数里直接当数组用
__global__ void k(...) { float v = c_coeff[i % 64]; }
```

**硬件特性**：

| 特性       | 说明                                                     | 用公告板的话说                          |
| ---------- | -------------------------------------------------------- | --------------------------------------- |
| 容量       | 每设备 64 KB（`__constant__` 变量总大小）                | 公告板就那么大，只能挂最常用的          |
| 缓存       | 专门的常量缓存（与 L1 独立）                             | 一块**专门的**公告栏，不跟别的抢地方    |
| **广播**   | **同一个 warp 内所有线程读同一个地址时，一次访问搞定**   | 32 个人看同一块板 → 一趟 ✅             |
| **串行化** | 同一个 warp 内线程读**不同**地址时，会按地址**串行**处理 | 32 个人各问各的 → **排队 32 次** ❌     |

**所以常量内存的适用场景非常明确**：

```text
✅ 所有线程读同一个值（或少量几个值）  → 广播，极快
❌ warp 内每个线程读不同的地址        → 串行化，比全局内存还慢
```

**⚠️ 特别提醒"比全局内存还慢"这一条**：

常量缓存**每个周期只能提供一个值**。所以如果 32 个线程要 32 个不同的地址，硬件只能**一个一个来**——**32 个周期**。

而全局内存呢？它虽然延迟高，但**带宽大**，32 个不同的地址**可以并行处理**（只要它们在合适的范围内）。

> 💡 **所以常量内存是个"偏科生"**：**广播场景世界第一，散列场景全班倒数。**
> 用错了，**你花力气建的"快速通道"反而变成了瓶颈**。

**🎯 正反例对照（这才是关键）**：

```cpp
// ✅ 正例：所有线程读同一个 ch → 广播，飞快
__global__ void scaleConstantMem(const float* in, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        int ch = i % CHANNELS;                    // 注意：ch 在 warp 内是变化的
        out[i] = in[i] * c_scale[ch] + c_bias[ch];
    }
}
```

> 🤔 **等一下，这里 `ch = i % CHANNELS` 不是每个线程都不同吗？**

**好眼力！** 这确实是这个例子的一个隐藏问题——如果 `CHANNELS` 大于 32，那么 warp 内 32 个线程会读到 **32 个不同的地址**，**触发串行化**。

**那为什么例子里没事？** 因为 `CHANNELS = 8`，warp 内的 32 个线程只落在 **8 个不同的地址**上——而**落在同一个地址上的那几个线程**（比如线程 0、8、16、24 都读 `c_scale[0]`）会**合并成一次广播**。

👉 所以实际是 **8 次串行访问**，而不是 32 次。**能接受，但不是最优。**

**✅ 真正的"完美广播"场景长这样**：

```cpp
// 所有线程读同一个值（内层循环里的固定系数）
__global__ void convWithConstant(const float* in, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    float s = 0.0f;
    #pragma unroll
    for (int j = 0; j < 2 * R + 1; ++j) {
        // c_w[j]：对固定的 j，warp 内 32 个线程读的是同一个地址！
        //          → 100% 广播，一次访问搞定 ✅
        s += in[i + j] * c_w[j];
    }
    out[i] = s;
}
```

> 🎯 **看出区别了吗？**
> - 前一个例子：`c_scale[ch]` 里 **`ch` 依赖线程号** → 地址随线程变 → 可能串行。
> - 后一个例子：`c_w[j]` 里 **`j` 是循环变量，与线程号无关** → 32 个线程**铁定读同一地址** → 完美广播。
>
> **判断口诀：看下标里有没有 `threadIdx`。有 → 要小心；没有 → 放心用。**

**典型用法**：卷积核权重、固定系数、小查找表（且查找模式是"同一 warp 读同一个位置"）。

**怎么写入？两种方式**：

```cpp
// 1) cudaMemcpyToSymbol：最常用
CUDA_CHECK(cudaMemcpyToSymbol(c_coeff, h_coeff, bytes));

// 2) 从设备内存写（需要 cudaMemcpyToSymbol 的 DeviceToDevice 版本）
CUDA_CHECK(cudaMemcpyToSymbol(c_coeff, d_coeff, bytes, 0, cudaMemcpyDeviceToDevice));

// 3) 从符号读回主机（调试用）
CUDA_CHECK(cudaMemcpyFromSymbol(h_buf, c_coeff, bytes));
```

**注意**：`cudaMemcpyToSymbol` 的第一个参数是**符号本身**，不是它的地址。传 `&c_coeff` 会得到错误的结果或编译错误（在 CUDA 里会产生 `invalid device symbol` 错误）。

> 🏢 **用一个类比理解这个"不加 `&`"的怪规矩**：
> `c_coeff` 在主机端**不是一个真实存在的变量**——它只是**显存里的一个门牌号**。
> 主机代码（CPU 那边）根本不知道这个门牌号在哪，它只知道"有个叫 `c_coeff` 的房间"。
> `cudaMemcpyToSymbol` 的工作方式是：**报出房间名**，由运行时去查表找到地址，再往里送货。
> 所以你要给的是**名字**（符号），不是**地址**（`&符号`——主机压根拿不到这个地址）。

#### 📖 `__ldg` 与只读缓存

```cpp
// 显式要求走只读数据缓存
float v = __ldg(ptr + i);
```

**`__ldg` 的作用**：把加载操作走**只读数据缓存路径**（texture path），与 L1 的写通路分离。

> 🍳 类比：仓库里有一批"**确定不会改动**"的原料（比如配方书）。
> 你可以把它们**单独放在一个只读的书架上**，大家随便翻，不用跟"会变的货物"抢通道。

**什么时候有用？**

- 数据在整个 kernel 生命周期内**确定不会被写**；
- 访存有局部性，希望它在只读缓存里长时间驻留；
- 或者你就是想让编译器知道"这不会被改动"，从而敢于做更激进的指令重排。

**`const __restrict__` 是更现代的做法**：

```cpp
__global__ void k(const float* __restrict__ in, float* __restrict__ out, int n) {
    out[i] = in[i];    // 编译器看到 const __restrict__，一般会自动发 LDG
}
```

**实测经验**：在 sm_35 及以后的架构上，`const __restrict__` 和显式 `__ldg` 生成的指令**通常完全一样**。所以：

- **优先写 `const T* __restrict__`**（更干净，自动享受优化）；
- 只有当你需要"明确表达意图"或维护老代码时，才写 `__ldg`。

**怎么验证？**

```bash
cuobjdump -sass your_app | Select-String 'LDG'    # Windows
cuobjdump -sass your_app | grep LDG               # Linux
```

如果看到 `LDG.E` 之类，说明走了全局/只读加载；看到 `LDC` 则是常量内存加载。

---

#### 🤔 一个反直觉的现实：常量内存常常"看不出收益"

`constant_ldg.cu` 里的三个版本（全局直读 / 共享内存 / 常量内存），实测耗时**很可能几乎一样**。

**为什么？** 因为那个 kernel 是**显存带宽受限**的：读 64 MB、写 64 MB。

> 🏭 用工厂的话说：**整条产线的瓶颈在"仓库大门太窄"上**，而你花力气优化的是"某个工人少跑了一趟"。
> **瓶颈不在那儿，你的优化自然就看不见。**

**那怎么才能看出常量内存的收益？让"访问参数"成为瓶颈：**

```cpp
// 把内层循环改成这样，参数读取次数翻 100 倍
float s = 0.0f;
for (int r = 0; r < 100; ++r) s += in[i] * c_scale[ch];
out[i] = s + c_bias[ch];
```

这时 v3 的优势会明显显现。

> 🎯 **这个"怎么设计实验才能暴露你想测的因素"的思路，比结果本身更重要。**
> **如果你的优化没效果，先别怀疑优化手段——先问一句："我优化的那一步，真的是瓶颈吗？"**

### 1.11 寄存器与占用率

#### 🪑 场景：一间教室能坐多少人

这是本章最后一个概念，也是最容易被误解的一个。

> **你有一间教室**（一个 SM）。
> **教室里有 1536 把椅子**（每 SM 最多 1536 个线程）。
> **每把椅子旁边有个储物柜**（寄存器），柜子有 65536 个格子，**全班共用**。

**规则**：

- 学生（线程）**必须坐下才能上课**；
- 每个学生**需要若干格子放自己的东西**（每个线程用 N 个寄存器）；
- **如果柜子不够分，就来不了那么多学生**。

**"占用率（Occupancy）"就是**：

```text
占用率 = 实际坐下的学生数 / 椅子总数
       = 实际驻留线程数 / 每 SM 最大线程数
```

> 🎯 **那占用率高就是好事吗？** 别急，这正是本节要打破的迷信。先看怎么算。

---

#### 🗃️ 寄存器是怎么分配的

- 每个 SM 有 **65536 个 32-bit 寄存器**（大多数架构）。
- 寄存器按**块**分配，粒度通常是 256 个寄存器。
- **每线程最多 255 个寄存器**。

> 🪑 **用教室的话说**：储物柜是**按小组（块）整租**的，不能拆开。一个小组 256 人，每人要 32 个格子，那就要租 `256 × 32 = 8192` 个格子，**哪怕有人用不满也照样占着**。

**占用率的计算**：

```text
每 SM 最大驻留块数 = min(
    每 SM 最大线程数 / 块大小,
    每 SM 寄存器总数 / (每线程寄存器数 × 块大小),
    每 SM 共享内存 / 每块共享内存,
    每 SM 最大块数（通常 16 / 24 / 32）
)

占用率 = (驻留块数 × 块大小) / 每 SM 最大线程数
```

**🧩 为什么要取 `min`？** 因为**四个条件里最紧的那个说了算**：

| 限制条件 | 用教室的话说                                   |
| -------- | ---------------------------------------------- |
| 线程数   | 椅子不够了                                     |
| 寄存器   | 储物柜格子不够了                               |
| 共享内存 | 教室里的操作台面积不够了                       |
| 块数上限 | 硬件规定"一个教室最多放 16 个小组"（管理能力） |

> 💡 **这就是为什么优化占用率往往让人困惑：你优化了一个，结果发现另一个才是瓶颈。**

**举个完整的例子**（RTX 3060：每 SM 1536 线程、65536 寄存器、100 KB 共享内存、最多 16 块/SM）：

```text
kernel 用 32 个寄存器/线程，块大小 256，无共享内存

按线程数： 1536 / 256 = 6 个块
按寄存器： 65536 / (32 * 256) = 8 个块
按共享内存： 无限
按块数上限：16 个块

→ min = 6 个块 = 1536 线程
→ 占用率 = 1536 / 1536 = 100%
```

**🎯 现在看最有趣的部分：寄存器用量变化会怎样？**

```text
寄存器 32 个/线程 → 65536/(32×256) = 8 个块 → 但线程数限制 6 个 → 6 块 → 100%
寄存器 40 个/线程 → 65536/(40×256) = 6.4 → 6 个块           → 6 块 → 100%
寄存器 42 个/线程 → 65536/(42×256) = 6.09 → 6 个块          → 6 块 → 100%
寄存器 43 个/线程 → 65536/(43×256) = 5.95 → 5 个块 ⚠️        → 5 块 → 83.3%
寄存器 48 个/线程 → 65536/(48×256) = 5.33 → 5 个块          → 5 块 → 83.3%
```

**看出规律了吗？**

```text
32 → 40 → 42：占用率一直是 100%（纹丝不动）
42 → 43：    占用率突然从 100% 掉到 83.3%   ← 悬崖式下跌
```

> 🎯 **关键洞察：寄存器对占用率的影响是"阶梯式"的，不是线性的。**
> **从 32 涨到 40 可能毫无影响，从 42 涨到 43 就掉一档。**

**💡 这个性质有非常大的实用价值**：

- **反过来说**：你**可以免费多用 10 个寄存器**（32 → 42），占用率一点不掉！
- 而这 10 个寄存器可能正好用来做寄存器分块（1.9 节 v3），换来更高的数据复用。

> 🎯 **这就是"寄存器换性能"的理论依据**：只要不跨过阶梯边界，多用寄存器是**白赚**的。
> `-Xptxas -v` 报出寄存器数以后，先算一下"下一个阶梯边界在哪"，就知道自己还有多少免费额度。

#### 🎛️ 两个控制工具

**🅰️ 工具一：`__launch_bounds__`（推荐）**

```cpp
// 告诉编译器："这个 kernel 最多用 256 线程/块，我至少要 2 块/SM"
__global__ void __launch_bounds__(256, 2) myKernel(...) { ... }
```

**第一个参数**是块大小的上界，**第二个参数**（可选）是"每 SM 最少要驻留几块"。

**编译器会为这个承诺做寄存器预算**：

```text
可用寄存器/线程 = 65536 / (minBlocksPerSM × maxThreadsPerBlock)
                = 65536 / (2 × 256) = 128
```

如果原本它想用 160 个寄存器，现在会被压到 128 以内。

**⚠️ 但代价是：压寄存器可能导致 spill（溢出），反而更慢。**

用教室的话说：

> 学校规定"这个班必须至少招 2 个组进来"，于是**储物柜必须省着分**。
> 每个学生只发 128 个格子，东西放不下的**只能堆到教室外面的走廊上**（本地内存 = 显存）。
> **虽然教室里人多热闹了，但每个人拿东西都要跑一趟走廊。**

所以：

> **`__launch_bounds__` 不是万能药。加之前先测基线的寄存器数和占用率，加了之后再测一次。只有数据说它变快了，才留下它。**

**🅱️ 工具二：`-maxrregcount=N`（慎用）**

```bash
nvcc -O3 -maxrregcount=32 kernel.cu -o kernel
```

它给**整个文件里所有 kernel** 设置寄存器上限。问题是：

- 它不知道哪个 kernel 需要更多寄存器，一律砍到 N，很容易引发 spill；
- 它会影响所有 kernel，无法针对性调优。

> 🪑 类比：**"全校所有班级一律每人只发 32 个储物格。"**
> 但文科班可能够用，工科班（计算密集）根本不够——**一刀切必然误伤**。

**更好的做法**是用 `__launch_bounds__` 精确控制到某个 kernel。

#### 💧 寄存器溢出（Spill）

**什么是 spill？** 当编译器需要的寄存器超过可用数量时，它会把一部分变量放到**本地内存（Local Memory）**里。

**🔴 关键事实：本地内存物理上就在显存里。**

> 🪑 **"本地"这个名字极具误导性！**
> 它叫"local"，让人以为"就在身边、很快"——**完全相反**。
> **它只是"每个线程私有"的地址空间，物理上住在显存里，走的是全局内存的通路**（有 L1/L2 缓存帮忙）。

用教室的话说：

> 储物格不够用，学生把东西**堆到了走廊上**。走廊虽然在"教室外面不远处"，但**拿一次要走出教室**。
> **名字叫"本地"，实际是"异地"。**

所以 spill 的代价：

```text
spill store/load 的延迟 ≈ 全局内存延迟（400+ 周期）
只不过它们通常能命中 L1/L2，所以实际是 ~30~200 周期
```

比寄存器慢几十到几百倍。**少量的 spill 也许能忍，大量 spill 是性能杀手。**

**怎么发现？**

```bash
nvcc -O3 -Xptxas -v kernel.cu -o kernel
```

输出里会出现：

```text
ptxas info : Compiling entry function 'gemmRegTiled' for 'sm_86'
ptxas info : Function properties for gemmRegTiled
    64 bytes stack frame, 48 bytes spill stores, 32 bytes spill loads
ptxas info : Used 128 registers, 8192 bytes smem, 400 bytes cmem[0]
```

- `stack frame` 非 0 → 有问题；
- `spill stores` / `spill loads` 非 0 → **就是它**。

**另一种方式（运行时 API）**：

```cpp
cudaFuncAttributes attr;
cudaFuncGetAttributes(&attr, myKernel);
printf("regs=%d, localSize=%zu\n", attr.numRegs, attr.localSizeBytes);
// localSizeBytes != 0 说明有 spill
```

**spill 的常见原因与对策**：

| 原因                                        | 对策                                     |
| ------------------------------------------- | ---------------------------------------- |
| 每线程算太多元素（比如 16×16 的寄存器分块） | 调小分块（8×8 或 4×4）                   |
| 数组下标是运行期变量，编译器无法放进寄存器  | 用 `#pragma unroll` 让下标成为编译期常量 |
| 加了过严的 `__launch_bounds__`              | 放宽或去掉                               |
| 用了 `-maxrregcount` 全局限制               | 改成 `__launch_bounds__` 精确控制        |
| 局部数组太大（比如 `float tmp[64]`）        | 改成共享内存，或者拆成多次小批量处理     |

---

#### 🔥 一个最重要的实战经验（能解释 90% 的"我的局部数组怎么这么慢"）

> **数组下标是"运行期变量"时，局部数组一定会被放到本地内存里（因为寄存器不能被动态索引）。**

**为什么？** 因为**寄存器没有地址**。你不能问"第 k 号寄存器里是什么"（k 是运行时才知道的）。所以只要下标是变量，编译器就**只能**把它放到有地址的内存里——也就是本地内存（=显存）。

```cpp
// ❌ tmp 会被放到本地内存，因为 k 是运行期变量
float tmp[8];
for (int k = 0; k < 8; ++k) tmp[k] = a[k];
float s = 0;
for (int k = 0; k < 8; ++k) s += tmp[k] * w[k];

// ✅ 用 #pragma unroll 展开，让下标变成编译期常量，编译器就能放进寄存器
float tmp[8];
#pragma unroll
for (int k = 0; k < 8; ++k) tmp[k] = a[k];
float s = 0;
#pragma unroll
for (int k = 0; k < 8; ++k) s += tmp[k] * w[k];
```

> 🪑 **用教室的话说**：
> `tmp[k]` 里的 `k` 是变量，等于说"**我要拿我第 k 个格子里的东西，但 k 是多少我现在还不知道**"。
> 储物柜（寄存器）**没有编号牌**，你只能同时捧着几样东西——**你没法"按编号找"**。
> 所以编译器只能说："那你就别放柜子里了，**去走廊上找个带编号的箱子吧**（本地内存）。"
>
> **加上 `#pragma unroll` 之后**：循环被展开成 8 条独立语句，`k` 变成了字面量 0、1、2...7。
> 现在每一句都是"**拿第 0 个**""**拿第 1 个**"——编译器知道具体是谁了，**于是直接分配 8 个寄存器**。

**这一条能解释 90% 的"为什么我的局部数组这么慢"的问题。**

---

#### 🎯 最后：破除"占用率迷信"（本章最重要的观念转变）

很多初学者学会算占用率以后，会陷入一个误区：**拼命想把占用率刷到 100%。**

**这个方向常常是错的。**

**回到教室的比喻**：

```text
方案 A：教室里坐 1536 个人，每人只能拿 32 个格子 → 每人干 1 份活
方案 B：教室里只坐 384 个人，每人能拿 128 个格子 → 每人干 8 份活
```

**哪个更快？** 取决于**这些活是"要等人"的还是"要算的"**：

| 场景                                   | 该选哪个                  | 为什么                                             |
| -------------------------------------- | ------------------------- | -------------------------------------------------- |
| **纯访存型**（向量加、拷贝、转置）     | **方案 A：高占用率**      | 大家都在等内存，**人越多越能把延迟藏住**（1.2 节） |
| **计算密集 + 高复用**（分块矩阵乘）    | **方案 B：低占用率也可**  | 每人手里的活就够干了，**不需要靠人多藏延迟**       |

> 🎯 **这就是 1.2 节埋下的伏笔**：
> **"用海量的并发线程来把单次访问的高延迟藏起来"**——这是高占用率的价值所在。
> **但如果你的 kernel 本来就不怎么等内存（复用率高），那"人多"就没那么重要了。**

**一个真实的数据对照**（`matrix_mul.cu` 的实测）：

| kernel         | 寄存器 | 共享内存 | 占用率 | 耗时    | GFLOPS      |
| -------------- | ------ | -------- | ------ | ------- | ----------- |
| `gemmNaive` v1 | 16     | 0        | **最高** | 3.85 ms | 69.7        |
| `gemmTiled` v2 | 32     | 8 KB     | 中     | 0.98 ms | 273.8       |
| `gemmRegTiled` v3 | **64** | 2 KB   | **最低** | 0.52 ms | **516.0**   |

> 🔍 **看这张表**：**寄存器用得最少的 v1 最慢（慢 7 倍），寄存器用得最多的 v3 最快。**
> **"占用率最高"的 kernel 输给了"占用率最低"的 kernel。**

**这是本章最后一个核心洞察**：

> **"占用率最大化"是一个常见的误区。它是手段，不是目的。真正的目的是"让 SM 始终有活可干"。**
> 如果一个线程用 128 个寄存器干了 8 倍的活，它可能比 4 个各用 32 个寄存器、每个只干 1 倍活的线程更快。

**✅ 正确的思考顺序**：

```text
1. 先用 ncu / 计时测出真实耗时        ← 一切从数据开始
2. 判断瓶颈在哪：
     访存受限 → 优化访存模式（合并、分块、减少重复）
     计算受限 → 优化指令、复用、寄存器分块
     延迟受限 → 这时候才轮到"提高占用率"
3. 只有在"确实在等延迟"时，占用率才是你的武器
```

> 💡 **记住一句话**：**占用率是"座位利用率"，不是"学习成绩"。**
> 教室坐满了但大家都在打瞌睡（等内存），还不如坐一半但人人埋头干活。

### 2.1 `coalescing.cu` —— 把"合并"这件事量化

```cpp
// 完整代码见 code/lessons/ch02_memory/coalescing.cu
#include <cmath>
#include <cstdio>
#include <vector>

#include "../common/cuda_check.h"
#include "../common/cuda_timer.h"

constexpr int BLOCK = 256;

// A. 合并访存（正确示范）
__global__ void coalescedKernel(const float* __restrict__ a,
                                float* __restrict__ out,
                                int n) {
    float sum = 0.0f;
    int stride = blockDim.x * gridDim.x;
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride) {
        sum += a[i];     // 相邻线程读相邻地址 -> 一个 warp 覆盖 128 连续字节
    }
    if (threadIdx.x == 0) out[blockIdx.x] = sum;
}

// B. 跨步访存（错误示范）
__global__ void stridedKernel(const float* __restrict__ a,
                              float* __restrict__ out,
                              int n) {
    float sum = 0.0f;
    const int S = 32;    // 故意取 32：正好让一个 warp 完全散开
    int stride = blockDim.x * gridDim.x * S;
    // 全局编号 g 的线程读 a[g*32]：
    // 线程 0 读 a[0]、线程 1 读 a[32]、... 地址相差 128 字节
    for (int i = (blockIdx.x * blockDim.x + threadIdx.x) * S; i < n; i += stride) {
        sum += a[i];
    }
    if (threadIdx.x == 0) out[blockIdx.x] = sum;
}

// C. 反向合并访存：顺序颠倒但区间连续，仍然是合并的
__global__ void reversedKernel(const float* __restrict__ a,
                               float* __restrict__ out,
                               int n) {
    float sum = 0.0f;
    int stride = blockDim.x * gridDim.x;
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride) {
        int j = n - 1 - i;
        if (j >= 0) sum += a[j];
    }
    if (threadIdx.x == 0) out[blockIdx.x] = sum;
}

// D. AoS：每个粒子 12 字节，但只读 x 分量
struct ParticleAoS { float x, y, z; };

__global__ void aosKernel(const ParticleAoS* __restrict__ p,
                          float* __restrict__ out, int n) {
    float sum = 0.0f;
    int stride = blockDim.x * gridDim.x;
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride) {
        sum += p[i].x;    // 只用了 12 字节里的 4 字节
    }
    if (threadIdx.x == 0) out[blockIdx.x] = sum;
}

// E. SoA：把 x 抽成独立数组
__global__ void soaKernel(const float* __restrict__ px,
                          float* __restrict__ out, int n) {
    float sum = 0.0f;
    int stride = blockDim.x * gridDim.x;
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride) {
        sum += px[i];     // 连续的 float 数组，完美合并
    }
    if (threadIdx.x == 0) out[blockIdx.x] = sum;
}
```

`main` 里对每个 kernel 用 `CudaTimer::measure` 跑 10 次取中位数，并用 `CudaTimer::bandwidthGBs` 换算有效带宽。

### 2.2 `matrix_mul.cu` —— 三级演进（核心代码）

```cpp
// 完整代码见 code/lessons/ch02_memory/matrix_mul.cu
constexpr int TILE = 32;    // v1/v2 的块尺寸
constexpr int BM = 64;      // v3 块覆盖的输出行数
constexpr int BN = 64;      // v3 块覆盖的输出列数
constexpr int BK = 16;      // v3 每次从 K 加载的深度

// ---------- v1 朴素 ----------
__global__ void gemmNaive(const float* __restrict__ A,
                          const float* __restrict__ B,
                          float* __restrict__ C,
                          int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < M && col < N) {
        float acc = 0.0f;
        for (int k = 0; k < K; ++k) {
            // 每线程对整个 K 循环都要走两趟全局内存 —— 这就是病根
            acc += A[row * K + k] * B[k * N + col];
        }
        C[row * N + col] = acc;
    }
}

// ---------- v2 共享内存分块 ----------
__global__ void gemmTiled(const float* __restrict__ A,
                          const float* __restrict__ B,
                          float* __restrict__ C,
                          int M, int N, int K) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;
    float acc = 0.0f;

    for (int k0 = 0; k0 < K; k0 += TILE) {
        int aCol = k0 + tx, bRow = k0 + ty;
        // 越界填 0：0 乘任何数都是 0，不影响结果，
        // 而且避免了在热循环里加判断
        As[ty][tx] = (row < M && aCol < K) ? A[row * K + aCol] : 0.0f;
        Bs[ty][tx] = (bRow < K && col < N) ? B[bRow * N + col] : 0.0f;

        __syncthreads();    // 第一次：生产者-消费者屏障

        #pragma unroll
        for (int k = 0; k < TILE; ++k) {
            acc += As[ty][k] * Bs[k][tx];
        }

        __syncthreads();    // 第二次：防覆盖屏障
    }
    if (row < M && col < N) C[row * N + col] = acc;
}

// ---------- v3 寄存器分块 ----------
__global__ void gemmRegTiled(const float* __restrict__ A,
                             const float* __restrict__ B,
                             float* __restrict__ C,
                             int M, int N, int K) {
    constexpr int TM = 4, TN = 4;   // 每线程算 4x4 个输出

    __shared__ float As[BM][BK];    // 64 x 16
    __shared__ float Bs[BK][BN];    // 16 x 64

    int tx = threadIdx.x;           // 0..15
    int ty = threadIdx.y;           // 0..15
    int threadRowBase = ty * TM;
    int threadColBase = tx * TN;

    float acc[TM][TN];
    #pragma unroll
    for (int i = 0; i < TM; ++i)
        #pragma unroll
        for (int j = 0; j < TN; ++j)
            acc[i][j] = 0.0f;

    int blockRow = blockIdx.y * BM;
    int blockCol = blockIdx.x * BN;

    for (int k0 = 0; k0 < K; k0 += BK) {
        // ---- 协作加载：用线性编号 -> 二维坐标，保证合并访存 ----
        #pragma unroll
        for (int t = 0; t < (BM * BK) / 256; ++t) {
            int flat = t * 256 + ty * 16 + tx;
            int r = flat / BK, c = flat % BK;
            int gr = blockRow + r, gc = k0 + c;
            As[r][c] = (gr < M && gc < K) ? A[gr * K + gc] : 0.0f;
        }
        #pragma unroll
        for (int t = 0; t < (BK * BN) / 256; ++t) {
            int flat = t * 256 + ty * 16 + tx;
            int r = flat / BN, c = flat % BN;
            int gr = k0 + r, gc = blockCol + c;
            Bs[r][c] = (gr < K && gc < N) ? B[gr * N + gc] : 0.0f;
        }
        __syncthreads();

        // ---- 计算：共享内存 -> 寄存器 -> 乘加 ----
        #pragma unroll
        for (int k = 0; k < BK; ++k) {
            float aReg[TM], bReg[TN];
            #pragma unroll
            for (int i = 0; i < TM; ++i) aReg[i] = As[threadRowBase + i][k];
            #pragma unroll
            for (int j = 0; j < TN; ++j) bReg[j] = Bs[k][threadColBase + j];

            // 16 次乘加全部用寄存器里的值，复用率是 v2 的 4 倍
            #pragma unroll
            for (int i = 0; i < TM; ++i)
                #pragma unroll
                for (int j = 0; j < TN; ++j)
                    acc[i][j] += aReg[i] * bReg[j];
        }
        __syncthreads();
    }

    // ---- 写回 ----
    #pragma unroll
    for (int i = 0; i < TM; ++i) {
        int row = blockRow + threadRowBase + i;
        if (row >= M) break;
        #pragma unroll
        for (int j = 0; j < TN; ++j) {
            int col = blockCol + threadColBase + j;
            if (col < N) C[row * N + col] = acc[i][j];
        }
    }
}
```

`main` 里对三个版本分别跑、校验（用相对误差）并报告 GFLOPS。

### 2.3 `transpose.cu` —— 共享内存 + padding

```cpp
// 完整代码见 code/lessons/ch02_memory/transpose.cu
constexpr int BDIM = 32;
constexpr int PAD = 1;

// v1 朴素：读合并、写不合并
__global__ void transposeNaive(const float* __restrict__ in,
                               float* __restrict__ out, int n) {
    int col = blockIdx.x * BDIM + threadIdx.x;
    int row = blockIdx.y * BDIM + threadIdx.y;
    if (row < n && col < n) {
        // 写 out[col*n + row]：warp 内 col 在变，地址跨 n 个 float —— 不合并！
        out[col * n + row] = in[row * n + col];
    }
}

// v2 共享内存：把"不合并"的动作搬到共享内存里
__global__ void transposeShared(const float* __restrict__ in,
                                float* __restrict__ out, int n) {
    __shared__ float tile[BDIM][BDIM];
    int tx = threadIdx.x, ty = threadIdx.y;
    int col = blockIdx.x * BDIM + tx;
    int row = blockIdx.y * BDIM + ty;
    if (row < n && col < n) tile[ty][tx] = in[row * n + col];   // 读：合并
    __syncthreads();                                            // 等 tile 填满
    int outRow = blockIdx.x * BDIM + ty;
    int outCol = blockIdx.y * BDIM + tx;
    if (outRow < n && outCol < n) out[outRow * n + outCol] = tile[tx][ty];  // 写：合并
}

// v3 加 padding：消掉共享内存里可能的 bank conflict
__global__ void transposePadded(const float* __restrict__ in,
                                float* __restrict__ out, int n) {
    __shared__ float tile[BDIM][BDIM + PAD];    // 32 x 33
    int tx = threadIdx.x, ty = threadIdx.y;
    int col = blockIdx.x * BDIM + tx;
    int row = blockIdx.y * BDIM + ty;
    if (row < n && col < n) tile[ty][tx] = in[row * n + col];
    __syncthreads();
    int outRow = blockIdx.x * BDIM + ty;
    int outCol = blockIdx.y * BDIM + tx;
    if (outRow < n && outCol < n) out[outRow * n + outCol] = tile[tx][ty];
}
```

**为什么 padding 在这里可能有用？** 看 `tile[tx][ty]` 这个访问（注意 tx/ty 交换了）：如果按"warp 内 `tx` 变化"来分析，地址差是 `(BDIM + PAD) = 33` 个字。33 与 32 互质 → 无冲突；而如果是 32 列，地址差是 32 → 32 路冲突。

**注意条件句**："如果按 warp 内 tx 变化来分析"。在二维块 `(32, 32)` 里，一个 warp 的 `tx` 是 0~31、`ty` 是固定的（warp 沿 x 切），所以 `tile[tx][ty]` 确实是"tx 变、ty 固定"。所以 v2 会冲突、v3 不会。

**但实测结果可能相差不大**，因为转置的瓶颈通常在**全局内存带宽**上，bank conflict 被掩盖了。**这正是 `transpose.cu` 想告诉你的：优化要看数据。**

### 2.4 `bank_conflict.cu` —— 量化 + 一个反例

```cpp
// 完整代码见 code/lessons/ch02_memory/bank_conflict.cu
constexpr int BLOCK = 256, TILE = 32, ITER = 512;
constexpr int SMEM_FLOATS = BLOCK * TILE;   // 8192 个 float = 32 KB

// 实验 1：一维数组，不同的 stride
__global__ void strideAccessKernel(float* __restrict__ out, int stride) {
    __shared__ float buf[SMEM_FLOATS];
    for (int i = threadIdx.x; i < SMEM_FLOATS; i += blockDim.x)
        buf[i] = (float)(i % 17);
    __syncthreads();

    float acc = 0.0f;
    for (int it = 0; it < ITER; ++it) {
        // 用 & 掩码代替取模（8192 是 2 的幂）
        int idx = (threadIdx.x * stride + it) & (SMEM_FLOATS - 1);
        acc += buf[idx];
    }
    // 汇总回共享内存，防止编译器把整个循环优化掉
    __shared__ float partial[BLOCK];
    partial[threadIdx.x] = acc;
    __syncthreads();
    if (threadIdx.x == 0) {
        float s = 0.0f;
        for (int i = 0; i < BLOCK; ++i) s += partial[i];
        out[blockIdx.x] = s;
    }
}

// 实验 2：二维 tile 里"按行访问"（warp 内 tx 变、ty 固定）
template <int STRIDE>
__global__ void rowAccessKernel(float* __restrict__ out) {
    __shared__ float tile[TILE][STRIDE];
    int tx = threadIdx.x, ty = threadIdx.y;
    tile[ty][tx] = (float)((ty * 7 + tx) % 13);
    __syncthreads();

    float acc = 0.0f;
    for (int it = 0; it < 8; ++it) {
        int dx = (tx + it) % TILE;
        #pragma unroll
        for (int ty2 = 0; ty2 < TILE; ++ty2)
            acc += tile[ty2][dx] * 0.5f;    // dx 变、ty2 固定
    }
    // ... 汇总（同上）
}
```

**实验 1 的预期结果**（`ITER = 512`，256 块 × 256 线程）：

| stride | 冲突程度  | 相对耗时                |
| ------ | --------- | ----------------------- |
| 1      | 无冲突    | 最快                    |
| 2      | 2 路      | 约 1.x 倍               |
| 4      | 4 路      | 约 2~4 倍               |
| 8      | 8 路      | 约 4~8 倍               |
| 16     | 16 路     | 约 8~16 倍              |
| **32** | **32 路** | **最慢，可能 10~30 倍** |

**实验 2 是个反例**：对"按行访问"的 kernel 加 padding（`[32][33]`），性能**反而变差**。因为按行访问用 32 列本来就没有冲突，改成 33 之后地址差变成 33，虽然还是互质（无冲突），但**每行多一个字的空洞**让缓存行的利用率下降，索引计算也变复杂了。

**这个反例就是本章最重要的一课**：

> **"消除 bank conflict" 不是目的，"让程序更快"才是目的。**
> **任何优化手段都要回答三个问题：原来慢在哪？为什么这个手段能变快？怎么用数据证明它变快了？**

### 2.5 `reduce_shared.cu` —— 共享内存归约 + 静态/动态分配

```cpp
// 完整代码见 code/lessons/ch02_memory/reduce_shared.cu
constexpr int BLOCK = 256;

// v1：静态共享内存 + 树形归约
__global__ void reduceSharedStatic(const float* __restrict__ in,
                                   float* __restrict__ out, int n) {
    // 必须 volatile！否则编译器会把值缓存在寄存器里，
    // 在 __syncthreads() 之后仍然读到旧值 —— 这是 CUDA 的经典陷阱
    __shared__ volatile float sdata[BLOCK];

    int tid = threadIdx.x;
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;

    // 步骤 1：本线程负责的元素先加到自己的寄存器里
    float sum = 0.0f;
    for (; i < n; i += stride) sum += in[i];
    sdata[tid] = sum;
    __syncthreads();

    // 步骤 2：树形归约，每轮规模减半，共 log2(256) = 8 轮
    for (int s = blockDim.x / 2; s > 0; s >>= 1) {
        if (tid < s) sdata[tid] = sdata[tid] + sdata[tid + s];
        __syncthreads();   // 每轮都要同步，否则会读到别人还没更新的值
    }

    // 步骤 3：每块贡献一个部分和
    if (tid == 0) out[blockIdx.x] = sdata[0];
}

// v2：动态共享内存（大小由启动时决定）
__global__ void reduceSharedDynamic(const float* __restrict__ in,
                                    float* __restrict__ out, int n) {
    extern __shared__ volatile float sdata[];   // 大小在 <<<>>> 第三个参数里
    // ... 其余与 v1 完全相同
}

// v3：前 32 个元素只用 warp shuffle（第 3 章会详细展开）
__device__ float warpReduceSum(float val) {
    for (int offset = 16; offset > 0; offset >>= 1)
        val += __shfl_down_sync(0xffffffffu, val, offset);
    return val;
}
```

**动态共享内存的启动写法**：

```cpp
reduceSharedDynamic<<<grid, block, BLOCK * sizeof(float)>>>(dIn, dOut, N);
//                               ^^^^^^^^^^^^^^^^^^^^^^^ 第三个参数：字节数
```

**关于 `volatile` 的深入解释**：为什么 v1 里 `sdata` 必须加 `volatile`？

看这一段：

```cpp
for (int s = blockDim.x / 2; s > 0; s >>= 1) {
    if (tid < s) sdata[tid] += sdata[tid + s];
    __syncthreads();
}
```

编译器有权假设"共享内存里的值不会被别的线程悄悄改掉"（除非遇到同步原语）。它可能把 `sdata[tid + s]` 的值缓存在寄存器里，然后在下一轮迭代时**直接复用寄存器里的旧值**，而不是重新从共享内存读。但那个值已经被别的线程更新了 → **结果错误**。

加 `volatile` 就是告诉编译器："这块内存任何时候都可能变，每次都真的去读。"

> 🍳 **用 1.6 节的厨房比喻说**：
> 编译器是个"偷懒的传菜员"——它看你**刚刚才从操作台上拿过一次盐**，就心想：
> "反正盐又不会自己变，我**记在脑子里**就行了，下次不用再跑一趟操作台。"
> 问题是——**别的厨师往操作台上的盐罐里加了盐**，它脑子里记的还是**旧的咸度**。
> `volatile` 就是一句命令：**"别偷懒，每次都必须亲眼去操作台看一眼。"**

**另一种写法**是读完立刻加 `__syncwarp()`，但 `volatile` 更直观，而且是经典教材（PMPP）里的标准做法。

### 2.6 `constant_ldg.cu` —— 常量内存与只读缓存

```cpp
// 完整代码见 code/lessons/ch02_memory/constant_ldg.cu
constexpr int CHANNELS = 8, MAX_CH = 64;

// 常量内存：文件作用域声明，所有核函数可见
__constant__ float c_scale[MAX_CH];
__constant__ float c_bias[MAX_CH];

// v3：参数放常量内存，warp 内所有线程读同一个 ch -> 广播，极快
__global__ void scaleConstantMem(const float* __restrict__ in,
                                 float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        int ch = i % CHANNELS;
        out[i] = in[i] * c_scale[ch] + c_bias[ch];
    }
}

// __ldg：显式走只读缓存
__global__ void copyWithLdg(const float* __restrict__ in,
                            float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = __ldg(in + i);
}

// const __restrict__：现代编译器的标准做法，通常自动生成 LDG
__global__ void copyWithRestrict(const float* __restrict__ in,
                                 float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = in[i];
}

// 主机端写入常量内存：注意第一个参数是"符号"本身，不加 &
CUDA_CHECK(cudaMemcpyToSymbol(c_scale, hScale.data(), CHANNELS * sizeof(float)));
```

**ⓘ 一个必须知道的现实**：这个例子里三个版本（全局直读 / 共享内存 / 常量内存）的耗时**很可能几乎一样**。原因见 1.10 节和程序里的提示：这个 kernel 是**显存带宽受限**的（读 64 MB 写 64 MB），参数读取的开销被完全掩盖了。

**那怎么才能看出常量内存的收益？** 让"访问参数"成为瓶颈：

```cpp
// 把内层循环改成这样，参数读取次数翻 100 倍
float s = 0.0f;
for (int r = 0; r < 100; ++r) s += in[i] * c_scale[ch];
out[i] = s + c_bias[ch];
```

这时 v3 的优势会明显显现。**这个"怎么设计实验才能暴露你想测的因素"的思路，比结果本身更重要。**

### 2.7 `occupancy.cu` —— 寄存器、占用率与 spill

```cpp
// 完整代码见 code/lessons/ch02_memory/occupancy.cu

// 1) 打印核函数的静态属性
cudaFuncAttributes attr{};
CUDA_CHECK(cudaFuncGetAttributes(&attr, (const void*)kernelNoBounds));
printf("每线程寄存器数     : %d\n", attr.numRegs);
printf("静态共享内存       : %zu 字节\n", attr.sharedSizeBytes);
printf("本地内存（spill 用）: %zu 字节\n", attr.localSizeBytes);

// 2) 计算一个 SM 最多能驻留几个这样的块
int numBlocks = 0;
CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(
    &numBlocks, (const void*)kernelNoBounds, blockSize, 0));

cudaDeviceProp prop{};
CUDA_CHECK(cudaGetDeviceProperties(&prop, 0));
double occ = 100.0 * numBlocks * blockSize / prop.maxThreadsPerMultiProcessor;

int minGridSize = 0, bestBlock = 0;
CUDA_CHECK(cudaOccupancyMaxPotentialBlockSize(
    &minGridSize, &bestBlock, (const void*)kernelNoBounds, 0, 0));

```

**`__launch_bounds__` 的对比**：

```cpp
// 无约束：编译器为了性能可能用很多寄存器
__global__ void kernelNoBounds(...) { ... }

// 承诺"最多 256 线程/块，至少 4 块/SM"
// 编译器会被迫把寄存器压到 65536/(4*256) = 64 以内
__global__ void __launch_bounds__(256, 4) kernelWithBounds(...) { ... }
```

**注意**：压缩寄存器可能引发 spill，反而更慢。**必须实测。** 这个程序里两个 kernel 是纯访存型，所以差别会很小——这也是一个重要结论（"寄存器/占用率的影响要在计算密集、高延迟依赖的核函数里才明显"）。

## 3. 代码逐行解析

### 3.1 `coalescing.cu` 中 A 和 B 为什么"读的元素个数相同但速度不同"

**A（合并）**：

```text
线程 0 -> a[0]     ┐
线程 1 -> a[1]     │  一个 warp 覆盖 a[0..31]
...                │  字节范围 [0, 128)
线程 31 -> a[31]   ┘
```

硬件发出的访存请求：**1 个 128 字节段（或 4 个 32 字节 sector）**，全部用满 → 带宽利用率 100%。

**B（跨步 32）**：

```text
线程 0 -> a[0]      ┐
线程 1 -> a[32]     │  一个 warp 覆盖 a[0], a[32], a[64], ...
...                 │  字节范围分散在 [0, 4096) 内
线程 31 -> a[992]   ┘
```

硬件发出的访存请求：**32 个不同的 32 字节 sector**，每个只用 4 字节 → 带宽利用率 **12.5%**。

**这就是纯粹的性能损失**：读的元素个数完全一样（都是 32 个 float），但有效带宽差了 8 倍（32 字节 sector 粒度下），在 128 字节段粒度下更惨。

**所以有效带宽的计算要小心**：

- 如果按"理论需要读的字节数"算，B 的"有效带宽"会看起来很低（这是对的，说明实际效率低）；
- 如果按"硬件实际搬运的字节数"算，B 的带宽可能看起来正常（因为搬了很多没用的数据）。

**`CudaTimer::bandwidthGBs` 用的是"理论需要的字节数"**，所以它能正确反映"效率"。这也是为什么业界都用有效带宽（Effective Bandwidth）这个指标。

### 3.2 为什么 `reversedKernel` 仍然是合并的

```cpp
int j = n - 1 - i;   // i 是全局编号
sum += a[j];
```

对 `<<<2, 32>>>`、`n = 64`：

```text
块 0：i = 0..31    ->  j = 63, 62, ..., 32
块 1：i = 32..63   ->  j = 31, 30, ...,  0

块 0 的 warp：访问 a[32] 到 a[63]
块 1 的 warp：访问 a[0]  到 a[31]
```

每个 warp 覆盖的都是**一段连续的 128 字节**，只不过"线程 0 读的是这段里最大的地址"。**硬件看的是一个 warp 覆盖的地址区间，不关心谁读哪个。**

**这一点非常重要**：它意味着你可以自由地设计"线程到数据的映射"，只要保证**一个 warp 覆盖的地址区间是连续的**就行。这为"反向遍历"、"螺旋遍历"、"按块分组"等灵活的数据编排打开了空间。

### 3.3 分块矩阵乘法的四个阶段为什么必须按这个顺序

```cpp
for (int k0 = 0; k0 < K; k0 += TILE) {
    // 阶段 1：加载        ← 写共享内存
    As[ty][tx] = ...;
    Bs[ty][tx] = ...;
    __syncthreads();     //  ← 屏障 A
    // 阶段 3：计算        ← 读共享内存
    for (int k = 0; k < TILE; ++k) acc += As[ty][k] * Bs[k][tx];
    __syncthreads();     //  ← 屏障 B
}
```

**为什么屏障 A 必须存在？**

如果没有屏障 A：线程 X 可能已经加载完自己的 `As[ty][tx]` 并开始计算，而线程 Y 还没加载完。X 读 `As[ty][k]`（其中 `k` 对应 Y 负责的列）就会读到**上一轮的旧值或未初始化的垃圾**。

**为什么屏障 B 必须存在？**

如果没有屏障 B：快的线程已经进入下一轮、把 `As[ty][tx]` 覆盖成了新数据；慢的线程还在读上一轮的数据 → **读到新数据和旧数据的混合**。

**为什么两个屏障都要，而且不能合并成一个？**

因为它们保护的是**两个不同的依赖方向**：

```text
屏障 A：写（加载）→ 读（计算）     生产者-消费者
屏障 B：读（计算）→ 写（加载）     防覆盖
```

**如果只有一个屏障会怎样？**

假设只有屏障 A（把屏障 B 删掉）：

```text
轮 0: 加载 -> syncA -> 计算 -> [无屏障] -> 轮 1 加载 -> syncA -> 计算
                    ↑                        ↑
             快线程算完了直接跑去加载轮 1，覆盖了慢线程正在读的数据
```

**结果错误，而且"有时对有时错"**——取决于硬件怎么调度。这种 bug 最难查，因为它在你的机器上可能"从来没出过错"。

**这就是为什么 [第 3 章](ch03_同步通信与原子操作.md) 要专门讲同步**：内存和同步是分不开的。

### 3.4 关于 `if (row >= M) break;` 这个写回优化

在 v3 的写回部分：

```cpp
#pragma unroll
for (int i = 0; i < TM; ++i) {
    int row = blockRow + threadRowBase + i;
    if (row >= M) break;      // 行越界就没必要继续了
    #pragma unroll
    for (int j = 0; j < TN; ++j) {
        int col = blockCol + threadColBase + j;
        if (col < N) C[row * N + col] = acc[i][j];
    }
}
```

**为什么用 `break` 而不是 `continue`？** 因为 `threadRowBase + i` 随 `i` 单调递增，一旦 `row >= M`，后面的 `i` 只会更大，全都越界。用 `break` 直接跳出，能省掉后续的判断。

**为什么行用 `break` 而列用 `if (col < N)`？** 因为列是内层循环的变量，`col` 随 `j` 递增，理论上也能用 `break`。但这里用了 `if`，原因是：

- 内层循环只有 4 次迭代，用 `if` 的代价很小；
- 用 `break` 会破坏 `#pragma unroll` 的展开（编译器需要生成额外的跳转逻辑）。

**这是一个微妙的取舍**：在极短的循环里，**让编译器能完整展开**往往比"省几次判断"更值钱。

### 3.5 `cudaMemcpyToSymbol` 的符号语义

```cpp
CUDA_CHECK(cudaMemcpyToSymbol(c_scale, hScale.data(), CHANNELS * sizeof(float)));
//                         ^^^^^^^ 符号本身，不是 &c_scale
```

**为什么不能加 `&`？**

`__constant__` 变量在主机端**不是一个真正的变量**——它只是设备端的一个符号名。主机编译器不知道它的地址（它在显存里）。所以 `cudaMemcpyToSymbol` 的机制是：

1. 编译 `.cu` 时，`nvcc` 把 `c_scale` 登记为一个**设备符号**，并把它记录在可执行文件的符号表里；
2. 运行时，`cudaMemcpyToSymbol` 通过 `c_scale` 这个**符号引用**去符号表里查到它的设备地址；
3. 然后往那个地址拷贝数据。

**加 `&` 会发生什么？**

在 Ubuntu/Windows 上，`&c_scale` 会产生"取一个主机端不存在的东西的地址"的语义，通常会导致编译错误或 `cudaErrorInvalidSymbol`。**记住：不带 `&`。**

**`cudaMemcpyToSymbol` 的完整签名**：

```cpp
cudaError_t cudaMemcpyToSymbol(const void* symbol, const void* src,
                               size_t count, size_t offset = 0,
                               enum cudaMemcpyKind kind = cudaMemcpyHostToDevice);
```

- `offset`：往符号内部偏移多少字节开始写。**可以用来只更新数组的一部分**，比如：

  ```cpp
  // 只更新第 3 个元素
  cudaMemcpyToSymbol(c_coeff, &newValue, sizeof(float), 3 * sizeof(float));
  ```

- `kind`：源在哪。要从设备内存拷进符号，用 `cudaMemcpyDeviceToDevice`。

### 3.6 如何正确设计一个"带宽对比"实验

`coalescing.cu` 里的实验设计有几个必须注意的点，这些点同样适用于你自己以后做的任何性能对比：

| 要点                    | 做法                                | 为什么                                       |
| ----------------------- | ----------------------------------- | -------------------------------------------- |
| **固定计算量**          | 所有 kernel 都做"读 n 个元素并累加" | 否则差异可能来自计算，不是访存               |
| **固定内存访问量**      | A 和 B 都读 n 个元素                | 让"事务利用率"成为唯一变量                   |
| **避免写操作污染**      | 只让 `threadIdx.x == 0` 写一个值    | 否则写的开销会混进测量                       |
| **防止死代码消除**      | 把结果真的写到全局内存              | 否则编译器可能发现"结果没人用"而删掉整个循环 |
| **同样的网格配置**      | 用同一个 `grid`/`block`             | 否则线程数差异会引入新变量                   |
| **预热 + 多次取中位数** | 用 `CudaTimer::measure(f, 10, 2)`   | 消除升频、缓存冷启动的干扰                   |

**最后一条特别重要**：如果你把 kernel 的返回值算出来却从不使用，编译器的**死代码消除**会把它整个删掉——你会测到一个"快得离谱"的时间。这就是为什么 `coalescing.cu` 里所有 kernel 最后都会 `out[blockIdx.x] = sum;`。

### 3.7 占用率的"阶梯"效应与实测建议

回到 1.11 节的例子。重要结论：

```text
寄存器 32 个/线程，块 256：6 块/SM -> 100% 占用率
寄存器 40 个/线程，块 256：6 块/SM -> 100%（还有余量）
寄存器 42 个/线程，块 256：6 块/SM -> 100%  （临界点，65536/(42*256)=6.09）
寄存器 43 个/线程，块 256：5 块/SM -> 83%   ← 掉一档！
```

**这是"阶梯"**：寄存器的变化只有在跨过某个整数边界时才影响占用率。

**实测建议**：

1. 先用 `-Xptxas -v` 看基线寄存器数；
2. 用 `occupancy.cu` 里的方法算出理论占用率；
3. 试着加 `__launch_bounds__(256, 6)` 把寄存器压到 42 以内；
4. **再测一次实际耗时**。如果变快了，留下；变慢了（spill 导致），去掉。

**通常的规律**：

| 情况                                  | 结论                                                  |
| ------------------------------------- | ----------------------------------------------------- |
| 纯访存型 kernel（向量加、拷贝、转置） | 占用率越高越好 → 值得压寄存器                         |
| 计算密集 + 高数据复用（分块矩阵乘）   | 每线程多用寄存器换来复用更值 → **不要盲目追高占用率** |
| 有个别 kernel 性能诡异                | 先看 `-Xptxas -v` 有没有 spill                        |

**这是本章最后一个核心洞察**：

> **"占用率最大化"是一个常见的误区。它是手段，不是目的。真正的目的是"让 SM 始终有活可干"。**
> 如果一个线程用 128 个寄存器干了 8 倍的活，它可能比 4 个各用 32 个寄存器、每个只干 1 倍活的线程更快。

## 5. 动手练习

### 练习 2.1 [基础] 把"不合并"改成"合并"

下面这段代码把一个 `N×N` 矩阵的每一行求和，但访存是不合并的：

```cpp
__global__ void rowSumBad(const float* __restrict__ a,
                          float* __restrict__ out, int N) {
    int row = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    for (; row < N; row += stride) {
        float s = 0.0f;
        for (int c = 0; c < N; ++c) {
            s += a[row * N + c];     // 每个线程顺序扫自己这一行
        }
        out[row] = s;
    }
}
```

**要求**：

1. 说明为什么这段代码"不合并"（提示：看同一个 warp 内相邻线程的地址）。
2. 改成"每个线程负责一列的一段"的版本，让访存变成合并的（外围仍然是每一行求和）。
3. 在 `N = 2048` 上测两个版本，报告加速比。

<details>
<summary>参考做法</summary>

**为什么慢**：同一个 warp 内，`threadIdx.x` 是 0~31，`row` 也是 0~31，所以线程 0 访问 `a[0*N + c]`、线程 1 访问 `a[1*N + c]` —— 地址相差 `N = 2048` 个 float。**一个 warp 的 32 次访问分散在 32 个相隔 8 KB 的位置**，每次只用到 4 字节。

**改法：让相邻线程处理"同一行的相邻列"**，用共享内存或原子操作做行内归约：

```cpp
// 每个块处理一行的一段：块内 tx 负责连续的列
__global__ void rowSumBetter(const float* __restrict__ a,
                             float* __restrict__ out, int N) {
    // 每块负责一整行；块内 256 个线程各负责 N/256 个连续元素中的一段
    int row = blockIdx.x;
    if (row >= N) return;

    const float* p = a + (size_t)row * N;

    // 每个线程按 blockDim.x 的步长扫这一行
    // 关键：同一时刻，warp 内线程访问的是连续的 32 个元素
    float s = 0.0f;
    for (int c = threadIdx.x; c < N; c += blockDim.x) {
        s += p[c];      // 相邻线程地址差 1 -> 合并！
    }

    // 块内归约（用共享内存）
    __shared__ float sdata[256];
    sdata[threadIdx.x] = s;
    __syncthreads();
    for (int step = blockDim.x / 2; step > 0; step >>= 1) {
        if (threadIdx.x < step) sdata[threadIdx.x] += sdata[threadIdx.x + step];
        __syncthreads();
    }
    if (threadIdx.x == 0) out[row] = sdata[0];
}

// 启动：每行一个块
rowSumBetter<<<N, 256>>>(d_a, d_out, N);
//   N = 2048 行 -> 2048 个块，每块 256 线程
```

**这个改法为什么会快？** 内核循环里 `p[c]` 的 `c` 在同一个 warp 内是连续的（`threadIdx.x` 0~31），所以一个 warp 覆盖连续的 128 字节 → 合并访存。

**预期**：`rowSumBetter` 通常比 `rowSumBad` 快 **2~8 倍**（具体倍数取决于 N 和卡）。在 RTX 3060 上以 N=2048 实测大致是 3~5 倍的量级，你的机器可能不同。

**一个替代方案**：如果 N 很小（比如 64），可以让"每行一个 warp"，用 `__shfl_down_sync` 做 warp 内归约，连共享内存都省了（第 3 章）。

</details>

### 练习 2.2 [基础] 给矩阵乘法加"越界填 0"的验证

`gemmTiled` 里用了"越界填 0"的技巧：

```cpp
As[ty][tx] = (row < M && aCol < K) ? A[row * K + aCol] : 0.0f;
```

**要求**：

1. 解释为什么填 0 是**正确**的（不会改变结果）。
2. 把填 0 改成填 `1.0f`，跑一遍，观察是否得到错误结果。**记录错误的表现**（是全部错、还是只有边界块错？）。
3. 把填 0 改成"不填"（即 `As[ty][tx] = A[row * K + aCol];`，去掉判断），用 M=N=K=513（一个质数，故意不是 32 的倍数）跑一遍，观察结果和 `compute-sanitizer` 的报告。

<details>
<summary>参考做法</summary>

**1. 填 0 为什么正确？**

矩阵乘法的内层是 `acc += As[ty][k] * Bs[k][tx]`。如果某个位置的 A 或 B 被填成了 0，那么对应的乘积项就是 0，累加起来对结果**没有任何影响**。

更形式化地说：我们实际上在计算一个"被 pad 到 TILE 倍数尺寸"的矩阵乘法，其中 pad 区域填 0。因为 `A_pad × B_pad` 中所有涉及 pad 区域的乘积都是 0，所以结果和原尺寸的乘法一致。

**2. 填 1.0f 会怎样？**

结果会错误。`As` 的 pad 区域填 1 之后，`acc` 会多加上 `1 * Bs[k][tx]` 这些项。**只有"越界"的那些位置会错**——也就是矩阵边缘的那些块。

具体表现：

- 如果 `M`、`N`、`K` 都是 32 的倍数（比如 512），**跑出来完全正确**，因为根本没有越界，`? :` 的假分支从不执行；
- 如果有一个不是 32 的倍数（比如 513），**只有最右/最下/最后的那些块会错**。

**这就是为什么"用 512 测试通过了"不能证明代码正确** —— 你必须用**非整除的尺寸**测一次。这是一个非常重要的测试纪律：

> **测试用例必须包含"不等于任何 tile 尺寸整数倍"的尺寸，比如 513、1000、1023。**

**3. 去掉判断会怎样？**

```cpp
As[ty][tx] = A[row * K + aCol];      // 越界读！
```

以 M=N=K=513，TILE=32：

```text
网格 = ceil(513/32) = 17 个块
17 * 32 = 544 > 513
```

所以块 16 里的 `row` 会到 544-1 = 543 > 512 → `A[543 * 513 + k]` 越界。`compute-sanitizer` 会报：

```text
========= Invalid __global__ read of size 4 bytes
=========     at 0x... in gemmTiled(...)
=========     by thread (0,0,0) in block (0,16,0)
=========     Address 0x... is out of bounds
```

**注意 `block (0,16,0)`** —— 正好是最后一行块（`blockIdx.y = 16`）。sanitizer 会精确指出是哪个线程、哪个块越界了，这就是它的价值。

</details>

### 练习 2.3 [进阶] 把 block 从 32×32 改成 16×16，会怎样？

用 `matrix_mul.cu` 的 v2（`gemmTiled`）做实验：

```cpp
// 原版：TILE = 32，blocksize = (32, 32) = 1024 线程
dim3 block(32, 32);

// 新版：TILE = 16，blocksize = (16, 16) = 256 线程
//   注意 TILE 同时是"块覆盖的输出尺寸"和"加载的 tile 尺寸"
```

**要求**：

1. 把 `TILE` 改成 16，`block` 改成 `(16,16)`，重新编译运行。记录耗时与 GFLOPS。
2. 解释为什么变小后**全局内存访问量增加**了（写出计算公式）。
3. 解释为什么**占用率提高了**（共享内存用量从 8 KB 降到 2 KB，块从 1024 线程降到 256 线程）。
4. 结论：在你的卡上，哪个更好？

<details>
<summary>参考做法</summary>

**1. 结果**：在多数卡上 TILE=16 会比 TILE=32 **慢**（因为全局内存访问翻倍）。但共享内存用量小、占用率高，在某些带宽充裕而延迟敏感的卡上可能追平。

**2. 全局内存访问量**：

```text
每线程全局读次数 = 2 * (K / TILE)
TILE = 32:  2 * K/32 = K/16
TILE = 16:  2 * K/16 = K/8     ← 翻倍！
```

整体全局内存访问量 = `2 * M*N*K / TILE`，和 TILE 成反比。所以 TILE 减半，全局内存访问量翻倍。

**3. 占用率**：

```text
TILE = 32: 共享内存 = 2 * 32 * 32 * 4 = 8192 字节/块，块 = 1024 线程
           按共享内存：100 KB / 8 KB = 12 个块 → 但每 SM 最多 1536 线程 = 1.5 个块
           → 按线程数限制，只能驻留 1 个块 = 1024 线程 → 占用率 66.7%

TILE = 16: 共享内存 = 2 * 16 * 16 * 4 = 2048 字节/块，块 = 256 线程
           按共享内存：100 KB / 2 KB = 50 个块（限制在 16 个块/SM）
           按线程数：1536 / 256 = 6 个块
           → 6 个块 = 1536 线程 → 占用率 100%
```

**所以 TILE=16 的占用率明显更高（100% vs 66.7%）**，但访存效率更低（全局内存访问量翻倍）。

**4. 结论**：这是一个典型的**"复用 vs 占用率"权衡**。通常 TILE=32 更优，因为它减少了最关键的那个成本（全局内存访问）。但这也说明：

> **不要只看占用率一个指标。** 100% 占用率的慢 kernel 和 67% 占用率的快 kernel，后者更好。

**进阶实验**：试试 TILE=32 但块用 `(32, 8)`（256 线程，每线程负责 TILE/8 = 4 行），这样共享内存还是 8 KB 但块只有 256 线程 → 占用率能到 100%，同时保持 TILE=32 的复用率。**这是"两全其美"的思路**，也是真实优化中最常见的做法（把"块覆盖的尺寸"和"块内线程数"解耦，让每个线程负责多个输出元素）。这正是 v3 寄存器分块的思想。

</details>

### 练习 2.4 [进阶] 用共享内存优化转置，并解释 padding 是否必要

**要求**：

1. 跑 `transpose.cu`，记录 v1/v2/v3 的耗时。

2. 把你的 `PAD` 从 1 改成 3、5，观察 v3 的耗时变化。是否存在"最佳 padding"？

3. 用 `ncu` 测量 v2 和 v3 的 bank conflict 次数，验证你的推断：

   ```bash
   ncu --metrics l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum ./transpose
   ```

4. 如果 v2 和 v3 的 bank conflict 次数都是 0，那说明什么？你该怎么解释这个结果？

<details>
<summary>参考做法</summary>

**2. padding 的影响**：PAD 从 1 改到 3、5，通常会看到耗时变化不大（因为没有冲突可消）。但如果 PAD 是 `32` 的倍数（比如把 PAD 写成 32），那等于"没 padding"，冲突会回来。**PAD 必须让"行宽"与 32 互质**，所以 1、3、5、7 都可以。

**3. 如果 v2 和 v3 的 bank conflict 次数都是 0**：

说明 `tile[tx][ty]` 这个访问模式**本来就不冲突**。分析一下：在 `block(32, 32)` 里，一个 warp 的 `tx` 是 0~31、`ty` 是固定的。访问 `tile[tx][ty]` 时地址 = `tx * 32 + ty`（v2 的布局），bank = `(tx*32 + ty) % 32 = ty` —— 对固定 `ty`，32 个线程的 bank **全是 `ty`**！

**按这个分析，v2 应该是有 32 路冲突的！** 所以如果 ncu 报 0 次冲突，那你需要检查：

- 是不是编译器做了优化（比如把共享内存访问改成了直接读全局内存，或者用了向量化）？
- 是不是 `ncu` 统计的指标名不对（不同 CUDA 版本的指标名有差异，用 `ncu --query-metrics | grep bank` 查）？
- 是不是 `tile[tx][ty]` 被编译器识别为"只需要读一次"，从而合并了访问？

**要点**：**当"理论分析"和"实测数据"矛盾时，优先相信数据，然后去搞清楚为什么理论错了。** 这个调查过程本身就是最有价值的学习。

（一个常见的技术原因：现代编译器会把这个 kernel 的 `tile` 数组整个优化到寄存器里——因为 `tile[tx][ty]` 对每个线程来说访问的地址是确定的，且数据量小。此时根本没有共享内存访问，也就无从谈冲突。用 `cuobjdump -sass` 看有没有 `LDS` 指令就能确认。）

</details>

### 练习 2.5 [进阶] 写一个"用共享内存消除重复全局读取"的例子

**要求**：实现一个一维卷积：

```text
out[i] = sum_{j=-R}^{R} in[i+j] * w[j+R]
```

其中 `R = 8`（所以 `w` 有 17 个元素）。

要求：

1. 写一个**朴素版本**：每个线程读 `2R+1 = 17` 个输入值。
2. 写一个**共享内存版本**：每个块先把"自己负责的区间 + 两侧 halo 区"搬进共享内存，然后从共享内存做卷积。
3. 分析两个版本的全局内存读取次数（每线程）。
4. 测量并报告加速比。

<details>
<summary>参考做法</summary>

```cpp
constexpr int R = 8;
constexpr int BLOCK = 256;

// 把权重放在常量内存（所有线程都读同样的值 -> 广播）
__constant__ float c_w[2 * R + 1];

// v1 朴素：每线程读 2R+1 个输入
__global__ void conv1DNaive(const float* __restrict__ in,
                            float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    float s = 0.0f;
    #pragma unroll
    for (int j = -R; j <= R; ++j) {
        int k = i + j;
        // 边界处理：越界当成 0（Replicate 或 Zero padding 都可以，这里用 Zero）
        if (k >= 0 && k < n) s += in[k] * c_w[j + R];
    }
    out[i] = s;
}

// v2 共享内存：每块加载 BLOCK + 2R 个输入（含两侧 halo）
__global__ void conv1DShared(const float* __restrict__ in,
                             float* __restrict__ out, int n) {
    // halo：左右各 R 个
    __shared__ float s[BLOCK + 2 * R];
    const int base = blockIdx.x * BLOCK;

    // 注意 BLOCK + 2R = 272 个元素，256 个线程 -> 有的线程要搬 2 个
    for (int t = threadIdx.x; t < BLOCK + 2 * R; t += BLOCK) {
        int g = base + t - R;              // 全局下标（左侧 halo 是 base - R）
        s[t] = (g >= 0 && g < n) ? in[g] : 0.0f;
    }
    __syncthreads();

    int i = base + threadIdx.x;
    if (i >= n) return;
    float sum = 0.0f;
    #pragma unroll
    for (int j = 0; j < 2 * R + 1; ++j) {
        sum += s[threadIdx.x + j] * c_w[j];    // 从共享内存读，复用 R 次
    }
    out[i] = sum;
}
```

**3. 全局内存读取次数的分析**：

```text
v1 朴素：每线程 2R+1 = 17 次全局读（相邻线程有大量重叠读，但硬件只能靠 L1 缓存吸收一部分）
         总读取量 ≈ 17 * n 个 float

v2 共享内存：每块加载 BLOCK + 2R = 272 个，被 BLOCK = 256 个线程共享
             每线程摊到 272/256 ≈ 1.06 次全局读
             总读取量 ≈ 1.06 * n 个 float

减少倍数 ≈ 16 倍
```

**4. 预期结果**：`conv1DShared` 通常比 `conv1DNaive` 快 **2~6 倍**（不是 16 倍，因为 v1 的重复读取大量命中了 L1 缓存，L1 帮它挡住了很多开销）。**具体倍数取决于 R 的大小和 L1 的命中率**：R 越大、重叠越多、L1 越撑不住，共享内存的优势越明显。

**两个额外收获**：

- **`c_w` 放在常量内存是对的**：所有线程读同样的权重（`c_w[j]` 对固定 `j` 是同一地址）→ 广播 → 极快。

- **halo 区的大小是 `2R`**：这是 stencil/卷积类问题的通用结构。R 越大，halo 占比越大，共享内存的收益越低（因为 halo 部分是被重复加载的）。所以这类问题常用"大块 + 多维 tile"来摊薄 halo 成本。

  </details>

### 练习 2.6 [挑战] 把矩阵乘法优化到更高的 GFLOPS

**要求**：以 `gemmRegTiled`（v3）为基础，尝试下面几种改动，每次只改一个变量，记录 GFLOPS：

1. **把每线程的分块从 4×4 改成 8×8**（需要把块改成 `(8, 8)`，覆盖 64×64 输出）。
2. **把 `BK` 从 16 改成 8 或 32**。
3. **给内层循环加 `__launch_bounds__`**，控制寄存器数。
4. **用 `float4` 向量化加载**（需要 `__align__(16)` 和 16 字节对齐的地址）。
5. 对比 cuBLAS 的 `cublasSgemm`（[第 7 章](ch07_生态库与工程化.md)）。

**要求**：做一张表格，写明每次改动后的：寄存器数（`-Xptxas -v`）、spill 字节数、占用率（`occupancy.cu` 的方法）、耗时、GFLOPS。然后回答："哪个改动收益最大？为什么？"

<details>
<summary>参考做法</summary>

**预期的定性结论**（你的机器上数值会不同）：

| 改动                   | 预期效果                 | 原因                                                                                              |
| ---------------------- | ------------------------ | ------------------------------------------------------------------------------------------------- |
| 4×4 → 8×8              | **可能变快，也可能变慢** | 共享内存访问量再减半（复用率从 2 升到 4），但寄存器从 ~64 涨到 ~128+，可能触发 spill 或占用率骤降 |
| BK = 16 → 32           | 略快                     | 每次加载更少的次数，但共享内存翻倍（可能降低占用率）                                              |
| BK = 16 → 8            | 略慢                     | 加载次数翻倍，共享内存减半                                                                        |
| 加 `__launch_bounds__` | 看具体情况               | 如果能避免 spill 且提高占用率，有效；否则可能引发 spill                                           |
| `float4` 加载          | **通常明显变快**         | 一次加载 16 字节，减少指令数、提高访存效率。这是最值得做的一项                                    |

**`float4` 的实现要点**：

```cpp
// 共享内存也要按 float4 对齐
__shared__ __align__(16) float As[BM][BK];
__shared__ __align__(16) float Bs[BK][BN];

// 把 4 个连续的 float 当一次加载
const float4* A4 = reinterpret_cast<const float4*>(A);
// ... 需要确保 BK 是 4 的倍数，且地址 16 字节对齐
```

**对 `cublasSgemm` 的对比**：cuBLAS 通常能达到该卡峰值 FP32 的 **70%~90%**，而手写的 v3 大约在 **15%~40%**。差距的来源是：

- 更激进的分块（128×128、每线程 8×8）；
- 向量化加载 + 更好的共享内存布局（避免 bank conflict）；
- 精心调度的寄存器分配，正好避开 spill；
- 针对具体架构用汇编级优化（`SASS` 手调）；
- 双缓冲/异步流水线（`cp.async`，[第 6 章](ch06_CUDA高级特性.md)）。

**但更重要的结论是**：

> **先判断"该不该自己写"。** 如果 cuBLAS 能满足需求（标准 GEMM，FP32/FP16），**直接用 cuBLAS**。自己写 kernel 的价值在于：非标准算子、融合算子、特殊数据布局。这是 [第 7 章](ch07_生态库与工程化.md) 会展开的工程判断。

**做这个练习最大的收获**不是性能数字，而是：**你会亲身感受到"优化是试出来的，不是想出来的"**——每一个改动都要测，而测出来的结果经常和直觉相反。

</details>

## 6. 常见错误与排查

### 6.1 访存类错误

| 错误信息 / 现象                         | 原因                                               | 解决办法                                                                     |
| --------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------- |
| 有效带宽只有峰值的 10%~30%              | 访存不合并                                         | 检查同一 warp 内相邻线程的地址差；用 `ncu` 看 `l1tex__t_sectors_per_request` |
| 相邻线程地址差 = 32 或更大的常数        | 典型的不合并模式                                   | 重构索引，让 `threadIdx.x` 直接对应连续地址                                  |
| AoS 结构的带宽只有预期的一半以下        | 每个事务里只用了部分字节                           | 改成 SoA，或调整访问模式                                                     |
| 用了 `float4` 但报 `misaligned address` | 地址没有 16 字节对齐                               | 检查 `cudaMalloc` 的对齐（通常 256 字节），以及访问偏移是否 4 的倍数         |
| 转置/卷积比预期慢很多                   | 写跨步（不合并）                                   | 用共享内存做中转，让"读"和"写"各自合并                                       |
| 修改了 `PAD` 但性能没变                 | 原本就没有 bank conflict                           | 用 `ncu` 确认冲突次数，不要盲改                                              |
| 共享内存访问变慢                        | 存在 bank conflict                                 | 分析"warp 内相邻线程的地址差"是否与 32 互质；考虑 padding 或错位访问         |
| 加了 padding 反而变慢                   | 该访问模式本来无冲突，padding 引入了空洞和额外计算 | 去掉 padding（见 `bank_conflict.cu` 的实验 2）                               |

### 6.2 共享内存与同步类错误

| 错误信息 / 现象                                              | 原因                                         | 解决办法                                                                                                  |
| ------------------------------------------------------------ | -------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 结果时对时错，换个块大小就变了                               | 缺 `__syncthreads()`（通常是"防覆盖"那一个） | 对照分块矩阵乘法的四个阶段检查屏障                                                                        |
| `__syncthreads()` 卡死 / 程序挂住                            | 屏障被放在"只有部分线程能到达"的分支里       | 把屏障移到所有线程都会执行的位置；条件必须对整块统一                                                      |
| 共享内存里的数据是垃圾                                       | 读了没有初始化的共享内存（上一个块留下的）   | 使用前先初始化；注意 `BLOCK + 2R` 这类"比线程数多"的数组要完整填满                                        |
| `ptxas error : Entry function 'x' uses too much shared data` | 共享内存超了每块上限                         | 查 `prop.sharedMemPerBlock`；减小 tile 或改用动态共享内存 + `cudaFuncSetAttribute` 提高上限（需 CC 7.0+） |
| 声明了动态共享内存但启动时忘了第三个参数                     | `extern __shared__` 得到的是 0 字节          | 启动时写 `<<<grid, block, bytes>>>`                                                                       |
| 多个动态共享内存数组互相覆盖                                 | `extern __shared__` 只有一个起点             | 手工用指针切分：`float* b = smem + aSize;`                                                                |
| `__syncthreads()` 之后的共享内存值还是旧的                   | 编译器把值缓存在寄存器里                     | 需要时加 `volatile`（见 `reduce_shared.cu`）                                                              |

### 6.3 寄存器与占用率类错误

| 错误信息 / 现象                                  | 原因                                           | 解决办法                                        |
| ------------------------------------------------ | ---------------------------------------------- | ----------------------------------------------- |
| `error: too many resources requested for launch` | 每块线程数 × 每线程寄存器数 > 每 SM 寄存器总量 | 减小块大小；或加 `__launch_bounds__` 限制寄存器 |
| `-Xptxas -v` 报 `spill stores/loads` 非 0        | 寄存器不足，变量被放到本地内存                 | 见 6.4 的对策表                                 |
| 局部数组访问特别慢                               | 数组下标是运行期变量 → 一定放本地内存          | 用 `#pragma unroll` 让下标成为编译期常量        |
| 加了 `__launch_bounds__` 反而更慢                | 寄存器被压缩引发 spill                         | 放宽或去掉；先测基线再决定                      |
| 占用率 100% 但性能很差                           | 高占用率不等于高性能；瓶颈可能在访存模式       | 检查合并访存、共享内存冲突、算术强度            |
| 占用率只有 25% 但性能很好                        | 每线程做了很多活、寄存器复用高，这是正常的     | **不要盲目追求占用率**，看实际耗时              |

### 6.4 寄存器溢出（spill）的排查清单

```text
发现 spill 后，按这个顺序试：

1. 定位是哪个 kernel（-Xptxas -v 的输出会写明函数名）
2. 看那个 kernel 的"每线程元素数"是不是太大了
   → 4x4 通常安全；8x8 常会有问题；16x16 基本一定会 spill
3. 看局部数组的下标是不是运行期变量
   → 加 #pragma unroll
4. 看有没有多余的临时变量、或者被内联的深层函数
   → 用 __forceinline__ 或反过来用 __noinline__
5. 考虑放宽 __launch_bounds__ 的 minBlocksPerSM
6. 去掉 -maxrregcount（如果用了）
7. 如果以上都不行，接受少量 spill + 用 ncu 确认它是否真的是瓶颈
```

**注意**：**少量 spill 未必是灾难**。如果 spill 的变量在 L1 里热度很高，实际代价可能很小。判断标准永远是**实测耗时**，而不是"有没有 spill"。

### 6.5 一个系统性的排查流程

```text
发现 kernel 慢，按这个顺序查：

第 1 步：它是访存受限还是计算受限？
   算算术强度 = 浮点运算次数 / 搬运字节数
   → 算术强度低（< 5 flops/byte）→ 大概率访存受限，重点看访存

第 2 步：访存受限的话，有效带宽是多少？
   有效带宽 = 搬运字节数 / 耗时
   → 只有峰值的 10%~30% → 查合并访存（本章 1.5 节）
   → 已经到 60%~85% → 已经接近硬件上限，改访存模式没用

第 3 步：有没有重复读取？
   算一下"实际的全局内存读取量" vs "理论需要的数据量"
   → 重复率高 → 用共享内存分块（本章 1.7 节）

第 4 步：用了共享内存之后，有没有 bank conflict？
   → 用 ncu 看 l1tex__data_bank_conflicts_pipe_lsu
   → 有的话，看"warp 内相邻线程地址差"是否与 32 互质

第 5 步：共享内存访问已经很快之后，是不是共享内存访问量本身太多了？
   → 考虑寄存器分块（本章 1.9 节 v3）

第 6 步：检查寄存器与占用率
   → -Xptxas -v 看寄存器和 spill
   → 用 occupancy.cu 的方法算占用率
   → 试 __launch_bounds__，测，留还是去掉用数据决定

第 7 步：全部做完还是不够快？
   → 考虑算法级优化（更小的数据量、更好的数据布局）
   → 考虑用现成的库（cuBLAS）
```

**这个流程体现了 [第 4 章](ch04_性能分析与优化方法论.md) 的核心思想**：**优化是一个"测量 → 假设 → 改动 → 再测量"的闭环**，不是一堆技巧的堆砌。

## 7. 本章小结

### 7.1 要点清单

**内存金字塔**

- 延迟差几个数量级：寄存器(1) << 共享内存(20) << L2(200) << 全局(400+)。
- 容量反向：寄存器(KB) << 共享内存(百 KB) << L2(MB) << 全局(GB)。
- **优化的本质：把频繁访问的数据从"慢而大"搬到"快而小"**。

**全局内存**

- `cudaMalloc` / `cudaMemcpy`（四个方向）/ `cudaFree`；`cudaMalloc` 的参数是 `&ptr`。
- 页锁定内存（`cudaMallocHost`）让 DMA 直达，拷贝更快，是异步拷贝的前提。
- 统一内存（`cudaMallocManaged`）代码简洁，但**必须配 `cudaMemPrefetchAsync`** 才有好性能（CUDA 13 起该函数与 `cudaMemAdvise` 的设备参数改为 `cudaMemLocation`，写法见上文）。
- **合并访存**：判断标准是"同一个 warp 内相邻线程的地址是否也相邻"。
  - 合并：一个 warp 覆盖连续的 128 字节 → 1 个事务。
  - 不合并：地址分散在 32 个段 → 32 个事务，**有效带宽掉一个数量级**。
  - 反直觉但重要：**"反向连续"仍然是合并的**。
- AoS 浪费事务内的字节，**SoA 是 GPU 上的常规选择**（当你不总是访问全部字段时）。

**共享内存**

- `__shared__`（静态）或 `extern __shared__`（动态，启动时第三个参数指定字节数）。
- 速度约是全局内存的 10~20 倍，容量每块 48~227 KB。
- **`__syncthreads()`**：块内屏障。必须保证所有线程都能到达（或都不到达）。
- **Bank conflict**：32 个 bank，`bank = (字地址) % 32`。
  - 冲突的条件：warp 内多个线程访问**同一 bank 的不同地址**。
  - 完全相同的地址不算冲突（**广播**）。
  - 判断规则：**warp 内相邻线程的地址差与 32 互质 → 无冲突**。
  - 消除方法：padding（32→33）、错位访问、利用广播。
  - ⚠️ **padding 不是万能药**：对"按行访问"的场景反而有害。

**分块（Tiling）与矩阵乘法**

- 朴素 GEMM 的病根是**重复读取**（重复率 = 2MNK/(MK+KN)）。
- **v2 共享内存分块**：全局内存访问量减少约 TILE 倍（TILE=32 时约 32 倍）。
  - 四个阶段：加载 → syncA → 计算 → syncB。**两个屏障缺一不可**。
  - 越界填 0 是正确且高效的技巧。
- **v3 寄存器分块**：每线程算 TM×TN 个输出，把共享内存读取量再降 TM*TN/(TM+TN) 倍。
  - 代价：寄存器压力上升、占用率下降。
  - 这是"复用 vs 占用率"权衡的经典案例。

**常量内存与只读缓存**

- `__constant__`：64 KB，专门的常量缓存，**同一 warp 读同一地址时广播极快**；读不同地址会串行化。
- `cudaMemcpyToSymbol(c_coeff, ...)`：第一个参数是**符号本身，不加 `&`**。
- `__ldg` / `const T* __restrict__`：走只读数据缓存。现代编译器对后者会自动生成与 `__ldg` 相同的指令。

**寄存器与占用率**

- 占用率 = 每 SM 实际驻留线程数 / 每 SM 最大线程数。
- 受限因素取最小值：线程数 / 寄存器 / 共享内存 / 每 SM 块数上限。
- **寄存器对占用率的影响是"阶梯式"的**，跨过整数边界才掉一档。
- `__launch_bounds__(maxThreads, minBlocksPerSM)` 是精确控制寄存器预算的工具；`-maxrregcount` 是全局的、不推荐的。
- **寄存器溢出（spill）**：局部数组下标是运行期变量时必定发生。
  - 发现方式：`-Xptxas -v` 的 `spill stores/loads`，或 `cudaFuncGetAttributes` 的 `localSizeBytes`。
  - 主要对策：`#pragma unroll` 展开、减小每线程分块、放宽 `__launch_bounds__`。
- **高占用率 ≠ 高性能**。这是本章最后一个、也是最重要的观念转变。

### 7.2 自检问题

**Q1：什么情况下"相邻线程访问相邻地址"不是合并的？**

<details>
<summary>答案要点</summary>

严格说，"相邻线程访问相邻地址"就是合并的定义，它总是合并的。真正需要警惕的是**看起来连续、实际上不连续**的情况：

1. **元素大小不对齐**：`struct` 数组里只访问某个字段，地址差是 `sizeof(struct)` 而不是字段大小。
2. **跨行边界**：一维网格的编号跨过了矩阵行的边界（比如把二维数组当一维处理时，warp 横跨两行）。
3. **间接寻址**：`a[idx[i]]` 里 `idx` 是无规律的值，就算 `i` 连续，实际地址也不连续。
4. **二维块里 `blockDim.x` 不是 32 的倍数**：一个 warp 会横跨两行，访问断开。

所以真正的判断标准是：**一个 warp 的 32 个线程访问的实际地址，是否落在一段连续的 128 字节里。**

</details>

**Q2：为什么分块矩阵乘法需要两个 `__syncthreads()`？删掉一个会怎样？**

<details>
<summary>答案要点</summary>

- **第一次（加载后）**：生产者-消费者屏障。保证所有线程都写完了共享内存，才能开始读。删掉会导致某些线程读到未初始化或上一轮的垃圾数据。
- **第二次（计算后）**：防覆盖屏障。保证所有线程都读完了当前 tile，才能往里写下一轮的数据。删掉会导致"快的线程覆盖了慢的线程正在读的数据"。

两者保护的是**不同方向的依赖**，不能互相替代。

**表现**：结果"有时对有时错"，而且换个块大小、换个卡可能就"好了"。这种 bug 极难查，所以同步纪律必须严格。

</details>

**Q3：`__shared__ float tile[32][32]` 和 `[32][33]` 有什么区别？什么时候该用哪个？**

<details>
<summary>答案要点</summary>

区别在**行宽**，从而影响 `bank = (行*行宽 + 列) % 32`：

- `[32][32]`：按列访问（warp 内列固定、行变）→ `bank = 列 % 32` 恒定 → **32 路冲突**。按行访问（warp 内列变）→ `bank = 列` → 无冲突。
- `[32][33]`：按列访问 → `bank = (行 + 列) % 32`，随行变化 → **无冲突**。按行访问 → `bank = (行 + 列) % 32`，但此时行固定、列变，所以还是 32 个不同 bank → **也无冲突**（但索引计算变复杂、每行有 1 个字的空洞）。

**选择**：

- 如果 warp 内是**按行访问** → 用 `[32][32]`（本来就无冲突，padding 反而增加开销）。

- 如果 warp 内是**按列访问** → 用 `[32][33]`。

- **判断依据是实测**：用 `ncu` 看 bank conflict 计数，别靠推理。

  </details>

**Q4：为什么 `__constant__` 内存对"所有线程读同一个地址"很快，对"读不同地址"很慢？**

<details>
<summary>答案要点</summary>

常量缓存的设计目标是**广播**：当同一个 warp 的 32 个线程请求同一个地址时，硬件只发出一次请求，把结果广播给所有线程 —— 等价于一次访问的开销。

但常量缓存**没有为"多个不同地址"做并行化**：如果 32 个线程请求 32 个不同的地址，硬件只能**逐个地址串行处理**（因为常量缓存每个周期只能提供一个值）。结果是 32 倍的开销，**比全局内存还慢**。

所以正确的使用场景是：小的、所有线程都读同样的值（或少量几个值）的参数表，比如卷积核权重、物理常数、查找表（且同一 warp 读同一位置）。

</details>

**Q5：`-Xptxas -v` 报 `96 bytes spill stores, 64 bytes spill loads`，你怎么办？**

<details>
<summary>答案要点</summary>

**先定位，再判断，最后对症下药：**

1. **定位**：这个输出会写明是哪个函数。用 `cudaFuncGetAttributes` 确认 `localSizeBytes`。

2. **判断严重性**：少量 spill（比如几十字节）可能影响不大；如果 spill 字节数比寄存器数还大，那就是严重问题。**最终判断标准是实测耗时**。

3. **对症下药**（按可能性排序）：

   - 每线程元素太多（8×8 或 16×16 的寄存器分块）→ 降到 4×4；
   - 局部数组下标是运行期变量 → 加 `#pragma unroll`；
   - `__launch_bounds__` 的 `minBlocksPerSM` 太严 → 放宽；
   - 用了 `-maxrregcount` → 去掉，改用 `__launch_bounds__`。

4. **验证**：重新编译，确认 spill 归零，再测耗时。如果耗时没变好，说明 spill 不是瓶颈，前面的努力白费了（这也是有价值的结论）。

   </details>

**Q6：写出一个"每个线程处理 4 个连续 float"的向量加法核心代码，并说明它是合并的还是不合并的。**

<details>
<summary>答案要点</summary>

```cpp
__global__ void vectorAdd4(const float* __restrict__ A,
                           const float* __restrict__ B,
                           float* __restrict__ C, int n) {
    int i = (blockIdx.x * blockDim.x + threadIdx.x) * 4;
    if (i + 3 < n) {
        // 每个线程处理 4 个连续元素
        float4 a = *reinterpret_cast<const float4*>(A + i);
        float4 b = *reinterpret_cast<const float4*>(B + i);
        float4 c;
        c.x = a.x + b.x;
        c.y = a.y + b.y;
        c.z = a.z + b.z;
        c.w = a.w + b.w;
        *reinterpret_cast<float4*>(C + i) = c;
    } else {
        for (int k = 0; k < 4 && i + k < n; ++k) C[i + k] = A[i + k] + B[i + k];
    }
}
```

**合并性分析**：这是**合并的**，而且是**更高效的合并**。线程 `t` 访问地址 `[4t, 4t+4)`，线程 `t+1` 访问 `[4t+4, 4t+8)`。整个 warp 覆盖 `[4*32t0, 4*32t0 + 512)` 字节的**连续区间**。

关键区别：**每个线程一次加载 16 字节（`float4`），所以一个 warp 一次请求覆盖 512 字节**，只需要 4 个 128 字节段。而"一个线程一个 float"的写法需要访问同样的 512 字节，但要用 4 次 warp 级请求。

**收益**：减少了指令数（1 次 128 位加载 vs 4 次 32 位加载），降低了访存指令的发射压力。

**前提条件**：

- 地址必须 16 字节对齐（`i` 是 4 的倍数，且指针本身对齐）；
- `float4` 要求 16 字节对齐，否则会报 `misaligned address`。

**这种技术叫"向量化访存"**，在后面 [第 8 章](ch08_综合项目实战.md) 的项目里是标准优化之一。

</details>

你现在知道了：

- 怎么用合并访存把有效带宽从 10% 提到 80%；

**但有一件事我一直没敢深入展开：`__syncthreads()` 到底保证了什么？**

- 它保证"所有线程都到达了这里"，但它**保证全局内存的可见性吗**？
- 为什么 `__syncthreads()` 只能用在块内，**块与块之间**怎么办？
- 多个线程要同时往一个地址写（比如直方图计数），该用什么？

这些是 [第 3 章 同步通信与原子操作](ch03_同步通信与原子操作.md) 的主题：

1. **内存可见性与编译器重排序**：为什么"我写了、你读到了旧值"。
2. **`__syncwarp()` / `__threadfence()`**：warp 级同步与内存栅栏的区别。
3. **Warp Shuffle**：`__shfl_down_sync` / `__shfl_xor_sync`，不用共享内存做归约和扫描。
4. **原子操作**：`atomicAdd` / `atomicCAS`，以及"原子争用"这个性能陷阱。
5. **Cooperative Groups**：跨块的同步与协作（需要协作启动）。
6. **流与并发**：`cudaStreamCreate` / `cudaMemcpyAsync`，让拷贝和计算重叠起来。

学完第 3 章，你就能写出"多块协作"的程序，并且理解为什么"并行程序的正确性"比"并行程序的性能"更难保证。
