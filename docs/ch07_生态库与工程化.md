## 1. 概念讲解

### 1.1 为什么不什么都自己写

先说结论：**在 GPU 编程里，"自己写"通常是最后的选择，而不是第一选择。**

原因有三个，而且都很硬：

**原因一：库已经被针对每一代硬件调过参了。**
一个生产级的 SGEMM 库里有几十种实现（kernel），它会在运行时根据矩阵形状、数据类型、目标架构选一个最合适的。手写版本一般只用一种形状的配置，换个矩阵尺寸就会掉一大截性能。[第 8 章](ch08_综合项目实战.md) 你会亲手把朴素 GEMM 优化到接近 cuBLAS —— 而且你会看到，即使做到最后一步，也还是有差距。

**原因二：库的正确性是经过大规模验证的。**
数值计算里最贵的不是算得慢，是**算错了却不知道**。cuBLAS/cuFFT 这类库在成千上万种输入组合上被验证过，你手写的 kernel 大概率只在你自己想到的那几种输入上试过。

**原因三：工程代码的可维护性。**
一个 3000 行的手写 kernel 库，半年后只有你能改；换成三行 cuBLAS 调用 + 一句注释，任何人都能接手。

但这不是说库永远是对的。**库解决不了的问题有三类**，遇到这三类你就必须自己写：

| 类别 | 典型例子 | 为什么库不行 |
|---|---|---|
| 库没覆盖的算子 | 自定义损失函数、领域专用的融合算子、图算法 | 根本没有这个 API |
| 融合多步为一个 kernel | LayerNorm+GeLU 融合、卷积+BN 融合 | 库一次只做一个算子，中间结果反复读写显存 |
| 特殊的访存/精度需求 | 非连续布局、混合精度、定点数、稀疏+稠密混合 | 库的接口不支持这种布局 |

> **一个经验法则**：如果一个算子的热点是"访存"，那么把它和相邻算子**融合**通常能赢过"两个库调用各做一半 + 一次显存往返"。这也是 FlashAttention、各种 fused MLP 能显著快于"标准算子拼起来"的原因。

### 1.2 判断表：该自己写还是该用库

下面这张表，建议你把它当成查表工具用。判断顺序是**从上往下**，命中哪一行就用哪一行的方案。

| 你的需求 | 首选方案 | 次选方案 | 自己写的理由 |
|---|---|---|---|
| 稠密矩阵乘、矩阵向量乘、三角求解 | cuBLAS | cuBLASLt（更灵活）+ 融合 epilogue | 需要特殊的输出融合（如 GEMM+自定义激活）时用 cuBLASLt 的 epilogue，仍不必自己写 |
| 批量的小矩阵乘（几百个 4x4 ~ 64x64） | `cublasSgemmStridedBatched` | 自己写（批量太怪时） | stride/分组不规则，库的批量接口表达不了 |
| 稀疏矩阵运算 | cuSPARSE / cuSPARSELt | 自己写 CSR kernel | 稀疏结构特殊（如块稀疏 + 特定分组） |
| FFT（1D/2D/3D、实数/复数、批量） | cuFFT | cuFFTDx（设备端 FFT，用于融合进 kernel） | FFT 要嵌在一个更大 kernel 的中间步骤里 |
| 随机数 | cuRAND | 自己写 xorshift（只要求"看起来随机"时） | 不需要统计品质，只要快，且要复现 |
| 归约（求和/最值/范数） | CUB `DeviceReduce` | Thrust `reduce` | 归约要和相邻计算融合在同一个 kernel 里 |
| 前缀和 / 扫描 | CUB `DeviceScan` | Thrust `inclusive_scan` | 同上，或需要特殊的分段（segmented）语义 |
| 排序 | CUB `DeviceRadixSort` | Thrust `sort` | key 太大不能基数排序、需要自定义比较器且数据量小 |
| 逐元素变换（Map） | Thrust `transform` | 自己写（本来就不难） | 想要融合多个逐元素操作、或要精确控制向量化宽度 |
| 深度学习前向/反向 | cuDNN | 自己写（特殊形状/布局） | 输入形状特殊、算子需要和别的算子融合 |
| 推理部署（整模型） | TensorRT | ONNX Runtime + TensorRT EP | 需要自定义插件（TensorRT Plugin） |
| 直方图、Stencil、图算法、自定义迭代求解器 | — | — | **这类就该自己写**，库不覆盖 |
| 一个算子被调用上百万次且很小 | — | — | 需要自己写并把多个小 kernel 融合成一个大 kernel |

### 1.3 一个更实用的决策流程

上面的表是"静态"的。真正面对一个陌生问题时，按这个顺序走：

1. **先写出 CPU 版本。** 不管最后用不用，你需要一个可信的参考结果。这一步永远不能省。
2. **搜一遍有没有现成库。** 关键词是"算法名 + cuBLAS/cuSPARSE/cuDNN/Thrust/CUB"。CUDA Toolkit 自带文档，NVIDIA 的 `cuda-samples` 仓库里几乎每个库都有例子。
3. **如果库能覆盖，先接库。** 接完测一下：库的耗时占整个任务的比例是多少？如果库只占 10%，那你花一周手写去优化它，最多也只能提升 10% 中的一部分 —— 这叫**阿姆达尔定律**，别把力气用错地方。
4. **如果库覆盖不了或者占比很大，再考虑自己写。** 这时你有两件事要做：先用 `ncu` 确认瓶颈在哪（[第 4 章](ch04_性能分析与优化方法论.md)），再决定是"重写 kernel"还是"融合 kernel"。
5. **写完之后，一定要拿它和库（或 CPU）对拍。** 见 2.9 节的单元测试部分。

### 1.5 库的通用使用套路：五步法

几乎所有 CUDA 库（cuBLAS、cuFFT、cuSPARSE、cuDNN）都是同一套流程。掌握了这个套路，学一个新库的时间从"一天"变成"半小时"。

```
① 创建句柄        create(&handle)
       │            句柄里装着 stream、workspace、算法选择等上下文
       ▼
② 创建描述符      createXxxDescriptor(...) / 或用参数直接描述
       │            描述符只说"形状/类型/布局"，不持有数据
       ▼
③ 查询工作区      xxxGetWorkspaceSize(...) / xxx_bufferSize(...)
       │            库内部要临时显存，大小由它算，你来分配
       ▼
④ 执行            xxxExec(...) / cublasSgemm(...)
       │            异步执行，和 kernel 一样
       ▼
⑤ 销毁            destroy(...) + free(...)
```

三个关键认知：

1. **句柄可以复用。** 创建句柄是有成本的（初始化上下文），在循环里反复创建是典型的新手错误。同理，**plan / 描述符也应该复用**，只要形状不变。
2. **工作区大小只有运行时才知道。** 库会根据设备、算法、数据形状自己算，所以你没法在编译期确定它。这就是"先传 `nullptr` 问一次、再分配"这种两段式 API 存在的原因。
3. **库调用也是异步的。** 和 kernel 一样，它把任务提交到 stream 上就返回了。**计时和取结果之前必须同步**，否则你测到的是"提交耗时"。

### 1.6 cuBLAS 的列主序陷阱（本章最重要的一个坑）

这是新手使用 cuBLAS 时**最容易出错、最难自己发现**的地方。请认真读三遍。

#### 1.6.1 事实：cuBLAS 只用列主序

BLAS 标准诞生于 Fortran 时代，而 Fortran 的数组是**列主序**（column-major）的。cuBLAS 完全遵循这个标准。所以：

> `cublasSgemm` 认为你传给它的每一个指针，指向的都是一个**列主序**存储的矩阵。

但 C/C++ 里的二维数组是**行主序**（row-major）的。这就是全部麻烦的来源。

#### 1.6.2 两种存储的区别

一个 2x3 的矩阵

```
       列0  列1  列2
行0  [  a    b    c  ]
行1  [  d    e    f  ]
```

- **行主序**（C 语言）：内存里是 `a b c d e f`。同一行的元素挨在一起。
- **列主序**（Fortran/cuBLAS）：内存里是 `a d b e c f`。同一列的元素挨在一起。

#### 1.6.3 关键洞察：同一块内存，两种解读

注意上面那句话：**"内存里是 `a b c d e f`"这件事，和"它被解读成什么矩阵"是两回事。**

同一段内存 `a b c d e f`：

- 按行主序解读，它是 `[[a,b,c],[d,e,f]]`，形状 2x3。
- 按列主序解读，它是 `[[a,d],[b,e],[c,f]]`，形状 3x2。

**列主序解读的结果，正好是行主序解读结果的转置！**

这就是解决整个问题的钥匙：

> 如果我们有一段行主序的矩阵 `A`（M x K）、`B`（K x N）、`C`（M x N），
> 那么把它们原封不动地交给 cuBLAS（它按列主序解读），
> cuBLAS 眼中看到的就是 `Aᵀ`（K x M）、`Bᵀ`（N x K）、`Cᵀ`（N x M）。

#### 1.6.4 推导出正确的调用

我们要算的是行主序意义下的 `C = A · B`。

对等式两边同时转置：`Cᵀ = Bᵀ · Aᵀ`。

把 1.6.3 的结论代进去：cuBLAS 眼中的 `Cᵀ` = cuBLAS 眼中的 `Bᵀ` × cuBLAS 眼中的 `Aᵀ`。

也就是说，cuBLAS 要执行的是一个标准的列主序 GEMM：

```
C_cb(m x n) = A_cb(m x k) · B_cb(k x n)
```

其中：

| cuBLAS 参数 | 值 | 对应到我们的数据 |
|---|---|---|
| `m`（A_cb 的行数，也是 C_cb 的行数） | `N` | Cᵀ 是 N x M |
| `n`（B_cb 的列数，也是 C_cb 的列数） | `M` | |
| `k`（公共维度） | `K` | |
| `A_cb` 指针 | `dB`（我们的 B） | Bᵀ 是 N x K |
| `lda`（A_cb 的前导维度 = 行数） | `N` | |
| `B_cb` 指针 | `dA`（我们的 A） | Aᵀ 是 K x M |
| `ldb` | `K` | |
| `C_cb` 指针 | `dC` | Cᵀ 是 N x M |
| `ldc` | `N` | |

于是得到那行"看起来很奇怪但完全正确"的代码：

```cpp
// 行主序 C = A*B 的正确 cuBLAS 写法：
// 把 A 和 B 的位置换一下，m/n 换一下，ld 用行主序意义下的"每行元素数"
cublasSgemm(handle, CUBLAS_OP_N, CUBLAS_OP_N,
            N, M, K,            // 注意：是 N, M, K —— 不是 M, N, K！
            &alpha,
            dB, N,              // "A" 参数传 B，lda = N（B 的每行元素数）
            dA, K,              // "B" 参数传 A，ldb = K（A 的每行元素数）
            &beta,
            dC, N);             // ldC = N
```

#### 1.6.5 `lda` 到底是什么

`lda` = **leading dimension**（前导维度）。定义是：

> 在列主序存储里，同一列中相邻两个元素之间相隔多少个元素。

对列主序的 `A_cb`（N 行 K 列，"每行 K 个元素"是行主序的说法；列主序下同一列相邻元素相隔 N 个元素），所以 `lda = N`。

**一个更好记的说法**：`lda` 是"这块内存按行主序看时，一行有多少个元素"。

- 我们的 `B` 是行主序 K x N，一行 N 个元素 → `lda = N` ✓
- 我们的 `A` 是行主序 M x K，一行 K 个元素 → `ldb = K` ✓
- 我们的 `C` 是行主序 M x N，一行 N 个元素 → `ldc = N` ✓

#### 1.6.6 两种常见写法的选择

| 写法 | 代码 | 适用场景 |
|---|---|---|
| **交换 A/B 法**（推荐） | 传 `CUBLAS_OP_N`，交换 A、B 指针与 m/n | 数据本来就是行主序，不想额外转置 |
| **先转置再算** | 先把 A、B 转成列主序，再按 `M,N,K` 正常调用 | 需要以列主序保存结果时；但要额外两次转置（可能比 GEMM 还贵） |

再强调一遍：**交换 A/B 之后，`m` 和 `n` 也必须交换。** 只交换指针不交换维度是最常见的错误写法，它会给出一个形状不对的答案，或者干脆越界读。

### 1.7 跨平台与替代方案（保持视野）

CUDA 不是唯一的 GPU 计算方案。了解替代品的思路，能帮你在需要时快速迁移。

| 方案 | 厂商 | 语言/接口 | 移植难度 | 生态成熟度 |
|---|---|---|---|---|
| **CUDA** | NVIDIA | CUDA C++ | — | 最成熟，库最全 |
| **HIP / ROCm** | AMD | HIP（语法几乎等同 CUDA） | 极低，多数代码改个前缀就能跑 | 中等，库覆盖在快速补齐 |
| **SYCL / oneAPI** | Intel（也支持 NVIDIA/AMD） | 标准 C++ 模板 | 中，需重写 kernel 为 `parallel_for` | 中等 |
| **OpenCL** | 跨厂商标准 | C99 + 主机 API | 中高，需手写大量样板代码 | 稳定但生态增长停滞 |
| **Metal** | Apple | MSL | 高，只面向 Apple 平台 | Apple 平台内成熟 |
| **Triton** | OpenAI 等 | Python DSL | 需改写为块级编程 | 快速成长（主要是深度学习） |

**迁移的核心策略：抽象出"计算核"这一层。**

真实项目里，可移植性靠的不是"写一次到处跑"，而是**把平台相关的代码限制在一个薄层里**：

```
你的应用逻辑（平台无关）
        │
        ▼
   计算接口层  ← 只有这一层知道自己跑在什么硬件上
        │
   ┌────┴────┬─────────┐
   ▼         ▼         ▼
 CUDA 后端  HIP 后端  CPU 后端
```

如果你的代码里到处散落着 `cudaMalloc` 和 `<<<>>>`，那它就永远绑定 NVIDIA 了。本章 2.9 节的 CMake 工程会演示这个"接口层 + 多后端"的最简形式。

**HIP 的迁移可行性有多高？** 官方工具 `hipify-perl` / `hipify-clang` 可以自动把 CUDA 源码转成 HIP：
- `cudaMalloc` → `hipMalloc`
- `cudaMemcpy` → `hipMemcpy`
- `__global__`、`<<<>>>`、`threadIdx` 等**完全一致**
- `cuBLAS` → `rocBLAS`，`cuFFT` → `rocFFT`，`cuDNN` → `MIOpen`

所以你会看到很多项目的做法是：`#include <cuda_runtime.h>` 换成 `#include <hip/hip_runtime.h>`，其余不变。

### 2.1 cuBLAS：完整 GEMM 示例

完整文件：[`code/lessons/ch07_ecosystem/cublas/cublas_sgemm.cu`](../code/lessons/ch07_ecosystem/cublas/cublas_sgemm.cu)

```cpp
// ============================================================
//  cublas_sgemm.cu —— 用 cuBLAS 做单精度矩阵乘法 C = A * B
//
//  本程序重点演示三件事：
//    1) 行主序（C 语言风格）的数据，如何正确地喂给"列主序"的 cuBLAS
//    2) cublasSgemm 每一个参数到底是什么意思
//    3) 如何与 CPU 参考实现对比、如何测 GFLOPS
// ============================================================

#include <cstdio>
#include <cstdlib>
#include <cmath>
#include <vector>
#include <random>

#include <cublas_v2.h>
#include "../common/cuda_check.h"

// cuBLAS 的状态码不是 cudaError_t，所以需要自己的检查宏。
// 这是工程里的常见做法：每个库配一个 CHECK 宏。
#define CUBLAS_CHECK(expr)                                                        \
    do {                                                                          \
        cublasStatus_t _st = (expr);                                              \
        if (_st != CUBLAS_STATUS_SUCCESS) {                                       \
            fprintf(stderr, "\n[CUBLAS ERROR] %s:%d\n  call : %s\n  code : %d\n", \
                    __FILE__, __LINE__, #expr, (int)_st);                         \
            exit(EXIT_FAILURE);                                                   \
        }                                                                         \
    } while (0)

// 统一的 GPU 计时器。为什么不用 CPU 上的 clock()？
// 因为 kernel 是异步启动的，CPU 计时会把"启动耗时"当成"计算耗时"。
class CudaTimer {
public:
    CudaTimer() {
        CUDA_CHECK(cudaEventCreate(&start_));
        CUDA_CHECK(cudaEventCreate(&stop_));
    }
    ~CudaTimer() { cudaEventDestroy(start_); cudaEventDestroy(stop_); }
    void start() { CUDA_CHECK(cudaEventRecord(start_, 0)); }
    float stop() {
        CUDA_CHECK(cudaEventRecord(stop_, 0));
        CUDA_CHECK(cudaEventSynchronize(stop_));
        float ms = 0.f;
        CUDA_CHECK(cudaEventElapsedTime(&ms, start_, stop_));
        return ms;
    }
private:
    cudaEvent_t start_{}, stop_{};
};

// CPU 参考实现：行主序 C = A * B，尺寸 M x N = (M x K) * (K x N)
static void cpuSgemm(int M, int N, int K,
                     const float* A, const float* B, float* C) {
    for (int i = 0; i < M; ++i)
        for (int j = 0; j < N; ++j) {
            float acc = 0.f;
            for (int k = 0; k < K; ++k)
                acc += A[i * K + k] * B[k * N + j];
            C[i * N + j] = acc;
        }
}

// 相对误差比较，浮点结果绝不能用 == 比较
static bool verify(const float* ref, const float* got, int n, float tol = 1e-3f) {
    float maxAbs = 0.f, maxRel = 0.f;
    for (int i = 0; i < n; ++i) {
        float diff = fabsf(ref[i] - got[i]);
        maxAbs = fmaxf(maxAbs, diff);
        maxRel = fmaxf(maxRel, diff / fmaxf(1.f, fabsf(ref[i])));
    }
    printf("  最大绝对误差 = %.3e，最大相对误差 = %.3e\n", maxAbs, maxRel);
    return maxRel < tol;
}

int main() {
    printDeviceInfo();

    const int M = 1024, N = 1024, K = 1024;
    const size_t bytesA = (size_t)M * K * sizeof(float);
    const size_t bytesB = (size_t)K * N * sizeof(float);
    const size_t bytesC = (size_t)M * N * sizeof(float);

    // ---------- 1. 准备数据（行主序，和普通 C 数组完全一样） ----------
    std::vector<float> hA((size_t)M * K), hB((size_t)K * N);
    std::mt19937 rng(1234);
    std::uniform_real_distribution<float> dist(-1.f, 1.f);
    for (auto& v : hA) v = dist(rng);
    for (auto& v : hB) v = dist(rng);

    float *dA = nullptr, *dB = nullptr, *dC = nullptr;
    CUDA_CHECK(cudaMalloc(&dA, bytesA));
    CUDA_CHECK(cudaMalloc(&dB, bytesB));
    CUDA_CHECK(cudaMalloc(&dC, bytesC));
    CUDA_CHECK(cudaMemcpy(dA, hA.data(), bytesA, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(dB, hB.data(), bytesB, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemset(dC, 0, bytesC));

    // ---------- 2. 创建句柄 ----------
    // 句柄里保存着 stream、workspace、算法选择等上下文，
    // 创建一次反复使用即可。频繁创建/销毁会带来不必要的开销。
    cublasHandle_t handle = nullptr;
    CUBLAS_CHECK(cublasCreate(&handle));
    CUBLAS_CHECK(cublasSetStream(handle, 0));   // 和 cudaMemcpy 用同一条流

    // ---------- 3. 调用 GEMM ----------
    const float alpha = 1.0f;
    const float beta  = 0.0f;
    CudaTimer timer;

    // 预热一次：第一次调用会包含库内部初始化，不计入正式计时
    CUBLAS_CHECK(cublasSgemm(handle, CUBLAS_OP_N, CUBLAS_OP_N,
                             N, M, K, &alpha,
                             dB, N,     // "A" 传 B，lda = N
                             dA, K,     // "B" 传 A，ldb = K
                             &beta, dC, N));
    CUDA_CHECK_SYNC();

    const int repeat = 10;
    timer.start();
    for (int r = 0; r < repeat; ++r) {
        CUBLAS_CHECK(cublasSgemm(handle, CUBLAS_OP_N, CUBLAS_OP_N,
                                 N, M, K, &alpha,
                                 dB, N, dA, K,
                                 &beta, dC, N));
    }
    float ms = timer.stop() / repeat;

    // ---------- 4. 取回结果并与 CPU 对比 ----------
    std::vector<float> hC((size_t)M * N), hRef((size_t)M * N);
    CUDA_CHECK(cudaMemcpy(hC.data(), dC, bytesC, cudaMemcpyDeviceToHost));

    printf("[cuBLAS] 平均耗时 %.3f ms，等效算力 %.1f GFLOPS\n",
           ms, 2.0 * M * N * K / (ms * 1e-3) / 1e9);

    cpuSgemm(M, N, K, hA.data(), hB.data(), hRef.data());
    bool ok = verify(hRef.data(), hC.data(), M * N);
    printf("  正确性: %s\n", ok ? "通过 ✔" : "失败 ✘");

    // ---------- 5. 收尾 ----------
    CUBLAS_CHECK(cublasDestroy(handle));
    CUDA_CHECK(cudaFree(dA));
    CUDA_CHECK(cudaFree(dB));
    CUDA_CHECK(cudaFree(dC));
    return ok ? EXIT_SUCCESS : EXIT_FAILURE;
}
```

### 2.2 cuBLAS 的 stride 批量接口

完整文件：[`code/lessons/ch07_ecosystem/cublas/cublas_strided_batch.cu`](../code/lessons/ch07_ecosystem/cublas/cublas_strided_batch.cu)

场景：深度学习里"一批样本各做一次全连接"、批量最小二乘等，都是"同一个形状的矩阵乘法要做几百上千次"。逐个调用 `cublasSgemm` 会被 CPU 端的启动开销拖死，`StridedBatched` 只发一次调用，让 GPU 端自己循环。

核心调用（对比 2.1 的 `cublasSgemm`，多了三个 `stride` 参数和一个 `batchCount`）：

```cpp
    const float alpha = 1.f, beta = 0.f;
    // stride 的单位是"元素个数"，不是字节！这是最常见的坑之一。
    const long long strideA = (long long)M * K;   // 第 b 个矩阵相对第 b-1 个的偏移（元素数）
    const long long strideB = (long long)K * N;
    const long long strideC = (long long)M * N;

    cublasSgemmStridedBatched(handle,
                              CUBLAS_OP_N, CUBLAS_OP_N,
                              N, M, K,                          // 同样是 N, M, K
                              &alpha,
                              dB, N, strideB,                   // A 参数 = B
                              dA, K, strideA,                   // B 参数 = A
                              &beta,
                              dC, N, strideC,
                              batch);                           // 批量个数
```

**什么时候用不了 stride 接口？** 当每个小矩阵的大小不一样，或者它们在内存里不是等距排列时。这时有两条路：

1. 用 `cublasSgemmBatched`，它接收一个**指针数组**（`const float**`），可以任意指向；
2. 自己写 kernel —— 如果批量里每个矩阵都很小（比如 4x4），自己写一个"一个 block 算一个矩阵"的 kernel 往往更快（见 [第 5 章](ch05_核心算法模式实战.md)）。

### 2.3 cuFFT：一维 FFT 完整示例

完整文件：[`code/lessons/ch07_ecosystem/cufft/cufft_1d.cu`](../code/lessons/ch07_ecosystem/cufft/cufft_1d.cu)

```cpp
// ============================================================
//  cufft_1d.cu —— 用 cuFFT 做一维复数 FFT，并与朴素 DFT 对拍
//
//  知识点：
//    1) cufftPlan1d / cufftExecC2C 的最小用法
//    2) cufftComplex 就是 float2，内存布局是 (re, im) 交错
//    3) 库的结果到底对不对：用 O(N^2) 的朴素 DFT 在小 N 上验证
// ============================================================

#include <cstdio>
#include <cstdlib>
#include <cmath>
#include <vector>

#include <cufft.h>
#include <cuda_runtime.h>
#include "../common/cuda_check.h"

// 自己定义 pi：MSVC 下 M_PI 需要 _USE_MATH_DEFINES 才可见
static const double kPi = 3.14159265358979323846;

#define CUFFT_CHECK(expr)                                                        \
    do {                                                                         \
        cufftResult _r = (expr);                                                 \
        if (_r != CUFFT_SUCCESS) {                                               \
            fprintf(stderr, "\n[CUFFT ERROR] %s:%d\n  call : %s\n  code : %d\n", \
                    __FILE__, __LINE__, #expr, (int)_r);                         \
            exit(EXIT_FAILURE);                                                  \
        }                                                                        \
    } while (0)

// 填充输入：一个"双频正弦波"，方便肉眼看出频谱峰值
__global__ void fillSignal(cufftComplex* x, int n, float f1, float f2) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;                 // 线程数通常多于数据量，必须边界检查
    float t = (float)i / (float)n;
    float v = sinf(2.0f * 3.14159265f * f1 * t)
            + 0.5f * sinf(2.0f * 3.14159265f * f2 * t);
    x[i].x = v;      // 实部
    x[i].y = 0.f;    // 虚部：实数信号虚部为 0
}

// CPU 朴素 DFT：O(N^2)，只用来在小 N 上验证 cuFFT
// X[k] = sum_n x[n] * exp(-2*pi*i*k*n/N)
static void naiveDFT(const std::vector<cufftComplex>& in,
                     std::vector<cufftComplex>& out, int n) {
    for (int k = 0; k < n; ++k) {
        double re = 0.0, im = 0.0;
        for (int j = 0; j < n; ++j) {
            double ang = -2.0 * kPi * (double)k * (double)j / (double)n;
            double c = cos(ang), s = sin(ang);
            re += (double)in[j].x * c - (double)in[j].y * s;
            im += (double)in[j].x * s + (double)in[j].y * c;
        }
        out[k].x = (float)re;
        out[k].y = (float)im;
    }
}

int main() {
    printDeviceInfo();
    const int N = 1024;      // 小尺寸：朴素 DFT 只有百万次运算，瞬间完成

    // ---------- 1. 建 plan ----------
    // plan 里保存了旋转因子表、分解方案等，属于"昂贵的准备工作"。
    // 数据形状不变时，建一次 plan，反复 cufftExec。
    cufftHandle plan = 0;
    CUFFT_CHECK(cufftPlan1d(&plan, N, CUFFT_C2C, 1));   // 1 = 批量个数

    // ---------- 2. 分配设备内存并填充 ----------
    cufftComplex* d_in = nullptr;
    cufftComplex* d_out = nullptr;
    CUDA_CHECK(cudaMalloc(&d_in, N * sizeof(cufftComplex)));
    CUDA_CHECK(cudaMalloc(&d_out, N * sizeof(cufftComplex)));

    const int block = 256;
    fillSignal<<<(N + block - 1) / block, block>>>(d_in, N, 5.0f, 23.0f);
    CUDA_CHECK_KERNEL();

    // ---------- 3. 执行变换 ----------
    // cufftExecC2C 默认是异步的（和 kernel 一样），
    // 计时/取回结果前必须同步。
    CUFFT_CHECK(cufftExecC2C(plan, d_in, d_out, CUFFT_FORWARD));
    CUDA_CHECK_SYNC();

    // ---------- 4. 取回并验证 ----------
    std::vector<cufftComplex> hIn(N), hOut(N), hRef(N);
    CUDA_CHECK(cudaMemcpy(hIn.data(), d_in, N * sizeof(cufftComplex), cudaMemcpyDeviceToHost));
    CUDA_CHECK(cudaMemcpy(hOut.data(), d_out, N * sizeof(cufftComplex), cudaMemcpyDeviceToHost));

    naiveDFT(hIn, hRef, N);

    float maxRel = 0.f;
    for (int k = 0; k < 64; ++k) {
        float dr = fabsf(hOut[k].x - hRef[k].x);
        float di = fabsf(hOut[k].y - hRef[k].y);
        float mag = fmaxf(1.f, sqrtf(hRef[k].x * hRef[k].x + hRef[k].y * hRef[k].y));
        maxRel = fmaxf(maxRel, fmaxf(dr, di) / mag);
    }
    printf("前 64 个频点与朴素 DFT 的最大相对误差 = %.3e  ->  %s\n",
           maxRel, maxRel < 1e-3f ? "通过 ✔" : "失败 ✘");

    // ---------- 5. 反向变换，应能还原原信号 ----------
    CUFFT_CHECK(cufftExecC2C(plan, d_out, d_out, CUFFT_INVERSE));  // 原地反向
    CUDA_CHECK_SYNC();
    CUDA_CHECK(cudaMemcpy(hOut.data(), d_out, N * sizeof(cufftComplex), cudaMemcpyDeviceToHost));
    // cuFFT 的正/反变换都不带 1/N 归一化，所以要在外面自己除
    float maxErr = 0.f;
    for (int i = 0; i < N; ++i) {
        float re = hOut[i].x / (float)N;
        maxErr = fmaxf(maxErr, fabsf(re - hIn[i].x));
    }
    printf("反变换还原信号的最大绝对误差 = %.3e（记得除以 N）\n", maxErr);

    CUFFT_CHECK(cufftDestroy(plan));
    CUDA_CHECK(cudaFree(d_in));
    CUDA_CHECK(cudaFree(d_out));
    return maxRel < 1e-3f ? EXIT_SUCCESS : EXIT_FAILURE;
}
```

### 2.4 cuRAND：主机端与设备端两种用法

完整文件：[`code/lessons/ch07_ecosystem/curand/curand_host_device.cu`](../code/lessons/ch07_ecosystem/curand/curand_host_device.cu)

cuRAND 有两套完全不同的接口，用途也不同：

| 接口 | 头文件 | 形态 | 适用场景 |
|---|---|---|---|
| **主机端 API** | `<curand.h>` | `curandGenerateUniform(gen, d_ptr, n)` | 一次性生成一大片随机数，之后拿去算 |
| **设备端 API** | `<curand_kernel.h>` | 每个线程持有 `curandState`，在核函数里调用 | 边算边取随机数（蒙特卡洛） |

设备端蒙特卡洛求 π 的核函数：

```cpp
#include <curand.h>
#include <curand_kernel.h>

// ============================================================
//  设备端蒙特卡洛估计圆周率
//  原理：在单位正方形里撒点，落在 1/4 圆内的比例 ≈ pi/4
//  每个线程用不同的 seed，保证互不重复
// ============================================================
__global__ void monteCarloPi(unsigned long long seed, int samplesPerThread,
                             unsigned long long* hits) {
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    // 初始化状态：curand_init(seed, sequence, offset, state)
    // sequence 用 tid 区分线程，offset 用 0 即可
    curandStatePhilox4_32_10_t state;
    curand_init(seed, tid, 0, &state);

    int local = 0;
    for (int i = 0; i < samplesPerThread; ++i) {
        // curand_uniform 返回 (0, 1] 的浮点数
        float x = curand_uniform(&state);
        float y = curand_uniform(&state);
        if (x * x + y * y <= 1.0f) ++local;
    }
    // 每个线程只写一次，用原子加汇总，把争用降到最低
    atomicAdd(hits, (unsigned long long)local);
}
```

主机端 API 的用法：

```cpp
    curandGenerator_t gen;
    // PSEUDO 表示伪随机（可复现），这是做数值实验时的默认选择
    CURAND_CHECK(curandCreateGenerator(&gen, CURAND_RNG_PSEUDO_DEFAULT));
    // 固定种子 = 结果可复现。否则你无法判断"结果变了"
    // 是因为改错了代码还是因为随机性。
    CURAND_CHECK(curandSetPseudoRandomGeneratorSeed(gen, 1234ULL));
    CURAND_CHECK(curandGenerateUniform(gen, d_rand, N));
    CUDA_CHECK_SYNC();      // 别忘了同步
    ...
    CURAND_CHECK(curandDestroyGenerator(gen));   // 生成器也要销毁
```

**两个必须知道的点**：

1. **`curandState` 要单独初始化。** 常见做法是先跑一个 `initStates` kernel 把每个线程的状态建好，再用另一个 kernel 消费它。这样状态可以复用、可以重现。
2. **一个状态不能被多个线程共用。** 那样会得到重复的随机序列，甚至产生竞态。每个线程必须有自己的一份状态，并且 `sequence` 参数要区分开。

### 2.5 Thrust：像写 STL 一样写 GPU 代码

完整文件：[`code/lessons/ch07_ecosystem/thrust/thrust_basics.cu`](../code/lessons/ch07_ecosystem/thrust/thrust_basics.cu)

Thrust 是 header-only 的，编译时**不需要加任何 `-l` 参数**。

```cpp
#include <thrust/device_vector.h>
#include <thrust/host_vector.h>
#include <thrust/sequence.h>
#include <thrust/transform.h>
#include <thrust/reduce.h>
#include <thrust/sort.h>
#include <thrust/count.h>
#include <thrust/execution_policy.h>

// 自定义仿函数（functor）：Thrust 的 transform 拿它做逐元素映射。
// 写成 struct 是因为要同时给 host 和 device 用，
// __host__ __device__ 两个限定符一个都不能少。
struct Saxpy {
    float a;
    Saxpy(float a_) : a(a_) {}
    __host__ __device__ float operator()(float x, float y) const { return a * x + y; }
};

int main() {
    const int N = 1 << 22;

    // host_vector 在 CPU 内存，device_vector 在显存。
    // 构造函数里的赋值会触发一次 H2D 拷贝。
    thrust::host_vector<float> hX(N), hY(N);
    // ... 填充 hX / hY ...
    thrust::device_vector<float> dX = hX;
    thrust::device_vector<float> dY = hY;
    thrust::device_vector<float> dZ(N);

    // ---------- Map ----------
    thrust::transform(dX.begin(), dX.end(), dY.begin(), dZ.begin(), Saxpy(2.0f));

    // ---------- Reduce ----------
    // 加 420 万个 float 会丢精度，所以用 double 做累加器
    double sum = thrust::reduce(thrust::device, dX.begin(), dX.end(),
                                0.0, thrust::plus<double>());

    // ---------- Sort ----------
    // 手写双调排序/基数排序要几百行，这里一行。
    // 库的价值在"排序"这种复杂算法上最明显。
    thrust::device_vector<int> dKeys = hKeys;
    thrust::device_vector<int> dVals = hVals;
    thrust::sort_by_key(dKeys.begin(), dKeys.end(), dVals.begin());

    // ---------- count_if + lambda ----------
    int nNeg = (int)thrust::count_if(thrust::device, dX.begin(), dX.end(),
                                     [] __device__(float v) { return v < 0.f; });
}
```

**Thrust 与手写 kernel 的取舍**：

| 维度 | Thrust | 手写 kernel |
|---|---|---|
| 开发速度 | 极快，一行一个算法 | 慢 |
| 性能 | 通常很好，但一次算法一趟显存 | 可以和相邻计算融合，省掉中间结果的读写 |
| 控制力 | 低（分块策略由库决定） | 完全可控 |
| 组合能力 | 弱：`transform` + `reduce` 是两次 kernel | 强：可以融成一个 |

**最关键的一条**：Thrust 的每一次算法调用 = 至少一次 kernel 启动 + 一次显存读写。所以**把多个 Thrust 调用串起来处理大数组时，中间结果的显存往返往往是真正的瓶颈**。这种情况下自己写一个融合 kernel 会赢。（[第 4 章](ch04_性能分析与优化方法论.md) 讲的 Roofline 模型能帮你判断该不该融合。）

### 2.6 CUB：设备级并行原语

完整文件：[`code/lessons/ch07_ecosystem/cub/cub_primitives.cu`](../code/lessons/ch07_ecosystem/cub/cub_primitives.cu)

Thrust 给你"整个容器上的算法"，CUB 给你"块级/设备级的积木"。当你已经有一个自己的核函数，只想在其中插入一次 device 级归约时，用 CUB 更自然，也更容易控制临时显存。

所有 CUB 设备级原语都是**三步走**：

```cpp
#include <cub/cub.cuh>

    // 1) 先传 nullptr 的临时显存指针，问它"你需要多少字节"
    //    CUB 会走一条"只算需求、不干活"的轻量路径
    size_t tempBytes = 0;
    cub::DeviceReduce::Sum(nullptr, tempBytes, dIn, dOut, N);

    // 2) 按它的答复分配临时显存
    void* dTemp = nullptr;
    CUDA_CHECK(cudaMalloc(&dTemp, tempBytes));

    // 3) 真正调用
    cub::DeviceReduce::Sum(dTemp, tempBytes, dIn, dOut, N);

    // ---- 前缀和：同样的三步 ----
    size_t scanBytes = 0;
    cub::DeviceScan::InclusiveSum(nullptr, scanBytes, dIn, dOut, N);
    void* dScanTemp = nullptr;
    CUDA_CHECK(cudaMalloc(&dScanTemp, scanBytes));
    cub::DeviceScan::InclusiveSum(dScanTemp, scanBytes, dIn, dOut, N);

    // ---- 基数排序：key-value 一起搬 ----
    size_t sortBytes = 0;
    cub::DeviceRadixSort::SortPairs(nullptr, sortBytes, dKeys, dKeysOut,
                                    dVals, dValsOut, M);
    void* dSortTemp = nullptr;
    CUDA_CHECK(cudaMalloc(&dSortTemp, sortBytes));
    cub::DeviceRadixSort::SortPairs(dSortTemp, sortBytes, dKeys, dKeysOut,
                                    dVals, dValsOut, M);

    // 收尾：CUB 不负责释放你申请的临时显存
    CUDA_CHECK(cudaFree(dTemp));
    CUDA_CHECK(cudaFree(dScanTemp));
    CUDA_CHECK(cudaFree(dSortTemp));
```

> **为什么是"两段式 API"？** 因为 CUB 内部会按设备（SM 数量、共享内存大小）和数据类型调整分块策略，临时空间大小只有运行时才知道。这个设计在 CUDA 生态里到处都是（cuSPARSE 的 `bufferSize`、cuDNN 的 `GetWorkspaceSize` 同理）。

CUB 还有一个"块级"API（`cub::BlockReduce`、`cub::BlockScan`），它**不申请任何显存**，直接在你的 kernel 里用共享内存做归约。当你的 kernel 里已经有 `__syncthreads` 结构的树形归约时，换成一个 `BlockReduce` 通常能少写 20 行且更快。

#### 2.7.1 cuSPARSE：CSR 格式的 SpMV

完整文件：[`code/lessons/ch07_ecosystem/cusparse/cusparse_spmv.cu`](../code/lessons/ch07_ecosystem/cusparse/cusparse_spmv.cu)

稀疏矩阵用 **CSR 格式**（Compressed Sparse Row）存储，这是稀疏计算的通用语言：

```
csrRowPtr : 长度为 M+1，第 i 行的非零元在 [csrRowPtr[i], csrRowPtr[i+1])
csrColInd : 每个非零元的列号
csrVal    : 每个非零元的值
```

CUDA 11.0 起推荐用 **generic API**：

```cpp
#include <cusparse.h>

    cusparseHandle_t handle;
    CUSPARSE_CHECK(cusparseCreate(&handle));
    // HOST 模式：alpha/beta 是主机上的普通变量（这是默认值）
    CUSPARSE_CHECK(cusparseSetPointerMode(handle, CUSPARSE_POINTER_MODE_HOST));

    // 描述稀疏矩阵（只说形状和布局，不持有数据）
    cusparseSpMatDescr_t matA;
    CUSPARSE_CHECK(cusparseCreateCsr(&matA, M, M, nnz,
                                     dRowPtr, dColInd, dVal,
                                     CUSPARSE_INDEX_32I, CUSPARSE_INDEX_32I,
                                     CUSPARSE_INDEX_BASE_ZERO, CUDA_R_32F));
    // 描述稠密向量
    cusparseDnVecDescr_t vecX, vecY;
    CUSPARSE_CHECK(cusparseCreateDnVec(&vecX, M, dX, CUDA_R_32F));
    CUSPARSE_CHECK(cusparseCreateDnVec(&vecY, M, dY, CUDA_R_32F));

    // 三步走的工作区
    const float alpha = 1.0f, beta = 0.0f;
    size_t bufferSize = 0;
    CUSPARSE_CHECK(cusparseSpMV_bufferSize(handle, CUSPARSE_OPERATION_NON_TRANSPOSE,
                                           &alpha, matA, vecX, &beta, vecY,
                                           CUDA_R_32F, CUSPARSE_SPMV_ALG_DEFAULT,
                                           &bufferSize));
    void* dBuffer = nullptr;
    if (bufferSize > 0) CUDA_CHECK(cudaMalloc(&dBuffer, bufferSize));

    // 执行
    CUSPARSE_CHECK(cusparseSpMV(handle, CUSPARSE_OPERATION_NON_TRANSPOSE,
                                &alpha, matA, vecX, &beta, vecY,
                                CUDA_R_32F, CUSPARSE_SPMV_ALG_DEFAULT, dBuffer));

    // 销毁描述符和句柄
    CUSPARSE_CHECK(cusparseDestroyDnVec(vecX));
    CUSPARSE_CHECK(cusparseDestroyDnVec(vecY));
    CUSPARSE_CHECK(cusparseDestroySpMat(matA));
    CUSPARSE_CHECK(cusparseDestroy(handle));
```

**SpMV 是典型的内存带宽受限算法**：非零元数量决定访存量，浮点运算极少（每个非零元两次 FLOP）。所以评价它的指标是 **GB/s**，而不是 GFLOPS。如果你的 SpMV 达不到带宽上限的 60%，问题多半在访存模式上。

#### 2.7.2 cuDNN：卷积前向的五个步骤

完整文件：[`code/lessons/ch07_ecosystem/cudnn/cudnn_conv_forward.cu`](../code/lessons/ch07_ecosystem/cudnn/cudnn_conv_forward.cu)（需要安装 cuDNN，链接 `-lcudnn`）

cuDNN 把这套"五步法"体现得最完整，理解它就理解了所有描述符式 API：

```cpp
    // 1) 句柄
    cudnnHandle_t handle;
    CUDNN_CHECK(cudnnCreate(&handle));

    // 2) 描述符：只说"形状"，不持有数据
    cudnnTensorDescriptor_t xDesc, yDesc;
    cudnnFilterDescriptor_t wDesc;
    cudnnConvolutionDescriptor_t convDesc;
    CUDNN_CHECK(cudnnCreateTensorDescriptor(&xDesc));
    CUDNN_CHECK(cudnnSetTensor4dDescriptor(xDesc, CUDNN_TENSOR_NCHW,
                                           CUDNN_DATA_FLOAT, N, C, H, W));
    CUDNN_CHECK(cudnnSetFilter4dDescriptor(wDesc, CUDNN_DATA_FLOAT,
                                           CUDNN_TENSOR_NCHW, K, C, R, S));
    // CROSS_CORRELATION = 深度学习里的"卷积"（不翻转核），别选成 CUDNN_CONVOLUTION
    CUDNN_CHECK(cudnnSetConvolution2dDescriptor(convDesc, padH, padW, strideH, strideW,
                                                dilH, dilW, CUDNN_CROSS_CORRELATION,
                                                CUDNN_DATA_FLOAT));

    // 输出形状让库来算，自己算很容易在 padding/stride 上出错
    int n_out, c_out, h_out, w_out;
    CUDNN_CHECK(cudnnGetConvolution2dForwardOutputDim(convDesc, xDesc, wDesc,
                                                      &n_out, &c_out, &h_out, &w_out));
    CUDNN_CHECK(cudnnSetTensor4dDescriptor(yDesc, CUDNN_TENSOR_NCHW, CUDNN_DATA_FLOAT,
                                           n_out, c_out, h_out, w_out));

    // 3) 让库帮你挑算法（不同算法在显存占用和速度上差别很大）
    cudnnConvolutionFwdAlgoPerf_t perf;
    int returned = 0;
    CUDNN_CHECK(cudnnGetConvolutionForwardAlgorithm_v7(handle, xDesc, wDesc, convDesc,
                                                        yDesc, 1, &returned, &perf));

    // 4) 问算法要多少 workspace
    size_t wsBytes = 0;
    CUDNN_CHECK(cudnnGetConvolutionForwardWorkspaceSize(handle, xDesc, wDesc, convDesc,
                                                        yDesc, perf.algo, &wsBytes));
    void* dWs = nullptr;
    if (wsBytes > 0) CUDA_CHECK(cudaMalloc(&dWs, wsBytes));

    // 5) 执行
    const float alpha = 1.0f, beta = 0.0f;
    CUDNN_CHECK(cudnnConvolutionForward(handle, &alpha, xDesc, dX,
                                        wDesc, dW, convDesc, perf.algo,
                                        dWs, wsBytes, &beta, yDesc, dY));
```

**生产环境的建议**：直接用 **cuDNN Frontend**（header-only 的 C++ 封装）。它把上面这一大堆描述符管理包装成了图（graph）的形式，可读性好得多，而且支持自动调优（autotuning）。上面这份 legacy API 代码的价值在于让你看清"描述符"这个东西的本质。

#### 2.7.3 TensorRT：推理部署

TensorRT 不是"算子库"，而是**整套推理优化器**。你给它一个训练好的模型（ONNX / PyTorch），它做：

1. **层融合**：把 Conv+BN+ReLU 合成一个 kernel，减少显存往返。
2. **精度校准**：把 FP32 量化成 FP16/INT8，配合校准集保证精度损失可控。
3. **kernel 自动调优**：为每一层在候选实现里选最快的。
4. **显存复用**：静态规划整个网络的显存使用，避免反复分配。

使用流程（概念级）：

```
ONNX 模型
   │ ① 构建阶段（离线，只在部署机器上做一次）
   ▼
TensorRT Builder ──► 序列化成 .engine 文件
   │
   │ ② 运行阶段（在线）
   ▼
反序列化 engine ──► 绑定输入输出显存 ──► executeV2() ──► 结果
```

**什么时候需要自己写 TensorRT 插件？** 当模型里有 TensorRT 不认识的算子时。插件就是一个你自己实现的 CUDA kernel，注册到 TensorRT 的算子表里。这时你就回到了本章开头那张决策表的最后一行。

### 2.8 Python 生态衔接

CUDA 的最终用户常常是 Python 用户。有四种典型的"从 Python 到 GPU"的路径，选择取决于你的需求：

| 方式 | 你写什么 | 上手难度 | 性能上限 | 典型用途 |
|---|---|---|---|---|
| **CuPy** | NumPy 风格调用 | ★ | 库级（就是 cuBLAS/cuFFT） | 替换 NumPy 做科学计算 |
| **Numba `@cuda.jit`** | Python 写的 CUDA kernel | ★★ | 接近手写 C++ | 快速原型、中等复杂度 kernel |
| **PyTorch C++ 扩展** | 真正的 `.cu` 文件 | ★★★ | 完全可控 | 生产级自定义算子 |
| **Triton** | Python 的块级 DSL | ★★ | 接近 cuBLAS（深度学习算子） | 融合算子、注意力等 |

#### 2.8.2 Numba

完整文件：[`code/lessons/ch07_python/numba_saxpy.py`](../code/lessons/ch07_python/numba_saxpy.py)

```python
from numba import cuda
import numpy as np

@cuda.jit
def saxpy_kernel(x, y, a, n):
    i = cuda.grid(1)          # 等价于 blockIdx.x * blockDim.x + threadIdx.x
    if i < n:                 # 边界检查：线程数通常多于元素数
        y[i] = a * x[i] + y[i]

d_x = cuda.to_device(x)       # 显式搬到显存，自己控制何时搬
d_y = cuda.to_device(y)
threads = 256
blocks = (n + threads - 1) // threads
saxpy_kernel[blocks, threads](d_x, d_y, np.float32(2.5), n)
cuda.synchronize()            # 和 CUDA C 一样：异步，必须同步才能取结果
```

**两个坑**：
1. 第一次调用会触发 JIT 编译，可能耗时几百毫秒到几秒。**测性能前必须预热。**
2. `cuda.synchronize()` 不能省，否则你测到的是"下发命令的时间"。

Numba 和 CuPy 可以通过 `__cuda_array_interface__` 协议**零拷贝共享显存**（`numba.cuda.as_cuda_array(cupy_array)`），非常方便。

**`vector_add_cuda.cu`**（关键部分，完整文件：[`code/lessons/ch07_python/torch_ext/vector_add_cuda.cu`](../code/lessons/ch07_python/torch_ext/vector_add_cuda.cu)）：

```cpp
#include <torch/extension.h>
#include <cuda_runtime.h>
#include <c10/cuda/CUDAException.h>

__global__ void vectorAddKernel(const float* __restrict__ a,
                                const float* __restrict__ b,
                                float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = a[i] + b[i];   // 越界检查不能省
}

torch::Tensor vectorAdd(torch::Tensor a, torch::Tensor b) {
    // TORCH_CHECK 检查失败会抛异常，比段错误友好得多
    TORCH_CHECK(a.is_cuda() && b.is_cuda(), "输入必须是 CUDA 张量");
    TORCH_CHECK(a.scalar_type() == torch::kFloat32 &&
                b.scalar_type() == torch::kFloat32, "只支持 float32");
    TORCH_CHECK(a.sizes() == b.sizes(), "两个张量形状必须一致");

    // contiguous()：本来就是连续的张量不会拷贝，只返回自身，
    // 所以这是"零成本的安全网"。忘了它就会读到错误的数据。
    auto a_c = a.contiguous();
    auto b_c = b.contiguous();
    auto out = torch::empty_like(a_c);

    const int n = (int)a_c.numel();
    const int threads = 256;
    const int blocks = (n + threads - 1) / threads;

    // 用当前流，这样自动兼容 torch.cuda.stream(...) 的流语义
    vectorAddKernel<<<blocks, threads, 0, at::cuda::getCurrentCUDAStream()>>>(
        a_c.data_ptr<float>(), b_c.data_ptr<float>(), out.data_ptr<float>(), n);

    C10_CUDA_KERNEL_LAUNCH_CHECK();   // 早检查早发现
    return out;
}

PYBIND11_MODULE(TORCH_EXTENSION_NAME, m) {
    m.def("vector_add", &vectorAdd, "向量加法 (CUDA)，c = a + b");
}
```

构建与使用：

```bash
python setup.py build_ext --inplace
python test_ext.py
```

**三个最容易踩的坑**（都写在代码注释里了）：

| 坑 | 后果 | 解法 |
|---|---|---|
| 忘了 `.contiguous()` | 对非连续张量算出错误结果 | 在 C++ 入口统一 `contiguous()` |
| 用了默认流而不是当前流 | 和 PyTorch 其它算子乱序，出现玄学 bug | `at::cuda::getCurrentCUDAStream()` |
| 没做 `C10_CUDA_KERNEL_LAUNCH_CHECK()` | kernel 里的错误延迟到很久以后才爆出来，极难定位 | 启动后立刻检查 |

#### 2.8.4 Triton（了解）

完整文件：[`code/lessons/ch07_python/triton_demo.py`](../code/lessons/ch07_python/triton_demo.py)

Triton 的心智模型和 CUDA C 完全不同：

```
CUDA C  : 线程 -> 元素      （你管 threadIdx、共享内存、__syncthreads）
Triton  : 程序 -> 数据块     （你只管块内的向量化运算，其余交给编译器）
```

```python
@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n_elements, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(axis=0)              # 这是第几个"程序实例"（≈ block）
    offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements              # 掩码 ≈ CUDA 里的 if (i < n)
    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(out_ptr + offsets, x + y, mask=mask)
```

**要不要学 Triton？** 建议：先把 CUDA C 学扎实（你现在正在做的事），再按需学 Triton。Triton 在深度学习算子上效率极高，但它把"线程映射/共享内存/同步"这三件最费脑的事交给了编译器，代价是你失去了对硬件细节的完全控制 —— 而恰恰是这些细节，是你在 [第 2 章](ch02_内存层次与访存优化.md) 和 [第 4 章](ch04_性能分析与优化方法论.md) 里学到的东西。

#### 2.9.2 `__CUDACC__` 条件编译与 CPU 回退

**核心技巧**：让**同一份 `.cpp` 源码**在"有 CUDA"时被 `nvcc` 编译、在"没 CUDA"时被普通 C++ 编译器编译。

[`code/projects/cmake_skeleton/src/gemm_api.cpp`](../code/projects/cmake_skeleton/src/gemm_api.cpp)（结构示意）：

```cpp
#include "gemm.h"

// ------------------------------------------------------------
// 第一部分：CPU 实现。任何编译器都必须能编译这一段。
// ------------------------------------------------------------
void sgemmCPU(int M, int N, int K, const float* A, const float* B, float* C) {
    // 朴素三重循环：慢，但它是"正确性基准"，必须无条件可用
    for (int i = 0; i < M; ++i)
        for (int j = 0; j < N; ++j) {
            float acc = 0.f;
            for (int k = 0; k < K; ++k) acc += A[i * K + k] * B[k * N + j];
            C[i * N + j] = acc;
        }
}

// ============================================================
// 第二部分：GPU 实现。只有 nvcc 会进来编译。
// __CUDACC__ 是 nvcc 会自动定义的宏，这就是"条件编译"的开关。
// ============================================================
#ifdef __CUDACC__
#include <cuda_runtime.h>

template <int TILE>
__global__ void tileSgemmKernel(int M, int N, int K,
                                const float* __restrict__ A,
                                const float* __restrict__ B,
                                float* __restrict__ C) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];
    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;

    float acc = 0.f;
    for (int t = 0; t < (K + TILE - 1) / TILE; ++t) {
        // 越界时填 0，而不是直接 return：
        // 因为块内所有线程都要参与 __syncthreads，提前退出会造成死锁
        As[ty][tx] = (row < M && t * TILE + tx < K) ? A[row * K + t * TILE + tx] : 0.f;
        Bs[ty][tx] = (col < N && t * TILE + ty < K) ? B[(t * TILE + ty) * N + col] : 0.f;
        __syncthreads();
        for (int k = 0; k < TILE; ++k) acc += As[ty][k] * Bs[k][tx];
        __syncthreads();
    }
    if (row < M && col < N) C[row * N + col] = acc;
}

void sgemmGPU(int M, int N, int K, const float* A, const float* B, float* C) {
    // ... cudaMalloc / cudaMemcpy / 启动 kernel / 取回结果 ...
}

bool gpuAvailable() {
    int count = 0;
    if (cudaGetDeviceCount(&count) != cudaSuccess) return false;
    return count > 0;
}

const char* backendName() { return "CUDA (GPU)"; }

// ============================================================
// 第三部分：没有 CUDA 编译器时，接口仍然要存在，只是退回 CPU。
// ============================================================
#else

void sgemmGPU(int M, int N, int K, const float* A, const float* B, float* C) {
    // 静默退化会让人误以为"GPU 跑了但很慢"，所以这里必须给出提示
    fprintf(stderr, "[提示] 本二进制未编译 CUDA 支持，sgemmGPU 退回 CPU 实现\n");
    sgemmCPU(M, N, K, A, B, C);
}

bool gpuAvailable() { return false; }
const char* backendName() { return "CPU (无 CUDA 编译器)"; }

#endif  // __CUDACC__
```

#### 2.9.4 数值正确性的单元测试

完整文件：[`code/projects/cmake_skeleton/tests/test_gemm.cpp`](../code/projects/cmake_skeleton/tests/test_gemm.cpp)

不依赖任何测试框架也能写出有用的测试。核心是四条纪律：

```cpp
#include "gemm.h"
#include <cstdio>
#include <cmath>
#include <vector>
#include <random>

static int g_failed = 0;

static void checkShape(int M, int N, int K) {
    std::vector<float> A((size_t)M * K), B((size_t)K * N);
    std::vector<float> C1((size_t)M * N), C2((size_t)M * N, 0.f);

    // 纪律 1：固定种子 -> 同一组输入永远复现同一个失败
    std::mt19937 rng(M * 1000003u + N * 1009u + K);
    std::uniform_real_distribution<float> dist(-1.f, 1.f);
    for (auto& v : A) v = dist(rng);
    for (auto& v : B) v = dist(rng);

    sgemmCPU(M, N, K, A.data(), B.data(), C1.data());
    sgemmGPU(M, N, K, A.data(), B.data(), C2.data());

    // 纪律 2：用相对误差，绝不用 ==
    float maxRel = 0.f;
    for (size_t i = 0; i < C1.size(); ++i)
        maxRel = std::fmax(maxRel, std::fabs(C1[i] - C2[i]) / std::fmax(1.f, std::fabs(C1[i])));

    const char* mark = maxRel < 1e-3f ? "PASS" : "FAIL";
    if (maxRel >= 1e-3f) ++g_failed;
    printf("[%s] M=%d N=%d K=%d  最大相对误差 = %.3e\n", mark, M, N, K, maxRel);
}

int main() {
    printf("=== gemm 单元测试 ===\n");
    // 纪律 3：覆盖边界。这些用例往往比大矩阵测试更早发现 bug
    checkShape(1, 1, 1);        // 最小规模：最容易暴露索引写死的问题
    checkShape(16, 16, 16);     // 正好一个 tile
    checkShape(17, 31, 33);     // 非整除：验证边界处理
    checkShape(64, 64, 1);      // K=1 退化成外积
    checkShape(100, 128, 96);   // 不规则形状
    printf("=== %s ===\n", g_failed == 0 ? "全部通过" : "存在失败用例");
    // 纪律 4：返回非零退出码，让 CI 能自动发现问题
    return g_failed == 0 ? 0 : 1;
}
```

#### 2.9.5 性能测试框架的写法

性能测量比正确性测量更容易出错。一个可信的测量函数必须做四件事：

```cpp
// 1) 预热：第一次启动包含模块加载、上下文初始化、算法选择等一次性开销
for (int i = 0; i < warmup; ++i) launch();
cudaDeviceSynchronize();

// 2) 多次测量，每次都单独计时
std::vector<float> times;
for (int i = 0; i < repeat; ++i) {
    timer.start();
    launch();
    times.push_back(timer.stop());     // CudaTimer::stop 里已经同步了
}

// 3) 排序后取中位数（比均值更抗离群点）
std::sort(times.begin(), times.end());
float median = times[times.size() / 2];

// 4) 同时报告最小值：噪声只会让耗时变大，所以 min 最接近"纯计算"时间
float best = times.front();
```

再加一条**纪律**：**同一个结论至少要测两个不同的尺寸**。只在 1024³ 上得出的"v7 比 v5 快"很可能在 512³ 上就反过来了（流水线序言开销占比变高）。

#### 2.9.6 工程目录组织建议

一个有一定规模的 CUDA 项目，推荐这样组织：

```
myproject/
├── CMakeLists.txt
├── cmake/                      # 自定义 CMake 模块（如 FindXXX.cmake）
├── include/myproject/          # 对外头文件（不含 CUDA 语法！）
│   └── api.h
├── src/
│   ├── cpu/                    # CPU 后端
│   ├── cuda/                   # CUDA 后端（.cu 全在这里）
│   │   ├── kernels/
│   │   └── cuda_backend.cpp
│   └── common/                 # 跨后端共享的工具
├── tests/                      # 单元测试 + 数值对拍
├── benchmarks/                 # 性能测试（独立目标，不进默认构建）
├── examples/                   # 最小可运行示例
├── docs/
└── third_party/
```

三条经验：

1. **`.cu` 文件集中放在一个目录里。** 这样一眼就能知道"哪些代码依赖 CUDA"。
2. **对外头文件里绝不出现 `__global__` / `float4` / `cudaMalloc`。** 一旦出现，就永远无法编译到没有 CUDA 的平台上。
3. **benchmarks 用独立的目标（`add_executable` + 不进 `all`）。** 基准测试不该拖慢日常构建。

## 3. 代码逐行解析

### 3.1 `cublasSgemm` 的九个参数逐个拆

```
cublasSgemm(handle, opA, opB, m, n, k, alpha, A, lda, B, ldb, beta, C, ldc)
```

| 位置 | 参数 | 含义 | 我们的值（行主序 MxNxK） |
|---|---|---|---|
| 1 | `handle` | 句柄，携带 stream 和上下文 | `handle` |
| 2 | `opA` | 对 A_cb 是否转置 | `CUBLAS_OP_N`（不转置） |
| 3 | `opB` | 对 B_cb 是否转置 | `CUBLAS_OP_N` |
| 4 | `m` | C_cb 的行数 = A_cb 的行数 | `N` |
| 5 | `n` | C_cb 的列数 = B_cb 的列数 | `M` |
| 6 | `k` | 公共维度 | `K` |
| 7 | `alpha` | 缩放系数（**主机指针**） | `&alpha` |
| 8 | `A` | A_cb 的指针 | `dB` |
| 9 | `lda` | A_cb 的前导维度 | `N` |
| 10 | `B` | B_cb 的指针 | `dA` |
| 11 | `ldb` | B_cb 的前导维度 | `K` |
| 12 | `beta` | C 的缩放系数（**主机指针**） | `&beta` |
| 13 | `C` | C_cb 的指针 | `dC` |
| 14 | `ldc` | C_cb 的前导维度 | `N` |

六条必须记住的规则：

1. **`alpha` / `beta` 传的是指针，不是值。** 因为默认的指针模式是 host，所以传 `&alpha` 即可；如果设成 device 模式，就得传设备指针。
2. **`m` / `n` 是"输出矩阵"的维度**，`k` 是收缩维度。
3. **`beta = 0` 时，语义上是 `C := alpha*A*B`，但 cuBLAS 不保证不读 C 的旧值。** 有些实现会先读后写。所以如果你不想让 NaN/Inf 从旧的 C 传播进来，**要么先 `cudaMemset` 清零，要么确保 C 里没有脏数据**。这是很多人"结果里出现 NaN"的原因。
4. **`lda >= max(1, m)` 是硬性要求**（不转置时）。`lda` 可以大于 `m`（比如你只用了大矩阵的一个子块），但不能小于。
5. **行主序下 `lda` 等于"一行有多少个元素"**，这是最好记的口诀。
6. **默认流要显式设置。** 如果你在别的 stream 上做拷贝，却让 cuBLAS 在 stream 0 上算，就会出现"结果还没算完就被拷走"的竞态。用 `cublasSetStream` 对齐。

### 3.2 cuFFT 代码里的三个关键点

1. **`cufftPlan1d(&plan, N, CUFFT_C2C, 1)` 的最后一个参数是"批量个数"。** 做批量 FFT 时把它设成 batch，数据按 `[batch][N]` 连续排列即可，比循环调用快得多。
2. **`cufftExecC2C` 是异步的。** 计时和 `cudaMemcpy` 之前必须 `cudaDeviceSynchronize()` 或 `cufftDestroy`（它内部会同步）。
3. **正/反变换都不带 `1/N` 归一化。** `FFT(FFT⁻¹(x)) = N·x`。所以反变换之后要自己除以 N。这是信号处理里最容易忘的一步，忘了会得到比原信号大 N 倍的结果。

### 3.3 CUB 的"问一次再分配"为什么要这样写

```cpp
cub::DeviceReduce::Sum(nullptr, tempBytes, dIn, dOut, N);
```

当临时指针传 `nullptr` 时，CUB 走一条只计算临时空间需求、不实际执行计算的路径。所以在循环里这样写是安全的（不会真的算一遍）。这也意味着**不要在两次调用之间改变 `N` 或数据类型**，否则第一次问出来的 `tempBytes` 就不对了。

### 3.4 Thrust 的 `device_vector` 为什么不能随便按下标访问

```cpp
thrust::device_vector<float> dX = hX;
dX[0] = 42.f;    // 这一句会触发一次 D2H 拷贝 + 一次 H2D 拷贝！
```

`device_vector::operator[]` 返回的是一个代理对象（`thrust::device_reference`），它内部会：
1. 把那个元素从显存拷到主机；
2. 你可能修改它；
3. 再把整个元素拷回显存。

所以"在循环里按下标访问 `device_vector`"是一个经典的性能灾难。**只在调试和初始化时偶尔用一下**，正式代码里用 `thrust::transform` / `thrust::copy` / `raw_pointer_cast`。

### 3.5 CMake 里 `set_source_files_properties(... LANGUAGE CUDA)` 的作用

默认情况下 CMake 按扩展名决定用哪个编译器：`.cu` 给 nvcc，`.cpp` 给 C++ 编译器。而我们的 `gemm_api.cpp` 需要在有 CUDA 时用 nvcc 编译（这样 `__CUDACC__` 才会被定义），所以必须显式改它的 `LANGUAGE` 属性。

**注意**：源文件属性是在 generate 阶段生效的，所以写在 `add_library` 之后也没问题。但如果同一个文件被两个 target 以不同语言使用，就会打架 —— 那种情况下应该老老实实拆成两个文件。

### [挑战] 练习 5：写一个 PyTorch 自定义 CUDA 扩展

实现一个"按行做 softmax"的 CUDA 扩展：

- 输入：形状 `(rows, cols)` 的 float32 CUDA 张量，`cols` 在 1 到 8192 之间；
- 输出：同形状，每行 softmax；
- 必须处理"`cols` 不是 32 的倍数"的情况；
- 用 `torch.softmax(x, dim=1)` 对拍，误差阈值 `1e-5`；
- 性能目标：在 `rows=4096, cols=1024` 上，做到 `torch.softmax` 的 **70% 以上**。

**难点提示**：一行可能有 8192 个元素，一个线程块装不下。你需要按 `cols` 大小分两种情况：
- `cols` 较小（能放进 48KB 共享内存）：一行一个块，用共享内存做两遍扫描（求 max，再求 sum/exp）；
- `cols` 很大：用"一个 warp 处理一行"的 warp 级归约策略。

另外要注意**数值稳定性**：先减最大值再取 exp（`exp(x - max)`），否则 `exp(1000)` 会溢出成 Inf。

### [挑战] 练习 6：判断该用库还是该自己写

下面 6 个需求，分别写出你的选择和理由（每个不超过 3 句话）：

1. 一个形状为 `(512, 512)` 的矩阵求逆。
2. 在一个已经写好的卷积 kernel 里，统计输出中大于阈值的元素个数。
3. 对 10 亿个 `uint32` 做基数排序。
4. 计算 `y = tanh(Wx + b)`，其中 Wx 是一个 GEMM。
5. 一个只有 8 个元素的数组求和，被调用 100 万次。
6. 对一批 1 万个 3x3 矩阵做批量求逆。

**参考答案要点**：

1. 用 **cuSOLVER**（`cusolverDnSgetrf` + `cusolverDnSgetrs`，或直接 `cusolverDnSmatinv`）。自己写 LU 分解费力不讨好。
2. 用 **CUB 的 `DeviceReduce::Sum`** 配合一个判断仿函数，或者用 `cub::BlockReduce` 直接在 kernel 里做。别为了统计再读一遍显存。
3. 用 **CUB 的 `DeviceRadixSort`**。10 亿个 `uint32` 的基数排序，库版本会做多趟、多流流水，手写很难追上。
4. 用 **cuBLAS 做 GEMM + 自己写一个融合的 epilogue kernel**。注意 GEMM 的输出 `(M, N)` 和偏置的广播维度要对上；如果性能还不够，考虑 cuBLASLt 的 epilogue。
5. **自己写**，而且应该把 100 万次调用**批量化**成一次 kernel。单次启动一个 kernel 去加 8 个数，99.9% 的时间花在启动开销上。
6. **自己写**。cuBLAS 的批量接口不支持"每个矩阵求逆"；而 1 万个 3x3 求逆适合"一个 block 处理一个矩阵"或者"一个线程处理一个矩阵"（3x3 完全可以在寄存器里做完）。

## 6. 常见错误与排查

| 错误信息 / 现象 | 原因 | 解决办法 |
|---|---|---|
| 结果看起来是"转置过的" | 忘了 cuBLAS 是列主序，或者只交换了指针没交换 `m`/`n` | 回看 1.6 节，确认 `m=N, n=M, lda=N, ldb=K, ldc=N` 且 A/B 指针交换 |
| `CUBLAS_STATUS_INVALID_VALUE` | `lda` 小于 `m`，或维度为负 | 检查 `lda >= max(1,m)`、`ldb >= max(1,k)`、`ldc >= max(1,m)` |
| `CUBLAS_STATUS_NOT_INITIALIZED` | 忘了 `cublasCreate(&handle)`，或句柄在别的线程里 | 每个线程用自己的句柄，或创建后再用 |
| 结果里出现 NaN/Inf，但输入是干净的 | `beta=0` 时 C 里有脏数据（cuBLAS 不保证不读它） | 调用前 `cudaMemset(dC, 0, ...)` |
| 误差在 1e-3 量级（而不是 1e-6） | 在 CC 8.0+ 上，cuBLAS 可能用 TF32 张量核心算 FP32 GEMM | 需要严格 FP32 时用 `cublasSetMathMode(handle, CUBLAS_PEDANTIC_MATH)`；只做验证时可接受则放宽容差到 1e-2 |
| `libcublas.so: cannot open shared object file` | 运行时的库找不到 | `export LD_LIBRARY_PATH=/usr/local/cuda/lib64:$LD_LIBRARY_PATH`；Windows 下把 CUDA 的 `bin` 加进 `PATH` |
| `undefined reference to cublasCreate` | 忘了 `-lcublas` | 加 `-lcublas`（顺序放在源文件之后） |
| `CUFFT_INVALID_SIZE` | `cufftPlan1d` 的 N 参数不合理（如 0 或超大素数） | N 最好能分解成 2/3/5/7 的乘积；纯大素数会退化得很慢 |
| FFT 反变换结果比原信号大 N 倍 | 忘了除归一化因子 | 反变换后除以 N |
| cuRAND 生成的随机数有重复片段 | 多个线程共用了同一个 `curandState`，或 `sequence` 参数一样 | 每个线程一份状态，`curand_init(seed, tid, 0, &state)` |
| `curandGenerateUniform` 之后取到的数据是旧的 | 忘了同步（cuRAND 也是异步的） | 取数据前 `cudaDeviceSynchronize()` |
| Thrust 程序编译报一大堆模板错误 | 忘了 `#include <thrust/execution_policy.h>`，或仿函数缺 `__device__` | 逐条看第一条错误；仿函数必须同时标 `__host__ __device__` |
| `device_vector` 的循环非常慢 | 按下标访问触发了逐元素的 H2D/D2H 拷贝 | 改用 `thrust::transform` / `raw_pointer_cast` |
| CUB 报 `temp_storage_bytes` 不匹配 / 结果错乱 | 两次调用之间改变了 `N` 或数据类型 | 形状变化时重新执行"问一次"的步骤 |
| `cudaErrorInvalidDeviceFunction` 或运行时报"no kernel image is available" | 编译的 arch 和显卡不匹配 | 用 `-arch=native`，或显式指定显卡架构 |
| CMake 报 `No CMAKE_CUDA_COMPILER could be found` | nvcc 不在 PATH 里 | 安装 CUDA Toolkit 或 `export PATH=/usr/local/cuda/bin:$PATH` |
| CMake 报 `Unsupported gpu architecture 'compute_native'` | CMake 版本低于 3.24 | 改成显式架构：`-DCMAKE_CUDA_ARCHITECTURES=75` |
| `__CUDACC__` 分支没生效，`sgemmGPU` 直接调了 CPU | 忘了 `set_source_files_properties(... LANGUAGE CUDA)` | 在 `CMakeLists.txt` 里加上这一句 |
| nvcc 报 `-Xptxas -v` 参数错误 | 在 CMake 里把两个参数写成了一个带空格的字符串 | 写成 `-Xptxas=-v` |
| PyTorch 扩展编译时找不到 `torch/extension.h` | `setup.py` 里没导入 `torch`，或 PyTorch 未安装 | `import torch` 在 `setup.py` 顶部，并确保 PyTorch 与 CUDA 版本匹配 |
| 扩展对非连续张量算错 | 忘了 `.contiguous()` | 在 C++ 入口统一 `contiguous()`；用 `test_ext.py` 里的切片用例自测 |
| 扩展里的错误延迟很久才报出来 | 没做 `C10_CUDA_KERNEL_LAUNCH_CHECK()` | 每次启动 kernel 后立即检查 |
| 同样的程序换了张卡性能差一倍 | 没设 arch，或者卡本身差一倍 | 用 `-arch=native` 重编；报告里必须写明 GPU 型号 |

## 7. 本章小结

### 7.1 要点清单

1. **优先用库。** 只有三类情况才自己写：库没覆盖的算子、需要把多个算子融合、有特殊的布局/精度需求。
2. **所有 CUDA 库都是同一套五步法**：创建句柄 → 创建描述符 → 查询工作区 → 执行 → 销毁。学一次，到处用。
3. **cuBLAS 是列主序的。** 行主序数据要算 `C = A*B`，就把 A、B 指针交换、`m`/`n` 交换、`lda=N, ldb=K, ldc=N`。这是本章最重要的知识点。
4. **`lda` 就是"按行主序看，一行有多少个元素"。**
5. **库调用是异步的。** 计时和取结果之前必须同步。
6. **cuFFT 正反变换都不带 `1/N`。** 反变换后要自己除。
7. **cuRAND 有两种接口**：主机端批量生成、设备端每线程一个状态。`curandState` 不能跨线程共享。
8. **Thrust 一行一个算法，但每次调用至少一趟显存往返。** 需要融合时自己写。
9. **CUB 是"已经写好 kernel 之后往里插原语"的最佳选择。** 记住"问一次再分配"的两段式套路。
10. **工程化的三条纪律**：接口与实现分离、CPU 回退可编译、核心 kernel 必须有自动化测试。
11. **测试要固定种子、覆盖边界、用相对误差、返回退出码。**
12. **性能测量必须预热 + 多次 + 取中位数**，并且在同一台机器上对比。
13. **跨平台靠"抽象出计算接口层"**，而不是"写一次到处跑"。
14. **在纯访存算子上，自己写不会比 PyTorch 快。** 这不是水平问题，是带宽上限。
15. **不要编造性能数字。** 报告里永远写清楚"在哪张卡、哪个形状、什么编译参数"。

### 7.2 自检问题（附答案要点）

**Q1：什么情况下你会放弃 cuBLAS 自己写 GEMM？**
A：当 GEMM 只是整个计算链中的一步，而它的输出需要立刻被另一个算子消费时 —— 这时把两步融合成一个 kernel，省掉中间结果的一次写 + 一次读，收益往往超过 cuBLAS 本身的性能优势。另外，特殊的稀疏结构或极小的批量矩阵也是自己写的理由。

**Q2：`cublasSgemm(handle, CUBLAS_OP_N, CUBLAS_OP_N, N, M, K, &alpha, B, N, A, K, &beta, C, N)` 里为什么是 `N, M, K` 而不是 `M, N, K`？**
A：因为行主序的 `A(MxK)` 被 cuBLAS 按列主序解读成了 `Aᵀ(KxM)`。要计算 `C = A·B` 就变成计算 `Cᵀ = Bᵀ·Aᵀ`，即一个 `(N×M) = (N×K)·(K×M)` 的列主序 GEMM，所以 `m=N, n=M, k=K`，且第一个矩阵指针传 `B`、`lda=N`。

**Q3：`lda` 是什么？行主序数据喂给 cuBLAS 时它等于什么？**
A：leading dimension，"同一列中相邻元素相隔多少个元素"。行主序数据喂给 cuBLAS 时，它等于"这一行有多少个元素"。

**Q4：为什么 CUB 要先传 `nullptr` 问一次临时显存大小？**
A：因为 CUB 会根据设备（SM 数、共享内存大小）和数据规模动态决定分块策略，临时空间大小只有运行时才知道。

**Q5：cuFFT 反变换后为什么要除以 N？**
A：cuFFT 的正变换和反变换都不带归一化因子，`IFFT(FFT(x)) = N·x`。所以反变换后要除以 N 才能还原。

**Q6：Thrust 的 `sort` 和 CUB 的 `DeviceRadixSort` 该选哪个？**
A：要排 `key-value` 对、key 是整数/浮点这类可以按位比较的类型，优先 `DeviceRadixSort`（它是非比较排序，`O(n)` 趟数很少）。需要自定义比较器、或者数据量不大且类型不适合基数排序，用 Thrust 的 `sort`。

**Q7：怎样让一个 CUDA 工程在没有 GPU 的机器上也能编译？**
A：三步：① 用 `check_language(CUDA)` 检测而不是直接 `enable_language(CUDA)`；② 把 GPU 代码放在 `#ifdef __CUDACC__` 里，并提供 CPU 回退实现；③ 用 `set_source_files_properties(... LANGUAGE CUDA)` 让同一份源码在两种情况下交给不同编译器。

**Q8：为什么"在循环里按下标访问 `device_vector`"是性能灾难？**
A：`operator[]` 返回代理对象，每次访问都会触发一次显存 → 主机的拷贝（以及可能的回写）。应该用 `transform`/`copy`/`raw_pointer_cast` 批量处理。

**Q9：性能测试为什么必须预热，并且要测多次取中位数？**
A：第一次启动包含模块加载、上下文初始化、算法选择等一次性开销，不代表稳态性能；单次测量受系统噪声影响大，中位数比均值更抗离群点。

**Q10：一个 TensorRT 不支持的算子，你要怎么处理？**
A：写一个 TensorRT 插件（Plugin）：实现自定义 CUDA kernel + 注册到 TensorRT 的算子表里。本质上就是回到"自己写 kernel"，只是接口规则由 TensorRT 定义。
