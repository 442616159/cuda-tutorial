## 0. 本章导读

### 0.1 学完这一章你能做什么

前四章你学会了「怎么在 GPU 上写正确的代码」和「怎么让它变快」。这一章解决的是**迁移问题**：拿到一个从没见过的问题，你能不能一眼看出它属于哪一类并行模式，然后用已经验证过的套路把它写出来？

学完本章，你将能够：

1. **给任意一个问题归类**：它是 Map、Reduce、Scan、Scatter/Gather 还是 Stencil？归类决定了线程怎么映射、内存怎么布局、优化往哪使劲。
2. **写出接近带宽峰值的归约**：从交错寻址一路改到 warp shuffle，并说清楚每一步「原来慢在哪、为什么能变快、怎么用数据证明」。
3. **实现 work-efficient 的前缀和**：理解 up-sweep / down-sweep 这棵二叉树，并用「分块扫描 + 扫描块和 + 加回偏移」的三阶段结构支持任意长度输入。
4. **用共享内存 tiling 优化 Stencil**：正确处理 halo 区（包括四个角），把全局访存从 5 次/点降到约 1 次/点。
5. **实现双调排序和基数排序**：记住比较器的方向判断公式 `(i & k) == 0`，理解基数排序为什么依赖 scan 和「稳定」。
6. **用 CSR / ELL 两种格式做 SpMV**：知道什么时候每线程一行、什么时候每 warp 一行，以及为什么 SpMV 永远是带宽受限。
7. **写一个层次化 BFS**：用 `atomicCAS` 做「抢占式标记」保证每个顶点只进 frontier 一次，并能说出它的三处固有瓶颈。
8. **识别并修掉浮点求和的精度灾难**：掌握分块求和、Kahan 补偿求和，知道什么时候该上 double。
9. **用 SpMV + 归约 + 逐元素运算拼出一个完整的 CG 迭代求解器**，并说出它每次迭代的访存代价。

### 0.2 一句话主线

> **GPU 编程的绝大部分工作，都不是「想出一个新算法」，而是「把一个已知的算法映射成规则的内存访问」。**

这一章出现的所有算法都有一个共同点：它们的**数学定义早就写好了**，我们要做的只是决定「哪个线程处理哪个数据、数据放在哪一级内存」。你会发现真正花时间的地方，永远是访存模式，而不是公式。

### 0.3 并行模式总览表

这张表是本章的目录，也是你以后遇到新问题时的第一把尺子。**先归类，再动手。**

| 模式 | 一句话定义 | 输出规模 | 典型代表 | 瓶颈 | 主要优化手段 |
|---|---|---|---|---|---|
| **Map** / Transform | 每个输出只依赖对应的一个输入 | 与输入同规模 | 向量加、激活函数、灰度化 | 带宽 | 合并访存、向量化（`float4`） |
| **Reduce** | 把 N 个数压成 1 个（或少数几个） | O(1) | 求和、求最值、求范数、点积 | 带宽 + 同步 | 顺序寻址、循环展开、Warp Shuffle |
| **Scan** / Prefix Sum | 每个输出依赖前面所有输入 | 与输入同规模 | 前缀和、压缩、排序的基石 | 带宽 + 同步层次 | work-efficient 树形扫描、分块 + 三阶段 |
| **Scatter** | 按数据决定写到哪里 | 与输入同规模 | 直方图、桶排序、粒子装箱 | 原子争用 | 块内私有副本、排序后压缩 |
| **Gather** | 按数据决定从哪里读 | 与输入同规模 | 查表、SpMV 的 `x[colIdx[j]]` | 随机访存延迟 | 提高局部性、重排数据、纹理缓存 |
| **Histogram** | Scatter 的特例：把元素投进 M 个桶 | M 个桶 | 图像直方图、字符统计 | 全局原子争用 | 每块私有直方图（见[第 3 章](ch03_同步通信与原子操作.md)） |
| **Stencil** | 每个输出依赖输入的一个邻域 | 与输入同规模 | 卷积、热传导、Jacobi 迭代 | 带宽（邻近元素被重复读） | 共享内存 tiling + halo、时间分块 |
| **Sort** | 排序 | 与输入同规模 | 双调排序、基数排序 | 带宽 + 随机写 | 网络规整化、按位稳定划分 |
| **SpMV** / 稀疏运算 | 稀疏矩阵 × 稠密向量 | 与行数同规模 | 迭代求解器、图算法 | 带宽 + 间接寻址 | CSR/ELL 格式选择、行内并行 |
| **图算法** | 沿边传播信息 | 与顶点数同规模 | BFS、PageRank、连通分量 | 负载不均 + 随机访存 | 方向优化、frontier 压缩 |

**怎么用这张表**：拿到一个新问题，先问三个问题。

1. **输出的一个元素，依赖输入的几个元素？**
   - 依赖 1 个 → Map（最省事）。
   - 依赖固定的一小片邻域 → Stencil。
   - 依赖全部 → Reduce 或 Scan（区别在输出是 1 个还是 N 个）。
   - 依赖数量由数据决定 → Gather（SpMV、查表）或 Scatter（直方图）。
2. **写出去的时候，多个线程会不会写同一个位置？**
   - 会 → 需要原子操作、私有副本或者先排序。
3. **读的时候，相邻线程读的是不是相邻地址？**
   - 不是 → 你的性能已经被判了死刑，先改数据布局。

## 1. 概念讲解

### 1.1 Reduce（归约）：并行计算的第一课

**归约** 是指把一个长度为 N 的数组通过一个满足结合律的二元运算压成一个（或少数几个）值。求和、求最大值、求平方和、求点积都是归约。

先打个比方：**归约就像一场淘汰赛**。64 个选手两两比赛，32 个胜者再两两比赛，最后决出冠军。只用 6 轮就决出了冠军，而不是 64 场单挑。

串行代码是「裁判挨个问一遍」：64 次提问。并行归约是「选手互相比」：log₂64 = 6 轮。

```cpp
// 串行版本：O(N) 次加法的同时，也意味着 O(N) 的延迟
float serialSum(const float* in, int n) {
    float s = 0.f;
    for (int i = 0; i < n; ++i) s += in[i];
    return s;
}
```

在 GPU 上，归约的难点**不是**「怎么并行」——这件事太显然了——而是下面三件事：

1. **两两配对之后，谁跟谁配？** 这决定了共享内存的 bank 冲突和 warp 发散。
2. **每一轮都要同步吗？** 只要跨线程交换数据，就必须让慢的线程追上快的。
3. **线程多于数据怎么办？** 大量线程分不到活，纯粹浪费。

本章 2.1 节会把这三个问题逐一解决，并用实测数据证明每一次改动确实有效。

**关键术语**：
- **交错寻址（Interleaved Addressing）**：线程 i 处理下标 2i 和 2i+1 这一对。看起来自然，实际上会造成 warp 发散和 bank conflict。
- **顺序寻址（Sequential Addressing）**：第 s 轮让线程 0..s-1 处理 `s[i] += s[i+s]`。活跃线程总是落在整数条 warp 上。
- **Warp 发散（Divergence）**：同一个 warp 内的线程走了不同的分支，硬件只能串行执行两条路径。
- **Bank Conflict**：同一个 warp 内两个线程访问了共享内存的同一个 bank 的不同地址，硬件必须分成两次访问。

### 1.2 Scan（前缀和）：并行算法的万能胶

**前缀和（Prefix Sum / Scan）** 是这样一个操作：给定 `a[0..n-1]`，输出 `s[i] = a[0] + a[1] + ... + a[i]`（包含式，inclusive）或 `s[i] = a[0] + ... + a[i-1]`（独占式，exclusive）。

打个比方：**归约是「总共花了多少钱」，扫描是「每次消费之后账户里的余额」**。前者只要一个数，后者要每一步的中间状态。

为什么说它是「万能胶」？因为很多看起来和加法无关的算法，都建立在前缀和之上：

- **流压缩（Stream Compaction）**：把满足条件的元素紧凑地排列。用前缀和算出每个保留元素应该写到哪个位置。
- **基数排序**：每一趟的稳定划分 = 一次谓词 + 一次前缀和（见 2.5 节，`radix_sort.cu` 真的就是这么写的）。
- **稀疏格式转换**：CSR 的 `rowPtr` 数组就是每行非零元个数的前缀和。
- **负载均衡**：把不均匀的工作量切成连续区间，前缀和给出每个线程的起点。
- **多边形扫描转换、字符串匹配、分段归约**……

**两种扫描的代价完全不同**：

| 算法 | 工作量（加法次数） | 深度（同步次数） | 共享内存访问 |
|---|---|---|---|
| 串行扫描 | n - 1 | 0 | 0 |
| Kogge-Stone（朴素双层） | n log n | log n（每层 2 次同步） | O(n log n) |
| Blelloch（work-efficient） | 2n | 2 log n（但不是每层都全块同步） | O(n) |

在 n = 1M 时，log₂n = 20，Kogge-Stone 的加法次数是 Blelloch 的 10 倍。所以生产代码一律用 Blelloch 那一类。

**关键术语**：
- **Inclusive Scan（包含式扫描）**：`out[i]` 包含 `in[i]` 自己。
- **Exclusive Scan（独占式扫描）**：`out[i]` 不包含 `in[i]`。Blelloch 天然产生独占式结果。
- **Up-sweep（归约阶段）**：自底向上把相邻两项相加，根节点最后得到总和。
- **Down-sweep（分发阶段）**：自顶向下把部分和分发给左右孩子，并把根部清零，把包含式变成独占式。
- **Work-efficient（工作量高效）**：总工作量与串行算法同阶（这里是 O(n)）。

### 1.3 Stencil（模板计算）：科学计算的主力

**Stencil** 是「每个输出点是输入的一个固定邻域的函数」。一维时最常见的是一阶导数近似 `(a[i+1] - a[i-1]) / 2h`，二维时是五点格式。图像处理里的卷积、模糊、锐化，物理仿真里的热传导、波动方程，都是 stencil。

打个比方：**它像给一张照片做「每个像素取周围 9 个像素的平均值」**。每个像素都会被读 9 次，而它的邻居也会被各自的邻域读一遍——**数据的复用率极高，但朴素实现完全没利用上**。

在 GPU 上，stencil 的核心技巧是**共享内存 tiling + halo（晕圈）**：

1. 每个线程块负责输出图像的一块 tile（比如 32×8）。
2. 把这块 tile **加上四周一圈 halo** 一起搬进共享内存（变成 34×10）。
3. 之后所有邻居读取都在共享内存里完成。全局访存次数从 5 次/点降到约 1.08 次/点。

**halo 是 stencil 最容易写错的地方**：主体由所有线程各搬一个；左右列 halo 由最左/最右列的线程顺手搬一整列；上下行 halo 由最上/最下行的线程搬一整行；**四个角必须单独指派**——这是 90% 的初学者会漏掉的地方，而且它只在图像边界之外才出错，很难靠简单测试发现。

**关键术语**：
- **Halo / Ghost Cell（晕圈 / 幽灵单元）**：tile 之外、但被 tile 内计算所需要的那一圈数据。
- **Temporal Blocking（时间分块）**：把多次时间步一起算，让同一块数据在共享内存里被用多次，进一步减少全局访存。
- **Arithmetic Intensity（算术强度）**：FLOP / Byte。五点格式的算术强度约 4 / 20 = 0.2，是彻底的带宽受限。

### 1.4 Histogram（直方图）：在最前面先说结论

直方图是 **Scatter** 的特例：`hist[bin(x[i])]++`。它的难点完全在于「多个线程同时给同一个桶加一」。

结论提前给出（详细推导和实测见[第 3 章](ch03_同步通信与原子操作.md)）：

- 直接对全局直方图 `atomicAdd`，在图像这种高度不均匀的输入上，会出现极端的原子争用，性能可能比 CPU 还差。
- 正确做法是**每个线程块先在共享内存里维护一份私有直方图**，块内做完再原子合并到全局。原子操作次数从「元素数」降到「桶数 × 块数」。
- 如果桶数很大（比如 65536 个桶），共享内存放不下，就要用「每个 warp 一份私有直方图」或者「排序后分段统计」的方案。

本章不再重复代码，请回看 `code/lessons/ch03_atomics_histogram/histogram.cu`。

### 1.5 Sort（排序）：两种截然不同的思路

GPU 上排序有两条主流路线，它们优化的是完全不同的东西。

**路线一：双调排序（Bitonic Sort）——把「比较」网络化**

双调排序基于一个漂亮的观察：如果把序列切成两半，前一半升序、后一半降序，那么「前一半的第 i 个」和「后一半的第 i 个」比较之后交换，就能保证**前一半的所有元素都小于后一半的所有元素**。反复运用这个性质，就得到一个 log²n 层的比较网络。

它的好处是**完全规整**：每一层的第 i 个元素只知道「跟 i^j 比较、方向由 (i & k) 决定」，没有分支、没有动态调度，完美契合 SIMT。

它的坏处是**工作量大**：O(n log²n) 次比较，比快排多一个 log n 因子，而且需要 log²n 层同步。

**路线二：基数排序（Radix Sort）——把「比较」换成「分配」**

基数排序从最低位开始，每一趟把数据**稳定地**按某几位重新分桶。n 个 32 位数只需要 32/按位数 趟，每趟的工作量是 O(n)。

它的好处是**工作量线性**，而且访存规整。它的全部难点在「稳定」二字：每一趟必须保证「原来在前面的，分到同一个桶之后仍然在前面」。而稳定划分恰好可以用**一次扫描**做出来：

```
predicate[i] = (第 b 位是 0) ? 1 : 0
prefix[i]    = 前 i 个元素中有多少个「第 b 位是 0」
totalZeros   = 所有位为 0 的元素个数
新位置 = 位为 0 ? prefix[i] : totalZeros + (i - prefix[i])
```

这就是为什么[1.2 节](#12-scan前缀和并行算法的万能胶)说 scan 是「万能胶」——排序直接架在它上面。

**关键术语**：
- **比较器（Comparator）**：双调排序的基本单元，对一对元素按指定方向做比较-交换。
- **稳定（Stable）**：值相等的元素在排序后保持原来的相对顺序。
- **LSD（Least Significant Digit）**：从最低位开始排，是基数排序的标准做法，必须稳定。
- **Onesweep**：现代基数排序的一次性散列写法：每块先算局部直方图，扫描后一次完成散列，把多趟合并成一趟。

### 1.6 SpMV（稀疏矩阵向量乘）：间接寻址的代价

**SpMV** 计算 `y = A * x`，其中 A 是稀疏矩阵。因为 A 里绝大多数元素是 0，存稠密矩阵既浪费显存又浪费带宽，所以要用专门的稀疏格式。

最常用的是 **CSR（Compressed Sparse Row）**：

```
rowPtr: 长度 n+1，rowPtr[i] 是第 i 行的第一个非零元在 values/colIdx 里的下标
colIdx: 长度 nnz，存每个非零元的列号
values: 长度 nnz，存每个非零元的值
```

比如三行四列的矩阵

```
[ 1  0  2  0 ]
[ 0  3  0  0 ]
[ 0  0  0  4 ]
```

的 CSR 是 `rowPtr = [0,2,3,4]`、`colIdx = [0,2,1,3]`、`values = [1,2,3,4]`。

SpMV 的 kernel 是：

```cpp
float sum = 0.f;
for (int j = rowPtr[row]; j < rowPtr[row+1]; ++j)
    sum += values[j] * x[colIdx[j]];   // 注意这里：这是一个 Gather
y[row] = sum;
```

注意 `x[colIdx[j]]`——**线程不知道下一个要读的地址在哪里，必须先把 `colIdx[j]` 读出来才知道**。这叫**间接寻址（indirect addressing）**，它带来两个后果：

1. 访存无法合并：相邻线程读的 `x` 地址取决于各自的 `colIdx`，可能相差十万八千里。
2. 无法预取：硬件流水线没法提前把数据拉进来。

再加上「每行的非零元个数不一样」导致的**负载不均**，SpMV 一般只能跑到理论带宽峰值的 30%～70%。这是整个 HPC 领域公认的难题。

**ELL 格式** 是另一种思路：把每行补齐到相同的长度 `maxNnz`，然后**按列主序**排列：

```
ellVal[k * n + row] ，k = 0 .. maxNnz-1
```

这样第 k 轮循环里，所有线程读的是 `ellVal[k*n + row]`，`row` 连续 → **完全合并访存**。代价是行长度差异大时会浪费大量空间和带宽。

### 1.7 图算法：把「边」当成数据

图算法在 GPU 上的入口是 **BFS（广度优先搜索）**，因为它的并行度最直观：**同一层里的所有顶点可以同时向外扩展**。

层次化 BFS 的结构是：

```
frontier = {src}
level = 0
while frontier 非空:
    对 frontier 里每个顶点 u，遍历 u 的所有邻居 v：
        如果 v 还没被访问过：标记 v 的层号，把 v 加入 nextFrontier
    frontier = nextFrontier
    level += 1
```

看起来简单，但有三个并发陷阱：

1. **多个线程可能同时发现同一个顶点 v**。必须用 `atomicCAS(&dist[v], -1, level+1)` 做「抢占式标记」，只有成功的那个线程才把 v 加进 frontier。
2. **往 nextFrontier 里写的位置不能重复**。用 `atomicAdd(nextSize, 1)` 原子地领一个下标。
3. **frontier 随时可能变得极大或极小**。第一层只有 1 个顶点（并行度为零），中间某一层可能吃掉一半顶点（并行度爆炸）。

再加上「每层结束都要把 frontier 大小拷回 host 才知道要不要继续」这个同步点，层次化 BFS 的性能瓶颈几乎从来不是算力，而是**负载不均 + host 往返 + 无效边访问**。工业级的解法是 **direction-optimizing BFS**（frontier 大时切换成 pull 方向）和 **frontier 压缩**，可以去看 Gunrock、Ligra 这两个库。

### 1.8 数值算法：浮点求和的精度灾难

这一节不讲并行，讲一个**只在并行程序里才明显**的坑。

浮点数只有 24 位有效位（float）。当你往一个大数上不断累加小数时，小数会被「吃掉」：

```
1.0e7 + 1.0   →   1.0e7        （1.0 完全没了）
```

串行求和时，累加器是**一条**不断变大的链，N 次加法有 N 次舍入，误差按 O(N) 增长。

并行归约的树形结构天然把误差降到了 O(log N)，因为部分和永远不会涨到那么大。

但如果你写的是「每个线程用 float 累加 100 万个元素，最后原子加」，那每个线程内部的误差还是 O(N/线程数) 级别。三种补救方案：

| 方案 | 做法 | 精度 | 代价 |
|---|---|---|---|
| **分块求和** | 每线程/每块用小累加器，最后用 double 汇总 | 误差降到 O(log N) | 几乎为零 |
| **Kahan 补偿求和** | 维护一个补偿项 `c`，把每次舍入丢掉的部分记下来，下次加回去 | 1 ulp 量级 | 每步从 1 次加法变成 4 次浮点运算 |
| **全 double** | 累加器直接用 double | 53 位尾数，基本无误差 | 消费级显卡上双精度吞吐只有单精度的 1/32 |

**实用建议**：默认用「float 分块累加 + double 汇总」；只有当块内也需要极高精度时才在块内开 Kahan。

**关键术语**：
- **ulp（unit in the last place）**：浮点数最低有效位对应的值。误差的常用度量单位。
- **Kahan 求和（补偿求和）**：用额外的加法「捡回」被舍入丢掉的低位。
- **Catastrophic Cancellation（灾难性抵消）**：两个相近的大数相减，有效位被吃光。数值算法里要尽量避免。

### 1.9 迭代求解器：把所有零件拼起来

最后用 **共轭梯度法（Conjugate Gradient, CG）** 收口，因为它的每一次迭代恰好用到了本章和前三章的全部零件：

```
r = b - A x          ← SpMV（第 5 章）+ axpy（第 1 章的 Map）
p = r                ← 拷贝
loop:
  Ap    = A p        ← SpMV
  alpha = (r·r)/(p·Ap)  ← 两次 Reduce（第 5 章）+ host 标量
  x    += alpha * p  ← axpy
  r    -= alpha * Ap ← axpy
  beta  = (r_new·r_new)/(r·r)  ← Reduce
  p     = r + beta*p ← axpby
```

每一个内核单独看都很简单，合起来的性能瓶颈一目了然：**每次迭代要把几个长度 N 的向量完整读写一遍**，而 N = 1M 时一个向量就是 4 MB，远远超出 L2 缓存。

这也是「为什么要融合内核（kernel fusion）」的最直观例子：`x += alpha*p` 和 `r -= alpha*Ap` 可以合成一个内核，少一次完整的读写往返。

#### v1：交错寻址 —— 最直观，也最慢

```cpp
__global__ void reduceInterleaved(const float* __restrict__ in,
                                  float* __restrict__ partial) {
    __shared__ float s[BLOCK];
    const int tid = threadIdx.x;

    // 每个线程先从全局内存取 1 个元素放进共享内存，之后整个归约都在片上完成。
    // 这一步是**合并访存**：相邻线程读相邻地址，一个 warp 的 32 次读合成一次事务。
    s[tid] = in[blockIdx.x * BLOCK + tid];
    __syncthreads();

    // 交错寻址：stride=1 时是 (0,1)(2,3)(4,5)…，stride=2 时是 (0,2)(4,6)…
    for (int stride = 1; stride < BLOCK; stride <<= 1) {
        if (tid % (2 * stride) == 0)
            s[tid] += s[tid + stride];
        __syncthreads();
    }
    if (tid == 0) partial[blockIdx.x] = s[0];
}
```

#### v2：顺序寻址 —— 一次改动解决两个问题

```cpp
__global__ void reduceSequential(const float* __restrict__ in,
                                 float* __restrict__ partial) {
```

#### v3：加载阶段展开 + 归约树完全展开

```cpp
__global__ void reduceUnrolled(const float* __restrict__ in,
                               float* __restrict__ partial) {
    __shared__ float s[BLOCK];
    const int tid = threadIdx.x;
    constexpr int ELEMS = 4;   // 每个线程在进入归约树前先加 4 个元素

    const int base = blockIdx.x * BLOCK * ELEMS + tid;
    float sum = 0.f;
#pragma unroll
    for (int k = 0; k < ELEMS; ++k)
        sum += in[base + k * BLOCK];   // 跨步 BLOCK，保证相邻线程仍然读相邻地址

    s[tid] = sum;
    __syncthreads();

    // 完全展开的归约树；stride 是编译期常量，循环开销为零
#pragma unroll
    for (int stride = BLOCK / 2; stride > 32; stride >>= 1) {
        if (tid < stride) s[tid] += s[tid + stride];
        __syncthreads();
    }
    // 最后只剩 warp 0 的 32 个线程活跃，用 __syncwarp() 就够了
    if (tid < 32) {
        s[tid] += s[tid + 32];
        __syncwarp();
#pragma unroll
        for (int stride = 16; stride > 0; stride >>= 1) {
            s[tid] += s[tid + stride];
            __syncwarp();
        }
    }
    if (tid == 0) partial[blockIdx.x] = s[0];
}
```

#### v4：Warp Shuffle —— 终极版本

```cpp
__global__ void reduceShuffle(const float* __restrict__ in,
                              float* __restrict__ partial) {
    __shared__ float s[BLOCK];
    const int tid = threadIdx.x;
    constexpr int ELEMS = 4;

    const int base = blockIdx.x * BLOCK * ELEMS + tid;
    float sum = 0.f;
#pragma unroll
    for (int k = 0; k < ELEMS; ++k)
        sum += in[base + k * BLOCK];

    s[tid] = sum;
    __syncthreads();

    // 阶段一：共享内存归约，直到只剩 32 个数为止
    for (int stride = BLOCK / 2; stride > 32; stride >>= 1) {
        if (tid < stride) s[tid] += s[tid + stride];
        __syncthreads();
    }

    // 阶段二：warp 内归约，全部走寄存器和 shuffle，零共享内存、零 __syncthreads
    if (tid < 32) {
        float v = s[tid];  // 此时 s[0..31] 已经汇总了全部 BLOCK 个元素
#pragma unroll
        for (int offset = 16; offset > 0; offset >>= 1)
            v += __shfl_down_sync(0xffffffffu, v, offset);
        if (tid == 0) partial[blockIdx.x] = v;
    }
}
```

#### 第二阶段：把各块的部分和汇总

```cpp
__global__ void reduceFinal(const float* __restrict__ in, int n,
                            float* __restrict__ out) {
    __shared__ float s[BLOCK];
    const int tid = threadIdx.x;

    float sum = 0.f;
    for (int i = tid; i < n; i += BLOCK) sum += in[i];   // 块内跨步循环，支持任意 n
    s[tid] = sum;
    __syncthreads();

    for (int stride = BLOCK / 2; stride > 0; stride >>= 1) {
        if (tid < stride) s[tid] += s[tid + stride];
        __syncthreads();
    }
    if (tid == 0) *out = s[0];
}
```

### 2.2 扫描：Kogge-Stone、Blelloch 和三阶段设备级扫描

#### A. Kogge-Stone：朴素但直观

```cpp
__global__ void koggeStoneBlock(const float* __restrict__ in,
                                float* __restrict__ out) {
    __shared__ float s[BLOCK];
    const int tid = threadIdx.x;
    const int gid = blockIdx.x * BLOCK + tid;

    s[tid] = in[gid];
    __syncthreads();

    for (int offset = 1; offset < BLOCK; offset <<= 1) {
        // 1) 先把要用到的旧值抓进寄存器
        const float v = (tid >= offset) ? s[tid - offset] : 0.f;
        __syncthreads();  // 2) 保证所有线程都读完了旧值
        s[tid] += v;      // 3) 再统一写回
        __syncthreads();  // 4) 保证所有线程都写完了，下一轮才能读
    }
    out[gid] = s[tid];
}
```

#### B. Blelloch：work-efficient 的 up-sweep + down-sweep

```cpp
constexpr int BLOCK = 256;
constexpr int ITEMS = 16;              // 每个线程负责 16 个元素
constexpr int TILE  = BLOCK * ITEMS;   // 每个块处理 4096 个元素

__global__ void blellochBlockExclusive(const float* __restrict__ in,
                                       float* __restrict__ out,
                                       float* __restrict__ blockTotal,
                                       int n) {
    __shared__ float s[TILE];  // 4096 * 4B = 16KB，在默认 48KB 限制内
    const int tid = threadIdx.x;
    const int base = blockIdx.x * TILE;

    // ---- 搬运：每线程搬 ITEMS 个元素。跨步 BLOCK 保证合并访存 ----
#pragma unroll
    for (int k = 0; k < ITEMS; ++k) {
        const int idx = base + k * BLOCK + tid;
        s[k * BLOCK + tid] = (idx < n) ? in[idx] : 0.f;  // 越界补 0，不破坏扫描结果
    }
    __syncthreads();

    // ---- up-sweep：自底向上求和 ----
    int offset = 1;
    for (int d = TILE >> 1; d > 0; d >>= 1) {
        __syncthreads();
        // d 可能大于线程数，所以用跨步循环；同层内各节点对互不相交，无竞争
        for (int i = tid; i < d; i += BLOCK) {
            const int ai = offset * (2 * i + 1) - 1;  // 左孩子
            const int bi = offset * (2 * i + 2) - 1;  // 右孩子（= 父节点）
            s[bi] += s[ai];
        }
        offset <<= 1;
    }

    // ---- 根部清零 + 记录块总和：这一步把「包含式」变成「独占式」 ----
    if (tid == 0) {
        blockTotal[blockIdx.x] = s[TILE - 1];
        s[TILE - 1] = 0.f;
    }

    // ---- down-sweep：自顶向下分发 ----
    for (int d = 1; d < TILE; d <<= 1) {
        offset >>= 1;
        __syncthreads();
        for (int i = tid; i < d; i += BLOCK) {
            const int ai = offset * (2 * i + 1) - 1;
            const int bi = offset * (2 * i + 2) - 1;
            const float t = s[ai];   // 先把左孩子的值存起来
            s[ai] = s[bi];           // 左孩子拿到父节点传下来的前缀
            s[bi] += t;              // 父节点加上原来的左孩子
        }
    }
    __syncthreads();

#pragma unroll
    for (int k = 0; k < ITEMS; ++k) {
        const int idx = base + k * BLOCK + tid;
        if (idx < n) out[idx] = s[k * BLOCK + tid];
    }
}
```

### 2.3 Stencil：二维 Jacobi 迭代

完整代码：`code/lessons/ch05_stencil/stencil.cu`。

```cpp
constexpr int BX   = 32;            // 块内 x 方向线程数
constexpr int BY   = 8;             // 块内 y 方向线程数
constexpr int SH_W = BX + 2;        // 含左右 halo
constexpr int SH_H = BY + 2;        // 含上下 halo

// 带边界处理的取数：越界一律返回 0，等价于零边界条件（Dirichlet 边界）
__device__ __forceinline__ float loadIn(const float* __restrict__ in,
                                        int x, int y, int w, int h) {
    if (x < 0 || x >= w || y < 0 || y >= h) return 0.f;
    return in[y * w + x];
}

// v1：朴素版本 —— 直接读全局内存，每个输出点 5 次全局访存
__global__ void jacobi2DNaive(const float* __restrict__ in,
                              float* __restrict__ out, int w, int h) {
    const int x = blockIdx.x * blockDim.x + threadIdx.x;
    const int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x >= w || y >= h) return;

    const float l = loadIn(in, x - 1, y, w, h);
    const float r = loadIn(in, x + 1, y, w, h);
    const float u = loadIn(in, x, y - 1, w, h);
    const float d = loadIn(in, x, y + 1, w, h);
    out[y * w + x] = 0.25f * (l + r + u + d);
}

// v2：共享内存 tiling + halo
__global__ void jacobi2DShared(const float* __restrict__ in,
                               float* __restrict__ out, int w, int h) {
    // SH_H * SH_W * 4B = 10 * 34 * 4 = 1360 字节，非常小
    __shared__ float tile[SH_H][SH_W];

    const int tx = threadIdx.x;
    const int ty = threadIdx.y;
    const int gx = blockIdx.x * BX + tx;
    const int gy = blockIdx.y * BY + ty;

    // 1) 主体：合并访存。同一个 warp 的 tx 连续，读的地址也连续。
    tile[ty + 1][tx + 1] = loadIn(in, gx, gy, w, h);

    // 2) 左右 halo
    if (tx == 0)       tile[ty + 1][0]        = loadIn(in, gx - 1, gy, w, h);
    if (tx == BX - 1)  tile[ty + 1][BX + 1]   = loadIn(in, gx + 1, gy, w, h);
    // 3) 上下 halo
    if (ty == 0)       tile[0][tx + 1]        = loadIn(in, gx, gy - 1, w, h);
    if (ty == BY - 1)  tile[BY + 1][tx + 1]   = loadIn(in, gx, gy + 1, w, h);
    // 4) 四个角：只有 (tx,ty) 同时落在角上的线程才处理 —— 最容易漏的一步
    if (tx == 0 && ty == 0)              tile[0][0]           = loadIn(in, gx - 1, gy - 1, w, h);
    if (tx == BX - 1 && ty == 0)         tile[0][BX + 1]      = loadIn(in, gx + 1, gy - 1, w, h);
    if (tx == 0 && ty == BY - 1)         tile[BY + 1][0]      = loadIn(in, gx - 1, gy + 1, w, h);
    if (tx == BX - 1 && ty == BY - 1)    tile[BY + 1][BX + 1] = loadIn(in, gx + 1, gy + 1, w, h);

    __syncthreads();  // halo 由不同线程写、被不同线程读，必须等全部写完

    // 5) 计算：列跨度是 SH_W = 34，34 % 32 = 2，无 bank conflict
    out[gy * w + gx] = 0.25f * (tile[ty][tx + 1]      // 上
                                + tile[ty + 2][tx + 1] // 下
                                + tile[ty + 1][tx]     // 左
                                + tile[ty + 1][tx + 2] // 右
    );
}
```

### 2.4 双调排序

完整代码：`code/lessons/ch05_sort/bitonic_sort.cu`。

```cpp
constexpr int TPB = 1024;   // 每个块 1024 个线程

// 核心比较器：对 (i, i^j) 这一对做比较-交换
__device__ __forceinline__ void compareExchange(float* a, float* b, bool ascending) {
    const float va = *a;
    const float vb = *b;
    // 用三元表达式代替 if/else，避免分支
    const bool needSwap = ((va > vb) == ascending);
    *a = needSwap ? vb : va;
    *b = needSwap ? va : vb;
}

// stage 1：块内双调排序（共享内存）
__global__ void bitonicSortTile(float* __restrict__ d, int n) {
    extern __shared__ float s[];
    const int tid = threadIdx.x;
    const int base = blockIdx.x * blockDim.x;

    s[tid] = d[base + tid];
    __syncthreads();

    for (int k = 2; k <= TPB; k <<= 1) {
        for (int j = k >> 1; j > 0; j >>= 1) {
            const int ixj = tid ^ j;          // 异或给出配对对象
            if (ixj > tid) {                  // 只有下标小的一方动手，避免重复
                const bool asc = ((tid & k) == 0);   // ★ 方向判断
                compareExchange(&s[tid], &s[ixj], asc);
            }
            __syncthreads();   // 每一层之后都要同步
        }
    }
    d[base + tid] = s[tid];
}

// stage 2：跨块的双调归并（全局内存），每启动一次只做一层
__global__ void bitonicStep(float* __restrict__ d, int n, int k, int j) {
    const int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    const int ixj = i ^ j;
    if (ixj > i) {
        const bool asc = ((i & k) == 0);   // 用**全局**下标取位
        compareExchange(&d[i], &d[ixj], asc);
    }
}
```

主机侧的调度：

```cpp

// 2) 归并：k 从 2*TPB 开始一路翻倍；每层一次 kernel 启动
```

### 2.5 基数排序：架在前缀和之上的排序

完整代码：`code/lessons/ch05_sort/radix_sort.cu`。

```cpp
// 谓词：第 bit 位是 0 记 1，是 1 记 0
__global__ void splitPredicate(const uint32_t* __restrict__ key,
                               uint32_t* __restrict__ pred, int n, int bit) {
    const int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) pred[i] = (((key[i] >> bit) & 1u) == 0u) ? 1u : 0u;
}

// 稳定散射：
//   prefix[i]     = 第 i 个元素之前有多少个「位为 0」的元素
//   i - prefix[i] = 第 i 个元素之前有多少个「位为 1」的元素
__global__ void splitScatter(const uint32_t* __restrict__ key,
                             const uint32_t* __restrict__ prefix,
                             uint32_t totalZeros,
                             uint32_t* __restrict__ out, int n, int bit) {
    const int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    const uint32_t z = prefix[i];
    const bool isZero = (((key[i] >> bit) & 1u) == 0u);
    const uint32_t pos = isZero ? z : (totalZeros + ((uint32_t)i - z));
    out[pos] = key[i];
}
```

一趟划分 = 谓词 → 前缀和 → 散射：

```cpp
static void radixPassOneBit(const uint32_t* d_key, uint32_t* d_tmp,
                            uint32_t* d_pred, uint32_t* d_prefix,
                            uint32_t* d_chunkSum, uint32_t* d_chunkOff,
                            int n, int bit) {
    const int grid = (n + BLOCK - 1) / BLOCK;
    splitPredicate<<<grid, BLOCK>>>(d_key, d_pred, n, bit);
    exclusiveScanU32(d_pred, d_prefix, d_chunkSum, d_chunkOff, n);   // ★ 复用扫描

    // 前缀和是独占的，所以「0 的总数」= 最后一个位置的前缀 + 最后一个元素自己的谓词
    uint32_t lastPrefix = 0, lastPred = 0;
    CUDA_CHECK(cudaMemcpy(&lastPrefix, d_prefix + n - 1, sizeof(uint32_t), cudaMemcpyDeviceToHost));
    CUDA_CHECK(cudaMemcpy(&lastPred, d_pred + n - 1, sizeof(uint32_t), cudaMemcpyDeviceToHost));
    const uint32_t totalZeros = lastPrefix + lastPred;

    splitScatter<<<grid, BLOCK>>>(d_key, d_prefix, totalZeros, d_tmp, n, bit);
    CUDA_CHECK_KERNEL();
}
```

### 2.6 SpMV：CSR 的三种写法

完整代码：`code/lessons/ch05_spmv/spmv_csr.cu`。这里用 5 点差分格式生成一个 G×G 网格的稀疏矩阵，n = G² 行，nnz ≈ 5n。

```cpp
// 核函数 A：每线程一行（CSR 标量版）
__global__ void spmvCsrScalar(const int* __restrict__ rowPtr,
                              const int* __restrict__ colIdx,
                              const float* __restrict__ values,
                              const float* __restrict__ x,
                              float* __restrict__ y, int nrows) {
    const int row = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= nrows) return;

    float sum = 0.f;
    for (int j = rowPtr[row]; j < rowPtr[row + 1]; ++j)
        sum += values[j] * __ldg(&x[colIdx[j]]);   // __ldg 走只读数据缓存
    y[row] = sum;
}

// 核函数 B：每 warp 一行（CSR + warp 归约）
__global__ void spmvCsrWarp(const int* __restrict__ rowPtr,
                            const int* __restrict__ colIdx,
                            const float* __restrict__ values,
                            const float* __restrict__ x,
                            float* __restrict__ y, int nrows) {
    const int warpId = (blockIdx.x * blockDim.x + threadIdx.x) >> 5;
    const int lane = threadIdx.x & 31;
    if (warpId >= nrows) return;

    const int start = rowPtr[warpId];
    const int end = rowPtr[warpId + 1];

    float sum = 0.f;
    for (int j = start + lane; j < end; j += 32)
        sum += values[j] * __ldg(&x[colIdx[j]]);

#pragma unroll
    for (int offset = 16; offset > 0; offset >>= 1)
        sum += __shfl_down_sync(0xffffffffu, sum, offset);

    if (lane == 0) y[warpId] = sum;
}

// 核函数 C：ELL 格式，每线程一行，完全合并访存
__global__ void spmvEll(const float* __restrict__ ellVal,
                        const int* __restrict__ ellCol,
                        const float* __restrict__ x,
                        float* __restrict__ y, int nrows, int maxNnz) {
    const int row = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= nrows) return;

    float sum = 0.f;
    for (int k = 0; k < maxNnz; ++k) {
        const size_t idx = (size_t)k * nrows + row;   // 列主序：相邻 row 的地址相邻
        const float v = ellVal[idx];
        if (v != 0.f)  // 空位直接跳过
            sum += v * __ldg(&x[ellCol[idx]]);
    }
    y[row] = sum;
}
```

### 2.7 层次化 BFS

完整代码：`code/lessons/ch05_graph/bfs.cu`。

```cpp
// 版本 1：直接对全局计数器做原子加
__global__ void bfsExpand(const int* __restrict__ frontier, int frontierSize,
                          const int* __restrict__ rowPtr,
                          const int* __restrict__ colIdx,
                          int* __restrict__ dist,
                          int* __restrict__ nextFrontier,
                          int* __restrict__ nextSize,
                          int level) {
    const int t = blockIdx.x * blockDim.x + threadIdx.x;
    if (t >= frontierSize) return;

    const int u = frontier[t];
    for (int e = rowPtr[u]; e < rowPtr[u + 1]; ++e) {
        const int v = colIdx[e];
        // ★ 只有第一个把 dist[v] 从 -1 改掉的线程才处理 v。
        //   如果只写 if (dist[v] == -1)，两个线程可能都通过判断、都往
        //   nextFrontier 里塞一份 v，frontier 里就出现重复顶点。
        if (atomicCAS(&dist[v], -1, level + 1) == -1) {
            const int pos = atomicAdd(nextSize, 1);
            nextFrontier[pos] = v;
        }
    }
}
```

```cpp
// 版本 2：先在块内攒批，每个块只做一次全局 atomicAdd
__global__ void bfsExpandShared(const int* __restrict__ frontier, int frontierSize,
                                const int* __restrict__ rowPtr,
                                const int* __restrict__ colIdx,
                                int* __restrict__ dist,
                                int* __restrict__ nextFrontier,
                                int* __restrict__ nextSize,
                                int level) {
    __shared__ int sCount;   // 块内计数器
    __shared__ int sBase;    // 本块在全局数组里的起点
    if (threadIdx.x == 0) sCount = 0;
    __syncthreads();

    const int t = blockIdx.x * blockDim.x + threadIdx.x;
    const bool active = (t < frontierSize);
    const int u = active ? frontier[t] : -1;

    int local[8];            // 本线程发现的新顶点先记在寄存器里
    int localLen = 0;
    if (active) {
        for (int e = rowPtr[u]; e < rowPtr[u + 1]; ++e) {
            const int v = colIdx[e];
            if (atomicCAS(&dist[v], -1, level + 1) == -1 && localLen < 8)
                local[localLen++] = v;
        }
    }

    int myBase = 0;
    if (localLen > 0) myBase = atomicAdd(&sCount, localLen);
    __syncthreads();

    if (threadIdx.x == 0) sBase = atomicAdd(nextSize, sCount);
    __syncthreads();

    for (int i = 0; i < localLen; ++i)
        nextFrontier[sBase + myBase + i] = local[i];
}
```

```cpp
// 版本 3：Kahan 补偿求和
__global__ void sumKahan(const float* __restrict__ in, double* __restrict__ out, int n) {
    float sum = 0.f;  // 累积和
    float c = 0.f;    // 补偿项（被舍入掉的那部分）
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += gridDim.x * blockDim.x) {
        const float y = in[i] - c;   // 先把上次丢掉的部分加回去
        const float t = sum + y;     // 这个加法会丢低位
        c = (t - sum) - y;           // ★ 精确地「找回」丢掉的部分
        sum = t;
    }
    sum = blockReduceSum(sum);
    if (threadIdx.x == 0) atomicAdd(out, (double)sum);
}
```

### 2.9 共轭梯度求解器

完整代码：`code/lessons/ch05_cg/cg.cu`。求解二维泊松方程 `-Δu = 1`（零边界）。

```cpp
// A. 矩阵无关的 SpMV：A 是 G x G 网格上的 5 点差分算子
__global__ void stencil5(const float* __restrict__ x, float* __restrict__ y, int g) {
    const int col = blockIdx.x * blockDim.x + threadIdx.x;
    const int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (col >= g || row >= g) return;

    const int i = row * g + col;
    const float c = x[i];
    const float l = (col > 0)     ? x[i - 1] : 0.f;
    const float r = (col < g - 1) ? x[i + 1] : 0.f;
    const float u = (row > 0)     ? x[i - g] : 0.f;
    const float d = (row < g - 1) ? x[i + g] : 0.f;

    y[i] = 4.f * c - (l + r + u + d);   // 标准的二阶中心差分
}

// B. 点积：网格跨步 + 块内 shuffle 归约 + 一次 double 原子加
__global__ void dotPartial(const float* __restrict__ a, const float* __restrict__ b,
                           double* __restrict__ out, int n) {
    float sum = 0.f;
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += gridDim.x * blockDim.x)
        sum += a[i] * b[i];

    __shared__ float s[32];
    const int lane = threadIdx.x & 31;
    const int wid = threadIdx.x >> 5;
#pragma unroll
    for (int offset = 16; offset > 0; offset >>= 1)
        sum += __shfl_down_sync(0xffffffffu, sum, offset);
    if (lane == 0) s[wid] = sum;
    __syncthreads();
    const int nwarps = blockDim.x >> 5;
    if (wid == 0) {
        sum = (lane < nwarps) ? s[lane] : 0.f;
#pragma unroll
        for (int offset = 16; offset > 0; offset >>= 1)
            sum += __shfl_down_sync(0xffffffffu, sum, offset);
        if (lane == 0) atomicAdd(out, (double)sum);
    }
}
```

## 3. 代码逐行解析

### 3.1 归约：每一步优化到底改了 무엇

这一节把 2.1 节的四个版本逐条拆开，回答 STYLE_GUIDE 要求的三个问题。

#### v1 → v2：从交错寻址到顺序寻址

**原来慢在哪？**

v1 的判断条件是 `tid % (2 * stride) == 0`。取 stride = 1 来看，一个 warp 里只有线程 0、2、4、…、30 会进入 `if`，另外 16 个线程被卡在分支外。

在 SIMT 硬件上，warp 内部 32 个线程是**一起取指、一起执行**的。如果它们走了不同分支，硬件只能：
1. 先让活跃的那 16 个执行 `s[tid] += s[tid+1]`；
2. 把另外 16 个也拉回来，执行空操作。

于是本来一条指令能干完的活，变成两条。更糟的是 `%` 运算在 GPU 上是一条**整数除法序列**（约 20 条指令），比一次比较贵得多。

除了发散，v1 还有 **bank conflict**：stride = 1 时，warp 里活跃线程访问 `s[0], s[2], s[4], …`，也就是 bank 0, 2, 4, …, 30——这恰好是 16 个不同的 bank，是不是没问题？

再仔细看：`s[tid] += s[tid + stride]` 会被编译成**两条**共享内存 load 指令：

- 第一条读 `s[tid]`：活跃线程 0,2,…,30 → bank 0,2,…,30。
- 第二条读 `s[tid+stride]`，即 `s[1], s[3], …, s[31]` → bank 1,3,…,31。

每条指令 16 个线程访问 16 个不同 bank，**没有冲突**，但**每条指令只用了 32 个 bank 里的一半**。也就是说，共享内存的带宽利用率只有 50%——16 个线程要用 32 个 bank 的代价。

**v2 为什么能变快？**

把「活跃线程集合」换成 `{0, 1, …, stride-1}`：

- stride = 128 时，活跃线程 0..127 = warp 0..3 全员参与，warp 4..7 全员不参与 → **零发散**。
- 只有 stride < 32 的最后 5 轮才有 warp 内发散。
- 取模换成了 `tid < stride`，一条整数比较。
- 每条 load 指令里，32 个线程访问 `s[0..31]` 或 `s[stride..stride+31]`——连续的 32 个地址，落在 32 个不同的 bank 上，**满带宽、零冲突**。

**怎么用数据证明？**

```bash
ncu --metrics smsp__sass_average_branch_targets_threads_uniform.pct,\
l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum,\
dram__bytes.sum.per_second ./reduce
```

第一个指标是「分支目标一致的线程比例」，v1 会明显低于 v2；第二个指标是共享内存 bank conflict 计数，v1 会高于 v2。

#### v2 → v3：循环展开与每线程多元素

**原来慢在哪？**

v2 有两个残留开销：

1. 归约树的每一轮都有一次循环判断和一次 `__syncthreads()`，共 8 轮。
2. 块数太多。N = 1M、BLOCK = 256 时是 4096 个块，每个块都要经历一遍完整的 8 轮归约，总同步次数 = 4096 × 8 = 32768 次。

**v3 为什么能变快？**

两处改动：

1. **加载阶段每线程处理 4 个元素**。块数从 4096 降到 1024，总同步次数降到 1/4。而且 `#pragma unroll` 展开之后，4 条独立的 load 指令形成**指令级并行（ILP）**——线程发出第一条 load 后不必等它返回就能发出第二条，硬件的内存流水线被填满，访存延迟被更好地掩盖。
2. **归约树完全展开**。`stride` 变成编译期常量后，循环控制指令消失，而且 `#pragma unroll` 展开的最后几级可以用 `__syncwarp()` 代替 `__syncthreads()`。

注意 `in[base + k * BLOCK]` 这个写法：第 k 次迭代里，相邻线程仍然读相邻地址（`base = blockIdx*1024 + tid`），**合并访存没有被破坏**。这是个容易搞错的地方——如果写成 `in[base + k]`，相邻线程会读地址相差 4 的位置，合并性就丢了。

**怎么用数据证明？**

```bash
ncu --metrics launch__registers_per_thread,\
smsp__inst_executed.sum,\
gpu__time_duration.sum ./reduce
```

展开之后指令总数会下降（循环控制没了），`gpu__time_duration` 会下降。

#### v3 → v4：用 Warp Shuffle 干掉最后 5 轮

**原来慢在哪？**

v2/v3 的最后 5 轮（stride = 16, 8, 4, 2, 1）里，只有 32 个线程有活干，其余 224 个线程全都在 barrier 上空等。而每一次 `__syncthreads()` 都要求块内所有线程到齐，是**全块最慢的那个线程决定进度**。

**v4 为什么能变快？**

关键认识：**当一个 warp 内的 32 个线程需要互相交换数据时，根本不需要共享内存，也不需要 `__syncthreads()`。**

`__shfl_down_sync(mask, v, offset)` 的语义是「每个线程拿到 lane + offset 那个线程的寄存器值（越界的线程返回自己的值）」。用它做归约：

```
offset=16: lane 0 拿到 lane16 的 v，lane 1 拿到 lane17 的 v，……
offset=8:  lane 0 拿到 lane8 的 v，……
…
offset=1:  lane 0 拿到 lane1 的 v  →  lane 0 就是总和
```

5 步、5 条指令、零共享内存访问、零 `__syncthreads()`。这是 CUB、Thrust 内部的做法。

**怎么用数据证明？**

```bash
ncu --metrics l1tex__data_pipe_lsu_wavefronts_mem_shared.sum,\
smsp__warp_issue_stalled_barrier_per_warp_active.pct ./reduce
```

v4 的共享内存访问次数会显著下降，`stall_barrier` 会降到接近 0。

### 3.2 扫描：一棵二叉树的两次遍历

#### 为什么 Kogge-Stone 要多花一次同步

看这一行：

```cpp
const float v = (tid >= offset) ? s[tid - offset] : 0.f;
__syncthreads();
s[tid] += v;
__syncthreads();
```

为什么读和写之间要有一次 `__syncthreads()`？

假设没有它。线程 0 执行完 `s[0] += s[-1]`（即不变）之后立刻进入下一轮，而此时线程 1 might 还没读完 `s[0]`。线程 0 写的 `s[0]` 是**这一轮的旧值**，线程 1 读到的却是**已经更新过的新值**——这就是经典的 **read-after-write 竞争**。

把它写进寄存器 `v` 再统一写回，就把「读」和「写」分成了两个阶段，中间插一次屏障即可。代价是每一轮两次 `__syncthreads()`。

#### Blelloch 的 up-sweep：图解

以 8 个元素 `[3, 1, 7, 0, 4, 1, 6, 3]` 为例。

**up-sweep（自底向上）**：

```
初始:      [3, 1, 7, 0, 4, 1, 6, 3]

d=4:        [3, 4, 7, 7, 4, 5, 6, 9]     s[1]+=s[0]; s[3]+=s[2]; s[5]+=s[4]; s[7]+=s[6]
d=2:        [3, 4, 7,11, 4, 5, 6,14]     s[3]+=s[1]; s[7]+=s[5]
d=1:        [3, 4, 7,11, 4, 5, 6,25]     s[7]+=s[3]  ← 根节点 = 总和
```

**根部清零**：`s[7] = 0`。

**down-sweep（自顶向下）**：

```
清零后:     [3, 4, 7,11, 4, 5, 6, 0]

d=1:        [3, 4, 7, 0, 4, 5, 6,11]     s[3]↔s[7] 交换后 s[7]+=原 s[3]=11
d=2:        [3, 0, 7, 4, 4,11, 6,15]     s[1]↔s[3]；s[5]↔s[7]
d=4:        [0, 3, 4, 7,11, 4,11,15]     ……
```

最终得到的就是**独占式前缀和**：`[0, 3, 4, 11, 11, 15, 16, 22]`。

验证一下：原数组 3, 1, 7, 0, 4, 1, 6, 3；独占前缀和 = 0, 3, 4, 11, 11, 15, 16, 22。✓

**每一次加法都只做一次**：up-sweep 做 n-1 次，down-sweep 做 n-1 次，总共 2n-2 次。对比 Kogge-Stone 的 n log n 次，n = 4096 时是 4096×12 = 49152 次 vs 8190 次，差 6 倍。

#### `offset` 和 `d` 的关系

这是 Blelloch 最容易看晕的地方。记住：

- `offset` 是**当前这一层里，同一个父节点下两个孩子的间距**。
- 节点 i 在**当前层次**下的下标是 `offset * (2i+1) - 1` 和 `offset * (2i+2) - 1`。
- up-sweep 时 `offset` 从 1 开始翻倍，`d` 从 TILE/2 开始减半；
- down-sweep 时 `offset` 从 TILE/2 开始减半（所以在循环开头就 `offset >>= 1`），`d` 从 1 开始翻倍。

**为什么 up-sweep 里要写 `for (int i = tid; i < d; i += BLOCK)`？**

因为 TILE = 4096、BLOCK = 256 时，最底层需要处理 2048 个节点对，但只有 256 个线程。用跨步循环让每个线程处理 8 对。同一层内不同的 i 对应的 `(ai, bi)` 互不相交，所以**这一层只需要开头一次 `__syncthreads()`**。

#### 三阶段扫描：为什么不是简单地把块内扫描串起来

单个块最多扫 TILE 个元素就满了。要扫 1M 个元素，必须分块：

- **天真做法**：块 0 扫完、块 1 扫完、……，然后让块 1 加上块 0 的总和，块 2 加上块 0+1 的总和…… 这在 GPU 上做不到，因为块之间不能同步。
- **正确做法（三阶段）**：
  1. 每个块独立地扫描自己那一段，同时把自己的段总和写到一个数组 `blockTotal` 里。
  2. 用一个块扫描 `blockTotal`，得到每个块前的偏移 `blockOffset`（**这是扫描的递归应用**）。
  3. 每个块把 `blockOffset[blockIdx.x]` 加到自己那段的所有元素上。

三个阶段各自都是完全并行的，这也是为什么说「扫描是分治的」。

### 3.3 Stencil 的 halo：为什么角必须单独处理

回看 2.3 节的代码，halo 分成了四组：

```cpp
tile[ty + 1][tx + 1]     // 主体：所有线程
if (tx == 0) ...         // 左列：最左列的 8 个线程
if (tx == BX-1) ...      // 右列：最右列的 8 个线程
if (ty == 0) ...         // 上行：最上行的 32 个线程
if (ty == BY-1) ...      // 下行：最下行的 32 个线程
if (tx==0 && ty==0) ...  // ★ 四个角：各只有 1 个线程负责
```

**为什么角会被漏掉？** 因为「左列」覆盖的是 `tile[1..BY][0]`（共享内存的第 0 列、第 1..BY 行），而「上行」覆盖的是 `tile[0][1..BX]`。它们的交集 `tile[0][0]` **谁都不管**。

如果漏掉 `tile[0][0]`，它的初值是 0。那么当块位于图像内部时，这个位置本该是从全局内存读来的真实邻居值，结果被当成 0 用——**计算结果错了，但只在 y 方向所有块边界处错**，非常难发现。

**验证办法**：用 `compute-sanitizer --tool initcheck ./stencil`，它能检测出读到未初始化共享内存的情况；或者干脆把每个块左上方那个点的结果和 CPU 对拍。

**为什么没有 bank conflict？**

`tile` 的列跨度是 `SH_W = 34`。同一个 warp 内 `ty` 固定、`tx = 0..31`，访问 `tile[ty][tx+1]` 时：

```
地址 = (ty * 34 + tx + 1) * 4 字节
bank = (ty * 34 + tx + 1) % 32 = (tx + 常数) % 32
```

`tx` 取 0..31 时，bank 也恰好取遍 0..31，**零冲突**。

如果 `SH_W` 恰好是 32 的倍数（比如不加 halo 的 32），那么 `bank = (ty*32 + tx) % 32 = tx % 32`，仍然是 32 个不同 bank——也没有冲突。但读取 `tile[ty][tx]` 和 `tile[ty][tx+2]` 这两条**独立指令**各自也没有冲突。

真正会造成冲突的是**列访问**（`tile[0][tx]`、`tile[1][tx]`、… 时所有线程访问同一个 bank），所以 34 这个「错位填充」主要保护的是上下方向访问的场景。RULE OF THUMB：**共享内存的二维数组，行跨度取 `宽度 + 1` 永远不会错。**

### 3.4 双调排序：方向位 `(i & k)` 到底在判断什么

这是双调排序唯一的「魔法」，必须讲透。

**双调序列（Bitonic Sequence）** 的定义：一个先单调增、后单调减（或者循环移位后满足这个性质）的序列。

双调排序的基本定理：**如果序列是双调的，那么把它的第 i 个和第 i+n/2 个比较（i < n/2），小的放前半、大的放后半，得到的前后两半各自都还是双调序列。**

于是「合并」可以递归进行：长度为 n 的双调序列，log₂n 层比较之后就能排好序。

现在的问题变成：**怎么把任意序列变成双调序列？**

答案是「自底向上构造」：

- k=2 时，把相邻两个元素配成 (升, 降)、(升, 降)、…，得到一堆长度 2 的双调序列。
- k=4 时，把相邻两个长度 2 的双调序列合并成一个升序、一个降序，得到一堆长度 4 的双调序列。
- k=8 时同理……

而「方向」就是在这个过程中指定的：

```
(i & k) == 0  →  这一段应该升序
(i & k) != 0  →  这一段应该降序
```

`k` 是**当前正在构造的双调序列的长度**。下标 i 的第 log₂k 位是 0，说明它落在长度为 k 的块的前一半（应该升序）；是 1，说明落在后一半（应该降序）。

举 k = 4 为例，下标 0..7：

| i | i & 4 | 方向 | 说明 |
|---|---|---|---|
| 0,1,2,3 | 0 | 升序 | 第一块 → 升序的双调序列 |
| 4,5,6,7 | 4 | 降序 | 第二块 → 降序的双调序列 |

两块拼起来就是 `[小, 中, 大, 最大 | 最大, 大, 中, 小]`——一个长度 8 的双调序列。✓

**再看归并阶段**：k = 8 时，下标 0..7 的 `i & 8` 全是 0，所以所有比较都是「升序方向」，也就是「小的放前面」。第一次比较（j = 4）把最小的一半放到前 4 位、最大的一半放到后 4 位；然后 j = 2、1 各自把两半排好。结果整个长度 8 的序列升序。✓

**为什么 `.cu` 里块内用 `tid & k` 而块间用 `i & k`？**

因为块内的 `base = blockIdx.x * blockDim.x` 是 `blockDim.x` 的整数倍，而 `k <= blockDim.x`，所以 `(base + tid) & k == tid & k`。这只在 `k <= TPB` 且 `base` 是 TPB 的倍数时成立。块间归并时 `k > TPB`，必须用全局下标。

### 3.5 基数排序：稳定性是怎么保证的

回看 2.5 节的 `splitScatter`，关键就是最后两行：

```cpp
const uint32_t z = prefix[i];
const bool isZero = (((key[i] >> bit) & 1u) == 0u);
const uint32_t pos = isZero ? z : (totalZeros + ((uint32_t)i - z));
out[pos] = key[i];
```

**为什么这是稳定的？**

对一个位为 0 的元素 i，它的新位置是 `z = prefix[i]` = 「所有下标小于 i 且位为 0 的元素个数」。因为 `prefix` 是**单调不减**的，所以下标小的 0 元素一定拿到更小的位置——**0 元素之间保持了原顺序**。

对位为 1 的元素 i，新位置是 `totalZeros + (i - z)`，其中 `i - z` = 「所有下标小于 i 且位为 1 的元素个数」。同样的道理，**1 元素之间也保持了原顺序**。

所以整个划分是稳定的。✓

**为什么必须稳定？**

因为 LSD 基数排序的正确性建立在「低位的排序结果不能被高位打乱」上。举个反例：数组 `[02, 01]`（十进制两位数），先排个位：

- 稳定：`[01, 02]`（个位 1 在前）→ 再排十位 → `[01, 02]`。✓
- 不稳定：假设变成 `[01, 02]` 也一样……用 `[12, 11]`：个位 2, 1。稳定排序后是 `[11, 12]`；不稳定可能还是 `[11, 12]`。换个例子：`[21, 11]` 个位都是 1，稳定保持 `[21, 11]`；再排十位得到 `[11, 21]` ✓。若不稳，个位那趟可能得到 `[11, 21]`，再排十位还是 `[11, 21]` ✓。

真正会出问题的是这个：`[13, 23, 12]`，个位 3, 3, 2。
- 稳定：`[12, 13, 23]`（13 在 23 前）→ 排十位（1,1,2）→ `[12, 13, 23]` ✓
- 不稳定：假设个位那趟把 23 排到了 13 前面，得到 `[12, 23, 13]` → 排十位（1,2,1）→ `[12, 13, 23]`……

嗯，这个例子也救回来了。真正致命的是**十位相同**的情况：`[132, 231, 121]`，个位 2,1,1。
- 稳定：`[231, 121, 132]` → 排十位（3,2,3）：2 的 121 先，然后 3 的按原顺序 231, 132 → `[121, 231, 132]` → 排百位（1,2,1）：1 的按原顺序 121, 132；2 的 231 → `[121, 132, 231]` ✓
- 若某一趟不稳定，十位相同的 231 和 132 顺序就可能颠倒，最终变成 `[121, 231, 132]` ✗

**结论：稳定性是 LSD 基数排序的生命线。** 而 CUDA 里的 `atomicAdd` 返回旧值这种「领号」机制是**不可靠的**——它不保证领号顺序和线程下标顺序一致。所以基数排序的散列必须靠**前缀和**算位置，不能靠原子加。

### 3.6 SpMV：三种写法的访存模式对比

把三种写法在同一个 warp 里的访存模式画出来（假设 32 个线程，每行 5 个非零元）：

**CSR 标量（每线程一行）**

```
线程 row:  for (j = rowPtr[row]; j < rowPtr[row+1]; ++j)
              读 values[j]      ← 线程 0 读 values[0..4]，线程 1 读 values[5..9]……
              读 colIdx[j]      ← 同上
              读 x[colIdx[j]]   ← ★ 地址由数据决定，完全随机
```

`values` 和 `colIdx` 的读取是**分段连续**的，基本上还能合并；但 `x[...]` 的读取完全随机，是主要的性能杀手。

**CSR 每 warp 一行**

32 个线程平摊一行的非零元。`values[j]` 里 `j = start + lane`，是连续的 32 个地址 → **完全合并**。`x[colIdx[j]]` 依然是随机的，但 32 个线程的请求可以同时在飞行中，延迟被并行掩盖。

代价是**调度粒度变成 32 线程**：如果大部分行只有 4 个非零元，那么 28 个线程完全浪费。

**ELL**

```
第 k 轮：所有线程读 ellVal[k*n + row]，row 连续 → 完全合并
         读 ellCol[k*n + row]，row 连续 → 完全合并
         读 x[ellCol[...]]               → 依然是随机的
```

ELL 把「结构性」的访存全部变成合并的，只留下 `x` 的 gather 无法避免。而且循环次数对所有线程都一样（`maxNnz`），**没有行间负载不均**。

**所以选择标准是**：

| 矩阵特征 | 推荐格式 |
|---|---|
| 每行非零元个数接近（如 stencil、规则网格） | ELL |
| 每行长度差异很大（如幂律图、有限元） | CSR + 每 warp 一行，或者混合格式 |
| 行数远大于每行长度 | CSR 每线程一行 |

### 3.7 BFS：`atomicCAS` 为什么不能换成 `if`

```cpp
// ✗ 错误的写法
if (dist[v] == -1) {
    dist[v] = level + 1;
    const int pos = atomicAdd(nextSize, 1);
    nextFrontier[pos] = v;
}
```

问题在于「判断」和「写入」是两条独立的指令，中间可以被别的线程插进来：

```
线程 A: 读 dist[v]，发现是 -1
线程 B: 读 dist[v]，发现也是 -1        ← A 还没写
线程 A: 写 dist[v] = level+1
线程 B: 写 dist[v] = level+1           ← 重复写
线程 A: pos = atomicAdd(...) = 5，写 nextFrontier[5] = v
线程 B: pos = atomicAdd(...) = 6，写 nextFrontier[6] = v   ← v 被加了两次！
```

`atomicCAS(addr, compare, val)` 把「读-比较-写」变成一个**不可分割**的操作，并返回**修改前的值**。只有返回 -1 的那个线程才知道「是我把它改掉了」，别的线程会拿到 `level+1`，判断失败。

```cpp
// ✓ 正确的写法
if (atomicCAS(&dist[v], -1, level + 1) == -1) {
    const int pos = atomicAdd(nextSize, 1);
    nextFrontier[pos] = v;
}
```

**这个模式的名字叫「抢占式标记」（claim-once）**，它在 GPU 编程里非常常见：BFS、连通分量、并查集、无锁哈希表、内存池分配……只要「多个线程竞争同一个资源，只允许一个成功」，它就是标准解法。

**版本 2 又优化了什么？**

注意 `bfsExpand` 里对全局 `nextSize` 做 `atomicAdd` 的位置是在**内层循环里**。如果某个顶点的出度是 100，一个线程就能对它做 100 次全局原子加。frontier 大时，成千上万个线程同时争抢同一个全局计数器，L2 里的那个 4 字节会变成整个 GPU 的瓶颈。

`bfsExpandShared` 的做法：
1. 每个线程先把发现的新顶点记在自己的寄存器数组 `local[8]` 里（因为最大出度是 8，够用）。
2. 用 `atomicAdd(&sCount, localLen)` 向**块内**计数器领一段连续下标——共享内存的原子操作比全局快一个数量级。
3. 块内所有线程做完之后，由 0 号线程**一次性**向全局计数器领 `sCount` 个连续位置。
4. 每个线程把 `local[i]` 写到 `sBase + myBase + i`。

全局原子操作次数从「新发现的顶点数」降到「块数」。

### 3.8 浮点精度：Kahan 的那三行到底在干什么

```cpp
const float y = in[i] - c;   // ①
const float t = sum + y;     // ②
c = (t - sum) - y;           // ③
sum = t;
```

假设 `sum = 1000000.0f`，`in[i] = 0.1f`。float 在 1000000 附近的 ulp 是 0.0625，所以 `0.1` 会被舍入成 `0.125` 或者干脆被吃掉。

- ① `y = 0.1f - c`。第一次 `c = 0`，所以 `y = 0.1f`。
- ② `t = 1000000.0f + 0.1f`。真实结果 1000000.1 无法精确表示，被舍入为 1000000.125（假设）。
- ③ `c = (t - sum) - y = (1000000.125 - 1000000.0) - 0.1 = 0.125 - 0.1 = 0.025`。

**`c` 精确地等于「这次加法多加了的部分」**。下一轮里 ① 会把它减掉：`y = 0.1 - 0.025 = 0.075`，于是总和被修正回来。

**为什么它有效？** 因为 ③ 里的 `t - sum` 是**精确的**（Sterbenz 引理：两个相近的浮点数相减不会有舍入误差），而 `(t - sum) - y` 这一减法同样精确。所以 `c` 里记录的就是真实的舍入量。

**代价**：每加一个数从 1 次浮点加法变成 4 次浮点运算，理论上慢 4 倍。但如果你的 kernel 是**带宽受限**（比如求和），浮点单元本来就在闲着，实际耗时可能几乎不变——这也是「用计算换精度」的典型例子。

## 5. 动手练习

### 练习 1 [基础] 给归约加上最值归约

把 `code/lessons/ch05_reduce/reduce.cu` 复制成 `reduce_max.cu`，把加法改成 `fmaxf`，求 1M 个随机 float 的最大值，并和 CPU 结果对拍。

**要点**：
- 单位元从 `0.f` 变成 `-INFINITY`（用 `-CUDART_INF_F` 或 `-1e38f`）。
- `__shfl_down_sync` 归约最后那段改成 `v = fmaxf(v, __shfl_down_sync(mask, v, offset))`。
- 想清楚：归约树的结构和运算是**解耦**的，只要运算是**可交换、可结合**的，同样的代码结构就能用。`max` 满足，`min` 满足，`乘法` 满足，**浮点加法不满足结合律**（这就是精度问题的根源）。

### 练习 2 [基础] 用归约实现向量点积和 L2 范数

写一个 `dot.cu`，实现 `dot(a, b)` 和 `norm2(a) = sqrt(dot(a, a))`，用同一套 warp shuffle 归约，并和 CPU 的 double 结果对比相对误差。

**要点**：
- `dot` 的输入是**两个**数组，网格跨步循环里一次读两个。
- 顺便量一下：`dot(a, b)` 的带宽是多少？理论峰值是多少？和纯求和的差距在哪？（提示：读的数据量翻倍了，但加法次数没变，所以算术强度提高了。）

### 练习 3 [进阶] 把三阶段扫描推广到任意长度

现在的 `scan.cu` 里，如果 `numBlocks > BLOCK` 就会退回 CPU。请把它改成**递归三阶段**：

1. 块内扫描 → `blockTotal`（长度 `numBlocks`）。
2. 如果 `numBlocks > TILE`，对 `blockTotal` 再递归地跑一次三阶段扫描。
3. 否则用一个块扫完。

**要点**：
- 递归深度最多 2 层（1M 元素 → 256 个块 → 1 个块）。
- 用一个循环代替递归会更简单：`while (numElems > TILE) { ... }`。
- 提示：这就是 CUB 的 `DeviceScan` 内部的结构。

### 练习 4 [进阶] 给 Stencil 加上时间分块

`stencil.cu` 现在每次迭代都要完整读写一遍数组（8 MB 读 + 8 MB 写 = 16 MB）。请在共享内存里连续做多次 Jacobi 迭代，减少全局访存：

**做法**：每个块把 tile + halo 搬进共享内存后，在共享内存里迭代 T 次，每次迭代只需要交换边缘的 halo（用相邻块的共享内存或者退回全局内存），最后再写回全局。

**要点**：
- 最简单的版本（不做块间 halo 交换）：每次共享内存迭代后，把 tile 内部（不含 halo）留在共享内存里，只重新加载 halo。这样全局读的次数从 `(BX+2)(BY+2)` 降到 `2*(BX+BY)+4`。
- 进阶版本：对 halo 做「冗余计算」——每个块自己多算一圈，这样完全不需要块间通信。
- 量一下 T = 1、2、4、8 时的耗时曲线，找出拐点（超过某个 T 之后，共享内存的 halo 重载会重新变成瓶颈）。

### 练习 5 [挑战] 让 BFS 也有深层次数

`bfs.cu` 里的随机图只有 5 层。请改成一个 **2D 网格图**（n = G×G 个顶点，每个顶点连上下左右四个邻居，就像 `stencil.cu` 那样），从左上角开始 BFS，统计层次数。

**要点**：
- 网格图的 BFS 层数约为 2G（从角到对角），层数多了，每层一次 `cudaMemcpy` 的 host 往返开销就会被放大。
- 观察：总耗时里有多少花在 kernel 上，多少花在 host 往返上？用 `nsys profile ./bfs` 看时间线上的空隙。
- 挑战：把「判断下一层是否为空」也放到设备端做（用 `cudaLaunchCooperativeKernel` + `grid.sync()`，见[第 3 章](ch03_同步通信与原子操作.md)），消掉所有的 host 往返。

### 练习 6 [挑战] 构造一个真正能让朴素求和崩掉的例子

现在的 `numeric.cu` 误差不够震撼。请构造一个数据，让「每线程 float 累加」的相对误差超过 1%，而「分块 + double 汇总」的误差仍在 1e-7 以下。

**提示**：让累加器长时间停留在很大的值上。比如：

```cpp
// 前一半是巨大的数，后一半是小到会被吃掉的数
in[i] = (i < n/2) ? 1.0e8f : 1.0f;
```

理论真值 = n/2 × 1e8 + n/2 × 1.0。在 float 下，1e8 附近的 ulp 是 8，所以每个 1.0 都会被吃掉一半左右。对比三种实现的最终结果。

**进阶**：把数据改成「交替大小」，观察误差如何随数据排布变化。这能让你真正理解「浮点加法不满足结合律」意味着什么——**同样的数据、同样的算法，只因为并行划分方式不同，结果就可能不同**。这也是为什么并行数值库要提供「结果可复现」的选项。

## 6. 常见错误与排查

| 错误信息 / 现象 | 原因 | 解决办法 |
|---|---|---|
| `cudaErrorIllegalAddress` | stencil 的 halo 没处理边界，读了 `in[-1]` | 用 3.3 节的 `loadIn()` 做边界检查；用 `compute-sanitizer ./stencil` 定位到具体行 |
| `__syncthreads()` 死锁（kernel 挂住、`cudaDeviceSynchronize` 不返回） | 归约树里 `if (tid < stride) { ... __syncthreads(); }` 把屏障写进了分支 | 屏障必须在所有线程都能到达的位置。把它挪到 `if` 外面 |
| 结果时对时错、每次运行不一样 | BFS 里只写了 `if (dist[v] == -1)` 而没用 `atomicCAS` | 换成 `atomicCAS`，见 3.7 节 |
| 归约结果和 CPU 差一点点 | 浮点加法不满足结合律，归约顺序不同 | 用相对误差判据（`rel < 1e-4`），或者改用 double 累加 |
| 求和结果偏差很大（>1%） | 每线程 float 累加器涨得太大，小数被吃掉 | 改用分块求和 + double 汇总，见 2.8 节 |
| 扫描结果只对了第一段，后面全是错的 | 三阶段扫描漏了阶段 3（`addBlockOffsets`） | 检查是否真的执行了 3 个 kernel；块内扫描给出的是「段内前缀」，不是「全局前缀」 |
| 双调排序结果完全乱掉 | 比较器的方向判断写反了，或者块内用了全局下标 | 块内 `k <= TPB` 时用 `tid & k`；块间必须用 `i & k`。检查 `if (ixj > i)` 有没有写 |
| 双调排序前一半对、后一半错 | `bitonicSortTile` 只处理了 `k <= TPB`，块间归并的 `k` 起始值写错 | 块间循环必须从 `k = TPB * 2` 开始 |
| 基数排序结果错乱 | 散列不「稳定」（用了 `atomicAdd` 领号而不是前缀和） | 必须用 `prefix[i]` 算位置，见 2.5 节；检查 `totalZeros` 算对没有（独占扫描要加回最后一个元素的谓词） |
| `spmvEll` 结果不对 | ELL 数组的下标写成了行主序（`ellVal[row*maxNnz+k]`） | ELL 是**列主序**：`ellVal[k*nrows + row]` |
| SpMV 的 `__ldg` 报错 | `__ldg` 需要 Compute Capability >= 3.5 | 现代显卡都满足；如果编译目标过低，直接改成普通下标访问 |
| 共享内存不够（`too much shared data`） | `s[TILE]` 的 TILE 设得太大 | 一般卡的每块共享内存上限是 48 KB（可配置到 96 KB+）。TILE = 4096 个 float = 16 KB 是安全值 |
| `cudaErrorLaunchOutOfResources` | 块大小 × 寄存器数超出了 SM 资源 | 用 `-Xptxas -v` 看寄存器数，加 `__launch_bounds__` 限制，或减小 BLOCK |
| 性能比 v1 还差 | 网格大小设得不对，SM 没喂饱 | 用 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 算最优网格；一般让 grid 数 = SM 数 × 每 SM 最多驻留块数 |
| `ncu` 报 `ERR_NVGPUCTRPERM` | Linux 下没有权限读性能计数器 | `sudo sh -c 'echo 1 > /proc/sys/kernel/perf_event_paranoid'`，或者用 `sudo ncu ...` |
| CG 不收敛 / 残差震荡 | 矩阵不是对称正定的，或者 `alpha` 的符号写错 | 5 点差分是 SPD 的；检查 `r -= alpha * Ap` 有没有写成 `+=` |
| `radix_sort` 的 `static_assert` 失败 | N 不是 TILE 的整数倍，或者块和数量超过 BLOCK | 改 N 或者改 ITEMS；或者按练习 3 的办法做递归扫描 |

## 7. 本章小结

### 7.1 要点清单

1. **先归类，再动手**。Map / Reduce / Scan / Scatter / Gather / Stencil / Sort / SpMV / 图算法——九种模式覆盖了 GPU 上 95% 的问题。
2. **归约的四步演进**，每一步解决一个具体问题：
   - v1 交错寻址 → warp 发散 + bank conflict + 昂贵的取模；
   - v2 顺序寻址 → 活跃线程落在整数条 warp 上，满 bank 带宽；
   - v3 展开 + 每线程多元素 → 减少块数与同步次数，提升 ILP；
   - v4 warp shuffle → 最后 5 轮彻底摆脱共享内存和 `__syncthreads()`。
3. **扫描是分治的**：块内 Blelloch → 扫描块和 → 加回偏移。Kogge-Stone 是 O(n log n) 工作量，Blelloch 是 O(n)，生产代码一律用后者。
4. **共享内存 tiling 的本质是「用一次全局读，换多次复用」**。Stencil 靠 halo、矩阵乘靠分块、SpMV 靠 ELL 的列主序排布——都是同一个思想。
5. **halo 的四个角必须单独处理**，这是 stencil 最经典的 bug。
6. **双调排序的比较器方向由 `(i & k)` 决定**：`== 0` 升序，`!= 0` 降序。它规整但工作量大（O(n log²n)）。
7. **基数排序必须稳定**，而稳定性只能靠前缀和实现——`atomicAdd` 领号不保证顺序。这就是「scan 是排序的基石」的具体含义。
8. **SpMV 永远是带宽受限的**。优化的方向是「让结构性访存合并」（ELL、行内并行），而不是「算得更快」。
9. **BFS 的 `atomicCAS` 是「抢占式标记」模式**，用来保证「多个线程争一个资源，只允许一个成功」。它的全局原子操作可以用「块内攒批」降到 1/块。
10. **浮点加法不满足结合律**，这是并行数值计算必须时刻记着的事。默认用「float 分块 + double 汇总」，需要极限精度时用 Kahan。
11. **性能一定要用数据说话**：每改一处就 profile 一次，`Duration` / `Memory Throughput` / `Warp Stall Reasons` 三个指标基本能定位所有问题。

### 7.2 自检问题（附答案要点）

**Q1：为什么归约里「顺序寻址」比「交错寻址」快？**

> 两点：(a) 活跃线程落在整数条 warp 上，消除了 stride ≥ 32 时的 warp 发散，并把昂贵的取模换成一次比较；(b) 每条共享内存 load 指令里 32 个线程访问连续的 32 个地址，落在 32 个不同 bank 上，零冲突且满带宽；交错寻址在 stride=1 时只有 16 个线程活跃，共享内存带宽用了一半。

**Q2：Blelloch 的 down-sweep 里为什么要把根节点清零？**

> 因为 up-sweep 结束后根节点存的是**总和**，而独占式扫描要求最后一个输出是「前 n-1 个元素之和」。把根清零相当于给整棵树「减去它自己」，之后的分发过程自然产生独占式前缀和。这是把包含式转成独占式最优雅的做法。

**Q3：三阶段扫描里，第二阶段（扫描块和）为什么可以用一个块完成？**

> 因为块的数量是 `N / TILE`，比 N 小了好几个数量级（1M / 4096 = 256）。256 个元素用一个 256 线程的块做一次 Blelloch 就够了。如果块的数量仍然超过一个块能处理的范围，就递归地再做一次三阶段——这就是 CUB `DeviceScan` 的结构。

**Q4：双调排序的方向判断 `(i & k) == 0` 中，`k` 是什么含义？**

> `k` 是当前正在构造 / 归并的**双调序列的长度**。下标 `i` 的第 log₂k 位是 0，说明它落在长度为 k 的块的前一半，这一半应该是升序；是 1 则落在后一半，应该降序。升一半、降一半合起来就是一个双调序列。

**Q5：基数排序里为什么不直接用 `atomicAdd` 领位置？**

> 因为 `atomicAdd` 返回旧值这个机制**不保证领号顺序和线程下标顺序一致**。线程 A 可能比线程 B 晚发出请求却先拿到号，于是同一个桶内元素的相对顺序被打乱，划分就不再稳定，LSD 基数排序的正确性随之崩塌。必须用前缀和（`prefix[i]`）来计算位置，它严格保证了「下标小的先」。

**Q6：SpMV 为什么很难跑到带宽峰值？**

> (a) `x[colIdx[j]]` 是间接寻址的随机 gather，无法合并、无法预取；(b) 每行非零元个数不同，同一个 warp 内线程的循环次数不一样，负载不均；(c) CSR 需要同时读 `colIdx`（4 字节）和 `values`（4 字节），有用的数据只占一半。ELL 格式能解决 (b)，把结构性访存变成合并的，但 (a) 和 (c) 是稀疏矩阵的本质困难。

**Q7：为什么说「float 分块求和 + double 汇总」几乎没有代价？**

> 因为汇总的只是几千个块级别部分和（1M / 1024 ≈ 1000 个），用 double 搬运的数据量可以忽略不计（4 KB vs 4 MB）。而块内仍然是 float 累加，浮点吞吐不变。所以这是一个「几乎免费的精度提升」——除非你的 kernel 是计算受限的，否则看不出耗时差异。

**Q8：CG 每次迭代的访存代价大概是多少？**

> 每次迭代有 1 次 SpMV、2 次 dot、3 次 axpy/axpby。每个 kernel 都要把长度 N 的数组完整读一遍（dot 读两遍、axpy 读两个写一个）。粗略估计每次迭代的访存字节数约为 `(1 + 2 + 2 + 3 + 3 + 2) × N × 4` ≈ 13 × N × 4 字节。N = 1M 时约 52 MB，除以 0.09 ms 得到约 580 GB/s——已经接近 RTX 3060 的带宽峰值了。所以 CG 的优化方向是**减少 kernel 数量（融合）**，而不是优化单个 kernel。

## 8. 下一章预告

到这里，你已经能用「原语 + 模式」把绝大多数并行算法写出来了。但你可能已经注意到，本章的代码里有一些**为了讲清楚原理而刻意简化的地方**：

- 双调排序用了 155 次 kernel 启动，一次只做一层；
- 基数排序每趟只处理 1 位，32 趟 × 5 个 kernel；
- 归约 v4 的 `ELEMS` 是拍脑袋写的 4；
- WMMA 那一段还没讲——我们甚至没有用上张量核心。

这些「不够极致」的地方，需要一些**现代 GPU 才有的硬件能力**才能补上：

- **动态并行**让你在设备端启动 kernel，把递归和自适应细分做成一个 kernel 调用；
- **Tensor Core / WMMA** 让一次指令完成 16×16×16 的矩阵乘，FP16 吞吐是 FP32 的 8 倍以上；
- **`cp.async` 异步拷贝**让数据从全局内存直接进共享内存、绕过寄存器，是「多阶段软件流水线」成立的前提；
- **线程块集群 + 分布式共享内存**让块之间可以直接读写对方的共享内存，halo 交换不用绕道显存；
- **统一内存进阶（`cudaMemAdvise` / 预取）**、**虚拟内存管理 API（VMM）**、**多 GPU P2P 与 NCCL**、**CUDA Graphs 的条件节点与循环节点**……

[第 6 章](ch06_CUDA高级特性.md) 就是讲这些。它的风格和本章不太一样：本章是「同一个算法的逐步优化」，第 6 章是「一个特性一个完整示例」，每个示例都会标注它需要的 Compute Capability 和编译参数。

> **在进入第 6 章之前，请确保你已经把本章的归约和扫描亲手敲过一遍。** 后面所有的优化技巧——cp.async 的分块加载、WMMA 的 fragment 布局、集群的 DSM 交换——底层都还是「合并访存 + 共享内存 + 同步」这三件事。基本功不牢，第 6 章会变成「抄代码但不知道为什么」。
