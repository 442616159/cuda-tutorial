## 1. 概念讲解

### 1.1 一个比喻：CPU 是博士，GPU 是几千个小学生

#### 🧱 场景：搬 10000 块砖，你会雇谁？

先建立最重要的一个直觉。

想象你要搬 10000 块砖：

- **CPU** 像一个**博士生**。他能做极其复杂的推理（分支预测、乱序执行、巨大的缓存），但只有 8～16 个"博士生"在干活。搬砖这种简单重复的活，他们干得慢，而且大部分时间在互相商量"这砖该放哪"。
- **GPU** 像一个**几千人的小学生施工队**。每个小学生只会做最简单的事（一次乘加运算），不会独立思考，但人多，且**所有人同时做同一件事**。搬砖这种活他们干得飞快。

**❌ 如果你让博士生去搬砖**：他一边搬一边思考人生，效率极低。

**✅ 如果你让小学生去做微积分**：他根本做不了。

> 🎯 **这就是整个 GPU 编程的核心思想**：
> **不是"谁更强"，而是"谁更适合这件事"。**
> 复杂逻辑交给博士，重复劳动交给施工队。

这就是**异构计算（Heterogeneous Computing）**的核心思想：

> 让 CPU 负责逻辑复杂、分支多、串行依赖强的部分；
> 让 GPU 负责数据量大、每个元素处理方式相同、彼此独立的部分。

> 💡 **怎么判断一件事该给谁做？** 看两个特征：
> - **"每个数据的处理方式是不是一样的？"** 一样 → 适合 GPU
> - **"这些数据之间有没有依赖？"** 没依赖 → 适合 GPU
>
> 搬砖：每块砖搬法一样、互相不依赖 → **GPU 的活** ✅
> 解一道数学证明题：每一步都依赖上一步 → **CPU 的活** ✅

对应到 CUDA 里的角色划分：

| 角色                | 别名    | 指谁                    | 职责                                       |
| ------------------- | ------- | ----------------------- | ------------------------------------------ |
| **Host（主机）**    | CPU 端  | 你的 CPU 和它的内存     | 分配显存、拷贝数据、启动核函数、读回结果   |
| **Device（设备）**  | GPU 端  | 你的 NVIDIA 显卡和它的显存 | 执行成千上万个线程做并行计算            |

**严谨定义**：Host 指的是运行 CUDA 运行时的主处理器及其可访问内存（主机内存）；Device 指的是通过 PCIe/NVLink 连接、由 CUDA 驱动管理的协处理器（GPU）及其独立显存。Host 与 Device 各自有独立的地址空间，数据必须显式或隐式地搬运。

> ⚠️ **"各自有独立的地址空间"这句话非常重要**，它是后面无数 bug 的根源：
> CPU 的内存（`malloc` 出来的）**GPU 看不见**；
> GPU 的显存（`cudaMalloc` 出来的）**CPU 也不能直接读**。
> **两边要交换数据，必须"搬"**——这就是下一张图里第 2 步和第 4 步在做的事。

一个典型的 CUDA 程序长这样：

```text
   Host 端（CPU）                          Device 端（GPU）
   ───────────────                         ────────────────
   1. cudaMalloc 申请显存      ──────►
   2. cudaMemcpy 拷贝数据      ──────►     显存里有了输入数据
   3. 启动核函数 kernel<<<>>>  ──────►     [几千个线程同时开跑]
                                            每个线程读自己的数据、
                                            算自己的结果、写回去
   4. cudaMemcpy 拷回结果      ◄──────     显存里有了输出数据
   5. 打印/校验
```

请记住这张图，后面 8 章讲的都是"怎么让第 3 步更快"。

> 🎯 **这张图就是全书的地图**：
> - **第 1 章**讲第 3 步里"几千个线程"是怎么编号、怎么分工的；
> - **第 2 章**讲第 2/4 步的搬运怎么能更快（合并访存），以及第 3 步内部怎么减少访存；
> - **第 3 章**讲这么多线程怎么协调（同步、原子操作）；
> - **第 4 章**讲怎么测量"到底快了多少"。

### 1.2 nvidia-smi：第一道体检

#### 🩺 场景：去医院体检，第一项永远是量体温

**nvidia-smi** 是 NVIDIA System Management Interface 的缩写，显卡驱动自带的管理工具。安装完驱动它就在系统 PATH 里了，**不需要装 CUDA Toolkit**。

> 🩺 **为什么它是"第一道体检"？**
> 因为它回答一个最根本的问题：**"我的显卡，系统认不认？"**
> 这个问题不先解决，后面装再多东西都是白费——**就像病人还没量体温，你就开始开药方**。

在命令行（Windows 用 CMD 或 PowerShell，Linux 用终端）敲：

```bash
nvidia-smi
```

你应该看到类似这样的输出（`在 RTX 3060 + 驱动 536.xx 上实测大致如下，你的机器可能不同`）：

```text
+---------------------------------------------------------------------------------------+
| NVIDIA-SMI 536.99                 Driver Version: 536.99       CUDA Version: 12.2     |
|-----------------------------------------+----------------------+----------------------+
| GPU  Name                     TCC/WDDM  | Bus-Id        Disp.A | Volatile Uncorr. ECC |
| Fan  Temp   Perf          Pwr:Usage/Cap |         Memory-Usage | GPU-Util  Compute M. |
|=========================================+======================+======================|
|   0  NVIDIA GeForce RTX 3060      WDDM  | 00000000:01:00.0  On |                  N/A |
| 30%   45C    P8              18W / 170W |    512MiB / 12288MiB |      2%      Default |
+-----------------------------------------+----------------------+----------------------+
```

**看这三行就够了**：

| # | 看什么 | 说明 |
| - | ------ | ---- |
| 1 | `NVIDIA-SMI 536.99` / `Driver Version: 536.99` | 你的**驱动版本** |
| 2 | `CUDA Version: 12.2` | ⚠️ **这个数字不是"你装的 CUDA 版本"**！它表示"当前驱动最高支持的 CUDA 运行时版本" |
| 3 | `NVIDIA GeForce RTX 3060` | 显卡型号，去 NVIDIA 官网可查到它的计算能力 |

#### ⚠️ 新手第一大坑：把 `CUDA Version` 当成"我装的版本"

这是**几乎每个人都会踩一次**的坑，值得单独讲清楚。

```text
❌ 错误理解：
   "nvidia-smi 显示 CUDA Version 12.2，所以我装的是 CUDA 12.2。"

✅ 正确理解：
   "nvidia-smi 显示 CUDA Version 12.2，说明我的驱动最多能支持到 12.2。
    我实际装的是哪个版本，要看 nvcc --version。"
```

**那这个数字到底有什么用？** 它是一道"**天花板**"：

| 你的驱动显示 | 你可以装的 Toolkit |
| ------------ | ------------------ |
| CUDA Version: 12.2 | ✅ 11.8、12.0、12.2 |
| CUDA Version: 12.2 | ❌ **12.4**（超了，装不了） |

**最重要的规则**：

> 🎯 **驱动版本决定你能用的最高 CUDA Toolkit 版本，而不是反过来。**

也就是说：驱动是 536.99（支持到 CUDA 12.2），**你可以装旧版**（11.8、12.0 都能跑，新驱动向下兼容），但**装不了更新的**（12.4 会失败）。

> 💡 **一个类比**：驱动就像"你家的电源插座规格"。
> 它决定了**你最多能用多大功率的电器**；但你完全可以插一个功率更小的电器——**旧的能用，新的不行**。

如果 `nvidia-smi` 报"不是内部或外部命令"，见 [第 6 节排查表](#61-环境类错误)。

#### 🐧 Linux 上的两个补充命令

```bash
# 从 PCI 总线角度看有没有 NVIDIA 设备（不依赖驱动）
lspci | grep -i nvidia

# 看内核模块有没有加载（驱动装没装好）
lsmod | grep nvidia
```

**这两个命令的组合，能瞬间定位"是硬件问题还是驱动问题"**：

| `lspci` 有设备 | `nvidia-smi` 正常 | 结论 |
| -------------- | ----------------- | ---- |
| ❌ 无 | ❌ 报错 | **硬件不在**：卡没插好 / 虚拟机没直通 / 是 AMD/Intel 显卡 |
| ✅ 有 | ❌ 报错 | **硬件在，驱动没装好** ← **最常见的情况** |
| ✅ 有 | ✅ 正常 | 环境没问题，可以继续 |

### 1.3 计算能力（Compute Capability, CC）

#### 📱 场景：就像手机的"型号 + 代数"

**生活化比喻**：CC 就像是显卡的"型号代号 + 能力等级"，跟你买手机看到"骁龙 8 Gen 3"是同一类东西。

> 📱 **为什么需要这样一个编号？**
> 因为 GPU 每一代都会**新增指令**、**改变内部结构**。
> 你写的程序得知道"我这块卡会不会某个指令"——总不能每次都去查"RTX 3060 支持 cp.async 吗？"
> **CC 就是这个"能力标签"。**

它由两部分组成：

```text
   CC 7.5    ← 主版本号 7，次版本号 5
   │  │
   │  └─ 次版本：同一代架构内的小改款（如 7.0 → 7.5 加了 Tensor Core 的改进）
   └──── 主版本：架构代际（7 = Volta/Turing，8 = Ampere，9 = Hopper/Ada）
```

**严谨定义**：计算能力是 NVIDIA 给每一代 GPU 架构定义的版本号，格式为 `major.minor`。它决定：

- SM 里各类功能单元的数量与组织方式；
- 支持哪些指令（如 `mma.sync`、`cp.async`、warp shuffle 的变体）；
- 各类资源的硬性上限（每块最大线程数、共享内存上限、寄存器数）；
- 编译时 `-arch=sm_XY` 该填什么。

**常见显卡与 CC 对照表**：

| 架构          | CC            | 代表显卡             | 本书示例可否跑通       |
| ------------- | ------------- | -------------------- | ---------------------- |
| Kepler        | 3.5 / 3.7     | GTX 780              | 勉强，部分特性不可用   |
| Maxwell       | 5.0 / 5.2     | GTX 980              | 前 5 章可跑            |
| Pascal        | 6.0 / 6.1 / 6.2 | GTX 1080、Tesla P100 | 前 5 章完全可跑      |
| Volta         | 7.0           | Tesla V100           | 全部基础特性           |
| Turing        | 7.5           | RTX 2080、T4         | 全部基础特性           |
| Ampere        | 8.0 / 8.6     | A100、RTX 3090 / 3060 | 全部基础特性          |
| Ada Lovelace  | 8.9           | RTX 4090 / 4060      | 全部基础特性           |
| Hopper        | 9.0           | H100                 | 全部基础特性           |

**怎么查自己显卡的 CC？** 三个办法：

1. 跑本章的 `device_query.cu`（**最准**）；
2. 维基百科 "CUDA" 词条的 "GPUs supported" 表格；
3. 打开 `nvidia-smi` 看型号，再去 NVIDIA 官网查。

#### 🎯 为什么 CC 对你很重要？（两个方向都会翻车）

编译时 `-arch=sm_75` 里的 `75` 就是 CC。**这个数字填错，两个方向都会出问题**：

| 你填的 | 你的卡 | 会发生什么 | 严重程度 |
| ------ | ------ | ---------- | -------- |
| `sm_75`（偏低） | 8.6 | 走 **PTX JIT**，能跑，但**启动慢、用不到新指令** | 🟡 轻微 |
| `sm_89`（偏高） | 8.6 | 报 `no kernel image is available for execution on the device` | 🔴 直接跑不了 |
| **不填** | 任意 | `nvcc` 用默认目标，**可能不是你的卡**，也可能编一堆用不上的架构 | 🟡 编译慢 |

> ⚠️ **"偏高"比"偏低"严重得多**：偏高是**直接跑不起来**，偏低只是慢一点。
> 所以**不确定的时候，宁可填低一点**（比如填 `sm_75` 能在所有 7.5 以上的卡上跑）。

> 💡 **本章后面 [练习 0.2](#练习-02-基础-制造一次架构不匹配) 会让你亲手制造一次"架构不匹配"**，亲眼看到这个错误信息——**见过一次，以后就不会慌了**。

### 1.4 CUDA Toolkit 里有什么

#### 🧰 场景：一个"开发工具箱"，不是一把锤子

**CUDA Toolkit** 是 NVIDIA 提供的一整套开发工具，**不是单一程序**。

> 🧰 **新手常见误解**："我装了 CUDA"——装了**哪个** CUDA？
> 装完 Toolkit，你得到的是一整箱工具，其中**最常用的只有 4 个**：

```text
   ┌──────────────────────────────────────────────────┐
   │  CUDA Toolkit（一个工具箱）                        │
   ├──────────────────────────────────────────────────┤
   │  ⭐ nvcc              ← 编译器（本章主角）         │
   │  ⭐ compute-sanitizer ← 查内存越界/竞态（保命工具）│
   │  ⭐ ncu / nsys        ← 性能分析（第 4 章）        │
   │  ⭐ cuda-gdb          ← GPU 调试器                 │
   │  ──────────────────────────────────────────────  │
   │  头文件 / 库 / 数学库 / 官方样例（支撑上述工具）   │
   └──────────────────────────────────────────────────┘
```

装完它你会得到：

| 组件                          | 路径（Linux 默认 `/usr/local/cuda-12.x/bin`） | 作用                                        |
| ----------------------------- | --------------------------------------------- | ------------------------------------------- |
| `nvcc`                        | `bin/nvcc`                                    | **CUDA 编译器**，本章主角                   |
| `cuda-gdb`                    | `bin/cuda-gdb`                                | GPU 调试器                                  |
| `compute-sanitizer`           | `bin/compute-sanitizer`                       | 内存越界/竞态检测（旧名 `cuda-memcheck`）   |
| `ncu`                         | `bin/ncu`                                     | Nsight Compute，逐 kernel 性能分析（第 4 章用） |
| `nsys`                        | `bin/nsys`                                    | Nsight Systems，系统级时间线（第 4 章用）   |
| `cuobjdump` / `nvdisasm`      | `bin/`                                        | 反汇编，看 SASS 汇编                        |
| 头文件                        | `include/cuda_runtime.h` 等                   | 你的代码 `#include` 的东西                  |
| 静态/动态库                   | `lib64/libcudart.so` 等                       | 链接时用                                    |
| 数学库                        | `lib64/libcublas` / `libcufft` …              | cuBLAS / cuFFT 等（第 7 章用）              |
| 官方样例                      | `samples/`（新版需单独从 GitHub 下）          | deviceQuery 等参考实现                      |

**版本选择的实用建议**：

| 建议 | 理由 |
| ---- | ---- |
| 装 **CUDA 11.8** 或 **CUDA 12.x** | 别装太老的（10.x 及以下很多新教材对不上） |
| 要跑 PyTorch 的话，**先看 PyTorch 官方支持的 CUDA 版本** | 装与之匹配的，能省掉一大堆麻烦 |
| 一台机器上**可以共存多个 CUDA 版本** | Linux 装在 `/usr/local/cuda-11.8`、`/usr/local/cuda-12.2`，用软链接 `/usr/local/cuda` 切换 |

> ⚠️ **"装哪个版本"这个决定，最好在装之前就想清楚**。
> 因为**重装 CUDA 经常比装第一次更麻烦**（残留的环境变量、软链接、PATH 顺序都要清理）。
> **如果你的目的是跑 PyTorch**，那就直接按 PyTorch 官网给的命令装，**别自己发挥**。

### 1.5 nvcc 编译流程：一个 `.cu` 文件的两条命

这是本章最"硬"的知识点，也是最能体现理解深度的地方。

#### 📄 场景：一份双语合同，要分别翻译给两个人

**生活化比喻**：一个 `.cu` 文件就像一份**双语合同**。合同里有些条款是给"甲方（CPU）"看的，有些是给"乙方（GPU）"看的。

> 📄 `nvcc` 的工作就是：**把合同拆开**
> - 甲方部分交给 `gcc`/`cl.exe` 翻译成**甲方的语言**（x86 机器码）；
> - 乙方部分交给 `ptxas` 翻译成**乙方的语言**（SASS 机器码）；
> - 最后把两份译文**装订成一本双方都能读的书**（可执行文件）。

**🧩 为什么不能只翻译一次？** 因为 CPU 和 GPU **说的是两种完全不同的"语言"**：

| | CPU（甲方） | GPU（乙方） |
|---|---|---|
| 指令集 | x86 / ARM | SASS |
| 谁翻译 | `gcc` / `cl.exe` | `ptxas` |
| 擅长 | 复杂逻辑、分支 | 海量并行 |

**这正是 [1.1 节](#11-一个比喻cpu-是博士gpu-是几千个小学生) 那个比喻的延续**——两个不同的角色，自然需要两套不同的编译器。

**严谨流程**：

```text
                    hello.cu （一份 .cu 源文件）
                          │
                          ▼
     ┌────────────────────────────────────────┐
     │ 第 1 步：nvcc 前端做"分离"              │
     │   - 扫描 __global__ / __device__ 标记   │
     │   - 把 GPU 代码切出来，把 CPU 代码留下  │
     └───────┬────────────────────┬───────────┘
             │                    │
   GPU 代码  │                    │  CPU 代码
             ▼                    ▼
   ┌──────────────────┐   ┌───────────────────────┐
   │ 编译成 PTX 虚拟汇编│   │ 去掉 __global__ 的函数体│
   │ (并行线程执行架构) │   │ 换成一次"启动核函数"的  │
   │  .ptx 文件        │   │ 运行时调用             │
   └────────┬─────────┘   └───────────┬───────────┘
            │                         │
            ▼                         ▼
   ┌──────────────────┐   ┌───────────────────────┐
   │ ptxas 把 PTX 汇编 │   │ 交给宿主编译器         │
   │ 成 SASS 机器码    │   │ (gcc / cl.exe) 编译    │
   │ (真正给 GPU 跑的) │   │ 成 CPU 的 .o 目标文件  │
   └────────┬─────────┘   └───────────┬───────────┘
            │                         │
            └────────────┬────────────┘
                         ▼
              ┌─────────────────────────┐
              │ fatbin：把 SASS/PTX 打包 │
              │ 成一个"胖二进制"段       │
              └────────────┬────────────┘
                           ▼
              ┌─────────────────────────┐
              │ host 链接器把所有 .o 和  │
              │ libcudart 链接成可执行文件│
              └────────────┬────────────┘
                           ▼
                    hello.exe / a.out
```

#### 🔍 关键一步：`__global__` 函数在 CPU 侧变成了什么？

这是最容易看不懂的地方。同一个 `helloFromGPU`，在两边**长得完全不一样**：

```cpp
// 你写的代码（一份）
__global__ void helloFromGPU() { printf("..."); }
```

```text
✅ GPU 侧（真身）：
   编译成 SASS 机器码，放进 fatbin 段。
   运行时由 GPU 真的执行这段代码。

✅ CPU 侧（替身）：
   函数体被"掏空"了！变成一个空壳 ——
   调用它 = "向 GPU 发一条启动命令"，仅此而已。
```

> 🎯 **这就是为什么 `helloFromGPU<<<1,1>>>()` 这行"看起来像函数调用，其实不是"**：
> 它在 CPU 侧被翻译成 `cudaLaunchKernel(...)` 这样的运行时调用。
> **CPU 从来不执行 `printf` 那一行**——它只是"派活"。

#### 📚 几个必须理解的名词

| 名词 | 是什么 | 类比 |
| ---- | ------ | ---- |
| **PTX** | **虚拟**的 GPU 汇编语言，与具体架构无关 | 世界语（谁都能翻译） |
| **SASS** | 真正跑在具体 GPU 上的机器指令，与架构强相关 | 方言（只有本地人懂） |
| **JIT** | 运行时把 PTX **现场**编译成当前架构的 SASS | 现场口译 |
| **Fatbin** | 把多个架构的 SASS + PTX 一起打包的容器段 | 一本"多语言对照词典" |

**逐个展开**：

- **PTX（Parallel Thread Execution）**：一种**虚拟**的 GPU 汇编语言，由 NVIDIA 定义、与具体架构无关。它像一个"中间语言"。
- **SASS（Shader Assembly）**：真正跑在具体 GPU 上的机器指令，与架构强相关。`sm_75` 的 SASS 不能跑在 `sm_89` 上（但通常能向上兼容执行 PTX）。
- **JIT（Just-In-Time）编译**：可执行文件里如果**同时**塞了 PTX 和 SASS，当它在"没被提前编译过的架构"上运行时，驱动会**现场**把 PTX 编译成该架构的 SASS。**这就是为什么有时第一次运行某个程序特别慢**——它在做 JIT。
- **Fatbin（胖二进制）**：把多个架构的 SASS + PTX 一起打包的容器段。`nvcc` 默认会生成一个包含多架构的 fatbin。

> 🎯 **用"词典"的比喻串起来**：
> - **SASS 是方言**：本地人（你的卡）一看就懂，**零延迟**，但换了地方就没人懂。
> - **PTX 是世界语**：谁都得先翻译一遍才能用，**有延迟**，但**到哪儿都能用**。
> - **fatbin 就是一本对照词典**：把"几种方言 + 世界语"都装订在一起，**到哪儿都能查**。
> - **JIT 就是现场口译**：查不到方言，就现场把世界语翻成当地方言——**第一次翻要时间，翻完记在本子上（缓存），下次就快了**。

#### 💥 这对你意味着什么？（症状 → 病因对照）

| 现象 | 原因 |
| ---- | ---- |
| 程序第一次运行慢，后面快 | 驱动在做 PTX→SASS 的 JIT 编译 |
| 报 `no kernel image is available` | fatbin 里没有你显卡架构的码，且没带可 JIT 的 PTX |
| `-arch=sm_XX` 指定的反而是旧架构 | 会走 JIT，性能可能略差、启动略慢 |
| 编译很慢 | 每多一个 `-gencode` 架构就多编译一遍 |

**实践建议**：自己开发时用**确切**的 `-arch=sm_XX`（编译快、性能好）；要发布给别人用时，用多个 `-gencode` 打包几个常见架构，并**带上 PTX 兜底**：

```bash
nvcc -O3 \
     -gencode arch=compute_75,code=sm_75 \
     -gencode arch=compute_86,code=sm_86 \
     -gencode arch=compute_89,code=sm_89 \
     -gencode arch=compute_90,code=compute_90 \
     hello.cu -o hello
```

注意最后一行 `code=compute_90`：它表示**只生成 PTX 不生成 SASS**，用作未知架构的兜底（让驱动去 JIT）。

> 💡 **`compute_XX` 和 `sm_XX` 有什么区别？** 这是个高频混淆点：
> - **`sm_75`** = "生成能在 sm_75 上**直接跑**的 SASS"（方言）
> - **`compute_75`** = "生成面向 7.5 能力的 **PTX**"（世界语）
>
> 所以 `arch=compute_75,code=sm_75` 表示"按 7.5 的标准，生成 7.5 的方言"；
> 而 `arch=compute_75,code=compute_75` 表示"按 7.5 的标准，生成世界语（不做方言）"。

### 1.6 核函数（Kernel）是什么

#### 📖 场景：一本发给几千人的工作手册

**生活化比喻**：核函数就是"施工队的工作手册"。你把这个手册复印几千份，每个工人（线程）拿一份，**每个人都从头到尾把手册执行一遍**，只不过每人负责的数据不同（靠 `threadIdx` 区分）。

> 📖 **这个比喻能解释三件新手最容易困惑的事**：

**困惑 1：为什么写了一次 `printf`，却打印了很多次？**

```cpp
__global__ void helloFromGPU() {
    printf("Hello!\n");     // ← 你只写了 1 次
}
helloFromGPU<<<1, 4>>>();   // ← 但会打印 4 次！
```

👉 **因为手册发给了 4 个工人，每个人都执行了一遍**。
**核函数体是"每个线程各执行一遍"的**，不是"整体执行一次"。

**困惑 2：几千个线程做同样的事，怎么保证不重复干活？**

👉 **靠 `threadIdx` / `blockIdx` 这些"工号"**。
手册里的代码写的是"**你，第 N 号工人，去搬第 N 块砖**"——每个工人执行同一份手册，但**N 不同，所以干的活不同**。

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;   // 算出"我是几号"
data[i] = ...;                                    // 干我自己那份活
```

**困惑 3：为什么核函数不能有返回值？**

👉 因为**手册是"派发"出去的，不是"调用"的**。
你不可能站在几千个工人面前等"谁先做完谁举手把结果交给我"——**你只能让他们把结果放到指定的筐里（显存），然后自己去取**。

**严谨定义**：核函数是用 `__global__` 限定符声明的函数，它在设备上执行、由主机代码通过 `<<<...>>>` 执行配置语法启动。一次启动会产生一个**网格（grid）**，网格由若干**线程块（block）**组成，每个块由若干**线程（thread）**组成；网格中每个线程都会执行一次核函数体。

本章你只需要知道最基础的形态：

```cpp
__global__ void helloFromGPU() {   // 声明 + 定义
    // 每个线程都会执行这里的代码
}

int main() {
    helloFromGPU<<<1, 1>>>();      // 启动：1 个块，每块 1 个线程
}
```

**`<<<>>>` 里两个数字的含义**（本章先记住这个，第 1 章会展开）：

```text
helloFromGPU<<< 1 , 1 >>>();
                │   │
                │   └─ 每个块里有几个线程  → 共 1 个
                └───── 网格里有几个块      → 共 1 个
                                        ⇒ 总线程数 = 1 × 1 = 1
```

> 🎯 **总线程数 = 第一个数 × 第二个数**。所以你 `<<<1,4>>>` 就有 4 个线程、打印 4 次。
> 这就是 [练习 0.1](#练习-01-基础-让-gpu-多打印几行) 要做的事。

关于 `<<<>>>` 里的数字怎么填、`threadIdx` 怎么用，是 [第 1 章](ch01_编程模型与线程索引.md) 的全部内容，本章先不展开。

### 1.7 关于 printf：设备端的 printf 是异步的

#### 📮 场景：往"慢递信箱"里投信

`hello.cu` 里用了 `printf`。它有几点和普通 C 的 `printf` 不同：

> 📮 **一句话概括**：设备端的 `printf` **不是直接打印到你的屏幕**，
> 而是先**丢进一个缓冲区（信箱）**，最后由 CUDA 运行时**统一取出来**转给你。

这带来四个后果：

| # | 特点 | 说明 | 你会遇到的现象 |
| - | ---- | ---- | -------------- |
| 1 | **它在 GPU 上执行** | 由 CUDA 运行时的"设备端 printf FIFO"缓冲，再转发到终端 | 你看到输出时，它其实已经在显存里排队很久了 |
| 2 | **输出顺序不保证** | 多个线程同时 printf，谁先谁后由调度决定 | 每次跑顺序都可能不一样 |
| 3 | **必须有 `cudaDeviceSynchronize()`** | 如果程序在 kernel 跑完前就 `return`，那些 printf 可能被丢弃 | **"我的 printf 没输出！"** |
| 4 | **性能很差** | 每个 printf 都要走一趟显存缓冲区并可能触发一次系统调用 | 在热循环里打 printf，程序会慢几十倍 |

> ⚠️ **第 3 条是新手最常踩的坑**，本章 [4.3 节](#43-预期输出) 会让你**亲手做一次实验**：
> 把 `cudaDeviceSynchronize()` 注释掉，**看着 GPU 的输出凭空消失**。
> 做过一次这个实验，你就永远不会忘记"kernel 是异步的"。

> 🎯 **性能提醒**：**永远不要在真正追求性能的核函数里用 `printf` 调试**。
> 那是 `compute-sanitizer` 和 `cuda-gdb` 的活（见 [6.5 节](#65-一个通用的排查流程)）。

### 1.8 "环境没装好"和"程序写错了"要分清

#### 🚑 场景：先分清是"车坏了"还是"路封了"

新手最容易被这件事搞崩溃：报错了，不知道是环境问题还是自己代码问题。

> 🚑 **为什么这件事这么重要？**
> 因为**两种问题的排查方向完全相反**：
> - **环境问题** → 去查驱动、PATH、版本，**跟你的代码没关系**；
> - **代码问题** → 去查索引、越界、拷贝方向，**跟你的环境没关系**。
>
> **搞错方向，你会花几个小时修一个根本不存在的问题。**

请建立这个判断习惯——**看错误信息出现在哪个阶段**：

```text
   ① nvidia-smi 就报错              → 环境问题（驱动）
   ② nvcc 找不到 / 编译报错          → 环境问题（PATH / 头文件）
   ③ 编译通过，运行报"没有设备"      → 环境问题（驱动/权限/远程会话）
   ④ 编译通过，运行报"架构不匹配"    → 你的 -arch 参数写错了
   ⑤ 编译通过，运行结果不对          → 代码问题（逻辑）
   ⑥ 编译通过，运行一半崩了          → 代码问题（越界）
```

**完整对照表**：

| 症状 | 大概率是哪类问题 |
| ---- | ---------------- |
| `nvidia-smi` 就报错 | 环境问题（驱动） |
| `nvcc: command not found` | 环境问题（PATH） |
| `nvcc --version` 正常，一编译就报 `#include <cuda_runtime.h> not found` | 环境问题（PATH 里的 nvcc 与 Toolkit 目录不一致） |
| 编译通过，运行报 `no CUDA-capable device is detected` | 环境问题（驱动/权限/远程会话） |
| 编译通过，运行报 `invalid device function` 或 `no kernel image` | **你的 `-arch` 参数写错了** |
| 编译通过，运行输出全 0 或垃圾值 | 代码问题（数据没拷对/索引算错） |
| 编译通过，运行一半崩了 | 代码问题（越界），用 `compute-sanitizer` 查 |

> 💡 **一个实用心法**：**"编译期的问题"基本都是环境问题，"运行期的问题"才可能是代码问题。**
> 因为编译只需要工具链，而运行需要真实的硬件和驱动。

下面正式开始动手。

## 2. 代码实战

本章有两个程序。**先跑通第一个，再看第二个**——第二个是给你以后排查环境用的工具。

另外，我们会把两个公共头文件放在 `code/common/`，此后所有章节都复用它俩：

- `code/common/cuda_check.h`：提供 `CUDA_CHECK`、`CUDA_CHECK_KERNEL`、`CUDA_CHECK_SYNC` 三个错误检查宏，以及一个 `printDeviceInfo()`。
- `code/common/cuda_timer.h`：提供 `CudaTimer` 类，用 `cudaEvent` 计时并支持"预热 + 取中位数"。

下面先贴 `cuda_timer.h`，因为从 [第 1 章](ch01_编程模型与线程索引.md) 开始每章都要用它测性能。

### 2.1 `code/common/cuda_timer.h`

```cpp
#pragma once
// ============================================================
//  cuda_timer.h —— CUDA 计时公共头文件
// ============================================================

#include <algorithm>
#include <cstdio>
#include <functional>
#include <vector>

#include <cuda_runtime.h>

#include "cuda_check.h"

// 取中位数（会修改传入的数组，所以按值接收）
static inline double medianOf(std::vector<double> v) {
    if (v.empty()) return 0.0;
    std::sort(v.begin(), v.end());
    size_t n = v.size();
    return (n % 2 == 1) ? v[n / 2] : 0.5 * (v[n / 2 - 1] + v[n / 2]);
}

// ------------------------------------------------------------
// CudaTimer：基于 cudaEvent 的计时器
//
// 为什么要用 cudaEvent 而不是 host 端 clock()？
//   因为 kernel 是"异步启动、异步执行"的，host 端计时会把
//   启动开销算进去、甚至可能测到 0。cudaEvent 记录在 GPU 的
//   时间线上，测的是真正的设备端耗时。
// ------------------------------------------------------------
class CudaTimer {
public:
    CudaTimer() {
        CUDA_CHECK(cudaEventCreate(&start_));
        CUDA_CHECK(cudaEventCreate(&stop_));
    }

    ~CudaTimer() {
        // 析构里不抛错：即使销毁失败也不该让程序崩溃
        cudaEventDestroy(start_);
        cudaEventDestroy(stop_);
    }

    // 禁止拷贝：事件句柄是独占资源，拷贝会导致重复销毁
    CudaTimer(const CudaTimer&) = delete;
    CudaTimer& operator=(const CudaTimer&) = delete;

    void start() { CUDA_CHECK(cudaEventRecord(start_, 0)); }

    float stopMs() {
        CUDA_CHECK(cudaEventRecord(stop_, 0));
        CUDA_CHECK(cudaEventSynchronize(stop_));  // 必须等 stop 事件真的发生
        float ms = 0.0f;
        CUDA_CHECK(cudaEventElapsedTime(&ms, start_, stop_));
        return ms;
    }

    float stop() { return stopMs(); }

    // 规范测量：预热 warmup 次后，再跑 iters 次取中位数
    static double measure(const std::function<void(double&, int)>& f,
                          int iters = 5, int warmup = 1) {
        std::vector<double> samples;
        for (int i = 0; i < warmup + iters; ++i) {
            double ms = 0.0;
            f(ms, i);
            if (i >= warmup) samples.push_back(ms);
        }
        return medianOf(samples);
    }

    // 有效带宽（GB/s）：bytes 是这次操作搬运的总字节数
    static double bandwidthGBs(double bytes, double ms) {
        if (ms <= 0.0) return 0.0;
        return bytes / (ms * 1e-3) / 1e9;
    }

    // 算力（GFLOPS）：flops 是浮点运算次数
    static double gflops(double flops, double ms) {
        if (ms <= 0.0) return 0.0;
        return flops / (ms * 1e-3) / 1e9;
    }

private:
    cudaEvent_t start_{};
    cudaEvent_t stop_{};
};
```

### 2.2 `code/lessons/ch00_hello/hello.cu` —— 第一个 CUDA 程序

```cpp
// ============================================================
//  ch00_hello/hello.cu
//  本书的第一个 CUDA 程序。
//
//  编译（在 code/lessons/ch00_hello 目录下）：
//      nvcc -O3 -arch=sm_75 hello.cu -o hello
// ============================================================

#include <cstdio>

#include "../common/cuda_check.h"

// ------------------------------------------------------------
// __global__ 表示这是一个"核函数"(kernel)：
//   - 它在 GPU（设备）上执行
//   - 它由 CPU（主机）用 <<<...>>> 语法启动
//   - 它的返回类型必须是 void（因为它的调用是异步的，返回值没地方放）
//
// 注意：核函数是"每个线程都执行一遍整个函数体"的。
//       <<<1,1>>> 表示只有 1 个线程，所以下面这句 printf 只打印一次。
//       如果写成 <<<1,4>>>，就会打印 4 次。
// ------------------------------------------------------------
__global__ void helloFromGPU() {
    // 这句 printf 是在 GPU 上执行的（设备端 printf，由 CUDA 运行时转发到终端）
    printf("Hello World from GPU!  (block %d, thread %d)\n",
           blockIdx.x, threadIdx.x);
}

int main() {
    // 1) 先确认真的有一块 NVIDIA 显卡被驱动识别到
    int deviceCount = 0;
    CUDA_CHECK(cudaGetDeviceCount(&deviceCount));
    if (deviceCount == 0) {
        printf("没有检测到支持 CUDA 的设备，本程序无法运行。\n");
        printf("请检查：显卡是否为 NVIDIA、驱动是否安装、是否在虚拟机/远程会话中。\n");
        return 0;  // 这是"环境没准备好"，不是程序错误，所以不用 exit(1)
    }

    // 2) 打印一行主机端的问候，用来和 GPU 的输出区分开
    printf("Hello World from CPU!  (检测到 %d 个 CUDA 设备)\n", deviceCount);

    // 3) 启动核函数：<<<网格维度, 线程块维度>>>
    //    这里 gridDim = 1、blockDim = 1，也就是"总共 1 个线程"
    helloFromGPU<<<1, 1>>>();
    // 核函数启动本身不返回错误码，必须用这个宏检查启动是否成功
    CUDA_CHECK_KERNEL();

    // 4) 关键一步：同步。
    //    kernel 启动是异步的（host 发出命令后立刻往下走），
    //    而 cudaDeviceSynchronize() 会等 GPU 把所有活干完。
    //    很多初学者看到"没有输出"就是因为程序结束时 kernel 还没跑完。
    //    另外，设备端 printf 的输出也依赖这一步之后才会被刷出来。
    CUDA_CHECK(cudaDeviceSynchronize());

    printf("Done.\n");
    return 0;
}
```

### 2.3 `code/lessons/ch00_hello/device_query.cu` —— 环境自查工具

这个程序不启动任何核函数，专门用来回答"我的卡到底是什么规格"。

```cpp
// ============================================================
//  ch00_hello/device_query.cu
//  查询本机所有 CUDA 设备的详细信息。
//
//  编译（在 code/lessons/ch00_hello 目录下）：
//      nvcc -O3 device_query.cu -o device_query
// ============================================================

#include <cstdio>

#include "../common/cuda_check.h"

// 把计算能力换算成便于阅读的提示
static void printComputeCapability(const cudaDeviceProp& prop) {
    printf("  计算能力 (CC)          : %d.%d\n", prop.major, prop.minor);
    printf("    说明：CC 决定了你能用哪些指令、哪些特性。\n");
    if (prop.major < 5) {
        printf("    提示：CC < 5.0 属于非常老的架构，warp shuffle / 统一内存等特性可能受限。\n");
    } else if (prop.major < 7) {
        printf("    提示：CC 5.x/6.x 可以完整跑通本书前 5 章的所有示例。\n");
    } else {
        printf("    提示：CC >= 7.0 支持本书提到的全部基础与进阶特性（Tensor Core 除外）。\n");
    }
}

int main() {
    int deviceCount = 0;
    CUDA_CHECK(cudaGetDeviceCount(&deviceCount));
    printf("检测到 %d 个 CUDA 设备。\n\n", deviceCount);

    if (deviceCount == 0) {
        printf("没有可用设备。常见原因：\n");
        printf("  1. 没有 NVIDIA 独立显卡（AMD/Intel 核显不支持 CUDA）；\n");
        printf("  2. 驱动没装好，或装的是过旧的驱动；\n");
        printf("  3. 你在 WSL / 虚拟机 / 远程桌面里，但没有做显卡直通。\n");
        return 0;
    }

    // 逐个设备查询。cudaGetDeviceProperties 一次拿到该设备的全部属性
    for (int i = 0; i < deviceCount; ++i) {
        cudaDeviceProp prop{};
        CUDA_CHECK(cudaGetDeviceProperties(&prop, i));

        printf("=================== 设备 %d ===================\n", i);
        printf("  设备名称              : %s\n", prop.name);
        printComputeCapability(prop);

        // SM（Streaming Multiprocessor，流多处理器）：GPU 的"计算核心"
        // 一个 SM 里有很多 CUDA 核心，SM 数量决定了 GPU 的并行规模
        printf("  SM 数量               : %d\n", prop.multiProcessorCount);

        printf("  全局显存大小          : %.2f GB\n",
               prop.totalGlobalMem / 1024.0 / 1024.0 / 1024.0);
        // CUDA 13 起 cudaDeviceProp 移除了 memoryClockRate / deviceOverlap 等字段，
        // 统一改用 cudaDeviceGetAttribute 查询，跨版本更稳。
        int memClockKHz = 0, asyncEngines = 0;
        CUDA_CHECK(cudaDeviceGetAttribute(&memClockKHz, cudaDevAttrMemoryClockRate, i));
        CUDA_CHECK(cudaDeviceGetAttribute(&asyncEngines, cudaDevAttrAsyncEngineCount, i));
        printf("  显存总线宽度          : %d bit\n", prop.memoryBusWidth);
        printf("  显存频率              : %.0f MHz\n", memClockKHz / 1000.0);

        printf("  Warp 大小             : %d   <-- 永远是 32，调度单位\n", prop.warpSize);
        printf("  每块最大线程数        : %d   <-- blockDim.x*y*z 的上限\n",
               prop.maxThreadsPerBlock);
        printf("  每块最大线程维度       : (%d, %d, %d)\n",
               prop.maxThreadsDim[0], prop.maxThreadsDim[1], prop.maxThreadsDim[2]);
        printf("  网格最大维度           : (%d, %d, %d)\n",
               prop.maxGridSize[0], prop.maxGridSize[1], prop.maxGridSize[2]);
        printf("  每 SM 最大线程数      : %d\n", prop.maxThreadsPerMultiProcessor);

        printf("  每块共享内存          : %.1f KB\n", prop.sharedMemPerBlock / 1024.0);
        printf("  每 SM 共享内存        : %.1f KB\n",
               prop.sharedMemPerMultiprocessor / 1024.0);
        printf("  每 SM 寄存器数        : %d 个 32-bit 寄存器\n",
               prop.regsPerMultiprocessor);

        printf("  是否支持统一内存      : %s\n",
               prop.unifiedAddressing ? "是" : "否");
        printf("  是否支持并发拷贝      : %s\n",
               asyncEngines > 0 ? "是" : "否");
        printf("================================================\n\n");
    }

    // 顺便演示：用 cudaDeviceGetAttribute 查询单个属性，
    // 它比 cudaGetDeviceProperties 轻量，适合只关心一两个指标的场景。
    int clockRateKHz = 0;
    CUDA_CHECK(cudaDeviceGetAttribute(&clockRateKHz, cudaDevAttrClockRate, 0));
    printf("设备 0 的核心时钟 : %.2f GHz\n", clockRateKHz / 1e6);

    int smCount = 0;
    CUDA_CHECK(cudaDeviceGetAttribute(&smCount, cudaDevAttrMultiProcessorCount, 0));
    printf("设备 0 的 SM 数量 : %d\n", smCount);

    return 0;
}
```

## 3. 代码逐行解析

### 3.1 关于 `cuda_check.h`：为什么必须有它

先看它的核心宏：

```cpp
#define CUDA_CHECK(expr)                                                        \
    do {                                                                        \
        cudaError_t _err = (expr);                                              \
        if (_err != cudaSuccess) {                                              \
            fprintf(stderr, "\n[CUDA ERROR] %s:%d\n  call : %s\n  msg  : %s\n", \
                    __FILE__, __LINE__, #expr, cudaGetErrorString(_err));       \
            exit(EXIT_FAILURE);                                                 \
        }                                                                       \
    } while (0)
```

逐点说明：

- **`do { ... } while (0)`**：这是 C 宏的标准写法。它让 `CUDA_CHECK(x);` 在语法上表现得像一个语句，从而在 `if (a) CUDA_CHECK(x); else ...` 这种场景下不会出错。
- **`cudaError_t _err = (expr);`**：先把表达式的值存下来，避免 `expr` 被求值两次（如果是 `cudaMalloc(...)` 就完蛋了）。
- **`#expr`**：把传入的表达式**字符串化**，报错时你能看到是哪一行代码挂了。这就是 `call : cudaMalloc(&d_a, bytes)` 那一行的来源。
- **`__FILE__` / `__LINE__`**：预定义的宏，报错时告诉你文件名和行号。
- **`cudaGetErrorString`**：把错误码翻译成人类能读的英文句子。
- **`exit(EXIT_FAILURE)`**：直接退出，而不是"打印一下继续跑"。

**为什么必须这么做？** 因为 CUDA 的错误传播机制非常"阴险"：

1. **核函数启动错误是异步的**：`kernel<<<>>>` 本身不返回错误码，要用 `cudaGetLastError()` 拿。这就是 `CUDA_CHECK_KERNEL()` 存在的理由。
2. **执行期错误会被"记住"并推迟到下一条 API**：如果 kernel 越界访问了内存，你不会立刻看到错，而是**下一次** CUDA 调用（可能是十行之后的 `cudaMemcpy`）才返回 `cudaErrorIllegalAddress`。这会让你对着错误的代码行查半天。
3. **错误码是"粘性"的**：一个错误可能被后续调用反复读到。

所以规矩是：**每一个 CUDA API 调用都包 `CUDA_CHECK(...)`，每一次 kernel 启动后面跟 `CUDA_CHECK_KERNEL()`，程序的关键节点用 `CUDA_CHECK_SYNC()`。** 这本书从头到尾都会这样做。

### 3.2 `helloFromGPU` 的三件事

```cpp
__global__ void helloFromGPU() {
    printf("Hello World from GPU!  (block %d, thread %d)\n",
           blockIdx.x, threadIdx.x);
}
```

**第一，`__global__` 是限定符不是返回类型。**

很多新手会写成 `global void ...` 或 `__global void ...`（一个下划线），这是编译错误。正确写法是**两个下划线 + global + 两个下划线**。限定符写在返回类型前面：

```cpp
__global__ void k();      // 正确
void __global__ k();      // 也能编译，但不推荐这种风格
```

**第二，`blockIdx` 和 `threadIdx` 是内置变量。**

它们不需要声明、不能赋值，由硬件在核函数开始执行时填好。它们都是 `dim3` 类型（一个含 `x`/`y`/`z` 三个 `unsigned int` 的结构体），所以要用 `.x` 取。因为 `<<<1,1>>>` 只有一个线程，这里打印出来永远是 `block 0, thread 0`。

**第三，返回值必须是 `void`。**

原因是核函数启动是**异步**的：主机发出启动命令后立刻继续执行下一行，此时 GPU 可能还没开始算。如果核函数有返回值，主机根本不知道该去哪里取。所以 CUDA 直接规定核函数必须返回 `void`；要拿结果就写进显存，再拷回主机。

### 3.3 `main` 的五步

**第 1 步：`cudaGetDeviceCount(&deviceCount)`**

```cpp
int deviceCount = 0;
CUDA_CHECK(cudaGetDeviceCount(&deviceCount));
```

这个调用会初始化 CUDA 运行时（第一次调用 CUDA API 时会做，通常耗时几十到几百毫秒），并返回系统里可见的 CUDA 设备数量。

**为什么要检查 0？** 因为在一台没有 N 卡的机器上，后续任何 `cudaMalloc` 都会失败。提前检查并给出**人话提示**（"请检查显卡是否为 NVIDIA"），比让程序在十行之后抛一个 `cudaErrorNoDevice` 友好得多。

注意这里 `return 0` 而不是 `return 1`：这是"环境不支持"而不是"程序有 bug"，返回 0 便于脚本自动化处理。

**第 2 步：区分 CPU 与 GPU 的输出**

```cpp
printf("Hello World from CPU!  (检测到 %d 个 CUDA 设备)\n", deviceCount);
```

这行是普通的 C 代码，在 CPU 上运行。加上它有两个好处：一是让"同一份代码里，CPU 和 GPU 各干了一部分活"这件事看得见；二是当 GPU 输出没出来时，你能立刻判断出"程序至少跑到了这里"。

**第 3 步：启动核函数**

```cpp
helloFromGPU<<<1, 1>>>();
CUDA_CHECK_KERNEL();
```

`<<<1, 1>>>` 是 CUDA 的**执行配置（Execution Configuration）**语法，`nvcc` 会把它翻译成一次运行时调用。两个数字分别是：

- 第一个 `1`：网格里有 **1 个线程块**；
- 第二个 `1`：每个线程块里有 **1 个线程**。

于是总共启动 1 个线程，`printf` 打印 1 次。

紧跟着的 `CUDA_CHECK_KERNEL()` 展开后是 `cudaGetLastError()` 的检查。**为什么不能省？** 因为如果 `<<<>>>` 里的参数非法（比如块大小超过 1024），错误只会被记录在"最后一次错误"里，不会抛异常也不会打印。不检查的话，程序会静悄悄啥也不干。

**第 4 步：`cudaDeviceSynchronize()`**

```cpp
CUDA_CHECK(cudaDeviceSynchronize());
```

这是整章最容易被忽略、也最重要的一行。

CUDA 的执行是**异步**的：`kernel<<<>>>` 只是把"启动这个 kernel"这个命令**放进默认流的队列**，然后 host 立刻返回。所以下面这段代码是有 bug 的：

```cpp
// ❌ 错误示范
helloFromGPU<<<1, 1>>>();
printf("Done.\n");
// main 返回，进程结束——此时 GPU 可能还没开始执行 kernel
```

`cudaDeviceSynchronize()` 会**阻塞 host**，直到设备上**所有**之前的任务（所有流）都完成。它同时也是：

- 让设备端 `printf` 的输出真的被刷到终端；
- 让执行期的错误（越界、非法指令）在这个点上暴露出来，而不是拖到后面某次无辜的 API 调用上。

**第 5 步：正常返回。**

### 3.4 `device_query.cu` 解析

**为什么它不启动 kernel？** 因为它要回答的是"我的环境行不行"，而不是"我的代码行不行"。不启动 kernel 意味着它永远不会遇到 `no kernel image available` 这类架构问题，是**最小可用性检查**。

**关键 API 1：`cudaGetDeviceProperties(&prop, i)`**

```cpp
cudaDeviceProp prop{};
CUDA_CHECK(cudaGetDeviceProperties(&prop, i));
```

`cudaDeviceProp` 是 CUDA 运行时定义的大结构体（几十个字段）。`prop{}` 用值初始化把所有字段清零，这是个好习惯——CUDA 的一些旧版本在某些驱动下不会把所有字段都填满，清零可以避免读到垃圾值。

**关键 API 2：`cudaDeviceGetAttribute(&value, attr, device)`**

```cpp
int smCount = 0;
CUDA_CHECK(cudaDeviceGetAttribute(&smCount, cudaDevAttrMultiProcessorCount, 0));
```

它和 `cudaGetDeviceProperties` 的区别是"点菜 vs 自助餐"：前者只查你指定的那一个属性，开销小、语义清晰，适合在性能敏感的代码里用（比如按 SM 数量决定 grid 大小）。缺点是属性名的命名风格和 `cudaDeviceProp` 的字段名不一样，需要查文档。

**字段解读（挑几个后面章节会用到的）**：

| 字段 | 含义 | 后面哪章会用到 |
| --- | --- | --- |
| `multiProcessorCount` | SM 的数量 | [第 1 章](ch01_编程模型与线程索引.md)（Grid-Stride Loop 的 grid 大小）、[第 2 章](ch02_内存层次与访存优化.md)（占用率） |
| `warpSize` | 永远是 32 | [第 1 章](ch01_编程模型与线程索引.md)（SIMT 与发散） |
| `maxThreadsPerBlock` | 通常是 1024 | [第 1 章](ch01_编程模型与线程索引.md)（块大小选择） |
| `sharedMemPerBlock` | 48 KB（老卡）或 48/96/163 KB | [第 2 章](ch02_内存层次与访存优化.md)（分块矩阵乘法） |
| `regsPerMultiprocessor` | 通常 65536 | [第 2 章](ch02_内存层次与访存优化.md)（寄存器压力与占用率） |
| `totalGlobalMem` | 显存容量 | [第 2 章](ch02_内存层次与访存优化.md)（`cudaMalloc` 能要多大） |

**输出中的两个小细节**：

- `prop.totalGlobalMem` 是字节数，除以三次 1024 换算成 GB。（严格说是 GiB，但业界都叫 GB。）
- `clockRateKHz` 是 kHz，除以 `1e6` 得到 GHz。

### 4.1 前置：安装 CUDA Toolkit

#### 🪟 Windows 安装步骤

1. 打开 https://developer.nvidia.com/cuda-downloads

   选 `local`（本地安装包）而不是 `network`（网络安装包），因为国内网络下 `network` 装到一半断线会留下一个烂摊子。

   ```text
   C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v12.2
   ```

   打开**新**的命令行窗口（重要：环境变量只对新窗口生效），执行：
   ```bash
   nvcc --version
   ```
   如果报"不是内部或外部命令"，见第 6 节。

### 4.2 第一步：用 nvcc 编译 hello.cu

**Windows（x64 Native Tools Command Prompt for VS 2022）**


**Linux / macOS（无 N 卡的 Mac 不能跑，但能编译）**

```bash

./hello
```

**`-arch=sm_75` 里的 `75` 必须换成你自己显卡的 CC**（用 `device_query` 或 `nvidia-smi` 查）。例如：

| 显卡 | 参数 |
| --- | --- |
| GTX 1080 | `-arch=sm_61` |
| RTX 2080 / T4 | `-arch=sm_75` |
| RTX 3090 | `-arch=sm_86` |
| RTX 4090 | `-arch=sm_89` |
| Tesla V100 | `-arch=sm_70` |

**参数解释**：

| 参数 | 作用 | 为什么需要 |
| --- | --- | --- |
| `-O3` | 让宿主编译器做最大化优化 | 不加的话性能可能差好几倍，尤其是循环 |
| `-arch=sm_75` | 生成 sm_75 的 SASS | 不指定会用默认目标，可能不是你的卡 |
| `-o hello` | 指定输出文件名 | 不加的话默认叫 `a.out`（Linux）/ `a.exe`（Windows） |

**关于 `-O3` 的一个坑**：`nvcc -O3` 只把 `-O3` 传给**宿主编译器**。要让 **设备端**也优化到最高，得用 `-Xptxas -O3`（这是默认值，一般不用管）或者干脆用 `-O3` 加上默认的设备端优化。想确认设备端优化等级，用：

```bash
nvcc -O3 -Xptxas -v -arch=sm_75 hello.cu -o hello
```

`-Xptxas -v` 会打印出每个核函数用了多少寄存器、多少共享内存、多少 spill（溢出）。**这是你以后最常用的诊断参数之一**，[第 2 章](ch02_内存层次与访存优化.md) 会详细讲怎么读它。

> ⚠️ **Windows 中文环境的小坑**：新建 `.cu` / `.h` / `.cpp` 源文件时，请务必保存为 **UTF-8 with BOM**。当系统 ANSI 代码页是 GBK（简体中文 Windows 默认）时，没有 BOM 的 UTF-8 中文源码会被编译器错解成"续行符"并吃掉换行，导致一堆 `expected a declaration`、`missing closing quote` 之类的**假语法错误**——它们跟你的代码逻辑毫无关系。本仓库 `code/` 下的示例源码都已带 BOM。

**`hello.exe`（Windows）**

```text

```

**`./hello`（Linux）**

```text
Hello World from CPU!  (检测到 1 个 CUDA 设备)

```

**三行的顺序是确定的**，因为：第一行是 host 代码；第三行是 host 代码；中间那行虽然由 GPU 产生，但被第 4 步的 `cudaDeviceSynchronize()` 强制在第三行之前完成。所以这三行的顺序不会变。

```text
Hello World from CPU!  (检测到 1 个 CUDA 设备)
Hello World from GPU!  (block 0, thread 2)
Hello World from GPU!  (block 0, thread 0)
Hello World from GPU!  (block 0, thread 3)
Hello World from GPU!  (block 0, thread 1)
Done.
```

**如果你把 `cudaDeviceSynchronize()` 注释掉**，很可能看到：

```text
Hello World from CPU!  (检测到 1 个 CUDA 设备)
Done.
```

GPU 的输出**没了**。这不是 bug，是异步执行的必然结果。请亲手做一遍这个实验，它会让你永远记住"kernel 是异步的"。

```text

```

### 4.5 第三步：用 CMake 编译

`nvcc` 命令行适合验证环境，但真实项目都用构建系统。CMake 从 **3.8** 开始支持 CUDA，**3.18** 起支持得比较完善。

```bash
cd code/lessons/ch00_hello

# 配置（-B build 表示生成到 build 目录，-S . 表示源码在当前目录）
cmake -B build -S . -DCMAKE_CUDA_ARCHITECTURES=75

# 编译
cmake --build build --config Release

# 运行（Linux / 单配置生成器）
./build/hello
./build/device_query

# 运行（Windows + Visual Studio 多配置生成器）
.\build\Release\hello.exe
.\build\Release\device_query.exe
```

**`CMakeLists.txt` 关键行解释**：

```cmake
project(cuda_ch00 LANGUAGES CXX CUDA)
```

**这一行是整个 CMake CUDA 支持的入口。** `LANGUAGES CXX CUDA` 告诉 CMake "这个工程要用 C++ 编译器和 CUDA 编译器"，CMake 会自动去找 `nvcc`，并把 `CMAKE_CUDA_COMPILER`、`CMAKE_CUDA_ARCHITECTURES` 等变量准备好。**漏掉 `CUDA` 会导致 `.cu` 文件被当成未知文件类型忽略掉**（表现为"编译成功但什么都没生成"）。

```cmake
set(CMAKE_CXX_STANDARD 17)
```

从 CUDA 11 开始，`nvcc` 对 C++17 支持良好。用 17 可以在 host 代码里写结构化绑定、`if constexpr` 等，写起来舒服。**注意别用 C++20 的协程/概念**，`nvcc` 对它们的支持还不完整。

```cmake
if(NOT CMAKE_BUILD_TYPE)
    set(CMAKE_BUILD_TYPE Release)
endif()
```

如果用户没指定构建类型，默认给 `Release`。这很重要：**CMake 默认是空构建类型，也就是不加任何 `-O`**。GPU 程序在 `-O0` 下性能可能差 10 倍以上，会让你的优化实验得出完全错误的结论。

**如果你用的是 Visual Studio 生成器（Windows 默认）**，`CMAKE_BUILD_TYPE` 会被忽略，改用 `--config Release`：

```bat
cmake --build build --config Release
```

这一点坑了无数人：**改了 CMakeLists 却发现性能没变，多半是编到了 Debug。**

```cmake
set(CMAKE_CUDA_FLAGS "${CMAKE_CUDA_FLAGS} --expt-relaxed-constexpr")
```

`--expt-relaxed-constexpr` 放宽了 `constexpr` 函数在设备代码里调用的限制。加上它，你可以放心地用一些标准库的常量表达式。这是个安全的开关。

```cmake
add_executable(hello hello.cu)
```

注意这里**没有写 `enable_language(CUDA)`**。因为 `project(... LANGUAGES ... CUDA)` 已经启用了。如果你想在子目录里启用，用 `enable_language(CUDA)`。

**指定架构的三种方式**（按推荐度排序）：

```cmake
# 方式 1（推荐）：命令行指定
#   cmake -B build -S . -DCMAKE_CUDA_ARCHITECTURES=86

# 方式 2：写死在 CMakeLists 里
set(CMAKE_CUDA_ARCHITECTURES 86)

# 方式 3：不指定，让 CMake 自动探测
#   注意：这在 CMake < 3.24 上可能探测失败或给出过时值，
#         表现为编译很慢（编了很多架构）或运行报 no kernel image
```

**CMake 3.24 以上**还支持 `native` 关键字，它会调用本机 GPU 来探测：

```cmake
set(CMAKE_CUDA_ARCHITECTURES native)
```

**验证 CMake 真的用了你指定的架构**：配置阶段会打印

```text
-- CUDA architectures = 75
```

如果这里是空的，说明没有生效，编译出来的可能是默认架构。

## 5. 动手练习

### 练习 0.1 [基础] 让 GPU 多打印几行

把 `hello.cu` 里的 `<<<1, 1>>>` 改成 `<<<1, 4>>>`，重新编译运行。

**要求**：解释为什么打印了 4 行、为什么顺序不确定、为什么这 4 行的 `blockIdx.x` 都是 0。

<details>
<summary>参考做法</summary>

只改一行：

```cpp
helloFromGPU<<<1, 4>>>();
```

- 打印 4 行：因为执行配置说"1 个块 × 4 个线程 = 4 个线程"，每个线程都完整执行一遍核函数体。
- 顺序不确定：4 个线程在同一个 warp 里，但设备端 printf 走的是一个共享 FIFO，多线程并发写入的顺序由硬件决定，CUDA 不做任何排序保证。
- `blockIdx.x` 都是 0：`<<<1, 4>>>` 的第一个参数是**网格维度**，只有 1 个块，所以所有线程都在 0 号块里。要看到不同的 `blockIdx.x`，得改成 `<<<4, 1>>>`。
</details>

### 练习 0.2 [基础] 制造一次"架构不匹配"

故意用一个和你显卡不匹配的架构编译，观察错误。

```bash
nvcc -O3 -arch=sm_90 hello.cu -o hello_wrong.exe
hello_wrong.exe
```

**要求**：记录你看到的完整错误信息，并解释为什么编译器没有在编译阶段就发现这个问题。

<details>
<summary>参考做法</summary>

你会看到类似：

```text
[CUDA ERROR] hello.cu:52
  call : cudaGetLastError()
  msg  : no kernel image is available for execution on the device
```

或运行时报：

```text
CUDA error: no kernel image is available for execution on the device
```

**为什么编译期发现不了？** 因为 `nvcc` 不知道你会把程序拿到哪张卡上跑。它只负责"按你要求生成 sm_90 的机器码"。架构匹配是在**运行时**由 CUDA 驱动检查的：它去可执行文件的 fatbin 段里找匹配当前设备的 SASS，找不到就报这个错。

**一个例外**：如果你在 `-arch=sm_90` 的同时还让它带上 PTX，驱动就能 JIT。例如 `-gencode arch=compute_75,code=compute_75` 生成的 PTX 可以在 7.5 及以上的任何卡上 JIT 执行。
</details>

### 练习 0.3 [基础] 看汇编

用 `-Xptxas -v` 编译 `hello.cu`，并生成 PTX：

```bash
nvcc -O3 -Xptxas -v -arch=sm_75 hello.cu -o hello
nvcc -O3 -ptx -arch=sm_75 hello.cu
```

**要求**：
1. 说出 `helloFromGPU` 用了多少个寄存器、多少字节共享内存。
2. 打开生成的 `hello.ptx`，找到 `.visible .entry helloFromGPU`，说说里面大概有什么。

<details>
<summary>参考做法</summary>

`-Xptxas -v` 的输出形如：

```text
ptxas info    : 0 bytes gmem
ptxas info    : Compiling entry function '_Z12helloFromGPUV' for 'sm_75'
ptxas info    : Function properties for _Z12helloFromGPUV
    0 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads
ptxas info    : Used 8 registers, 368 bytes cmem[0]
```

（寄存器数每个 CUDA 版本不同，8～16 之间都正常。）

几个要点：
- `_Z12helloFromGPUV` 是 C++ 名称修饰（name mangling）后的核函数名。`cuobjdump -syms` 或 `c++filt` 可以还原。
- `368 bytes cmem[0]` 是常量内存中的运行时参数区，不是你的共享内存。
- `0 bytes spill` 是好消息，后面的章节里你会在矩阵乘法中看到非零的 spill。

PTX 里你会看到：

```text
.visible .entry helloFromGPU()
{
    .reg .b32 %r<...>;
    ...
    // 调用设备端 printf 的一系列指令
    ...
    ret;
}
```

PTX 是**虚拟**汇编，寄存器是虚拟的（如 `%r<5>`），具体的物理寄存器分配在 `ptxas` 阶段完成。这就是"PTX 与架构无关"的含义。
</details>

### 练习 0.4 [进阶] 写一个报告"我的显卡规格"的小工具

基于 `device_query.cu`，写一个新程序 `my_report.cu`，只输出下面几行，并且**顺带计算**一个派生指标：

```text
显卡型号        : xxx
计算能力        : x.y
SM 数量         : xx
每 SM 最大线程  : xxxx
理论最大并发线程: xx * xxxx = <结果>
共享内存上限    : xx KB
建议的块大小    : 256
```

最后一行 **"建议的块大小"** 请按这个规则给出：如果 `maxThreadsPerBlock >= 256` 就输出 256，否则输出 `maxThreadsPerBlock`。再写一行注释说明为什么代码里硬编码 256（提示：256 是 32 的倍数，且对绝大多数架构都能达到较高占用率）。

<details>
<summary>参考做法</summary>

```cpp
#include <cstdio>
#include "../common/cuda_check.h"

int main() {
    cudaDeviceProp prop{};
    CUDA_CHECK(cudaGetDeviceProperties(&prop, 0));

    int maxConcurrent = prop.multiProcessorCount * prop.maxThreadsPerMultiProcessor;
    int blockSize = (prop.maxThreadsPerBlock >= 256) ? 256 : prop.maxThreadsPerBlock;

    printf("显卡型号        : %s\n", prop.name);
    printf("计算能力        : %d.%d\n", prop.major, prop.minor);
    printf("SM 数量         : %d\n", prop.multiProcessorCount);
    printf("每 SM 最大线程  : %d\n", prop.maxThreadsPerMultiProcessor);
    printf("理论最大并发线程: %d * %d = %d\n",
           prop.multiProcessorCount, prop.maxThreadsPerMultiProcessor, maxConcurrent);
    printf("共享内存上限    : %.0f KB\n", prop.sharedMemPerBlock / 1024.0);
    printf("建议的块大小    : %d\n", blockSize);
    // 256 是 32 的倍数（不会有半个 warp 浪费），
    // 同时小到能让寄存器/共享内存允许一个 SM 挂多个块，
    // 是所有架构上的"安全默认值"。
    return 0;
}
```

`理论最大并发线程` 这个指标很关键：它就是你后面算**占用率（Occupancy）**的分母。比如 RTX 3060 是 30 × 1536 = 46080 个线程。如果你启动的 grid 只有 1000 个线程，那 GPU 只被用了不到 3%——这就是 [第 1 章](ch01_编程模型与线程索引.md) 要讲的 Grid-Stride Loop 和"grid 开够大"的意义。
</details>

### 练习 0.6 [挑战] 验证"PTX 兜底 JIT"

实验设计：你只有一张 CC 8.6 的卡，但要生成一个"能在 8.6 上跑"的可执行文件，而**不允许**在编译命令里出现 `86`。

提示：用 `-gencode` 生成 PTX。

**要求**：
1. 写出编译命令。
2. 解释为什么它能跑起来。
3. 观察并记录：第一次运行和第二次运行的耗时有没有差别（用 PowerShell 的 `Measure-Command` 或 bash 的 `time`）。这个差别说明了什么？

<details>
<summary>参考做法</summary>

```bash
nvcc -O3 -gencode arch=compute_75,code=compute_75 hello.cu -o hello_jit.exe
```

关键：`code=compute_75` 表示"生成 compute_75 的 **PTX** 而不生成 SASS"。这个 PTX 是架构无关的中间码，随可执行文件一起发布。

运行时的过程：
1. 驱动看当前设备是 sm_86；
2. 在 fatbin 里找不到 sm_86 的 SASS；
3. 找到一个 compute_75 的 PTX（75 ≤ 86，兼容）；
4. **就地**把 PTX JIT 编译成 sm_86 的 SASS；
5. 执行。

第 4 步的编译结果会被驱动缓存在 `~/.nv/ComputeCache`（Linux）或 `%LOCALAPPDATA%\NVIDIA\ComputeCache`（Windows）。所以：

- **第一次运行明显慢**（要做 JIT 编译，通常是几十毫秒到几百毫秒的额外开销）；
- **第二次运行快**（命中缓存）。

手动清缓存可以复现第一次的慢：

```bash
# Linux
rm -rf ~/.nv/ComputeCache

# Windows PowerShell
Remove-Item -Recurse -Force "$env:LOCALAPPDATA\NVIDIA\ComputeCache"
```

**结论**：这就是为什么发布版要么打包好所有目标架构的 SASS，要么接受"首次启动慢"。对这个几百微秒就能跑完的 `hello` 来说，JIT 开销是主导；对跑几秒的大程序则几乎无感。
</details>

## 6. 常见错误与排查

### 6.1 环境类错误

| 错误信息 | 原因 | 解决办法 |
| --- | --- | --- |
| `'nvidia-smi' 不是内部或外部命令` / `nvidia-smi: command not found` | 显卡驱动没装，或安装了但 PATH 里没有它的目录 | Windows：把 `C:\Windows\System32` 加进 PATH（`nvidia-smi.exe` 在这里），然后**重开命令行**；Linux：`sudo apt install nvidia-driver-535` 后重启 |
| `nvidia-smi` 报 `NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver` | 驱动模块没加载（常见于内核升级后）或 Secure Boot 拦截了模块签名 | Linux：`sudo modprobe nvidia`；不行就重装驱动 `sudo apt install --reinstall nvidia-dkms-535`；如果开了 Secure Boot，需要给模块签名或关闭 Secure Boot |
| `nvcc: command not found` | CUDA 装了但 `bin` 目录不在 PATH | 见 6.2 |
| `nvcc --version` 显示的版本和你装的不一样 | PATH 里有多个 CUDA | `which -a nvcc`（Linux）/ `where nvcc`（Windows）看有几个，调整 PATH 顺序 |
| `fatal error: cuda_runtime.h: No such file or directory` | 编译时找不到头文件 | 指定 `-I` 路径：`nvcc -I/usr/local/cuda/include ...`；或修正 `CUDA_PATH` |
| `#include <cuda_runtime.h>` 能找到，但链接时报 `undefined reference to cudaMalloc` | `LD_LIBRARY_PATH` 没设 | `export LD_LIBRARY_PATH=/usr/local/cuda/lib64:$LD_LIBRARY_PATH`；或链接时加 `-L` 和 `-lcudart` |
| Linux 下 nvcc 报 `unsupported GNU version! gcc versions later than 12 are not supported` | 发行版自带的 gcc 太新，CUDA 版本不支持 | 装一个旧版 gcc：`sudo apt install gcc-11 g++-11`，然后 `nvcc -ccbin g++-11 ...` |
| Windows 下 nvcc 报 `Cannot find compiler 'cl.exe' in PATH` | 没装 MSVC，或不在 VS 的开发者命令行里 | 装 Visual Studio 并勾选"使用 C++ 的桌面开发"；从 **x64 Native Tools Command Prompt** 里编译 |
| WSL2 里 `nvidia-smi` 正常但不能跑 CUDA | WSL 的 CUDA 支持需要特定驱动（Windows 端）+ WSL 专用 Toolkit | 装 Windows 端 **WSL 专用驱动**（版本号带 `.0`，如 `536.25`），WSL 里**不要**装 Linux 驱动；按 NVIDIA 官方 "CUDA on WSL" 文档装 Toolkit |

### 6.2 PATH 问题的通用修法

**Windows**：

```bat
:: 看看当前 PATH 里有没有 CUDA
echo %PATH%

:: 临时加（只对当前窗口生效）
set PATH=%CUDA_PATH%\bin;%PATH%

:: 永久加（推荐用系统设置界面，或者用 setx）
setx PATH "%CUDA_PATH%\bin;%PATH%"
```

⚠️ `setx` 有坑：它会把 PATH 截断到 1024 字符，可能导致别的东西失效。**优先用"系统属性 → 环境变量"图形界面改**。

**Linux**：

```bash
# 写到 ~/.bashrc（不要写死版本号，方便以后切换）
export CUDA_HOME=/usr/local/cuda
export PATH=$CUDA_HOME/bin:$PATH
export LD_LIBRARY_PATH=$CUDA_HOME/lib64:$LD_LIBRARY_PATH

source ~/.bashrc
```

Linux 上 `/usr/local/cuda` 通常是一个**软链接**，指向具体的版本目录：

```bash
ls -l /usr/local/cuda
# lrwxrwxrwx 1 root root 21 ... /usr/local/cuda -> /usr/local/cuda-12.2
```

换版本时只要改这个软链接：`sudo ln -sfn /usr/local/cuda-11.8 /usr/local/cuda`。

### 6.3 编译类错误

| 错误信息 | 原因 | 解决办法 |
| --- | --- | --- |
| `error: identifier "__global__" is undefined` | 你在 `g++`/`cl.exe` 里编译了 `.cu` 文件 | 必须用 `nvcc` 编译 `.cu` |
| `error: a __global__ function must have void return type` | 核函数写了返回类型 | 改成 `void`，结果通过指针参数传出 |
| `error: calling a __global__ function from a __global__ function is not allowed` | 在核函数里直接调用另一个核函数 | CC 3.5+ 支持动态并行，但那需要显式开启且是 [第 6 章](ch06_CUDA高级特性.md) 的内容；一般情况应改成 `__device__` 函数 |
| `error: argument of type "float *" is incompatible with parameter of type "const float *"` | 参数类型不匹配 | 检查核函数签名的 `const` 和指针层级 |
| `error: expression must have pointer-to-object type` 在 `<<<>>>` 那行 | 把 `<<<>>>` 写在了普通函数调用上 | `<<<>>>` 只能用于核函数 |
| `nvcc fatal : Unsupported gpu architecture 'compute_89'` | CUDA 版本太旧，不认识这个 CC | 升级 Toolkit，或改用旧架构 |
| 编译特别慢（几分钟） | 没指定 `-arch`，`nvcc` 编了一堆架构 | 显式 `-arch=sm_XX` |
| `ptxas error : Entry function 'x' uses too much shared data` | 共享内存超了 | 减小分块或查 `sharedMemPerBlock`，见 [第 2 章](ch02_内存层次与访存优化.md) |
| `error: too many resources requested for launch` | 每块线程数 × 每线程寄存器数 超过 SM 上限 | 减小块大小，或加 `__launch_bounds__`，见 [第 2 章](ch02_内存层次与访存优化.md) |

### 6.4 运行类错误

| 错误信息 | 原因 | 解决办法 |
| --- | --- | --- |
| `no CUDA-capable device is detected` | 没有 N 卡 / 驱动没工作 / 在无显卡直通的虚拟机里 | 先跑 `nvidia-smi` 确认；容器里需要 `--gpus all`；远程会话要用 NVIDIA 官方驱动 |
| `no kernel image is available for execution on the device` | 编译的架构和显卡不匹配，且没有可 JIT 的 PTX | 用正确的 `-arch=sm_XX` 重新编译（见练习 0.2） |
| `invalid device function` | 同上，通常发生在指定的 CC 高于显卡实际 CC 时 | 同上 |
| `an illegal memory access was encountered` | 核函数访问了越界地址 | 用 `compute-sanitizer ./app` 定位到具体行；检查索引与 `if (i < n)` 保护 |
| `unspecified launch failure` | 通常是核函数崩溃（越界最常见） | 同上 |
| `the launch timed out and was killed` | Windows 上核函数跑太久（默认约 2 秒），被 WDDM 看门狗杀掉 | 别用 `<<<1,1>>>` 跑大循环；改成合理并行；或把显示驱动改成 TCC 模式（仅专业卡） |
| `out of memory` | 显存不够 | 减小 `N`；用 `cudaMemGetInfo` 查剩余显存；别忘了 `cudaFree` |
| 程序输出全 0 或垃圾值 | 常见于忘记 `cudaMemcpy`、方向写反、忘记同步 | 检查 `cudaMemcpy` 的 `cudaMemcpyHostToDevice` / `DeviceToHost` 方向；计时前加同步 |
| 设备端 `printf` 没输出 | 没同步或程序提前退出 | 加 `cudaDeviceSynchronize()` |
| `cudaErrorCudartUnloading` / 退出时报错 | 析构顺序问题：CUDA 运行时先于你的对象卸载 | 一般无害；把 CUDA 对象的生命周期放在 `main` 的局部作用域里可控 |

### 6.5 一个通用的排查流程

遇到问题按这个顺序走，能省下 80% 的时间：

```text
1. nvidia-smi 有输出吗？
   ├─ 没有 → 驱动问题，先解决驱动，别管 CUDA
   └─ 有 ↓
2. nvcc --version 有输出吗？
   ├─ 没有 → PATH 问题（见 6.2）
   └─ 有 ↓
3. 编译能过吗？
   ├─ 不能 → 看 6.3；把完整错误信息从头看起，nvcc 的第一个 error 才是根因
   └─ 能 ↓
4. device_query 能跑吗？
   ├─ 报 no CUDA-capable device → 环境问题
   └─ 能，看到了正确的 CC ↓
5. 你的程序报什么错？
   ├─ no kernel image / invalid device function → -arch 写错了
   ├─ illegal memory access → 代码越界，用 compute-sanitizer
   └─ 结果不对 → 代码逻辑问题
     ↓
6. 打开 compute-sanitizer：
   compute-sanitizer --tool memcheck ./your_app
```

**`compute-sanitizer` 是你最好的朋友**。它接替了旧的 `cuda-memcheck`，能精确报出越界访问、竞态、未初始化内存等问题：

```bash
# 内存检查（最常用）
compute-sanitizer ./your_app

# 共享内存竞态检查（第 2、3 章会用到）
compute-sanitizer --tool racecheck ./your_app

# 未初始化内存检查
compute-sanitizer --tool initcheck ./your_app
```

它会让程序慢几十倍，但**报出来的行号是精确的**，比对着代码猜强一百倍。

## 7. 本章小结

### 7.1 要点清单

- **异构计算**：CPU 负责逻辑复杂/串行的部分，GPU 负责数据量大/彼此独立的部分。两者有独立地址空间，数据要显式搬运。
- **`nvidia-smi`**：驱动级体检工具。它输出的 `CUDA Version` 是"驱动**最高支持**的 CUDA 版本"，不是"你装的版本"。
- **驱动与 Toolkit 的关系**：驱动决定你能装的 Toolkit 上限，不是反过来。
- **计算能力（CC）**：`major.minor` 形式的架构代号，决定可用指令、可用特性、各类资源上限，以及 `-arch=sm_XX` 该填什么。
- **CUDA Toolkit 的组成**：`nvcc`（编译器）、`cuda-gdb`、`compute-sanitizer`、`ncu`/`nsys`（性能工具）、头文件、库、数学库。
- **nvcc 编译流程**：分离主机码和设备码 → 设备码走 PTX → SASS；主机码交给 `gcc`/`cl.exe`；最后打包成 fatbin 并链接。
- **PTX 与 SASS**：PTX 是架构无关的虚拟汇编，SASS 是真实机器码。fatbin 里带 PTX 就能在新架构上 JIT。
- **`__global__` 核函数**：在 GPU 上执行、由 host 用 `<<<>>>` 启动、返回 `void`、参数按值传递。
- **异步执行**：`kernel<<<>>>` 立刻返回；要拿结果或看输出必须 `cudaDeviceSynchronize()`。
- **错误检查**：每个 CUDA API 都包 `CUDA_CHECK`，每次 kernel 启动后跟 `CUDA_CHECK_KERNEL()`，关键节点加 `CUDA_CHECK_SYNC()`。
- **构建**：`-O3` 和 `-arch=sm_XX` 是两个最不能省的编译参数；CMake 用 `project(... LANGUAGES CXX CUDA)` 启用 CUDA，Windows 上别忘了 `--config Release`。

### 7.2 自检问题

**Q1：`nvidia-smi` 里显示的 `CUDA Version: 12.2` 是什么意思？**

<details>
<summary>答案要点</summary>

它表示**当前驱动最高支持的 CUDA 运行时版本**是 12.2，**不是你安装的 Toolkit 版本**。你可以在同一台机器上装 CUDA 11.8，`nvcc --version` 会显示 11.8，而 `nvidia-smi` 依然显示 12.2。不要因为两个数字不一致就以为装错了。
</details>

**Q2：为什么核函数必须返回 `void`？**

<details>
<summary>答案要点</summary>

因为核函数启动是异步的：host 发出启动命令后立刻继续执行，此时设备端可能还没开始算。如果核函数有返回值，host 不知道该在哪里等、取哪个线程的返回值。CUDA 的规定是：结果写进设备内存，由 host 显式 `cudaMemcpy` 拷回。
</details>

**Q3：什么是 SASS 和 PTX，为什么可执行文件里要同时带它们？**

<details>
<summary>答案要点</summary>

- SASS 是真实 GPU 机器码，只对特定架构有效，执行时零编译开销。
- PTX 是架构无关的虚拟汇编，能被驱动 JIT 编译成任意（>= 其目标版本的）架构的 SASS。
- 带上 SASS 是为了在已知架构上启动快；带上 PTX 是为了在未知架构上"至少能跑"。
</details>

**Q4：为什么 `hello.cu` 里的 `cudaDeviceSynchronize()` 不能删？**

<details>
<summary>答案要点</summary>

两个原因：一是保证 GPU 输出被刷出来（设备端 printf 是缓冲的）；二是保证执行期错误在这一行暴露，而不是让程序带着错误悄悄退出。（实际上如果不加同步，进程退出时也会有隐式同步，但输出可能已被丢弃，且错误处理会失控。）
</details>

**Q5：为什么指定 `-arch=sm_XX` 这么重要？**

<details>
<summary>答案要点</summary>

- 指定过低（如用 `sm_35` 跑在 8.9 上）：走 PTX JIT，启动慢，且可能用不到新架构的指令优化。
- 指定过高（如用 `sm_90` 跑在 8.6 上）：直接报 `no kernel image is available`。
- 不指定：`nvcc` 用默认目标，很可能既不是你的卡，也编了一堆用不上的架构导致编译慢。

正确做法：开发时用确切的 CC，发布时打包多个架构 + PTX 兜底。
</details>

**Q6：看到 `no CUDA-capable device is detected`，你会怎么排查？**

<details>
<summary>答案要点</summary>

按顺序：
1. `nvidia-smi` 能不能出结果？不能 → 驱动问题（重装驱动/容器加 `--gpus all`）。
2. 能出结果但程序还是报错 → 检查运行环境是不是容器/WSL/远程会话，是否做了设备映射。
3. 多卡机器上 → 用 `CUDA_VISIBLE_DEVICES` 确认哪些设备可见。
4. 用 `cudaGetDeviceCount` 打印出实际看到的数量，而不是猜。
</details>

## 8. 下一章预告

你现在有了一个能跑 CUDA 的环境，也知道了"kernel 是异步的""错误要检查""架构要指定"。

但 `hello.cu` 里只有一个线程在干活——这比用 CPU 还慢。真正的 GPU 程序会启动**几万到几百万个线程**，让它们各管一小块数据。

下一章 [第 1 章 编程模型与线程索引](ch01_编程模型与线程索引.md) 要回答三个问题：

1. **线程是怎么组织的？** grid / block / thread 三层结构，`threadIdx`、`blockIdx`、`blockDim`、`gridDim` 四个内置变量。
2. **一个线程怎么知道该处理哪个数据？** 一维、二维、三维索引展开公式的推导过程。
3. **数据量是任意的，线程数怎么定？** Grid-Stride Loop 这个"标准写法"，以及为什么块大小要取 32 的倍数。

你会亲手写出第一个有实际意义的 GPU 程序——向量加法，并测量它相对 CPU 版本的加速比。
