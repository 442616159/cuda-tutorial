## 0. 本章导读

### 0.1 学完这一章你能做什么

前面三章你已经能写出**正确**的 CUDA 程序了。但「正确」只是及格线，真实项目里你还会遇到：

- 别人（或者三个月后的你）问：「这个 kernel 还能再快吗？」
- 自己的 kernel 比 cuBLAS 慢 10 倍，但**不知道慢在哪**；
- 改了一处代码，跑起来快了 20%，但不确定是真变快了还是机器抖动；
- 看了一堆教程，装了共享内存、用了 shuffle、开了 `--use_fast_math`，**结果更慢了**。

这些问题的共同点是：**你没有测量，只有猜测。**

学完本章，你将能够：

1. **用五步闭环代替瞎猜**：正确 → 基线 → profile → 只改最热的那一点 → 回归验证。每一步都有明确的产出物。
2. **算清三个关键指标**：有效带宽（GB/s）、算力（GFLOPS）、算术强度（FLOP/Byte）。任何 kernel 都能被这三个数字定位。
3. **用 Roofline 模型一眼判型**：这个 kernel 到底是被显存带宽卡住，还是被计算单元卡住？答案决定了你后面所有优化方向。
4. **读懂 `ncu` 的关键指标**：SOL（Speed of Light）百分比、Achieved Occupancy、Warp Stall Reasons、L1/L2 命中率、sectors per request。
5. **用 `nsys` 看时间线**：找出 kernel 之间的空隙、拷贝与计算能不能重叠、CPU 是不是瓶颈。
6. **正确使用编译选项**：知道 `-O3`、`-arch`、`--use_fast_math`、`-lineinfo`、`-G`、`-Xptxas -v` 各自做什么、什么时候不能用。
7. **看 PTX 和 SASS**：确认编译器有没有生成你想看到的指令（比如 FMA、向量化加载）。
8. **写一个可复用的计时类**，并且知道为什么「只跑一次」是错的。
9. **用 `compute-sanitizer` 给优化上保险**：优化最容易把正确性搞坏。

### 0.2 一句话主线

> **优化不是「让代码更快」，而是「把瓶颈从 A 挪到 B」。** 如果你不知道当前瓶颈在哪，你写的每一行优化代码都是在赌博。

## 1. 概念讲解

### 1.1 先讲一个反面故事

#### 🎭 场景：改了三个月，只快了 3 毫秒

小 A 写好了他的第一个矩阵乘法 kernel，`n = 1024` 跑 **28 毫秒**。他听说共享内存很厉害，于是照着教程加上了分块（tiling），再跑一次 —— **26 毫秒**。他不甘心，又加了 `--use_fast_math`，**25 毫秒**。

三个月后他才知道：

- 他的 kernel 在那张卡上应该能跑 **1 毫秒左右**，他改的两个地方都只碰到了皮毛；
- 真正的瓶颈是**每个线程都在从全局内存重复读 A 的一整行**，访存模式完全没合并；
- 而他之所以没看出来，是因为**他从来没有测过一个「已知答案」的基准**，比如「纯拷贝能达到多少带宽」。

这个故事的关键不是「他技巧不够」，而是 —— **他没有测量体系**。

### 1.2 优化五步闭环

#### 🔄 场景：为什么"优化"不能是一条直线

优化 GPU 程序的正确姿势是一个**闭环**，不是一条直线。每一步都必须有可检验的产出物。

> 🔄 **为什么必须是"闭环"？**
> 因为**你无法预测哪一步会有效**。
> - 你以为的瓶颈，可能不是真瓶颈；
> - 你改对的地方，可能收益很小；
> - 你改"优化"的地方，可能反而变慢。
>
> **唯一的出路是：每改一次，就测一次，然后回到起点重新判断。**

```text
        ┌──────────────────────────────────────────────────────┐
        │                                                      │
        ▼                                                      │
  ① 写正确、朴素的版本                                          │
        │   产出：CPU 对拍通过的基线实现                          │
        ▼                                                      │
  ② 建立基线与正确的指标                                        │
        │   产出：耗时 / 有效带宽 / GFLOPS，且和硬件峰值对比        │
        ▼                                                      │
  ③ Profile 找瓶颈                                             │
        │   产出：一句话结论「瓶颈是 X，证据是 ncu 指标 Y」        │
        ▼                                                      │
  ④ 只优化最热的那一个点                                        │
        │   产出：一次只改一处的补丁                             │
        ▼                                                      │
  ⑤ 回归验证：正确性 + 性能                                     │
        │   产出：新基线，或者"回滚"                             │
        └──────────────────────────────────────────────────────┘
```

#### 🔍 每一步的细节

**① 写正确、朴素的版本**

- 必须先有一个**可信的 CPU 参考实现**。GPU 代码是并行写的，出错方式千奇百怪，没有对拍你根本不知道结果对不对。
- 朴素版要**尽量简单**：一维索引、一元素一线程、不做任何优化。它的作用是当"标尺"。
- 千万别一上来就写共享内存 + shuffle + 向量化的"终极版本" —— 那样一旦出错，你需要在五个地方同时找 bug。

**② 建立基线与正确的指标**

这里最容易犯错：**指标选错了，后面全白干。**

| 场景 | 错误指标 | 正确指标 |
|---|---|---|
| 逐元素向量运算 | 耗时（ms） | 有效带宽（GB/s） |
| 矩阵乘法 | 耗时的加速比 | GFLOPS（要写清楚是 FP32 还是 FP16） |
| 归约 | 耗时 | 有效带宽 + 与理论峰值带宽的比值 |
| 稀疏运算 | 稠密矩阵的 GFLOPS | 实际搬运的字节数 / 非零元个数 |

为什么？因为**耗时只能告诉你"现在多快"，不能告诉你"离上限还有多远"**。有效带宽和 GFLOPS 是和硬件规格可比的量，它们才回答"还有多少空间"。

**③ Profile 找瓶颈**

问三个问题，按顺序：

1. **这个 kernel 一共花了多少时间？在总时间里的占比是多少？** —— 只优化占比最高的那个。
2. **它是访存受限还是计算受限？** —— 用 Roofline 判型，或者直接看 `ncu` 的 `Memory Throughput` 和 `Compute (SM) Throughput`。
3. **如果是访存受限，是带宽不够还是延迟没藏住？** —— 看 L1/L2 命中率和 Warp Stall Reasons。

**④ 只优化最热的那一个点**

**一次只改一处。** 这条规则听起来保守，但它能让你清楚地知道"这一处改动的收益是多少"。如果你同时改了四处，然后快了 30%，你根本不知道该保留哪一处。

**⑤ 回归验证**

两件事缺一不可：

- **正确性**：重新和 CPU 对拍。优化最常见的副作用就是"变快但算错"。
- **性能**：重复测量，确认收益稳定，而不是噪声。
- **回滚准备**：如果没变快（很常见！），要有干净的版本控制，果断回滚。**一个"看起来更高级但实测更慢"的改动，就应该删掉。**

#### 🕳️ 常见的心态陷阱

| 陷阱 | 表现 | 解药 |
|---|---|---|
| 过早优化 | 还没跑通就在想怎么用 shuffle | 回到第①步 |
| 迷信技巧 | "教程说共享内存快，我就一定用" | 用第④步的数据说话 |
| 同时改多处 | 一次提交改了 6 个地方 | 拆成 6 次提交 |
| 只看一次结果 | 跑一次快了 5% 就宣布胜利 | 预热 + 多次取中位数 |
| 不看占比 | 花三天优化一个只占 2% 的 kernel | 先看总时间拆分 |
| 忘了对拍 | 优化完只跑性能测试 | 把正确性测试写进同一份代码 |

### 1.3 有效带宽：判断访存效率的唯一正确指标

#### 🍽️ 打比方

把显存想象成一条高速公路。**理论峰值带宽**是这条路的设计通行量（比如每秒能过 500 GB）。你的 kernel 是路上的车流。

**有效带宽**就是你**实际**每秒运了多少货。它和理论峰值的比值，就是这条路的利用率。

#### 📖 严谨定义

```text
有效带宽 (GB/s) = 实际搬运的字节数 / 耗时(秒) / 1e9
```

三个要点：

**要点一：单位用 10 进制的 GB（1 GB = 10^9 字节），不是 GiB。** 因为显卡厂商的规格书用的是 10 进制。你的数字要能和规格书直接比较。

**要点二：「实际搬运的字节数」必须把读和写都算上。**

这是初学者最容易错的地方。看一个向量加法 `c[i] = a[i] + b[i]`：

| 数组 | 元素数 | 每元素字节 | 操作 | 字节数 |
|---|---|---|---|---|
| a | N | 4 | 读 | 4N |
| b | N | 4 | 读 | 4N |
| c | N | 4 | 写 | 4N |
| **合计** | | | | **12N** |

如果你拿 `N * 4`（数组大小）当分子，算出来的带宽会**虚高 3 倍**，看上去"超过了硬件峰值" —— 这时候你的指标就没有意义了。

**要点三：只统计"必须"的字节，还是"实际"的字节？**

这里有两个约定，都很常见，但**必须写清楚用的是哪个**：

- **理论最小访存量**（Theoretical Minimum）：按算法语义必须读写的字节数。矩阵乘法就是 `2n²·4`（读 A + 读 B + 写 C）。用它算出的带宽，**可以超过硬件峰值**，意思是"这个 kernel 还有很大优化空间，因为它实际搬的比必须的多"。
- **实际访存量**（Actual Traffic）：从 `ncu` 的 `Memory Workload Analysis` 里读出的真实 DRAM 流量。它永远不会超过硬件峰值，是"真实利用率"。

**汇报时请写清楚**：`有效带宽（按理论最小访存量 3n²·4 计算）= 320 GB/s`。这句话比一个光秃秃的 `320 GB/s` 有价值得多。

#### 🧮 理论峰值带宽怎么算

```cpp
// memoryClockRate: kHz（cudaDevAttrMemoryClockRate）
// memoryBusWidth : bit（CUDA 13 起属性名是 cudaDevAttrGlobalMemoryBusWidth）
double peakGBs = 2.0 * memClockKHz * (busWidth / 8.0) / 1.0e6;
```

> **CUDA 13 兼容提示**：设备属性枚举 `cudaDevAttrMemoryBusWidth` 从 CUDA 13 起改名为 `cudaDevAttrGlobalMemoryBusWidth`（数值仍是 37）。写跨版本代码时用 `#if CUDART_VERSION >= 13000` 选择属性名；`cudaDeviceProp::memoryClockRate` 等时钟成员在 CUDA 13 已被移除，时钟和位宽都请走 `cudaDeviceGetAttribute`。

这个 `2.0` 是 DDR/GDDR 的"每时钟周期传输两次"。注意这只是**估算**：

- HBM 的等效时钟和这个公式对不齐，算出来会偏小；
- 厂商规格书上的数字有时按"最大睿频"给，实际运行可能降频；
- 所以**不要纠结于"为什么只跑到 78%"**。实测能到理论值的 **70%～90%** 就已经非常健康。

#### 📊 经验区间

在常见的消费级/数据中心显卡上，流式访存 kernel 通常能跑到：

| kernel 类型 | 相对峰值带宽的典型区间 |
|---|---|
| 纯读（归约、搜索） | 80%～95% |
| 纯写（memset 类） | 80%～90% |
| 读 1 写 1（copy / scale） | 70%～90% |
| 读 2 写 1（向量加） | 70%～85% |
| 有间接寻址（SpMV、gather） | 20%～60% |

**你的机器可能不同。** 这些数字的用途不是"达标"，而是"判断你现在这个数字是否离谱"。

### 1.4 算力与算术强度

#### ⚡ 算力（GFLOPS / TFLOPS）

```text
GFLOPS = 浮点运算次数 / 耗时(秒) / 1e9
```

两个约定必须写清楚：

1. **一次 FMA 算 1 次还是 2 次？** 硬件层面，`a * b + c` 是一条 `FFMA` 指令，一次做完乘加。业界惯例是**算 2 次浮点运算**（一次乘法 + 一次加法），所以算力 = FMA 次数 × 2。
2. **什么精度？** FP32 / FP64 / FP16 / TF32 / INT8 的峰值差异可以是几十倍。写 `TFLOPS` 时一定要带精度。

峰值算力的估算：

```text
峰值 FP32 算力 (GFLOPS) = SM 数 × 每 SM 的 FP32 核心数 × 核心时钟(GHz) × 2
```

`每 SM 的 FP32 核心数` 随架构变化（Kepler 192、Maxwell 128、Pascal P100 是 64 而消费级是 128、Volta/Turing 64、Ampere GA100 是 64 而 GA10x 是 128、Hopper 128）。`code/lessons/ch04_perf_model/roofline.cu` 里有一张查表，**它是估算**，不要当成精确值。

#### 🔢 算术强度（Arithmetic Intensity, AI）

**这是本章最重要的一个概念。**

```text
算术强度 AI = 浮点运算次数 / 搬运字节数   （单位：FLOP/Byte）
```

#### 🍽️ 打比方

想象两个工人：

- **甲**：每次去仓库取 1 个零件，回来装配 1 个产品。
- **乙**：每次去仓库取 1 个零件，回来装配 100 个产品。

甲的时间几乎全花在**跑仓库**上（访存），乙的时间几乎全花在**装配**上（计算）。甲就是低算术强度，乙就是高算术强度。

AI 就是「跑一趟仓库能装配多少产品」。

#### 📋 几个典型 kernel 的 AI

| kernel | FLOPs | 搬运字节 | AI |
|---|---|---|---|
| 向量加 `c=a+b` | N | 12N | 0.083 |
| 二维 5 点 stencil（无 tiling） | 约 10N（5 FMA） | 约 20N | 0.5 |
| 归约求和 | N | 4N | 0.25 |
| 矩阵乘 `n=1024` | 2n³ | 3n²×4 | **170.7** |
| 矩阵乘 `n=64` | 2n³ | 3n²×4 | **10.7** |

看到重点了吗？**同一个算法，规模不同，AI 差了 16 倍。** 小规模矩阵乘是带宽受限的，大规模矩阵乘是计算受限的。这就是为什么「n 太小的时候 GPU 跑不满」。

### 1.5 Roofline 模型

#### 🍽️ 打比方

Roofline（屋顶线）就是给"性能"画一间房子：

- **屋顶**是水平的，代表**算力上限**：不管数据离得多近，每秒最多就能算这么多 FLOP。
- **斜坡**是从原点往上走的，代表**带宽上限**：每秒最多搬这么多字节，而你每做 1 次浮点运算至少要搬 `1/AI` 个字节，所以能支撑的算力是 `AI × 峰值带宽`。

实际性能就是这两条线里**低的那条**，形状就像屋顶。

#### 📖 严谨表述

```text
可达到性能 (GFLOPS) ≤ min( 峰值算力, 算术强度 × 峰值带宽 )
```

两条线的交点叫 **ridge point（屋脊点）**：

```text
AI_ridge = 峰值算力 / 峰值带宽
```

判据：

- **AI < AI_ridge**：落在**斜坡**上 → **带宽受限（memory bound）**。优化方向是「少搬字节」。
- **AI > AI_ridge**：落在**平顶**上 → **计算受限（compute bound）**。优化方向是「少算或算得更高效」。

#### 📈 ASCII 图

下面是 `code/lessons/ch04_perf_model/roofline.cu` 输出的一张典型屋顶线图（纵轴 GFLOPS，横轴算术强度，对数刻度）：

```text
  10000 |                          ##############################
        |                        ##
        |                      ##
        |                    ##
        |                  ##
   6000 |                ##
        |              ##
        |            ##
        |          ##            <-- 斜坡：性能 = AI × 峰值带宽
   3000 |        ##
        |      ##
        |    ##
        |  ##
        |##
      0 +---------------------------------------------------------
         0.0625   0.25      1        4       16       64      256    1024
          算术强度 AI（FLOP/Byte，对数刻度）
```

- **斜坡部分**：这段的性能完全由带宽决定，提高算力没有用。
- **平顶部分**：这段的性能完全由算力决定，减少访存没有用。
- **交点**：屋脊点。在示例那台机器上大约在 AI ≈ 20～60 之间。

#### 🔍 读图举例

假设屋脊点在 `AI = 30`：

| kernel | AI | 落在哪 | 优化方向 |
|---|---|---|---|
| 向量加 | 0.083 | 斜坡最左端 | 减少字节：融合多个 kernel、用更小数据类型 |
| stencil | 0.5 | 斜坡 | tiling 提高数据复用、一次读多用的共享内存 |
| 归约 | 0.25 | 斜坡 | 合并访存、提高有用字节占比 |
| matmul n=64 | 10.7 | 斜坡（靠右） | 提高块大小，让 AI 更大 |
| matmul n=1024 | 170.7 | 平顶 | FMA、寄存器分块、Tensor Core |

#### ⚠️ 关于 Roofline 的两个提醒

1. **它给的是上界，不是预测值。** 落在斜坡上不意味着你一定能跑到斜坡上写的那个数 —— 可能还有延迟没藏住、还有 bank conflict。Roofline 只说"你不可能超过这条线"。
2. **AI 要用实际访存量算，还是理论最小访存量？** 都可以，但要一致。用理论最小量算出来的点更靠右，用实际量算出来的更靠左。**判断瓶颈时用实际量**（因为瓶颈就是实际发生的），**评估优化空间时用理论量**。

### 1.6 延迟、吞吐与占用率

#### 🍽️ 打比方

一家餐厅：

- **吞吐（Throughput）**：一小时能服务多少桌客人。
- **延迟（Latency）**：一桌客人从进门到吃完离开要多久。

这两件事**没有必然联系**。一家店可以每桌吃 3 小时（高延迟），但同时开 100 桌，于是吞吐很高（高吞吐）。

GPU 就是这样：

- 一次全局内存访问的**延迟**可能是 **400～800 个时钟周期**（相比寄存器的 0～4 个周期，这是天文数字）；
- 但显存的**吞吐**极高（每秒几百 GB）。

那 GPU 怎么做到"高延迟 + 高吞吐"的？**靠同时挂很多个 warp。**

#### 🧮 用 little's law 理解占用率

排队论里有个著名公式：

```text
吞吐 = 并发数 / 延迟
```

反过来写：

```text
需要的并发数 = 目标吞吐 × 延迟
```

套到 GPU 上：假设你要把显存带宽跑满（目标吞吐 = 500 GB/s），每次访存延迟 600 个周期，显存时钟 1.5 GHz（即每次访存延迟约 400 纳秒）。那么你需要同时有

```text
500e9 字节/秒 × 400e-9 秒 = 200000 字节 "在途"
```

如果每次访存取 128 字节，就需要大约 1560 次访存在途 —— 约等于需要 **50 个 warp 同时有访存在飞**。

**这就是占用率（Occupancy）的意义：**

> **占用率 = 实际驻留在 SM 上的 warp 数 / SM 能容纳的最大 warp 数**

它不是目的，而是**手段**：它决定 SM 有多少"备用 warp"可以在别人等内存的时候顶上来干活。

#### 🔒 占用率是被三样东西限制的

| 限制因素 | 说明 | 怎么算 |
|---|---|---|
| 寄存器 | 每 SM 有固定数量的寄存器（如 65536 个），每个线程占用 R 个 | 最大线程数 = 65536 / R |
| 共享内存 | 每 SM 有固定数量的 shared memory（如 100 KB） | 最大块数 = 100KB / 每块用量 |
| 块数上限 | 每个 SM 能同时驻留的 block 数有硬件上限（常见 16～32） | 块太小会导致 warp 数上不去 |

三个限制里**最紧的那个**决定最终占用率。

#### ⚠️ 占用率不是越高越好

这是个反直觉但非常重要的结论。

- 占用率 100% 的 kernel，每个线程只能分到很少的寄存器。如果算法需要大量寄存器做累加（比如寄存器分块的矩阵乘法），强制压低寄存器会导致 **spill（溢出到本地内存）**，而本地内存实际上就在显存里 —— 那还不如少挂几个 warp。
- 一个已经在带宽上限附近的 kernel，再提高占用率也没有用，因为瓶颈根本不在"藏延迟"上。

**正确的判断方式**：

1. 先看 `ncu` 的 `Memory Throughput` 和 `Compute (SM) Throughput` 谁高 —— 谁高谁是瓶颈。
2. 如果 `Memory Throughput` 高但远没到峰值，再去看 `Warp Stall Reasons`：
   - 主要是 **Long Scoreboard**（等全局内存）→ 提高占用率或改善访存局部性有用；
   - 主要是 **Barrier**（等 `__syncthreads`）→ 是负载不均，提高占用率没用；
   - 主要是 **Not Selected**（有别的 warp 在跑）→ 说明已经很饱和了，不用管。
3. 如果这些都对上了，占用率低也无所谓。

**一句话：占用率是用来"解释为什么延迟没藏住"的，不是用来"当目标"的。**

### 1.7 Nsight Compute（`ncu`）：逐 kernel 的显微镜

`ncu` 会**让 kernel 重放很多遍**，每一遍采集不同的硬件计数器，所以它会**把程序变慢几十到几百倍**。它不适合用来测总耗时，只适合用来**诊断单个 kernel 的内部行为**。

#### 💻 常用命令

```bash
# 1) 全量采集（最慢，但信息最全）
ncu --set full ./matmul_opt

# 2) 只看 SpeedOfLight 这一节（最常用，快得多）
ncu --section SpeedOfLight ./matmul_opt

# 3) 只测指定 kernel，而且只测第一次启动
ncu --kernel-name matmulNaive --launch-count 1 ./matmul_opt

# 4) 只看几个指标（最快）
ncu --metrics gpu__time_duration.sum,dram__throughput.avg.pct_of_peak_sustained_elapsed \
    ./matmul_opt

# 5) 导出报告，之后再慢慢看（推荐！）
ncu -o report_matmul ./matmul_opt
ncu --import report_matmul.ncu-rep          # 命令行查看
# 也可以用 Nsight Compute 的图形界面打开 .ncu-rep 文件
```

#### 🚀 Speed of Light（SOL）—— 首先看这一节

这是 ncu 报告的第一节，也是**最重要的第一节**。它给你四个百分比：

```text
    Section: GPU Speed Of Light Throughput
    -------------------------------------
    Memory Throughput                                            [ % ]
       DRAM Throughput                     %             62.41
       L1/TEX Throughput                   %             48.07
       L2 Throughput                       %             35.12
    Compute (SM) Throughput                 %             21.66
```

**怎么读：**

| 现象 | 结论 |
|---|---|
| `Memory Throughput`（看 DRAM 那一行）高，`Compute` 低 | **带宽受限**。去优化访存。 |
| `Compute (SM) Throughput` 高，`DRAM` 低 | **计算受限**。去优化指令或换算法。 |
| 两者都低（比如都 < 40%） | **延迟受限**（Latency Bound）。检查占用率、Warp Stall、依赖链。 |
| 两者都很高（都 > 80%） | 已经接近硬件极限，收益空间很小。 |

**注意**：`DRAM Throughput` 是**相对峰值**的百分比。如果它显示 `62%`，意思是"你已经用掉了 62% 的显存带宽上限"。

#### 🪑 Occupancy 一节

```text
    Section: Occupancy
    -------------------------------------
    Block Limit SM                                  block            32
    Block Limit Registers                           block             6
    Block Limit Shared Mem                          block            17
    Block Limit Warps                               block             2
    Theoretical Occupancy                           %                25.00
    Achieved Occupancy                              %                22.87
    Achieved Active Warps Per SM                    warp              16.00
```

- **三个 `Block Limit`**：分别告诉你"寄存器 / 共享内存 / 硬件块数上限"各自允许多少块。**最小的那个就是你的限制来源**。上例中 `Block Limit Warps = 2` 最大，`Block Limit Registers = 6` —— 等等，2 才是最小，所以受限的是 `Block Limit Warps`（因为块大小是 1024，每个 SM 最多 2048 线程，只能放 2 个块）。
- **`Theoretical Occupancy`**：理论上限（由资源决定）。
- **`Achieved Occupancy`**：实测平均值。因为 kernel 有启动/收尾阶段，块数在尾巴上会减少，所以实测通常略低于理论值，这是正常的。
- **差值很大（比如理论 100% 实测 30%）才值得怀疑**：通常意味着负载严重不均（比如只有少数块在干重活）。

#### 🛑 Warp State / Warp Stall Reasons

这节告诉你**warp 为什么停下来等**。它是"延迟为什么没藏住"的直接证据。

```text
    Section: Warp State Statistics
    -------------------------------------
    Warp Cycles Per Issued Instruction                            8.4
    Stall Long Scoreboard                                       3.21
    Stall Barrier                                               1.42
    Stall Wait                                                  0.85
    Stall Not Selected                                          0.60
    Stall Short Scoreboard                                      0.22
    Stall MIO Throttle                                          0.14
    Stall Draining                                              0.02
```

| Stall 类型 | 含义 | 对策 |
|---|---|---|
| **Long Scoreboard** | 在等**全局内存**（L1 miss，去了 L2/DRAM） | 提高占用率、改善访存局部性、用 tiling、预取 |
| **Short Scoreboard** | 在等**共享内存**或 L1 命中 | 检查 bank conflict、减少共享内存往返 |
| **Barrier** | 在等 `__syncthreads()` | **负载不均**：重新划分任务；减少屏障次数 |
| **Wait** | 在等**固定延迟指令**（如纹理、某些 ALU 依赖） | 增加指令级并行（ILP），打散依赖链 |
| **Not Selected** | 有别的 warp 可以跑，调度器没选它 | 这是**好事**，说明 SM 很忙，不用管 |
| **MIO Throttle** | 共享内存 / 特殊功能单元的队列满了 | 减少 shared/shuffle 访问密度 |
| **Draining** | kernel 收尾，等待所有内存操作完成 | 正常现象，占比小不用管 |

**看占比最大的那一项。** 注意 `Not Selected` 和 `Selected` 其实是"没在等"的证据，理想情况下它们占比应该不小。

#### 💾 Memory Workload Analysis

```text
    Section: Memory Workload Analysis
    -------------------------------------
    Memory Throughput                                               |
    DRAM Throughput                                    %   62.41   |
    Mem Busy                                          %   70.13    |
    Max Bandwidth                                     %   68.02    |
    L1/TEX Hit Rate                                   %   12.50    |
    L2 Hit Rate                                       %   45.30    |
    Mem Pipes Busy                                    %   55.11    |
    ...
    Global Load Access Pattern                            |
    Sectors Per Request                                       4.0   |
```

**`Sectors Per Request` 是判断合并访存的金标准：**

- 一个内存"请求（request）"是**一个 warp 的一条访存指令**。
- 一个"sector"是 32 字节（L1/L2 的最小传输单位）。
- 一个 warp 的 32 个线程，如果访问 32 个连续的 float（128 字节），需要 **4 个 sector**（128 / 32 = 4）。这时 `Sectors Per Request = 4.0`，**完美的合并访存**。
- 如果访问的是跨步/随机地址，32 个线程可能碰到 32 个不同 sector，`Sectors Per Request = 32.0`，**效率只有 1/8**（因为一个 sector 里只有 4 字节有用）。

> **快速判据：`Sectors Per Request` 越接近 4 越好，超过 8 就说明访存模式有问题。**

#### 🚫 什么情况下不该用 ncu

- **测总耗时**：ncu 会让程序慢几十倍，用 `cudaEvent` 计时。
- **测量 I/O 密集型程序**：ncu 重放会重复执行文件读写等副作用，很危险。
- **第一次接触某个程序时就用 `--set full`**：输出太长会淹没你。先用 `--section SpeedOfLight`。

### 1.8 Nsight Systems（`nsys`）：系统级的时间线

`nsys` 和 `ncu` 的分工完全不同：

- **`ncu`**：一个 kernel 内部的显微镜（但不看整体）。
- **`nsys`**：整个程序的时间线（但不看 kernel 内部）。

#### 💻 常用命令

```bash
# 基本用法：采集并生成报告
nsys profile -o report ./streams

# 采集完直接打印统计摘要
nsys profile -o report --stats=true ./streams

# 只采集 CUDA 相关活动，减少噪声
nsys profile -o report --trace=cuda,nvtx --stats=true ./streams

# 采集之后用 GUI 打开
nsys-ui report.nsys-rep
```

#### 🔍 时间线上要看什么

`nsys` 的图形界面里，你会看到几条泳道：

```text
时间 →  ┌────────────────────────────────────────────────────────────┐
CPU     │ [cudaMalloc] [cudaMemcpyAsync] [kernel launch] [sync ] ... │
        ├────────────────────────────────────────────────────────────┤
Stream  │                  ▓▓▓▓▓▓▓ K1 ▓▓▓▓▓▓▓                        │
  0     ├────────────────────────────────────────────────────────────┤
Stream  │                        ▓▓▓▓▓▓▓ K2 ▓▓▓▓▓▓▓                  │
  1     ├────────────────────────────────────────────────────────────┤
Stream  │  ▒▒▒▒ H2D ▒▒▒▒  ▒▒▒▒ H2D ▒▒▒▒   ▒▒▒▒ D2H ▒▒▒▒              │
  2     └────────────────────────────────────────────────────────────┘
         ↑                                                     ↑
         空白 = GPU 空闲                                     空白 = GPU 空闲
```

**五个要点：**

1. **kernel 之间的空隙（gap）**。如果两个 kernel 之间有明显空白，而 CPU 泳道上那些时刻在忙着"launch"，说明**CPU 提交跟不上 GPU**。对策：CUDA Graphs、增大 batch、减少同步。
2. **拷贝与 kernel 是否重叠**。如果 H2D 色块和 kernel 色块在**时间上重叠**，说明多流起作用了。如果它们严格错开，说明流没生效（可能用了可分页内存，或者在默认流上）。
3. **`cudaMemcpy`（同步版）的耗时**。它是一条又长又粗的色块，而且期间 CPU 是阻塞的。
4. **kernel 的相对长度**。一眼就能看出哪个 kernel 是大头，值不值得优化。
5. **`cudaDeviceSynchronize` 的位置**。它是"CPU 停下来等 GPU"的证据。如果它在热路径上，就是性能杀手。

#### 🔧 `nsys` 的另一个用途：看 CPU 侧开销

如果每个 kernel 只跑 5 微秒，而 `nsys` 显示每次 launch 之间有 8 微秒的 CPU 时间，那你的程序**根本不是 GPU 受限，而是 CPU 受限**。这种情况下，kernel 优化得再好也没用，必须先解决提交开销。

### 1.9 常见瓶颈对策方法论

下表是本章最重要的一张表。它的用法是：**先确认现象（用工具），再对症下药，最后用同样的工具验证。**

#### 🐌 1.9.1 带宽远低于峰值

- **怎么确认**：`ncu` 的 `DRAM Throughput` 百分比很低，同时 `Sectors Per Request` 明显大于 4。
- **为什么**：访存没有合并。相邻线程访问的地址不连续，一个 32 字节的 sector 里只有几个字节是有用的，剩下的带宽全浪费了。
- **怎么改**：
  1. 调整索引顺序，让 `threadIdx.x` 对应**最快变化的那个维度**；
  2. 结构体数组（AoS）改成数组结构体（SoA）；
  3. 二维数据用 `cudaMallocPitch` 保证行对齐；
  4. 矩阵乘法的共享内存分块（tiling）提高数据复用。
- **怎么验证**：重跑 `ncu`，看 `Sectors Per Request` 是否降到 4 附近，`DRAM Throughput` 是否上升。

#### 🪑 1.9.2 占用率低

- **怎么确认**：`ncu` 的 Occupancy 一节，看三个 `Block Limit` 谁最小。
- **为什么**：寄存器或共享内存占用过多，或者块大小不合理。
- **怎么改**：
  1. `Block Limit Registers` 最小 → 用 `__launch_bounds__(blockSize, minBlocksPerSM)` 给编译器下硬指标，或者减小块大小；
  2. `Block Limit Shared Mem` 最小 → 减小 tiling 尺寸，或用动态共享内存精确控制；
  3. `Block Limit Warps` 最小且块很小 → 增大块大小（但别超过 1024，也别小于 128）。
- **怎么验证**：重跑，看 `Theoretical Occupancy` 是否上升；**并且**看耗时是否真的下降（可能不下降，见 1.6 节）。

#### 🛑 1.9.3 Warp 停顿在 Barrier

- **怎么确认**：`ncu` 的 `Stall Barrier` 占比很高。
- **为什么**：负载不均。典型场景是归约的最后几轮只有少数线程在干活，其余线程都在等；或者共享内存加载阶段有的线程要搬很多数据。
- **怎么改**：
  1. 改变归约的结构（比如用 shuffle 替代共享内存，直接砍掉大部分屏障）；
  2. 让 `__syncthreads()` 出现的位置更均匀；
  3. 重新划分任务，让每个线程的活差不多重。
- **怎么验证**：看 `Stall Barrier` 占比是否下降，整体耗时是否下降。

#### ⏳ 1.9.4 Kernel 间隙大

- **怎么确认**：`nsys` 时间线上,两个 kernel 之间存在明显空白。
- **为什么**：每次 kernel 启动要走一遍完整的驱动路径（几微秒）。kernel 越短、数量越多，这个开销占比越高。
- **怎么改**：
  1. CUDA Graphs（`code/lessons/ch03_graphs/graphs.cu`）；
  2. 合并小 kernel（把逐元素的几个操作融合成一个）；
  3. 增大每次处理的数据量，减少 launch 次数。
- **怎么验证**：`nsys` 上重新看间隙宽度。

#### 🚚 1.9.5 拷贝占主导

- **怎么确认**：`nsys` 上 H2D / D2H 的色块比 kernel 色块还长。
- **为什么**：PCIe 的带宽（约 12～32 GB/s）比显存带宽（几百 GB/s）低一个数量级。数据在主机和设备之间来回搬，就是整个程序的瓶颈。
- **怎么改**：
  1. **减少搬运次数**：把计算尽量留在 GPU 上做，中间结果不要 D2H 再 H2D；
  2. **异步 + 多流重叠**（`code/lessons/ch03_streams/streams.cu`）；
  3. **用页锁定内存**让 `cudaMemcpyAsync` 真的异步；
  4. **统一内存 + 预取**（`cudaMemPrefetchAsync`）；
  5. 如果数据本来就该在 GPU 上产生，就别让它回主机。
- **怎么验证**：`nsys` 上 H2D / D2H 与 kernel 是否重叠；总耗时是否下降。

#### ⚡ 1.9.6 计算受限

- **怎么确认**：`ncu` 的 `Compute (SM) Throughput` 很高、`DRAM Throughput` 低。
- **为什么**：指令吞吐打满了。常见原因是用了慢指令（除法、超越函数、`double`）、有分支发散、或者有依赖链导致流水线停顿。
- **怎么改**：
  1. 用 FMA 替代分离的乘加（编译器一般会自动做，看 SASS 确认）；
  2. 把 `1/x` 换成常量乘法（`--use_fast_math` 会做，但损失精度）；
  3. 消除 warp 内分支发散（见第 1 章）；
  4. 提高指令级并行（ILP）：让每个线程处理多个独立元素，把长依赖链拆开；
  5. 换低精度或 Tensor Core（第 6 章）。
- **怎么验证**：GFLOPS 是否上升；`Compute (SM) Throughput` 是否更接近峰值。

#### 💥 1.9.7 优化之后变错了

- **怎么确认**：`compute-sanitizer` + CPU 对拍。
- **为什么**：优化最常破坏的是「边界条件」和「同步」。
- **怎么改**：见 1.12 节。
- **怎么验证**：把正确性测试写进同一份可执行文件里，每次优化后都跑。

### 1.10 编译选项详解

#### 🅰️ 1.10.1 `-O3`

```bash
nvcc -O3 kernel.cu -o kernel
```

让 nvcc 做更激进的优化（循环展开、内联、指令调度）。默认 `-O3` 对设备代码已经是比较高的优化级别，但显式写出来没坏处。

**注意**：`-O3` 有时会把浮点运算重新结合，改变结果的最低位。如果你在做**严格数值对拍**（要求 bit-exact），这一点要知道。GPU 上的浮点求和本来就不满足结合律。

#### 🅱️ 1.10.2 `-arch=sm_XX`：一定要显式指定

```bash
nvcc -arch=sm_75 kernel.cu -o kernel
```

`sm_XX` 里的 `XX` 是**计算能力**（Compute Capability，CC）：

- `sm_70` = Volta（V100）
- `sm_75` = Turing（RTX 20 系、GTX 16 系）
- `sm_80` / `sm_86` / `sm_89` = Ampere / Ada
- `sm_90` = Hopper（H100）

**为什么不写会出问题**：nvcc 的默认架构可能是很低的一代（为了兼容性）。用 `sm_35` 编译出来的代码，在你的 RTX 4090 上可能跑得比 `sm_89` 慢好几倍，因为它用不到新指令（比如更宽的加载、更快的 shared memory 原子）。

**怎么查自己的**：

```bash
nvidia-smi --query-gpu=name,compute_cap --format=csv
```

**一个更省事的写法**：`-arch=native`（CUDA 11.5+）会自动检测本机 GPU。

**还想兼顾可移植性**？用 `-gencode` 同时生成多个版本：

```bash
nvcc -gencode arch=compute_75,code=sm_75 \
     -gencode arch=compute_86,code=sm_86 \
     kernel.cu -o kernel
```

代价是二进制体积变大、编译变慢。

#### 🅾️ 1.10.3 `--use_fast_math`：快，但要付出代价

```bash
nvcc -O3 --use_fast_math kernel.cu -o kernel
```

它打开了下面这一串：

| 开关 | 效果 |
|---|---|
| `-ftz=true` | 把非规格化浮点数当 0 处理 |
| `-prec-div=false` | 除法用近似倒数 + 牛顿迭代 |
| `-prec-sqrt=false` | 开方用近似方法 |
| `-fmad=true` | 允许把 `a*b+c` 合并成 FMA |

**代价**：

- `sinf` / `cosf` / `expf` / `logf` 会被换成精度低得多的实现；
- 除法和开方的精度下降；
- FMA 合并会让结果和 CPU 的参考值产生**低位差异**；
- `ftz` 会让极小值直接变成 0。

**什么时候能用**：图形学、神经网络推理、任何"数值误差容忍度高"的场景。

**什么时候不能用**：科学计算、需要和 CPU 严格对拍、累加大量极小值（比如物理仿真里的微小力）。

**替代方案**：只想用 FMA、不想牺牲除法/开方精度，就只加 `-fmad=true`（默认就开着）。

#### 🐞 1.10.4 `-lineinfo` 和 `-G`

```bash
nvcc -O3 -lineinfo kernel.cu -o kernel      # ✅ 推荐：保留行号信息，不影响性能
nvcc -G kernel.cu -o kernel_dbg             # ⚠ 调试版：会极大降低性能
```

- **`-lineinfo`**：生成行号信息。`ncu`、`nsys`、`compute-sanitizer` 的报告里就能显示**源码行号**。**几乎不影响性能，建议一直加。**
- **`-G`**：完整的设备端调试信息（`cuda-gdb` 需要）。它会**关掉几乎所有优化**，性能可能掉 10 倍以上。**只在调试时用。**

#### 🔬 1.10.5 `-Xptxas -v`：看寄存器、共享内存和 spill

这是**性价比最高的一个开关**。它让 ptxas（PTX 汇编器）打印每个 kernel 的资源用量：

```bash
nvcc -O3 -arch=sm_75 -Xptxas -v matmul_opt.cu -o matmul_opt
```

输出样例：

```text
ptxas info    : 0 bytes gmem
ptxas info    : Compiling entry function '_Z12matmulTiledPKfS0_Pfi' for 'sm_75'
ptxas info    : Function properties for _Z12matmulTiledPKfS0_Pfi
    0 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads
ptxas info    : Used 38 registers, 2048 bytes cmem[0], 8192 bytes smem

ptxas info    : Compiling entry function '_Z16matmulTiledRegPKfS0_Pfi' for 'sm_75'
ptxas info    : Function properties for _Z16matmulTiledRegPKfS0_Pfi
    32 bytes stack frame, 8 bytes spill stores, 8 bytes spill loads
ptxas info    : Used 104 registers, 2048 bytes cmem[0], 8192 bytes smem
```

**逐字段解读：**

| 字段 | 含义 | 怎么判断 |
|---|---|---|
| `Compiling entry function '_Z12...'` | kernel 的名字（被 C++ 名字修饰过，可以用 `c++filt` 反解） | — |
| `for 'sm_75'` | 目标架构 | 确认和你的显卡一致 |
| `stack frame` | 使用的栈帧大小 | 非 0 说明有本地内存使用 |
| **`spill stores` / `spill loads`** | **寄存器溢出到本地内存的字节数** | **非 0 就要警惕**。本地内存实际在显存里，每次 spill 都是一次访存 |
| `Used N registers` | 每个线程用的寄存器数 | 决定占用率上限：`65536 / N` 就是每 SM 最大线程数（假设寄存器是唯一限制） |
| `cmem[0]` | 常量内存用量（kernel 参数就放这里） | 一般不用管 |
| **`bytes smem`** | **静态共享内存用量** | 和 `sharedMemPerBlock`（通常 48 KB，可配置到更高）比较 |

**`spill` 是最值得关注的信号。** 如果你看到 `spill stores` 是几百字节，说明寄存器压力已经很大，性能大概率受影响。对策：

1. 用 `__launch_bounds__` 给编译器一个"少用寄存器"的约束（但可能反而增加 spill，要测）；
2. 用 `-maxrregcount=N` 全局限制寄存器数（更粗暴）；
3. 减少每个线程的寄存器累加器数量；
4. **接受它** —— 有时候 spill 一点点换来高占用率是划算的。看数据说话。

**用寄存器数算占用率**：

```text
每 SM 最大线程数 = regsPerMultiprocessor / regsPerThread
```

比如每 SM 有 65536 个寄存器，每个线程用 38 个，那么最多 `65536 / 38 ≈ 1724` 个线程。寄存器分配是按粒度对齐的（通常 8 个一组），实际会少一些。再和 `maxThreadsPerMultiProcessor`（常见 1024 或 2048）取小，就是实际上限。

`code/lessons/ch04_occupancy/occupancy.cu` 会用 API 把这些数字直接打印出来，比手算靠谱。

### 1.11 读懂 PTX 与 SASS

#### 🔀 两种中间表示

| 名称 | 是什么 | 谁生成 |
|---|---|---|
| **PTX** | 虚拟指令集，跨架构的中间码 | `nvcc -ptx` |
| **SASS** | 真正的机器指令，绑定具体架构 | ptxas 从 PTX 汇编而来 |

**关系**：CUDA C++ → (nvcc 前端) → PTX → (ptxas) → SASS → (驱动) → 机器码

#### 🔍 怎么看

```bash
# 生成 PTX（虚拟指令，跨架构）
nvcc -O3 -arch=sm_75 -ptx matmul_opt.cu -o matmul_opt.ptx
# 打开 matmul_opt.ptx 看，是文本

# 反汇编出 SASS（真实机器码）
cuobjdump -sass ./matmul_opt > matmul_opt.sass
# 或者
cuobjdump -sass ./matmul_opt | less

# 也可以从 cubin 反汇编
cuobjdump -xelf all ./matmul_opt
nvdisasm -c matmul_opt.sm_75.cubin
```

**给 SASS 加行号**（配合 `-lineinfo` 编译）：

```bash
nvcc -O3 -arch=sm_75 -lineinfo -cubin matmul_opt.cu -o matmul_opt.cubin
nvdisasm -g -c matmul_opt.cubin | head -100    # -g 显示源码行号
```

#### 📖 看几条典型 SASS 指令

```text
/*0a20*/  FFMA R5, R6, R7, R5 ;          // R5 = R6 * R7 + R5
/*0a30*/  LDG.E.128 R8, [R2] ;           // 从全局内存读 128 bit（4 个 float）到 R8..R11
/*0a40*/  STS.128 [R4], R8 ;             // 把 128 bit 存进共享内存
/*0a50*/  BAR.SYNC 0 ;                   // __syncthreads()
/*0a60*/  ATOMG.E.ADD R0, [R2], R1 ;     // 全局原子加
/*0a70*/  LDS.64 R4, [R6] ;              // 从共享内存读 64 bit
/*0a80*/  SHFL.DOWN PT, R5, R5, 0x10 ;   // warp shuffle
/*0a90*/  IMAD R2, R3, R4, R2 ;          // 整数乘加（地址计算）
/*0aa0*/  BRA 0xa20 ;                    // 跳转
```

**几个值得专门去找的东西：**

1. **`FFMA` 的数量**。理想的矩阵乘法内层循环应该几乎全是 `FFMA`。如果看到大量的 `IMAD`（整数乘加），说明**地址计算的开销超过了计算本身** —— 这是很多"看起来应该很快"的 kernel 慢的原因。
2. **`LDG.E.128` / `LDG.E.64`**。`.128` 表示一次读 128 bit（4 个 float）。如果你的 kernel 里全是 `LDG.E`（32 bit），说明编译器没有向量化，访存指令数是 4 倍。让编译器向量化的方法：让每个线程连续处理 4 个元素，并用 `float4` 类型的指针（要对齐）。
3. **`BAR.SYNC` 的次数**。数一下和你写的 `__syncthreads()` 数量对不对得上（编译器有时会合并或消除）。
4. **`BRA`（分支）的位置**。如果循环里有分支，说明可能有 warp 发散。
5. **`LDL` / `STL`（本地内存读写）**。出现它就说明有寄存器 spill，对应 `-Xptxas -v` 里的 `spill stores/loads`。

**不要试着"手写 SASS 优化"** —— 你会输给 ptxas。看 SASS 的目的是**验证**：确认编译器按你的预期生成了指令，比如你想用 FMA 它有没有用、你想向量化它有没有做。

### 1.12 用 compute-sanitizer 给优化上保险

优化最大的风险是"变快了但算错了"。`compute-sanitizer` 是 NVIDIA 官方提供的动态分析工具（它是旧 `cuda-memcheck` 的替代品）。

#### 🧰 四种工具

| 工具 | 检查什么 | 命令 |
|---|---|---|
| `memcheck` | 内存越界、非法访问、对齐错误 | `compute-sanitizer --tool memcheck ./app` |
| `racecheck` | **共享内存的数据竞争** | `compute-sanitizer --tool racecheck ./app` |
| `initcheck` | 读取未初始化的全局内存 | `compute-sanitizer --tool initcheck ./app` |
| `synccheck` | 非法的 `__syncthreads()` 使用 | `compute-sanitizer --tool synccheck ./app` |

#### 📝 典型用法

```bash
# 一定要配合 -lineinfo 编译，报错里才会带源码行号
nvcc -O2 -arch=sm_75 -lineinfo app.cu -o app

# 内存错误
compute-sanitizer --tool memcheck ./app

# 共享内存竞态（优化归约、直方图、scan 之后必跑）
compute-sanitizer --tool racecheck ./app

# 全部报告，不要只报第一个错误
compute-sanitizer --tool memcheck --launch-timeout 120 ./app

# 顺带检查有没有忘了释放的显存
compute-sanitizer --tool memcheck --leak-check full ./app
```

#### 🔍 怎么读报告

`memcheck` 的典型输出：

```text
========= Invalid __global__ write of size 4 bytes
=========     at 0x00000120 in oobWriteKernel(float*, int)+0x30
=========     by thread (256,0,0) in block (16,0,0)
=========     Address 0x7f2b40010000 is out of bounds
=========     Saved host backtrace up to driver entry point at kernel launch time
```

**四个关键信息**：

1. **错误的类型**（`Invalid __global__ write`）；
2. **出错的 kernel 和偏移**（`oobWriteKernel +0x30`）；
3. **出错的线程和块**（`thread (256,0,0) in block (16,0,0)`）；
4. **地址性质**（`out of bounds`）。

**第 3 条特别有用**：它告诉你**哪个全局下标**出了问题。`i = 16 * 256 + 256 = 4352`，如果你的数组只有 4096 个元素，一眼就知道是边界检查没做。

`racecheck` 的报告会指出**哪两个线程、在哪个共享内存地址上**存在竞争，并明确区分：

- **Race**：真的错了（至少一个写）；
- **Hazard**：可能存在，但不一定触发。

**注意**：`racecheck` **会让程序变慢很多**，而且它只检查共享内存。全局内存的竞态要靠 `memcheck` + 逻辑推理。

#### 📍 什么时候跑

**每次优化之后都要跑。** 具体来说：

- 改了同步结构（加/删/挪 `__syncthreads()`）→ **必跑 racecheck**；
- 改了索引计算 → 必跑 memcheck；
- 改了共享内存布局 → 必跑 racecheck；
- 提交代码之前 → 全跑一遍。

把这些命令写进你的构建脚本（`code/Makefile` 里加个 `check` 目标），比靠记忆可靠得多。

## 2. 代码实战

### 2.1 示例 1：可复用的 `CudaTimer` 计时类（`code/common/cuda_timer.h`）

**为什么不能简单写两个 `clock()` 相减？**

1. **kernel 是异步启动的。** `kernel<<<...>>>` 返回时，GPU 上的工作可能还没开始。CPU 侧测到的只是"提交耗时"。
2. **第一次总是偏慢。** 时钟要升频、指令缓存要预热、驱动要懒加载。
3. **单次测量抖动大。** 别的进程抢显存、系统中断都会污染结果。

所以正确做法是：**用 `cudaEvent` 记在 GPU 的时间线上 + 预热 + 多次采样取中位数。**

`cuda_timer.h` 提供的类（源码见该文件）：

```cpp
class CudaTimer {
public:
    CudaTimer() {
        // cudaEventDefault 计时精度足够；不需要 cudaEventBlockingSync
        CUDA_CHECK(cudaEventCreate(&start_));
        CUDA_CHECK(cudaEventCreate(&stop_));
    }

    ~CudaTimer() {
        // 析构里不抛错：即使销毁失败也不该让程序崩溃
        cudaEventDestroy(start_);
        cudaEventDestroy(stop_);
    }

    // 禁止拷贝：事件句柄是独占资源，拷贝会导致重复销毁
    CudaTimer(const CudaTimer&) = delete;
    CudaTimer& operator=(const CudaTimer&) = delete;

    // 在默认流上"打一个时间戳"
    void start() { CUDA_CHECK(cudaEventRecord(start_, 0)); }

    // 结束计时；内部做 cudaEventSynchronize，所以返回值就是真实耗时
    float stopMs() {
        CUDA_CHECK(cudaEventRecord(stop_, 0));
        CUDA_CHECK(cudaEventSynchronize(stop_));  // 必须等 stop 事件真的发生
        float ms = 0.0f;
        CUDA_CHECK(cudaEventElapsedTime(&ms, start_, stop_));
        return ms;
    }

    float stop() { return stopMs(); }

    // 规范测量：预热 warmup 次后，再跑 iters 次取中位数
    //   f 的签名是 void(double& ms, int iter)，在里面写上"要测的一段代码"
    static double measure(const std::function<void(double&, int)>& f,
                          int iters = 5, int warmup = 1) {
        std::vector<double> samples;
        for (int i = 0; i < warmup + iters; ++i) {
            double ms = 0.0;
            f(ms, i);
            if (i >= warmup) samples.push_back(ms);
        }
        return medianOf(samples);
    }

    // 顺手算一下有效带宽（GB/s）：bytes 是这次操作搬运的总字节数
    static double bandwidthGBs(double bytes, double ms) {
        if (ms <= 0.0) return 0.0;
        return bytes / (ms * 1e-3) / 1e9;
    }

    // 顺手算一下算力（GFLOPS）：flops 是浮点运算次数
    static double gflops(double flops, double ms) {
        if (ms <= 0.0) return 0.0;
        return flops / (ms * 1e-3) / 1e9;
    }

private:
    cudaEvent_t start_{};
    cudaEvent_t stop_{};
};
```

**四个设计要点，每个都有理由：**

| 设计 | 理由 |
|---|---|
| 用 `cudaEvent` 而不是 `clock()` | 事件记在 GPU 时间线上，不受 CPU 调度和异步提交影响 |
| `stopMs()` 内部同步 | 不同步的话，`cudaEventRecord(stop)` 之后立刻取时间可能取到中间值 |
| `CudaTimer(const CudaTimer&) = delete;` | 事件句柄是独占资源，拷贝会导致同一个句柄被销毁两次 |
| `measure()` 里先跑 `warmup` 次再采样 | 把"冷启动"的样本丢掉，只统计稳态 |

**另外还提供了 `code/common/cuda_bench.h`**，在 `CudaTimer` 之上做了两个更方便的封装：

```cpp
// 预热 3 次，采样 20 次，返回中位数（毫秒）
template <typename Fn>
static inline double medianMs(Fn&& fn, int warmup = 3, int repeats = 20);

// 换算
static inline double gbps(double bytes, double ms);        // GB/s
static inline double gflopsOf(double flops, double ms);    // GFLOPS
```

用法极其简单：

```cpp
double ms = medianMs([&] { myKernel<<<grid, block>>>(d_in, d_out, n); });
printf("耗时 %.4f ms，有效带宽 %.1f GB/s\n", ms, gbps(bytes, ms));
```

本章后面所有示例都用它。

### 2.2 示例 2：把有效带宽真正测出来（`code/lessons/ch04_timing/bandwidth/bandwidth_test.cu`）

这个程序测四种访存模式：

```cpp
__global__ void copyKernel(const float* __restrict__ in,
                           float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = in[i];                  // 读 1 写 1
}

__global__ void scaleKernel(const float* __restrict__ in,
                            float* __restrict__ out, float a, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = a * in[i];              // 读 1 写 1，多了一次乘法
}

__global__ void addKernel(const float* __restrict__ a,
                          const float* __restrict__ b,
                          float* __restrict__ c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];              // 读 2 写 1
}

// 只读求和：用网格步长循环 + warp 归约，防止编译器把"读了没用"的代码优化掉
__global__ void readOnlySum(const float* __restrict__ in,
                            float* __restrict__ out, int n) {
    float v = 0.f;
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n;
         i += blockDim.x * gridDim.x) {
        v += in[i];
    }
    for (int offset = 16; offset > 0; offset >>= 1) {
        v += __shfl_down_sync(0xffffffffu, v, offset);
    }
    if ((threadIdx.x & 31) == 0) atomicAdd(out, v);
}
```

**三个容易忽略的细节：**

1. **`__restrict__`**：告诉编译器这两个指针不重叠，它才能放心地做指令重排和缓存优化。不加通常也没错，但加上往往能更快。
2. **`readOnlySum` 为什么要归约**：如果只写 `v += in[i]` 而不使用 `v`，编译器会把整个循环删掉，测出来的时间是 0。
3. **字节数怎么算**：

```cpp
report("copy (读1写1)",     2.0 * bytes, tCopy,  peak);   // 读 N*4 + 写 N*4
report("scale (读1写1)",    2.0 * bytes, tScale, peak);
report("add (读2写1)",      3.0 * bytes, tAdd,   peak);   // 读 2N*4 + 写 N*4
report("readOnly (读1)",    1.0 * bytes, tRead,  peak);   // 只读
```

**理论峰值带宽的估算**：

```cpp
static double theoreticalPeakGBs(double memClockKHz, int busWidth) {
    return 2.0 * memClockKHz * ((double)busWidth / 8.0) / 1.0e6;
}
```

注意代码里用的是 `cudaDeviceGetAttribute(cudaDevAttrMemoryClockRate / cudaDevAttrMemoryBusWidth)`，而不是 `cudaDeviceProp` 的对应成员 —— 后者在不同 CUDA 版本里被移除过，属性接口更稳定。其中位宽属性从 CUDA 13 起改名为 `cudaDevAttrGlobalMemoryBusWidth`，所以真实代码用 `#if CUDART_VERSION >= 13000` 在两者之间做选择。

### 2.3 示例 3：寄存器、共享内存与占用率（`code/lessons/ch04_occupancy/occupancy.cu`）

程序里有四个 kernel，分别代表四种资源受限的情况：

```cpp
// A. 轻量型
__global__ void lightKernel(const float* __restrict__ in,
                            float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = in[i] * 2.0f + 1.0f;
}

// B. 重度使用寄存器，故意制造寄存器压力
__global__ void heavyKernel(const float* __restrict__ in,
                            float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    float acc[16];
#pragma unroll
    for (int k = 0; k < 16; ++k) acc[k] = in[i] * (float)(k + 1);
#pragma unroll
    for (int k = 0; k < 16; ++k) acc[k] = acc[k] * 1.0001f + 0.5f;
    float s = 0.f;
#pragma unroll
    for (int k = 0; k < 16; ++k) s += acc[k];
    out[i] = s;
}

// C. 用 __launch_bounds__ 给编译器下"硬指标"
__global__ void __launch_bounds__(BLOCK, 4)
boundedKernel(const float* __restrict__ in, float* __restrict__ out, int n) {
    /* 和 heavyKernel 一样的计算，但限定了每 SM 至少要放下 4 个块 */
}

// D. 大量使用共享内存，占用率被 shared memory 卡住
__global__ void sharedHeavyKernel(const float* __restrict__ in,
                                  float* __restrict__ out, int n) {
    // 每块 48 KB 共享内存 —— 大多数 SM 只有 96~100 KB，
    // 于是每个 SM 最多只能放 2 个这样的块。
    __shared__ float s[12 * 1024];          // 12K * 4B = 48 KB
    int t = threadIdx.x;
    s[t] = in[blockIdx.x * blockDim.x + t];
    __syncthreads();
    float v = 0.f;
    for (int k = t; k < 12 * 1024; k += blockDim.x) v += s[k];
    out[blockIdx.x * blockDim.x + t] = v;
}
```

**`__launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor)` 的含义**：

- 第一个参数：这个 kernel 最多用多少线程启动（让编译器知道线程数上限）；
- 第二个参数：**要求**编译器把资源压到"每 SM 至少能同时放下 N 个块"。

编译器会据此限制寄存器用量。代价是可能产生 spill，**所以一定要用 `-Xptxas -v` 和实测数据来验证它到底有没有帮助**。

程序用 API 把这些数字打印出来：

```cpp
cudaFuncAttributes attr{};
CUDA_CHECK(cudaFuncGetAttributes(&attr, heavyKernel));
printf("寄存器/线程 : %d\n", attr.numRegs);
printf("本地内存    : %d 字节（>0 说明有 spill）\n", (int)attr.localSizeBytes);

int blocksPerSm = 0;
CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(
    &blocksPerSm, heavyKernel, BLOCK, 0));
double occ = 100.0 * blocksPerSm * BLOCK / prop.warpSize
             / (prop.maxThreadsPerMultiProcessor / prop.warpSize);
```

以及让运行时帮你推荐块大小：

```cpp
int minGridSize = 0, blockSize = 0;
CUDA_CHECK(cudaOccupancyMaxPotentialBlockSize(
    &minGridSize, &blockSize, heavyKernel, 0, 0));
```

**这是"起点建议"，不是"最优解"。** 最优块大小还得实测。

### 2.4 示例 4：优化前后对比的完整案例（`code/lessons/ch04_case_study/matmul_opt.cu`）★核心

这是本章的收官案例，把「五步闭环」完整走一遍：**三个版本的矩阵乘法，每一版都验证正确性 + 计时 + 算加速比。**

#### 🔀 三个版本

**v1 朴素版**：每个线程算一个元素，直接从全局内存反复读。

```cpp
__global__ void matmulNaive(const float* __restrict__ A,
                            const float* __restrict__ B,
                            float* __restrict__ C, int n) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (row >= n || col >= n) return;

    float sum = 0.f;
    for (int k = 0; k < n; ++k) {
        sum += A[row * n + k] * B[k * n + col];
    }
    C[row * n + col] = sum;
}
```

**原来慢在哪**：A 的每一行被读了 `n` 次，B 的每一列也被读了 `n` 次。`n = 1024` 时，实际访存量是理论最小量的几百倍。

**v2 shared 分块版**：把 16×16 的 tile 搬进共享内存。

```cpp
#define TILE 16
__global__ void matmulTiled(const float* __restrict__ A,
                            const float* __restrict__ B,
                            float* __restrict__ C, int n) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int tx = threadIdx.x;
    int ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;

    float sum = 0.f;
    for (int k0 = 0; k0 < n; k0 += TILE) {
        As[ty][tx] = A[row * n + k0 + tx];
        Bs[ty][tx] = B[(k0 + ty) * n + col];
        __syncthreads();

        for (int k = 0; k < TILE; ++k) {
            sum += As[ty][k] * Bs[k][tx];
        }
        __syncthreads();     // 必须：否则下一轮写 As/Bs 会覆盖还没读完的数据
    }
    C[row * n + col] = sum;
}
```

**为什么能变快**：全局内存访问量降到原来的约 1/16（每个 tile 数据被 16 个线程复用）。用 `ncu` 看 `DRAM Throughput` 会明显上升，`Sectors Per Request` 保持 4。

**v3 分块 + 寄存器分块**：块级 tile 放大到 64×64，每线程算 4×4。

```cpp
#define BM 64           // 块级 tile 的行数
#define BN 64           // 块级 tile 的列数
#define BK 16           // k 方向的步长
#define TM 4            // 每线程负责的行数
#define TN 4            // 每线程负责的列数

__global__ void matmulTiledReg(const float* __restrict__ A,
                               const float* __restrict__ B,
                               float* __restrict__ C, int n) {
    __shared__ float As[BM][BK];      // 64 x 16
    __shared__ float Bs[BK][BN];      // 16 x 64

    int tx = threadIdx.x;             // 0..15
    int ty = threadIdx.y;             // 0..15

    int rowBase = blockIdx.y * BM + ty * TM;   // 本线程负责的起始行
    int colBase = blockIdx.x * BN + tx * TN;   // 本线程负责的起始列

    float acc[TM][TN];
#pragma unroll
    for (int i = 0; i < TM; ++i)
#pragma unroll
        for (int j = 0; j < TN; ++j) acc[i][j] = 0.f;

    for (int k0 = 0; k0 < n; k0 += BK) {
        // ---- 协作搬入 A 的 64x16 分块 ----
#pragma unroll
        for (int i = 0; i < TM; ++i) {
            As[ty * TM + i][tx] = A[(rowBase + i) * n + k0 + tx];
        }
        // ---- 协作搬入 B 的 16x64 分块 ----
#pragma unroll
        for (int j = 0; j < TN; ++j) {
            Bs[ty][tx * TN + j] = B[(k0 + ty) * n + colBase + j];
        }
        __syncthreads();

        // ---- 在共享内存上做 BK 次乘加，结果留在寄存器 ----
#pragma unroll
        for (int kk = 0; kk < BK; ++kk) {
            float aReg[TM], bReg[TN];
#pragma unroll
            for (int i = 0; i < TM; ++i) aReg[i] = As[ty * TM + i][kk];
#pragma unroll
            for (int j = 0; j < TN; ++j) bReg[j] = Bs[kk][tx * TN + j];
#pragma unroll
            for (int i = 0; i < TM; ++i)
#pragma unroll
                for (int j = 0; j < TN; ++j)
                    acc[i][j] += aReg[i] * bReg[j];
        }
        __syncthreads();
    }

#pragma unroll
    for (int i = 0; i < TM; ++i)
#pragma unroll
        for (int j = 0; j < TN; ++j)
            C[(rowBase + i) * n + colBase + j] = acc[i][j];
}
```

**为什么能再快一层**：

1. 每个线程从共享内存读 `4 + 4 = 8` 个数，却做了 `4 × 4 = 16` 次乘加 —— 共享内存流量大幅下降；
2. 累加器全在寄存器里，内层循环里**没有任何访存**，理想情况下 SASS 全是 `FFMA`；
3. 64×64 的块意味着每份数据被复用 64 次（而不是 v2 的 16 次）。

#### ✅ 正确性验证的巧思

程序没有用 `O(n³)` 的 CPU 三重循环（1024³ 太慢），而是利用了一个恒等式：

```text
sum_ij C_ij = sum_k (sum_i A_ik) · (sum_j B_kj)
```

推导：`C_ij = sum_k A_ik · B_kj`，所以

```text
sum_ij C_ij = sum_ij sum_k A_ik B_kj = sum_k (sum_i A_ik)(sum_j B_kj)
```

右边只要 `O(n²)` 就能算完。**这就是"给测试也做优化"的思路** —— 正确性测试不该成为开发的瓶颈。

```cpp
static double referenceChecksum(const float* A, const float* B, int n) {
    // 用 double 累加，避免 CPU 侧的舍入误差被误判成"GPU 算错"
    double total = 0.0;
    for (int k = 0; k < n; ++k) {
        double colSumA = 0.0;   // sum_i A[i][k]
        double rowSumB = 0.0;   // sum_j B[k][j]
        for (int i = 0; i < n; ++i) colSumA += A[i * n + k];
        for (int j = 0; j < n; ++j) rowSumB += B[k * n + j];
        total += colSumA * rowSumB;
    }
    return total;
}
```

**容差怎么定**：用 float 累加 1024 个乘积，误差可以到 1e-4 量级；总和规模在 1e2 左右。所以相对误差阈值取 `1e-3` 比较稳妥。**如果你把阈值定成 1e-6，你会被"误差"折磨一整天，而其实代码是对的。**

#### 📊 预期结果表

程序会打印这样一张表（数字随显卡变化）：

```text
--- 性能对比（各测若干次取中位数）---
  版本                   |   耗时(ms) |     GFLOPS |   加速比
  -----------------------+-----------+------------+---------
  v1 朴素                |     x.xxx |      xxx.x |    1.00x
  v2 shared 16x16        |     x.xxx |     xxxx.x |    x.xx x
  v3 shared + 寄存器分块 |     x.xxx |     xxxx.x |   xx.xx x
```

在 RTX 3060 这一档显卡上，`n = 1024` 时大致是：v1 几毫秒、v2 一点几毫秒、v3 零点几毫秒，GFLOPS 从不到 100 涨到 1000 以上。**你的机器可能不同**，但**趋势应该是一致的：v3 > v2 > v1**。

**如果趋势不对，说明有问题**：可能是 `-arch` 没指定、可能是共享内存 bank conflict 太严重、也可能是 v3 的寄存器 spill 太厉害（用 `-Xptxas -v` 查）。

#### 💥 一个刻意的"打脸"设计

程序最后按「理论最小访存量 = 3n²·4」换算等效带宽，并打印出来：

```cpp
double minBytes = 3.0 * bytes;         // 理论最小访存量：读 A + 读 B + 写 C
printf("  v1 : %7.1f GB/s\n", gbps(minBytes, t1));
printf("  v2 : %7.1f GB/s\n", gbps(minBytes, t2));
printf("  v3 : %7.1f GB/s\n", gbps(minBytes, t3));
```

**v1 的数字会远超硬件峰值。** 这不是 bug，而是 1.3 节讲的「理论最小访存量」的用法：**数字超过峰值 = 你实际搬的比必须的多得多**。这个对比本身就是"v1 访存效率极差"的量化证据。

### 2.5 示例 5：Roofline 模型（`code/lessons/ch04_perf_model/roofline.cu`）

程序做三件事：算两个天花板、画 ASCII 屋顶线、把几个典型 kernel 放上去判型。

```cpp
// 峰值带宽：显存时钟 × 位宽 / 8 × 2（DDR 每周期两次）
double peakBW = 2.0 * memClockKHz * (busWidth / 8.0) / 1.0e6;      // GB/s

// 峰值算力：SM 数 × 每 SM 核心数 × 时钟(Hz) × 2（FMA 算 2 次浮点）
int coresPerSm = fp32CoresPerSm(prop.major, prop.minor);
double peakF = (double)prop.multiProcessorCount * coresPerSm *
               (coreClockKHz * 1.0e3) * 2.0 / 1.0e9;               // GFLOPS

double aiRidge = peakF / peakBW;    // 屋脊点的算术强度
```

**每 SM 的 FP32 核心数**是一张按 CC 查的表（该函数里的注释说明了每一代的取值）。**这是估算**，因为同一代架构的不同型号（比如 A100 和 RTX 3090）核心数就不同。

ASCII 画的逻辑：

```cpp
for (int r = rows; r >= 0; --r) {
    double yLevel = peakF * r / rows;
    printf("%8.0f |", yLevel);
    for (int c = 0; c < cols; ++c) {
        // 横轴按对数均匀取样
        double t = (double)c / (cols - 1);
        double ai = aiMin * std::pow(aiMax / aiMin, t);
        double y = std::fmin(peakF, ai * peakBW);   // ★ 取两条线的较小值
        putchar(y >= yLevel ? '#' : ' ');
    }
    putchar('\n');
}
```

**`std::fmin(peakF, ai * peakBW)` 这一行就是 Roofline 的全部数学。** 一个 `min` 而已，但它的解释力极强。

然后对几个典型 kernel 判型：

```cpp
const Case cases[] = {
    {"向量加 c=a+b      ", 1.0 / 12.0, "读 2 写 1，AI 极低，铁定带宽受限"},
    {"二维 5 点 stencil ", 6.0 / 20.0, "每点 5 次乘加、读 4 邻居写 1（未做 tiling）"},
    {"矩阵乘 n=1024     ", 2.0 * 1024 / (3.0 * 4), "2n^3 FLOP / 3n^2*4 Byte，会跑到平顶上"},
    {"矩阵乘 n=64       ", 2.0 * 64 / (3.0 * 4), "n 太小时反而带宽受限"},
    {"归约求和           ", 1.0 / 4.0, "读 N 写 1，纯带宽受限"},

```

**最后两行是最有教育意义的**：同一个矩阵乘法算法，`n` 从 64 涨到 1024，AI 涨了 16 倍，判型从"带宽受限"翻转到"计算受限"。**算法相同，瓶颈不同，优化方向完全不同。**

```cpp
// bug 1：数组越界写 —— kernel 里没有边界检查，而网格又开多了一个块
__global__ void oobWriteKernel(float* a, int n) {
```

### 2.7 示例 7：计时方法论（`code/lessons/ch04_timing/timer/timer_demo.cu`）

程序连测 8 次同一个 kernel，打印最小 / 中位 / 最大：

```text

  连测 8 次的结果(ms)：0.1842 0.1851 0.1903 0.1917 0.1932 0.2011 0.2205 0.3012
```

```cpp
// 1) 手工计时
CudaTimer timer;
timer.start();

double total = timer.stopMs();

// 2) 规范测量：预热 + 多次 + 中位数
```

1. 写清楚**测的是什么**：数据规模、块大小、网格大小、编译选项、显卡型号；
2. 写清楚**怎么测的**：预热几次、采样几次、取什么统计量；
3. **带上误差范围**：比如「中位数 0.19 ms，8 次采样的极差在 ±5% 以内」。

## 3. 代码逐行解析

这一节挑三段代码，逐行讲清楚「为什么这么写」。

### 3.1 逐行解析：`bandwidth_test.cu` 里的测量与汇报

```cpp
static void report(const char* name, double bytesMoved, double ms, double peak) {
    double bw = gbps(bytesMoved, ms);
    printf("  %-22s | %10.4f | %9.1f | %6.1f%%\n",
           name, ms, bw, bw / peak * 100.0);
}
```

| 行 | 代码 | 为什么 |
|---|---|---|
| 1 | `double bytesMoved` | **字节数由调用方传进来**，因为不同 kernel 的搬运量不同（copy 是 2N，add 是 3N）。让调用方负责，函数本身不做假设。 |
| 2 | `gbps(bytesMoved, ms)` | 用统一的换算函数，保证全书所有地方的公式一致，不会这里除 1e9、那里除 1024³。 |
| 3 | `bw / peak * 100.0` | **打印占理论峰值的百分比**。这是最有信息量的一个数字：绝对值 `320 GB/s` 说明不了什么，`65%` 才能让你判断"还有没有空间"。 |

调用：

```cpp
double tAdd = medianMs([&] {
    addKernel<<<grid, BLOCK>>>(d_a, d_b, d_c, N);
}, 5, 30);
report("add (读2写1)", 3.0 * bytes, tAdd, peak);
```

| 行 | 代码 | 为什么 |
|---|---|---|
| 1 | `medianMs(..., 5, 30)` | 预热 5 次、采样 30 次。`warmup` 用于丢弃冷启动样本，`repeats` 越大统计越稳，但总时间也越长。 |
| 2 | lambda 里只有一行 kernel 启动 | **只测 kernel 本身**。如果把 `cudaMemcpy` 也放进去，测到的就是"端到端时间"，两个指标混淆了。 |
| 3 | `3.0 * bytes` | 向量加读 2 个数组、写 1 个数组。**这个 3 是有效带宽会不会算错的关键。** |

再看 `main` 的前半段：

```cpp
cudaDeviceProp prop{};
CUDA_CHECK(cudaGetDeviceProperties(&prop, 0));
int dev = 0;
CUDA_CHECK(cudaGetDevice(&dev));
int memClockKHz = 0, busWidth = 0;
// CUDA 13 起 cudaDevAttrMemoryBusWidth 改名为 cudaDevAttrGlobalMemoryBusWidth
#if CUDART_VERSION >= 13000
const cudaDeviceAttr kBusWidthAttr = cudaDevAttrGlobalMemoryBusWidth;
#else
const cudaDeviceAttr kBusWidthAttr = cudaDevAttrMemoryBusWidth;
#endif
CUDA_CHECK(cudaDeviceGetAttribute(&memClockKHz, cudaDevAttrMemoryClockRate, dev));
CUDA_CHECK(cudaDeviceGetAttribute(&busWidth,    kBusWidthAttr, dev));
double peak = theoreticalPeakGBs(memClockKHz, busWidth);
```

| 行 | 为什么 |
|---|---|
| `cudaGetDeviceProperties` | 拿设备名、SM 数量这些稳定存在的字段 |
| `cudaDeviceGetAttribute(..., cudaDevAttrMemoryClockRate, ...)` | 时钟和位宽走**属性接口**。`cudaDeviceProp::clockRate` / `memoryClockRate` 在不同 CUDA 版本里被移除过，属性接口跨版本更稳。位宽属性在 CUDA 13 起改名为 `cudaDevAttrGlobalMemoryBusWidth`，所以代码用 `#if CUDART_VERSION >= 13000` 选属性名。 |
| `theoreticalPeakGBs(memClockKHz, busWidth)` | 把公式抽成一个纯函数，方便单测和复用 |

### 3.2 逐行解析：`matmul_opt.cu` 里的对拍设计

```cpp
auto check = [&](const char* name) -> bool {
    float* h_C = (float*)malloc(bytes);
    CUDA_CHECK(cudaMemcpy(h_C, d_C, bytes, cudaMemcpyDeviceToHost));
    double s = 0.0;
    for (int i = 0; i < n * n; ++i) s += (double)h_C[i];
    double rel = fabs(s - refSum) / (fabs(refSum) + 1e-12);
    printf("  %-24s GPU 总和 = %14.4f，相对误差 = %.2e  %s\n",
           name, s, rel, rel < 1e-3 ? "✓" : "✗");
    free(h_C);
    return rel < 1e-3;
};
```

| 行 | 代码 | 为什么 |
|---|---|---|
| 1 | 参数是 `name` | 三个版本共用一段验证代码，只靠名字区分输出。**避免复制粘贴三份验证逻辑。** |
| 2 | `malloc(bytes)` | 拷回主机端再算总和。总和只有 1 个数，也可以直接用 `thrust::reduce`，但那引入依赖，这里手写更透明。 |
| 3 | `(double)h_C[i]` | **先把每个元素提升到 double 再累加。** 如果用 float 累加 100 万个元素，误差会累积到 1e-1 量级，和真正的错误分不清。 |
| 4 | `fabs(s - refSum) / (fabs(refSum) + 1e-12)` | **相对误差**，不是绝对误差。绝对误差会随数据规模变化，相对误差才是尺度无关的。加 `1e-12` 是防止除以 0。 |
| 5 | `rel < 1e-3 ? "✓" : "✗"` | 阈值取 `1e-3`。**这个阈值的依据**：float 有约 7 位有效十进制数字，累加 1024 项后有效位降到约 4 位，相对误差 1e-4 是正常的。取 1e-3 留了 10 倍余量。 |
| 6 | `free(h_C)` | 循环里调用，必须释放，否则三个版本泄漏 3 × 4 MB。 |

**这段代码体现了「优化验证」的一条原则：正确性检查必须和性能测量写在同一个可执行文件里。** 如果分成两个程序，你会在赶时间的时候"只跑性能那个"。

再看 `referenceChecksum`：

```cpp
static double referenceChecksum(const float* A, const float* B, int n) {
    double total = 0.0;
    for (int k = 0; k < n; ++k) {
        double colSumA = 0.0;
        double rowSumB = 0.0;
        for (int i = 0; i < n; ++i) colSumA += A[i * n + k];
        for (int j = 0; j < n; ++j) rowSumB += B[k * n + j];
        total += colSumA * rowSumB;
    }
    return total;
}
```

| 行 | 为什么 |
|---|---|
| `double total = 0.0` | 全部用 double 累加 |
| 内层两个循环 | `colSumA` 是 A 的第 k **列**之和（所以索引是 `i * n + k`，跨行读），`rowSumB` 是 B 的第 k **行**之和（所以索引是 `k * n + j`，连续读） |
| `total += colSumA * rowSumB` | 利用恒等式 `sum_ij C_ij = sum_k (sum_i A_ik)(sum_j B_kj)` |

**复杂度从 O(n³) 降到 O(n²)。** `n = 1024` 时，从约 10 亿次乘加降到约 100 万次，快了一千倍。

### 3.3 逐行解析：`roofline.cu` 里的一行数学

```cpp
double y = std::fmin(peakF, ai * peakBW);
```

这一行是整个 Roofline 模型：

- `ai * peakBW`：如果带宽是唯一限制，那么在算术强度为 `ai` 时能支撑的最大算力。
- `peakF`：算力本身的物理上限。
- `fmin(...)`：实际能达到的**不可能超过两者中较小的那个**。

再看判型的那一行：

```cpp
const char* verdict = (c.ai < aiRidge) ? "带宽受限" : "计算受限";
```

`aiRidge = peakF / peakBW`：解方程 `ai × peakBW = peakF` 得到 `ai = peakF / peakBW`。**小于屋脊点 = 在斜坡上 = 带宽受限。**

最后看那个 ASCII 画图的双重循环：

```cpp
for (int r = rows; r >= 0; --r) {              // 从高到低，因为终端是从上往下打印的
    double yLevel = peakF * r / rows;          // 这一行代表多少 GFLOPS
    for (int c = 0; c < cols; ++c) {
        double t = (double)c / (cols - 1);
        double ai = aiMin * std::pow(aiMax / aiMin, t);   // 对数插值
        double y = std::fmin(peakF, ai * peakBW);
        putchar(y >= yLevel ? '#' : ' ');      // 曲线下方的格子涂黑
    }
    putchar('\n');
}
```

| 行 | 为什么 |
|---|---|
| `r >= 0; --r` | 终端的第一行要对应**最大**的 GFLOPS，所以行号从大到小 |
| `aiMin * pow(aiMax / aiMin, t)` | **对数刻度插值**。AI 跨越 4 个数量级，线性刻度会把整个斜坡挤到最左边。`t ∈ [0,1]` 时 `ai` 从 `aiMin` 指数增长到 `aiMax`。 |
| `putchar(y >= yLevel ? '#' : ' ')` | 判断"这一行的 y 值是否在曲线下方"，是就涂 `#` |

**这段代码的价值**不在于画得多好看，而在于**让你亲手把 Roofline 的数学写一遍**。写完之后你不会再忘记 `min` 和屋脊点的含义。

## 6. 常见错误与排查

| 错误信息 / 现象 | 原因 | 解决办法 |
|---|---|---|
| 测出来的带宽超过硬件峰值好几倍 | 用「数组大小」当搬运字节数，忘了算读+写 | 用「读字节 + 写字节」；如果用的是理论最小量，在报告里注明 |
| 测出来的耗时是 0 ms 或极小 | 忘了 `cudaDeviceSynchronize`，测到的是提交耗时 | 用 `cudaEvent` + `cudaEventSynchronize`，或直接用 `CudaTimer` |
| 反复运行同一个 kernel，时间上下浮动 20% | 没有预热；或者系统里有别的 GPU 任务 | 预热 ≥ 3 次；采样 ≥ 20 次取中位数；关掉其他占显存的程序 |
| `-Xptxas -v` 显示大量 `spill stores` | 寄存器压力过大 | 减小块大小、减少每线程的累加器、或接受它（要看实测） |
| 加了 `--use_fast_math` 之后 CPU 对拍不过 | 它牺牲了除法和超越函数的精度，还开了 `ftz` | 只加 `-use_fast_math` 里你真正需要的子选项（如 `-fmad=true`）；或放宽容差并确认业务能接受 |
| `ncu` 报 `ERR_NVGPUCTRPERM` | 没有权限访问 GPU 性能计数器 | Linux 上需要 root 或者配置 `NVreg_RestrictProfilingToAdminUsers=0` |
| `ncu` 跑得极慢，甚至超时 | `ncu` 会重放 kernel 很多次，这是正常的 | 用 `--section SpeedOfLight` 而不是 `--set full`；用 `--launch-count 1` 限制次数 |
| `nsys` 报告里 CPU 泳道全是 `cudaLaunchKernel` | kernel 太短，CPU 提交是瓶颈 | 用 CUDA Graphs；合并 kernel；增大每次的数据量 |
| 时间线上拷贝和 kernel 完全不重叠 | 用了可分页内存，或者在默认流上 | 用 `cudaHostAlloc` 分配页锁定内存；用非默认流 |
| 优化后变快了，但结果不对 | 改了索引 / 同步 / 共享内存布局，破坏了正确性 | 立刻跑 `compute-sanitizer` + CPU 对拍；回滚到上一个正确版本 |
| `compute-sanitizer` 报的都是"别人的代码" | 第三方库（cuBLAS 等）内部也会被检查 | 用 `--launch-skip` / `--kernel-name` 限定范围 |
| `racecheck` 报 `Hazard` 但程序结果一直是对的 | `Hazard` 是"可疑"，不一定是真错 | 结合代码逻辑判断；只要有共享内存写后读，就该加屏障 |
| `-arch` 没写，性能莫名很差 | 编译器按默认（较低）架构生成代码 | 显式写 `-arch=sm_XX` 或 `-arch=native` |
| `nvdisasm` 找不到 cubin | 可执行文件里没有独立的 cubin | 先用 `cuobjdump -xelf all ./app` 提取，或直接用 `cuobjdump -sass` |
| 用 `-lineinfo` 之后性能下降明显 | 一般不会，`-lineinfo` 对性能影响很小 | 检查是不是误用了 `-G`（`-G` 会关掉优化，导致大幅下降） |

## 7. 本章小结

### 7.1 要点清单

- **优化是闭环，不是技巧的堆叠**：正确 → 基线 → profile → 只改一处 → 回归验证。
- **指标选错，后面全白干。** 逐元素操作用有效带宽，矩阵乘用 GFLOPS，归约用带宽占比。
- **有效带宽 = 实际搬运字节 / 耗时。** 「实际搬运字节」必须把读和写都算上；且要说明用的是理论最小量还是实际量。
- **算术强度 AI = FLOPs / Bytes。** 同一个算法，规模不同，AI 可以差十几倍。
- **Roofline 的全部数学就是一行 `min(峰值算力, AI × 峰值带宽)`。** 屋脊点 `AI = 峰值算力 / 峰值带宽`；左边带宽受限，右边计算受限。
- **延迟和吞吐是两件事。** GPU 靠「同时挂很多 warp」用吞吐掩盖延迟。所需并发数 ≈ 吞吐 × 延迟（little's law 的直觉）。
- **占用率是手段，不是目的。** 它用来解释"延迟为什么没藏住"，不用来当 KPI。
- **`ncu` 看 kernel 内部，`nsys` 看系统时间线。** 先看 SOL 判断瓶颈类型，再看 Warp Stall Reasons 找具体原因。
- **`Sectors Per Request` 越接近 4 越好**，超过 8 说明合并访存出了问题。
- **`-arch` 一定要写**；`-lineinfo` 几乎免费，建议常开；`-G` 只在调试时用；`--use_fast_math` 用之前想清楚精度要求。
- **`-Xptxas -v` 是最便宜的诊断工具**：看寄存器数估算占用率，看 `spill` 判断寄存器压力。
- **看 PTX / SASS 是为了验证，不是为了手写。** 数一数 `FFMA`、找一找 `LDG.E.128`、留意 `LDL/STL`。
- **计时必须预热 + 多次 + 取中位数。** 只跑一次得到的数据没有意义。
- **每次优化之后都要跑 `compute-sanitizer`。** 「今天没崩」不是正确性的证据。

### 7.2 自检问题

**Q1：为什么有效带宽比"耗时"更有用？**

答案要点：耗时只说"现在多快"，是尺度相关的；有效带宽可以**和硬件峰值直接比较**，从而回答"还有多少优化空间"。另外，有效带宽能立刻暴露"搬运字节数算错了"这类问题（超过峰值）。

**Q2：一个 kernel 的 `AI = 2`，机器的 `AI_ridge = 30`。它是什么类型？优化方向是什么？**

答案要点：`2 < 30`，落在斜坡上，**带宽受限**。优化方向是"减少搬运字节"：提高数据复用（tiling）、合并访存、把 AoS 改成 SoA、用更小的数据类型、融合多个 kernel 减少中间结果的读写。

**Q3：`ncu` 显示 `DRAM Throughput = 35%`、`Compute (SM) Throughput = 18%`，两者都不高。这说明什么？**

答案要点：**延迟受限（Latency Bound）**。硬件既没被带宽卡住也没被算力卡住，说明 warp 大部分时间在**等**。下一步去看 `Achieved Occupancy` 和 `Warp Stall Reasons`：如果占用率很低且 stall 主要是 Long Scoreboard，提高占用率有用；如果占用率已经很高，说明依赖链太长，需要增加指令级并行。

**Q4：`-Xptxas -v` 显示 `Used 128 registers` 和 `0 bytes spill`。你会怎么做？**

答案要点：先算占用率：假设每 SM 有 65536 个寄存器，`65536 / 128 = 512` 个线程，也就是 16 个 warp。如果 `maxThreadsPerMultiProcessor` 是 2048，那占用率上限只有 25%。**但这不一定是问题** —— 要先用 `ncu` 看瓶颈在哪。如果已经是带宽受限且达标，就不用动；如果是延迟受限，再考虑 `__launch_bounds__` 或减小块大小。注意**没有 spill 说明寄存器用得很值**，强行压会引入 spill。

**Q5：`nsys` 时间线上看到 kernel 之间有 8 微秒的空隙，而 kernel 只跑 5 微秒。怎么办？**

答案要点：这是典型的**提交受限**。对策：用 CUDA Graphs 把一串 kernel 录成图（一次提交整批）；或者合并 kernel（把逐元素的多个操作融合成一个）；或者增大每次处理的数据量。**这时候优化 kernel 本身几乎没用**，因为时间都花在空隙里了。

**Q6：优化之后快了 15%，你怎么判断这是真的还是噪声？**

答案要点：① 预热 + 至少 20 次采样取中位数，比较两个版本的**中位数**而不只是一次结果；② 看抖动范围（极差 / 中位数），如果抖动本身就有 ±10%，15% 的收益不可信；③ 反复交替测量（A/B/A/B），排除系统状态漂移；④ 用 `ncu` 从**指标**上确认（比如 `DRAM Throughput` 真的上升了、`Sectors Per Request` 真的降了）。**只有指标变化和耗时变化一致，才能下结论。**

[第 5 章](ch05_核心算法模式实战.md) 会系统梳理 GPU 上的**通用并行模式**，每一个都给出从朴素到优化的完整演进：
