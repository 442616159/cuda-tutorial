## 0. 本章导读

### 0.1 学完这一章你能做什么

在学完第 1、2 章之后，你已经能让成千上万个线程各干各的活了。但真实程序里，线程很少是「老死不相往来」的：

- 有的计算需要**先等**别的线程把数据准备好；
- 有的结果需要**汇总**到一起去；
- 有的共享状态需要**互斥**地修改；
- 有的数据需要从一块内存**搬**到另一块。

这些全都是「通信与同步」问题。学完本章，你将能够：

1. **判断该用哪一级同步**：warp 内用 `__syncwarp()`、块内用 `__syncthreads()`、跨块用 Cooperative Groups 的 `grid.sync()` 或多 kernel 拆分。再也不会「拿 `__syncthreads()` 打天下」。
2. **解释「为什么我的 kernel 结果时对时错」**：能指出这是竞态、可见性问题还是重排序问题，并选对 `__threadfence` 的变体。
3. **用 Warp Shuffle 做无共享内存的通信**：把 warp 内的归约、前缀和、广播写成寄存器级的 5 行代码，顺手省掉一次 shared memory 往返和若干次 `__syncthreads()`。
4. **正确使用原子操作并识别争用**：知道 `atomicAdd` 什么时候是朋友、什么时候是性能杀手，能用「块内私有直方图」把全局原子操作次数降几个数量级。
5. **理解为什么块间不能直接同步**，并会用 Cooperative Groups 绕过这个限制（同时知道它的硬约束）。
6. **用流和事件把传输与计算重叠起来**：写出一条真正的多流流水线，并用 `cudaEventRecord` / `cudaStreamWaitEvent` 表达跨流依赖。
7. **用 CUDA Graphs 把一串启动「录下来」反复重放**，知道它省的是启动开销而不是计算时间。

### 0.2 一句话主线

> **并行程序里没有「同时」，只有「先后关系」。同步原语的全部工作，就是把你需要的先后关系明确地表达出来。**

你写下的每一句同步语句，都在说一件事：「在这一点上，我要保证某些事已经发生了。」

## 1. 概念讲解

### 1.1 先从一个比喻开始：工厂流水线与交接班

想象一座工厂，里面有 **12 个车间**（SM），每个车间有 **几十条流水线**（warp），每条流水线上有 **32 个工位**（lane）。

- 同一车间里的工人共用**一块白板**（shared memory）。谁往白板上写了字，别人什么时候能看见？—— 这就是**内存可见性**问题。
- 车间主任吹哨时，**所有工人必须同时抬头**，否则有人还在埋头拧螺丝，有人已经开始读白板了 —— 这就是**屏障（barrier）**。
- 一条流水线上的 32 个工位离得极近，可以直接**把手里的零件递给隔壁**，不用跑去动白板 —— 这就是 **Warp Shuffle**。
- 全厂只有一个**打卡机**（全局计数器），几千个人同时去打卡，机器必须一个个处理 —— 这就是**原子操作 + 争用**。
- 12 个车间之间没有内部电话。厂长想让大家「全体暂停」只能靠**全厂广播**（网格级同步），代价极高，而且要求所有人必须都在厂里 —— 这就是**为什么块间不能随便同步**。

### 1.2 为什么需要同步：竞态条件

先看一段「看起来没问题」的代码：

```cpp
__global__ void broken(int* out) {
    __shared__ int s[256];
    int t = threadIdx.x;
    s[t] = t;                  // 每个线程把自己那一格写成自己的编号
    int neighbor = s[t ^ 1];   // 读隔壁线程写的那一格
    out[t] = neighbor;
}
```

你可能会想：「第 2 行执行完，第 3 行才执行，邻居的 `s[t^1]` 当然已经写好了。」

**这个想法是错的。** 原因有三层：

1. **执行单位是 warp，不是线程。** 一个 block 有 256 个线程，那是 8 个 warp。硬件调度器以 warp 为单位推进指令。warp0 完全可能已经执行到第 5 行，而 warp5 还在第 3 行排队。
2. **编译器会重排。** `s[t] = t` 是写共享内存，`s[t^1]` 是读共享内存，地址不同，编译器认为它们无关，完全可以把读提到写前面去（对普通变量它受 C++ 内存模型约束，但对 shared memory 这类受限场景，硬件与编译器都有相当大的自由度）。
3. **写缓冲。** 即使指令顺序对了，写可能还躺在缓冲里没落到共享内存阵列。

由此引出术语：

> **竞态条件（Race Condition）**：程序的最终结果依赖于多个并行执行单元之间的相对推进速度。换句话说，同一份代码、同一份输入，跑两遍可能得到不同结果。

> **未定义行为（Undefined Behavior, UB）**：标准或文档没有规定会发生什么。竞态条件下读到「什么值」就是未定义的：可能是旧值、新值、部分写入的混合值、也可能是看似正常的值。**它可能安静地给出错误答案，而不是崩溃 —— 这才是最可怕的。**

### 1.3 `__syncthreads()`：块内屏障

#### 打比方

`__syncthreads()` 就像车间主任吹的一声哨：

- **哨响之前**：每个工人都必须把手上的活干到「可以放下」的位置；
- **哨响那一刻**：谁都不许往下走，直到**所有人都到达哨位**；
- **哨响之后**：工人才能继续；并且在这之前所有人对白板的修改，现在**所有人都能看见**。

#### 严谨定义

```cpp
void __syncthreads();
```

CUDA 文档给出的语义有三条：

1. **屏障（Barrier）**：调用它的线程会一直阻塞，直到**同一个 block 内的所有线程**都执行到了这个调用点。注意是「线程」，不是「warp」—— 但实际硬件是按 warp 集合的。
2. **内存排序（Memory Ordering）**：在这个调用之前，块内所有线程对全局内存和共享内存的访问，对块内所有线程都是可见的。
3. **所有线程都必须可达**：如果块里有一部分线程永远到不了这个调用点，行为未定义（通常会挂死）。

第 3 条是本章后半段反复要强调的重点。

#### 用在哪里

```cpp
// 典型场景：生产者-消费者
__shared__ float tile[256];
tile[threadIdx.x] = loadFromGlobal(...);   // 各线程分别搬一块数据进来
__syncthreads();                            // 等所有人搬完
float v = tile[255 - threadIdx.x];          // 现在可以放心读别人搬的数据了
```

```cpp
// 典型场景：归约的每一轮都要同步
for (int stride = blockDim.x / 2; stride > 0; stride >>= 1) {
    if (threadIdx.x < stride) s[threadIdx.x] += s[threadIdx.x + stride];
    __syncthreads();      // 下一轮会读别人刚写的值，必须等
}
```

#### 代价

`__syncthreads()` 不是免费的：

- 它让整个 block 的推进速度**对齐到最慢的那个 warp**。哪怕 7 个 warp 早就到了，也要等第 8 个。
- 在循环里频繁调用会让 block 的并行度下降。

但请注意：**块内同步比你想的便宜得多**。真正贵的是网格级同步（见 1.12）。不要因为怕开销就省掉必要的 `__syncthreads()`，那是拿正确性换性能，一定亏。

#### 使用 `__syncthreads()` 的四条铁律

| 编号 | 规则 | 违反后果 |
|---|---|---|
| 1 | 块内**所有**线程都要执行到它 | 未定义行为，通常挂死 |
| 2 | 不能放在会发散的分支里（除非分支条件对全块一致） | 同上 |
| 3 | 不能放在 `if (threadIdx.x < n)` 这种「部分线程提前 return」之后 | 同上 |
| 4 | 它的作用范围只有**一个 block**，管不了别的 block | 误以为跨块同步了，结果错得莫名其妙 |

关于第 3 条，最常见的写法是：

```cpp
// ❌ 错误
if (i < n) {
    s[threadIdx.x] = ...;
    __syncthreads();          // 当 n 不是 blockDim 的整数倍时，部分线程不会进来
}

// ✅ 正确：把提前返回改成"谓词化"
bool active = (i < n);
if (active) s[threadIdx.x] = ...;
__syncthreads();              // 所有人都到
if (active) { ... }
```

第 4 条会在 1.11 详细展开。

### 1.4 `__syncwarp()`：warp 级的最小同步

#### 打比方

如果 `__syncthreads()` 是「全车间吹哨」，那 `__syncwarp()` 就是「一条流水线上拍一下肩膀」。32 个工位本来就挨在一起，拍拍肩膀就够同步了，没必要惊动全车间。

#### 严谨定义

```cpp
void __syncwarp(unsigned mask = 0xffffffff);
```

- 要求 `mask` 中置位的所有 lane 都执行到这个调用点，然后一起继续。
- `mask` 的每一位对应一个 lane（bit 0 对应 lane 0）。
- **需要 Compute Capability >= 7.0（Volta）**。在 Volta 之前，同一个 warp 的 32 个线程是锁步执行的（lockstep），不需要显式同步；Volta 引入了**独立线程调度（Independent Thread Scheduling, ITS）**，同一个 warp 的线程可以有各自的程序计数器，从此「同 warp 内通过 shared memory 传数据」也必须显式同步了。

#### 什么时候用

| 场景 | 该用什么 |
|---|---|
| 两个 warp 之间交换 shared memory 数据 | `__syncthreads()` |
| 同一个 warp 内部通过 shared memory 交换数据 | `__syncwarp()` |
| 同一个 warp 内部直接用 shuffle 交换 | `__shfl_*_sync` 自带同步，不用额外写 |
| 分支之后再汇聚 | `__syncwarp(mask)`，mask 要覆盖所有需要汇聚的 lane |

#### `__activemask()` 的陷阱

`__activemask()` 返回「此刻仍在执行这条指令的 lane 掩码」。它看起来很诱人：

```cpp
// ❌ 危险写法
unsigned m = __activemask();
float v = __shfl_sync(m, value, 0);
```

问题在于：**`__activemask()` 的结果依赖运行时调度，不可预测。** 你拿到掩码和真正执行 shuffle 之间，别的 lane 可能已经退出了。官方文档明确建议：**不要在发散的代码里用 `__activemask()` 去构造 shuffle 的掩码。** 正确做法是在控制流还没分岔时就确定好掩码，或者直接用常量 `0xffffffff`。

### 1.5 内存可见性与重排序：`__threadfence` 三兄弟

#### 打比方

`__syncthreads()` 是「全班举手集合」；`__threadfence()` 则是「把自己的作业交到老师办公室，确保全楼都能查到」。它**不要求别人做任何事**，只保证**你自己的写**已经跑得足够远、足够可见。

#### 为什么需要它

看下面这段「用标志位交接数据」的经典写法：

```cpp
// 生产者线程
data[0] = 42;      // (A) 写数据
flag = 1;          // (B) 写标志位，告诉别人"数据好了"
```

在现代 GPU 上，(B) 完全可能先于 (A) 到达 L2。消费者看到 `flag == 1` 时去读 `data[0]`，可能读到的还是旧值。

注意：这不是「编译器不聪明」，而是**内存模型允许这样做**。要禁止它，就必须显式插入一条**内存栅栏**。

#### 三个变体

| 函数 | 作用范围 | 典型用途 | 相对开销 |
|---|---|---|---|
| `__threadfence_block()` | 一个 block 内 | 块内通过全局内存/共享内存交接 | 最低 |
| `__threadfence()` | 整个设备（所有 block） | 跨块通过全局内存交接、全局归约 | 中 |
| `__threadfence_system()` | 设备 + 主机 + 其他 GPU | 与 CPU 或 P2P 通信，配合页锁定内存 | 最高 |

严谨一点的表述（来自 CUDA 文档）：

> `__threadfence()` 会让调用线程在它之前的所有全局内存和共享内存写操作，在它之后的所有写操作之前，对**设备内所有线程**可见。

三个关键词：**调用线程**、**它之前的写**、**可见**。

- 它**不阻塞**其他任何线程，也不等待任何人。
- 它**不保证别人的写已经完成**，只保证你自己的。
- 它**不保证读到最新值**（那是读方的责任，读方通常需要配合原子操作或 volatile）。

#### 一个必须记住的搭配

想实现「我干完了，通知别人」，正确顺序永远是：

```cpp
写数据;                 // (1)
__threadfence();        // (2) 保证 (1) 已经对全设备可见
atomicExch(&flag, 1);   // (3) 用原子操作发布标志（原子操作本身也是内存屏障）
```

第 3 步一定要用**原子操作**或 `volatile` 写，不能用普通写 —— 否则编译器可能把它优化掉，或者读者可能从缓存里读到旧值。

### 1.6 Warp Shuffle：寄存器级通信

#### 打比方

一个 warp 的 32 个 lane 就像同一条流水线上紧挨着的 32 个工位。Shuffle 就是「把手里的零件直接递给某个工位」，不需要放到白板上再让别人来拿。

#### 为什么快

- 数据不走共享内存，不产生任何访存指令；
- 不需要 `__syncthreads()`，延迟只有几个时钟周期；
- 不占用 shared memory 容量，也就不会挤占占用率。

#### 四个函数（全都带 `_sync` 后缀）

```cpp
// 1. 按 lane 编号取：拿到 srcLane 那个 lane 手里 v 的值
T __shfl_sync(unsigned mask, T var, int srcLane, int width = 32);

// 2. 向上取：拿到 (lane - delta) 那个 lane 的值
T __shfl_up_sync(unsigned mask, T var, unsigned delta, int width = 32);

// 3. 向下取：拿到 (lane + delta) 那个 lane 的值
T __shfl_down_sync(unsigned mask, T var, unsigned delta, int width = 32);

// 4. 异或取：拿到 (lane ^ laneMask) 那个 lane 的值
T __shfl_xor_sync(unsigned mask, T var, int laneMask, int width = 32);
```

参数说明：

- `mask`：参与这次通信的 lane 集合。**`mask` 里点名的 lane 必须都真的执行到了这条指令**，否则结果未定义。全部参与就写 `0xffffffffu`。
- `var`：要传的值（可以是 int / unsigned / long long / float / double，模板自动推导）。
- `width`：把 warp 再细分成若干组，默认 32（整 warp）。比如 `width = 16` 就变成两个独立的 16-lane 小组。
- **越界行为**：如果目标 lane 不存在（比如 `lane - delta < 0`，或 `lane + delta >= 32`），返回的是**调用者自己的值**，不是 0。这一点非常重要，做前缀和时必须用 `if` 把它排除掉。

#### 四个函数的典型用途

| 函数 | 用途 | 一句话记忆 |
|---|---|---|
| `__shfl_sync` | 广播、任意跨 lane 取值 | 「把第 k 号的值给我」 |
| `__shfl_down_sync` | warp 内归约（求和、求最值） | 「把右边邻居的值加给我」 |
| `__shfl_up_sync` | warp 内前缀和 | 「把左边邻居的值加给我」 |
| `__shfl_xor_sync` | 蝶形全归约、全交换 | 「和我对称的那个位置换一下」 |

#### 归约 vs 全归约

```cpp
// 归约：5 步之后只有 lane 0 拿到总和
__inline__ __device__ float warpReduceSum(float v) {
    for (int offset = 16; offset > 0; offset >>= 1)
        v += __shfl_down_sync(0xffffffffu, v, offset);
    return v;
}

// 全归约：5 步之后 32 个 lane 全都拿到总和
__inline__ __device__ float warpAllReduceSum(float v) {
    for (int offset = 16; offset > 0; offset >>= 1)
        v += __shfl_xor_sync(0xffffffffu, v, offset);
    return v;
}
```

为什么 `shfl_down` 只有 lane 0 有完整结果，而 `shfl_xor` 大家都有？画一下 `shfl_down`：lane0 拿 lane16，lane16 拿 lane32（不存在，返回自己的值）。信息总是从**小 lane 流向大 lane**，所以只有最左边的 lane 收全了。而 `xor` 是对称的，信息双向流动，最后所有 lane 都有全部信息。

### 1.7 投票函数：一次问遍整个 warp

#### 打比方

投票就是「举手」：老师问一个问题，全班 32 个人同时举手，老师一眼看过去就知道结果。

#### 三个函数

```cpp
// 1. 拿到位图：第 k 位为 1 表示 lane k 的 pred 为真
unsigned __ballot_sync(unsigned mask, int pred);

// 2. 只要有一个为真就返回非 0
int __any_sync(unsigned mask, int pred);

// 3. 全部为真才返回非 0
int __all_sync(unsigned mask, int pred);
```

注意返回值不同：`__ballot_sync` 返回 **32 位掩码**，`__any_sync` / `__all_sync` 返回 **0 / 1**。

#### 杀手级用法：流压缩（Stream Compaction）

「把数组中所有满足条件的元素，按原顺序紧凑地挪到数组前面」，这是过滤、去重、稀疏化的共同基础。用投票 + `__popc` 只要三行：

```cpp
bool pred = (in[i] >= 0);
unsigned mask = __ballot_sync(0xffffffffu, pred);   // 本 warp 谁的 pred 为真
int count = __popc(mask);                            // 本 warp 有几个合格的
int rank  = __popc(mask & ((1u << lane) - 1));       // 我前面有几个合格的 = 我排第几
```

`__popc(x)` 数二进制里 1 的个数。`mask & ((1u << lane) - 1)` 把 lane 位置以及更高的位全部抹掉，剩下的 1 的个数就是「比我 lane 号小的合格 lane 有几个」，也就是我的排名。

有了 `rank`，每个合格线程就知道自己该写到哪个位置了。跨 warp 的偏移用共享内存串一次前缀和即可（每块通常只有 4～8 个 warp，非常便宜）。

#### 投票函数也是屏障

`__ballot_sync`、`__any_sync`、`__all_sync` 都带 `_sync` 后缀，它们**同时是一次 warp 级同步**：掩码里点名的 lane 必须都执行到这条指令。所以不要在发散的分支里调用它们。

`__syncthreads()` 也有三个「顺便投票」的版本：

```cpp
int __syncthreads_count(int pred);   // 块内 pred 为真的线程数
int __syncthreads_and(int pred);     // 块内是否全为真
int __syncthreads_or(int pred);      // 块内是否存在为真
```

它们都是**块级**的（需要一个完整的 block），而且**隐含一次 `__syncthreads()`**。别把它们当作零成本查询。

### 1.8 原子操作：不可分割的读-改-写

#### 打比方

普通自增 `counter = counter + 1` 是「读出来 → 加一 → 写回去」三步。几千个人同时做这件事，就会发生这种事：

```
时刻 1: 线程 A 读出 counter = 5
时刻 2: 线程 B 读出 counter = 5
时刻 3: 线程 A 写回 6
时刻 4: 线程 B 写回 6      ← 两次自增只留下一次的效果
```

原子操作就是「整条流水线只允许一个人用」：读、改、写三步对外界表现为**不可分割的一个瞬间**。

> **原子操作（Atomic Operation）**：一个对内存的读-改-写序列，从其他线程的视角看，要么完全没发生，要么已经全部完成，不存在中间状态。

#### 常用清单

| 函数 | 作用 | 支持的典型类型 |
|---|---|---|
| `atomicAdd(addr, val)` | `*addr += val`，返回旧值 | int / unsigned / unsigned long long / float / double(CC≥6.0) |
| `atomicSub(addr, val)` | `*addr -= val` | 整数 |
| `atomicMax(addr, val)` | `*addr = max(*addr, val)` | 整数 |
| `atomicMin(addr, val)` | `*addr = min(*addr, val)` | 整数 |
| `atomicExch(addr, val)` | `*addr = val`，返回旧值 | 整数 / float |
| `atomicCAS(addr, cmp, val)` | 若 `*addr == cmp` 则 `*addr = val`，返回旧值 | 整数 |
| `atomicAnd/Or/Xor` | 位运算 | 整数 |
| `atomicInc(addr, val)` | 环形自增：`*addr = (*addr >= val) ? 0 : *addr + 1` | unsigned |
| `atomicDec(addr, val)` | 环形自减 | unsigned |

**注意：整数原子操作没有 `atomicAdd` 之外的双精度版本，也没有 float 版的 `atomicMax`。** 这两件事都需要手工绕一下：

#### 浮点 `atomicMax` 的位技巧

对**非负浮点数**，IEEE-754 的位模式作为整数比较时，大小顺序与浮点大小顺序**完全一致**。所以：

```cpp
atomicMax(reinterpret_cast<int*>(out), __float_as_int(v));   // 只对 v >= 0 成立
```

负数就不能这么干了（符号位是最高位，负数的位模式作为整数反而很大）。要支持负数，需要一个变换：非负数把符号位设成 1，负数整体取反，把它变成单调映射到无符号整数的形式。

#### `atomicCAS`：原子操作的万能钥匙

`atomicCAS` 是唯一一个「条件写」的原子操作，因此可以拿它拼出任何东西：

```cpp
// 手写 double 版原子加（CC < 6.0 时必需；CC ≥ 6.0 有内建版本）
__device__ __forceinline__ double atomicAddDouble(double* address, double val) {
    unsigned long long* p = reinterpret_cast<unsigned long long*>(address);
    unsigned long long old = *p;
    unsigned long long assumed;
    do {
        assumed = old;                    // 记下我读到的值
        // 用 assumed 推出"新值"，然后尝试 CAS：
        // 如果 *p 还是 assumed，就写入新值；否则 CAS 失败并返回最新的 *p
        old = atomicCAS(p, assumed,
                        __double_as_longlong(val + __longlong_as_double(assumed)));
    } while (assumed != old);             // 失败了就拿最新值重试
    return __longlong_as_double(old);
}
```

这是标准的**乐观重试（optimistic retry）**模式：假设没人来抢，抢了再重试。注意它不保证「谁先谁后」，只保证「结果不丢」。

### 1.9 争用：原子操作的性能陷阱

#### 为什么会慢

原子操作在硬件上不是「免费的锁」，而是由 **L2 缓存里的原子单元**完成的。对**同一个地址**的原子操作必须在那里**串行排队**：

- 1000 个线程各做 1 次 `atomicAdd(&counter, 1)`，硬件要处理 1000 次串行的读-改-写，每次几十个周期。
- 1000 个线程各做 1 次 `atomicAdd(&arr[i], 1)`（各自的地址），可以并行在不同 bank 上完成。

软件工程里管这叫**争用（Contention）**：多个执行单元抢同一个资源，导致串行化。

#### 量化一下

在 `code/lessons/ch03_atomics/atomics.cu` 里有一个直接的对比实验，两个 kernel 做**完全相同次数**的原子加，唯一的区别是打向同一个地址还是各自的地址：

```cpp
__global__ void atomToOneAddress(int* counter, int iters) {
    for (int k = 0; k < iters; ++k) atomicAdd(counter, 1);
}

__global__ void atomToOwnAddress(int* counters, int iters) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int* mine = counters + (i * 32);      // 每个线程间隔 128 字节，避免伪共享
    for (int k = 0; k < iters; ++k) atomicAdd(mine, 1);
}
```

在常见的消费级显卡上，两者的差距可以达到**一个数量级以上**（实测约为 10～40 倍，你的机器可能不同）。这个数字不需要你记，你需要记的是**结论**：

> **原子操作的代价主要不在「原子」本身，而在「争用」。** 优化原子操作的第一手段永远是「减少对同一地址的访问次数」。

#### 五种缓解手段

| 手段 | 做法 | 效果 |
|---|---|---|
| 1. 分片（Sharding） | 开 K 个计数器，按 `threadIdx.x % K` 分散写，最后再合并 | 争用降到 1/K |
| 2. 层级化（Hierarchical） | 先在 shared memory 里聚合，最后每块只做一次全局原子 | 全局原子次数降为「块数 × 桶数」 |
| 3. 私有化（Privatization） | 每块/每 warp 一份副本 | 同 2 |
| 4. 换算法 | 用归约代替原子加，用 scan 代替逐个累加 | 从根本上消除 |
| 5. 加退避 | 自旋失败时 `__nanosleep()` 一下 | 减少总线占用 |

第 2 条正是本章直方图实战的核心思想。

### 1.10 自旋锁与无锁结构

#### 自旋锁（Spin Lock）

用 `atomicCAS` 就能拼出一把锁：

```cpp
__device__ int g_mutex = 0;      // 0 = 空闲，1 = 已锁

// 上锁
while (atomicCAS(&g_mutex, 0, 1) != 0) {
    // 自旋等待
}

// ---- 临界区 ----
// 只有拿到锁的线程能进来

// 解锁
__threadfence();          // 先在临界区内的写对其他线程可见
atomicExch(&g_mutex, 0);  // 再释放锁
```

这里有两个容易漏掉的细节：

1. **解锁前必须 `__threadfence()`**。否则你写完临界区数据、马上释放锁，另一个线程拿到锁后可能读到的还是旧数据 —— 锁保护得了「互斥」，保护不了「可见性」。
2. **自旋很浪费**。几千个线程同时空转会把内存总线占满，反而拖慢持锁线程。真实工程里应该加退避：

```cpp
// 需要 CC >= 7.0
while (atomicCAS(&g_mutex, 0, 1) != 0) {
    __nanosleep(20);      // 睡 20 纳秒再试
}
```

#### 什么时候不该用锁

在 GPU 上，锁的性价比通常远低于 CPU：

- 线程数成千上万，锁竞争会呈爆炸式增长；
- 没有操作系统的调度器帮你「让出 CPU」，自旋就是纯浪费；
- 硬件没有为「线程挂起/唤醒」提供廉价机制。

**原则：能用原子操作解决的，不要用锁；能用层级归约解决的，不要用原子操作。** 锁基本只出现在「不得不维护一个复杂共享数据结构」的少数场景（比如设备端的内存分配器、稀疏图的动态更新）。

#### 无锁结构

**无锁（Lock-free）**指的是：算法不依赖互斥锁，而是靠原子操作 + 重试来保证正确性，从而保证「任意时刻至少有一个线程能推进」。典型模式就是上面 `atomicAddDouble` 里的 CAS 循环：

```
do {
    读当前值;
    计算新值;
} while (CAS 失败);
```

进步保证（progress guarantee）比锁好，但活锁（livelock）风险仍然存在，而且实现难度显著更高。第 6 章会看到 CUDA 提供的现成无锁结构。

### 1.11 为什么块间不能直接同步

#### 根本原因：没有「所有块同时在跑」这个保证

假设你写了一个 grid 级屏障：

```cpp
__device__ int g_counter = 0;

__global__ void badBarrier() {
    __threadfence();
    atomicAdd(&g_counter, 1);
    while (g_counter < gridDim.x) { }    // ❌ 自旋等所有块都到齐
    // ...
}
```

这段代码在 CPU 上是可行的（有操作系统帮你调度），在 GPU 上却会**挂死**。原因：

1. **网格里的块不是一次性全部启动的。** 一块 GPU 只能同时驻留有限数量的线程块（受 SM 数量、寄存器、共享内存限制）。假设你的 GPU 同时最多能跑 512 个块，而你的网格有 4096 个块 —— 那么前 512 个块必须**先跑完、退出**，才轮得到后面的块被调度上来。
2. 如果这前 512 个块都在 `while` 里自旋等「4096 个块到齐」，它们在等一个**永远不会满足**的条件（剩下的 3584 个块根本没机会启动）。这就是经典的**死锁**。
3. 更糟的是，**块之间的调度顺序完全没有任何保证**。你不能假设「块 0 一定比块 1 先跑」。

#### 那怎么办？三条出路

| 出路 | 做法 | 适用场景 |
|---|---|---|
| **拆分 kernel** | 把「需要全网格同步」的地方切成一个 kernel 边界 | 最常用、最安全 |
| **原子领号（单次归约模式）** | 每个块交卷 + `__threadfence()` + 原子计数，最后一块负责收尾 | 全局归约、全局最值 |
| **Cooperative Groups** | 用 `cudaLaunchCooperativeKernel` 启动，然后 `grid.sync()` | 需要**多次**全网格同步的算法 |

第一条为什么要提？因为**kernel 的结束本身就是一个天然的全局屏障**。启动两个 kernel，第二个 kernel 一定在第一个完全结束之后才开始。第 2 章里的「两段式归约」就是这个思路：第一个 kernel 每块算一个部分和，第二个 kernel 汇总。

代价是：每次 kernel 边界都有启动开销（约几微秒），而且中间结果必须先落到全局内存。如果算法里需要同步十几次，拆分 kernel 会变得很啰嗦，这时才考虑 Cooperative Groups。

### 1.12 Cooperative Groups：把网格当作一个整体

#### 打比方

Cooperative Groups 相当于给全厂装了一套「对讲机系统」。厂长按下按钮，12 个车间同时收到通知并停下来，等所有人都确认后才一起恢复。代价是：**你必须先申请到「全厂同时开会」的许可**（也就是网格必须能一次性装进 GPU）。

#### 基本用法

```cpp
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ void foo(int* data) {
    cg::grid_group grid = cg::this_grid();           // 拿到"全网格"句柄
    cg::thread_block block = cg::this_thread_block(); // 拿到"本块"句柄

    // ... 每个块各自干活 ...
    block.sync();          // 等价于 __syncthreads()
    // ... 把结果写到全局内存 ...
    grid.sync();           // ★ 全网格屏障：等所有块都到这一步
    // ... 现在可以安全地读别的块写的数据了 ...
}
```

#### 四种粒度的句柄

| 句柄 | 范围 | 获取方式 |
|---|---|---|
| `cg::thread_block` | 一个 block | `cg::this_thread_block()` |
| `cg::thread_block_tile<N>` | block 内 N 个连续线程（通常是 32） | `cg::tiled_partition<32>(block)` |
| `cg::coalesced_group` | 当前活跃的线程集合 | `cg::coalesced_threads()` |
| `cg::grid_group` | 整个 grid | `cg::this_grid()` |

`tiled_partition<32>` 拿到的 tile 自带 `shfl` / `shfl_down` / `shfl_up` / `shfl_xor` / `sync()` / `thread_rank()`，写起来比裸的 `__shfl_*_sync` 更清楚，最大的好处是**不用再手写 `0xffffffff` 掩码**，也就不容易写错。

#### 协作启动的三条硬约束

1. **设备必须支持。** 检查方式：

```cpp
int supported = 0;
cudaDeviceGetAttribute(&supported, cudaDevAttrCooperativeLaunch, dev);
```

2. **必须用 `cudaLaunchCooperativeKernel` 启动**，不能用 `<<<>>>`。

```cpp
void* args[] = {&d_in, &d_out, &n};
cudaLaunchCooperativeKernel((void*)myKernel, dim3(grid), dim3(block), args, shmemBytes, 0);
```

3. **网格必须能一次性全部驻留。** 也就是 `gridDim.x <= 每 SM 能容纳的块数 × SM 数量`。用 occupancy API 求出上界：

```cpp
int blocksPerSm = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&blocksPerSm, myKernel, blockSize, shmem);
int maxGrid = blocksPerSm * prop.multiProcessorCount;
```

超了会直接返回错误 `cudaErrorCooperativeLaunchTooLarge`。

#### `grid.sync()` 的代价与禁忌

- 它要**所有块都到达**，所以耗时由最慢的块决定；网格越大越慢。
- 它**不能在发散的分支或循环里调用**，必须被网格内**所有**线程以相同方式执行到。
- 它会让整个网格的并行度瞬间对齐，通常会打断流水线。**能用两次 kernel 解决的就别用它。**

### 1.13 流（Stream）：把设备当作流水线

#### 打比方

CUDA 的**流（Stream）**就是一条「命令队列」。你把操作压进去，GPU 按**先进先出**的顺序执行同一条流里的操作。不同的流之间**可以并发**。

- **默认流（default stream / NULL stream）**：你不指定流时，所有操作都进这里，全部串行。第 0～2 章写的代码全都在默认流上。
- **显式流**：`cudaStreamCreate()` 创建，用第 4 个启动参数 `<<<grid, block, shmem, stream>>>` 指定。

#### 异步拷贝的前提：页锁定内存

`cudaMemcpyAsync` 只有在**页锁定内存（pinned / page-locked memory）**之间才真正异步：

- 普通 `malloc` 得到的是**可分页内存**。GPU 的 DMA 引擎不能直接访问它，驱动必须先拷贝到一块内部暂存区。既然要中转，就**必须同步**等待，`cudaMemcpyAsync` 于是退化成了同步调用。
- `cudaHostAlloc()` 分配的页锁定内存，DMA 可以直接搬运，`cudaMemcpyAsync` 才真正「提交后立刻返回」。

代价：页锁定内存**不可换出**，分配太多会拖慢整个操作系统。用完记得 `cudaFreeHost()`。

#### 多流流水线

单流串行是这样的：

```
时间 →
H2D(段1) → K(段1) → D2H(段1) → H2D(段2) → K(段2) → D2H(段2) → ...
```

传输和计算完全错开，硬件有一半时间闲着。切成 4 段放到 4 条流上：

```
stream0: H2D(1) → K(1) → D2H(1)
stream1:          H2D(2) → K(2) → D2H(2)
stream2:                   H2D(3) → K(3) → D2H(3)
stream3:                            H2D(4) → K(4) → D2H(4)
```

stream1 的 H2D 用拷贝引擎，stream0 的 K 用 SM —— 两者**并行**。这就是**重叠（overlap）**。

三个前提：

1. 设备有**独立的拷贝引擎**（`cudaDevAttrAsyncEngineCount > 0`）；
2. 用的是**页锁定内存**；
3. 数据量足够大，否则传输时间还不够启动开销。

#### 跨流依赖：事件

流之间默认没有顺序。如果你想表达「stream B 必须等 stream A 的某一步做完」，用**事件（Event）**：

```cpp
cudaEvent_t ev;
cudaEventCreateWithFlags(&ev, cudaEventDisableTiming);

cudaEventRecord(ev, streamA);          // 在 streamA 的时间线上打一个路标
cudaStreamWaitEvent(streamB, ev, 0);   // 让 streamB 等这个路标
```

关键点：**`cudaStreamWaitEvent` 只阻塞目标流上「此后提交的工作」，完全不阻塞 CPU。** 相比之下 `cudaStreamSynchronize` 会把 CPU 卡住。所以做流间依赖时应该用事件，不要用同步。

### 1.14 CUDA Graphs：把一串启动录下来

#### 打比方

每次写 `kernel<<<grid, block>>>(...)`，CPU 都要走一遍完整的启动流程：打包参数、校验、提交命令。这大约要**几微秒**。

现在如果 kernel 本身只跑 10 微秒，那启动开销就占了将近一半。更糟的是，如果 CPU 提交不过来，GPU 就会在 kernel 之间**空转等待** —— 你在 nsys 时间线上会看到一串小空隙。

**CUDA Graphs 的比喻**：与其每次单独下订单，不如先录一份「标准作业流程」，之后一键重放整份流程。

#### 三段式 API

```cpp
// ---- 1. 捕获：把一串提交录成图 ----
cudaStream_t capStream;
cudaStreamCreate(&capStream);
cudaStreamBeginCapture(capStream, cudaStreamCaptureModeGlobal);

    addKernel<<<grid, block, 0, capStream>>>(...);    // 这些都不会真的执行
    mulKernel<<<grid, block, 0, capStream>>>(...);
    mixKernel<<<grid, block, 0, capStream>>>(...);

cudaGraph_t graph;
cudaStreamEndCapture(capStream, &graph);

// ---- 2. 实例化：把图"编译"成可执行的图对象（只做一次）----
cudaGraphExec_t graphExec;
cudaGraphInstantiate(&graphExec, graph, 0);          // CUDA 12 的签名

// ---- 3. 重放：一次调用提交整张图（可以反复来）----
cudaGraphLaunch(graphExec, 0);
```

**捕获期间的禁忌**：不要在捕获流上做同步操作。`cudaDeviceSynchronize()`、`cudaStreamSynchronize()`、以及任何依赖内存内容的 API 都会让捕获失败。`CUDA_CHECK_KERNEL()` 里的 `cudaGetLastError()` 虽然通常无害，但为了保险，捕获代码块里最好什么额外调用都不写。

#### 它省的是什么

| 省 | 不省 |
|---|---|
| CPU 侧的启动开销（每节点几微秒） | GPU 侧的实际计算时间 |
| kernel 之间的间隙 | 内存搬运时间 |
| CPU 占用（可以去做别的事） | 单次 kernel 的执行效率 |

**所以：长 kernel、带宽受限的 kernel 用图几乎没有收益；短小、数量多的 kernel 收益明显。** 一个经验判据是：如果 kernel 本身超过 100 微秒，图的收益可以忽略。

#### 图的其他能力

- **更新节点参数**：`cudaGraphExecKernelNodeSetParams()` 可以在不重新实例化的前提下改 kernel 参数，避免每帧重新建图。
- **自定义节点**：条件节点、循环节点（CUDA 12.3+）、内存分配节点。
- 第 6 章会展开更复杂的图用法。

### 2.1 示例 1：`__syncthreads()` 的语义（`code/lessons/ch03_sync/barrier/sync_basics.cu`）

这个程序把「不加屏障」和「加屏障」写在同一个文件里，直接对比结果。

```cpp
// 版本 A：错误示范 —— 写完 shared memory 后立刻读邻居的数据，中间没有屏障
__global__ void raceNoBarrier(int* out) {
    __shared__ int s[BLOCK];      // 每块一份，块内所有线程共享这块空间
    int t = threadIdx.x;

    s[t] = t;                     // 每个线程把自己那一格写成自己的编号

    // 这里故意不加 __syncthreads()。
    // 你可能会想「隔壁线程应该早就写完了」，但 GPU 的调度单位是 warp（32 线程），
    // 不同 warp 的推进速度完全独立：warp0 可能已经跑到这里，
    // 而 warp5 连 s[t]=t 都还没执行。此刻读 s[t^1] 读到的是未初始化垃圾。
    int neighbor = s[t ^ 1];

    out[blockIdx.x * blockDim.x + t] = neighbor;
}

// 版本 B：正确做法 —— 加一道屏障
__global__ void correctBarrier(int* out) {
    __shared__ int s[BLOCK];
    int t = threadIdx.x;

    s[t] = t;
    // __syncthreads() 同时承担两件事，缺一不可：
    //   (1) 屏障语义：块内每个线程都必须执行到这一行，谁都不能先往下走；
    //   (2) 可见性语义：屏障之前所有线程对 shared/global 的写，
    //       在屏障之后对块内所有线程都可见。
    __syncthreads();

    out[blockIdx.x * blockDim.x + t] = s[t ^ 1];
}
```

第三个 kernel 演示 `__syncthreads_count / _and / _or` 三个「顺便投票」的块级屏障：

```cpp
__global__ void blockVote(const int* in, int* cnt, int* allNonNeg, int* anyZero) {
    int g = blockIdx.x * blockDim.x + threadIdx.x;
    int v = in[g];                       // 每个线程取一个值

    int c = __syncthreads_count(v > 0);  // 本块有多少个正数
    int a = __syncthreads_and(v >= 0);   // 本块是不是全非负
    int o = __syncthreads_or(v == 0);    // 本块有没有 0

    // 与 warp 级投票函数不同，这三个函数给出的是「块」级结果，
    // 所以只需要一个线程负责写回即可。
    if (threadIdx.x == 0) {
        cnt[blockIdx.x]       = c;
        allNonNeg[blockIdx.x] = a;
        anyZero[blockIdx.x]   = o;
    }
}
```

**为什么这么写**：把三个函数的结果都写到寄存器里，再统一由一个线程写回全局内存，避免三次全局写。

### 2.2 示例 2：屏障写进分支里的后果（`code/lessons/ch03_sync/barrier/deadlock_demo.cu`）

```bash
nvcc -O2 -arch=sm_70 -DDEMO_DEADLOCK=1 deadlock_demo.cu -o deadlock_demo
```

程序提供了两种正确改法：

```cpp
// 改法 1：把屏障提到分支之外
__global__ void hoistedBarrierGood(const int* in, int* out) {
    __shared__ int s[BLOCK];
    int t = threadIdx.x;
    int v = in[blockIdx.x * BLOCK + t];

    if (t < BLOCK / 2) {          // 前半块线程负责搬数据
        s[t] = v * 2;
    }
    __syncthreads();              // ★ 放在 if 外面：无论走哪个分支都会到达
    if (t >= BLOCK / 2) {
        out[blockIdx.x * BLOCK + t] = s[t - BLOCK / 2] + v;
    } else {
        out[blockIdx.x * BLOCK + t] = v;
    }
}

// 改法 2：用「统一布尔量」代替分支
__global__ void predicatedBarrierGood(const int* in, int* out) {
    int t = threadIdx.x;
    int v = in[blockIdx.x * BLOCK + t];
    bool active = (v > 0);        // 把「要不要干活」写成布尔量，而不是 if

    __syncthreads();              // 所有线程无条件到达

    out[blockIdx.x * BLOCK + t] = active ? v * 10 : 0;
}
```

**两种改法的选择依据**：如果「要不要参与屏障」这件事本身就和分支条件无关（几乎总是如此），就用改法 1；如果确实需要先算出条件再决定行为，用改法 2 的谓词化写法。

### 2.3 示例 3：`__syncwarp()`（`code/lessons/ch03_sync/warp_sync/syncwarp.cu`）

```cpp
// 场景：warp 内做「右移一格」的数据交换
__global__ void warpShiftShared(const int* in, int* out) {
    __shared__ int s[N];
    int t = threadIdx.x;
    int lane = t & 31;

    s[t] = in[t];

    // 只需要本 warp 的 32 个 lane 对齐；用 __syncthreads() 会拖上整块，
    // 属于「大炮打蚊子」，块越大浪费越明显。
    __syncwarp();

    out[t] = (lane == 0) ? 0 : s[t - 1];
}
```

掩码版本的同步：

```cpp
__global__ void warpPartialSync(int* out) {
    int t = threadIdx.x;
    int lane = t & 31;
    unsigned evenMask = 0x55555555u;   // bit0,bit2,bit4,... 置位
    unsigned oddMask  = 0xAAAAAAAAu;   // bit1,bit3,bit5,... 置位

    int v = lane;
    if ((lane & 1) == 0) {
        __syncwarp(evenMask);          // 只有偶数 lane 会到这里
        v += 100;
    } else {
        __syncwarp(oddMask);           // 只有奇数 lane 会到这里
        v += 200;
    }
    out[t] = v;
}
```

### 2.4 示例 4：`__threadfence()` 与一次性全局归约（`code/lessons/ch03_sync/fence/threadfence.cu`）

这是本章最重要的模式之一：**只用一次 kernel 启动**完成整个数组的归约。

```cpp
__device__ unsigned int g_ticket = 0;      // 全局票据计数器
__device__ float g_partial[MAX_GRID];      // 每个块的部分和

__global__ void reduceOnePass(const float* in, float* out, int n) {
    __shared__ float s[BLOCK];
    int tid = threadIdx.x;
    int bid = blockIdx.x;

    // ---- 第一步：每个线程用网格步长循环累加自己负责的元素 ----
    float v = 0.f;
    for (int i = bid * blockDim.x + tid; i < n; i += blockDim.x * gridDim.x) {
        v += in[i];
    }

    // ---- 第二步：块内归约（shared memory 版本） ----
    s[tid] = v;
    __syncthreads();
    for (int stride = blockDim.x / 2; stride > 0; stride >>= 1) {
        if (tid < stride) s[tid] += s[tid + stride];
        __syncthreads();      // 下一轮要读别人刚写的值，必须同步
    }

    // ---- 第三步：块内 0 号线程负责「交卷」 ----
    if (tid == 0) {
        g_partial[bid] = s[0];      // (1) 把自己的部分和写到全局内存

        // (2) 关键的一行：保证 (1) 已经对全设备可见，否则「最后一个块」
        //     去读别的块的 g_partial 时可能读到的还是旧值 0。
        __threadfence();

        // (3) 原子领号，a 依次取到 0, 1, 2, ..., gridDim.x-1
        unsigned int a = atomicInc(&g_ticket, gridDim.x);

        // (4) 拿到最后一个号的块，说明其他块都已经交卷了
        if (a == gridDim.x - 1) {
            float sum = 0.f;
            for (int b = 0; b < gridDim.x; ++b) sum += g_partial[b];
            *out = sum;
        }
    }
}
```

程序会**重复跑 10 次**并统计正确次数。把 `__threadfence()` 去掉（`nvcc -DNO_FENCE=1`）之后再跑，你可能会看到结果开始不稳定 —— 这就是可见性问题的真实面目。

### 2.5 示例 5：Warp Shuffle 全家桶（`code/lessons/ch03_sync/shuffle/shuffle_reduce.cu`）

四个函数各配一个可复用的内联函数：

```cpp
#define FULL_MASK 0xffffffffu

// 1) warp 内归约：只有 lane 0 拿到完整结果
__inline__ __device__ float warpReduceSum(float v) {
    for (int offset = 16; offset > 0; offset >>= 1) {
        v += __shfl_down_sync(FULL_MASK, v, offset);
    }
    return v;
}

// 2) 蝶形全归约：32 个 lane 全都拿到总和
__inline__ __device__ float warpAllReduceSum(float v) {
    for (int offset = 16; offset > 0; offset >>= 1) {
        v += __shfl_xor_sync(FULL_MASK, v, offset);
    }
    return v;
}

// 3) warp 内前缀和（含自身）
__inline__ __device__ float warpInclusiveScan(float v) {
    int lane = threadIdx.x & 31;
    for (int offset = 1; offset < 32; offset <<= 1) {
        float n = __shfl_up_sync(FULL_MASK, v, offset);
        // 越界的 lane 会拿到自己的值，必须排除，否则会把自己加两遍
        if (lane >= offset) v += n;
    }
    return v;
}
```

**为什么 `warpInclusiveScan` 里必须写 `if (lane >= offset)`**：这是 shuffle 最经典的坑。`__shfl_up_sync` 在源 lane 不存在时返回**调用者自己的值**，如果不过滤，lane 0 会把自己加进自己，结果翻倍。

块级归约（shuffle + shared memory 混合）：

```cpp
__global__ void reduceShuffle(const float* in, float* out, int n) {
    __shared__ float warpSums[BLOCK / 32];
    int tid  = threadIdx.x;
    int lane = tid & 31;
    int wid  = tid >> 5;

    float v = 0.f;
    for (int i = blockIdx.x * blockDim.x + tid; i < n; i += blockDim.x * gridDim.x) {
        v += in[i];
    }

    v = warpReduceSum(v);                        // 每个 warp 内部先归约
    if (lane == 0) warpSums[wid] = v;            // 每个 warp 只写一个数
    __syncthreads();                             // 跨 warp 必须靠屏障 + shared

    // 第一个 warp 负责把 8 个 warp 的部分和收拢
    v = (tid < (int)(blockDim.x >> 5)) ? warpSums[tid] : 0.f;
    if (wid == 0) v = warpReduceSum(v);
    if (tid == 0) atomicAdd(out, v);             // 各块之间用原子加汇总
}
```

程序里同时放了**纯 shared memory 版本** `reduceSharedOnly` 做对照，并做了计时对比。结论你大概率会看到：**两者差不多**。为什么？因为这是一个带宽受限的 kernel（时间都花在从显存读 16 MB 数据上），shared memory 往返的那点开销根本不在关键路径上。

**这正是本章想让你养成的习惯**：一个优化手段值不值得用，不由它的「理论漂亮程度」决定，而由**当前瓶颈在哪里**决定。第 4 章的 Roofline 就是判断这件事的工具。

### 2.6 示例 6：投票函数与流压缩（`code/lessons/ch03_sync/vote/vote.cu`）

```cpp
__global__ void blockCompact(const int* in, int* out, int* blockCount, int n) {
    __shared__ int warpCount[BLOCK / 32];    // 每个 warp 合格元素个数
    __shared__ int warpOffset[BLOCK / 32];   // 每个 warp 在块内的起始偏移

    int tid  = threadIdx.x;
    int lane = tid & 31;
    int wid  = tid >> 5;
    int i    = blockIdx.x * blockDim.x + tid;

    bool pred = (i < n) && (in[i] >= 0);

    // 一次投票拿到整个 warp 的谓词位图
    unsigned mask = __ballot_sync(FULL_MASK, pred);

    // 我在本 warp 合格元素里的排名（0-based）
    int rank = __popc(mask & ((1u << lane) - 1));
    if (lane == 0) warpCount[wid] = __popc(mask);

    __syncthreads();   // warpCount 要被块内所有线程看到

    // 每块只有 8 个 warp，用「一个线程串行前缀和」最划算
    if (tid == 0) {
        int sum = 0;
        for (int w = 0; w < (int)(blockDim.x >> 5); ++w) {
            warpOffset[w] = sum;
            sum += warpCount[w];
        }
        blockCount[blockIdx.x] = sum;
    }
    __syncthreads();   // warpOffset 要被块内所有线程看到

    if (pred) {
        // 块内顺序 = warp 顺序 + warp 内排名顺序，与原始下标顺序一致
        int pos = blockIdx.x * blockDim.x + warpOffset[wid] + rank;
        out[pos] = in[i];
    }
}
```

**为什么两次 `__syncthreads()` 都不能省**：第一次保证「所有 warp 都写完了 `warpCount`」，第二次保证「所有线程都读到了 `warpOffset`」。少任何一个都会产生竞态。

`__any_sync` / `__all_sync` 的用法：

```cpp
__global__ void anyAllKernel(const int* in, int* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int v = (i < n) ? in[i] : 0;

    bool hasNeg  = __any_sync(FULL_MASK, v < 0);        // 本 warp 有没有负数
    bool allEven = __all_sync(FULL_MASK, (v & 1) == 0); // 本 warp 是不是全是偶数

    if ((i & 31) == 0 && i < n) {
        out[i >> 5] = (hasNeg ? 1 : 0) | (allEven ? 2 : 0);
    }
}
```

### 2.7 示例 7：原子操作全家桶（`code/lessons/ch03_atomics/atomics.cu`）

**错误示范 vs 正确示范**：

```cpp
// 非原子自增：*counter = *counter + 1 是「读-改-写」三步，会丢失更新
__global__ void countNonAtomic(volatile int* counter, int iters) {
    for (int k = 0; k < iters; ++k) {
        *counter = *counter + 1;
    }
}

// 原子自增：无论多少线程、多少次，一次都不丢
__global__ void countAtomic(int* counter, int iters) {
    for (int k = 0; k < iters; ++k) atomicAdd(counter, 1);
}
```

**为什么非原子版要加 `volatile`**：不加的话，`-O3` 会把整个循环折叠成 `*counter += iters`，竞态就消失了 —— 你反而看不到 bug。加上 `volatile` 是为了「忠实还原错误」，让竞态真实发生。这是个教学技巧，**不要在真实代码里这么写**。

**`atomicMax` 求浮点最大值**：

```cpp
__global__ void findMaxNonNegative(const float* in, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    float v = in[i];
    if (v < 0.f) return;              // 本例约定输入非负，负数直接跳过
    // 对非负浮点数，IEEE-754 的位模式作为 int 比较时顺序一致

}
```

**手写 double 原子加**：见 1.8 节的 `atomicAddDouble`，完整代码在文件里。

**自旋锁**：

```cpp
__device__ int g_mutex = 0;

__global__ void lockedIncrement(volatile int* counter, int iters) {
    for (int k = 0; k < iters; ++k) {
        while (atomicCAS(&g_mutex, 0, 1) != 0) { /* 自旋等待 */ }
        int tmp = *counter;
        *counter = tmp + 1;
        __threadfence();          // 确保临界区内的写对其他线程可见
```

### 2.8 示例 8：直方图实战（`code/lessons/ch03_atomics_histogram/histogram.cu`）★本章核心

问题：给一个 16 MB 的 `unsigned char` 数组，统计 256 个灰度值各出现多少次。

#### 方案 A：全局原子直方图

```cpp
__global__ void histogramGlobalAtomic(const unsigned char* data, int n,
                                      unsigned int* hist) {
    // 网格步长循环：让有限数量的线程处理任意长度的输入
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n;
         i += blockDim.x * gridDim.x) {
        // 读一次全局内存 + 一次全局原子加 —— 每次都要走 L2
        atomicAdd(&hist[data[i]], 1u);
    }
}
```

**它为什么慢**：对**全局内存**的原子操作要在 L2 的原子单元上排队。256 个桶只占 1 KB，几万个线程随机砸进去，平均每个桶要承受 `n / 256` 次串行访问。而且每次都要经历一次完整的 L2 往返。

#### 方案 B：每块私有 shared 直方图

```cpp
__global__ void histogramSharedPrivate(const unsigned char* data, int n,
                                       unsigned int* hist) {
    // 静态共享内存：256 个 unsigned int = 1 KB，任何设备都放得下
    __shared__ unsigned int local[BINS];

    // ---- 第 1 步：清零私有直方图 ----
    // 256 个桶 / 256 个线程 = 一人一个，循环写法兼容任意 blockDim
    for (int b = threadIdx.x; b < BINS; b += blockDim.x) {
        local[b] = 0u;
    }
    // 必须同步：别的线程马上就要对这些格子做原子加，
    // 如果它还读到「清零前」的旧值，结果就全错了。
    __syncthreads();

    // ---- 第 2 步：统计，全部落在共享内存上 ----
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n;
         i += blockDim.x * gridDim.x) {
        atomicAdd(&local[data[i]], 1u);      // 共享内存原子加，快得多
    }

    // 必须同步：等本块所有线程都统计完毕，local 才是完整的
    __syncthreads();

    // ---- 第 3 步：把私有直方图汇总到全局 ----
    // 全局原子操作的次数从 n 次降到「块数 × 256」次，
    // 而且是同块线程打不同地址，冲突也小得多。
    for (int b = threadIdx.x; b < BINS; b += blockDim.x) {
        unsigned int v = local[b];
        if (v > 0) {                          // 空桶直接跳过，能再省一笔
            atomicAdd(&hist[b], v);
        }
    }
}
```

#### 用数据证明它变快了

程序会做三件事：CPU 对拍验证正确性、各测 20 次取中位数、打印有效带宽。预期输出形状（数字随显卡变化）：

```text

  方案 B 私有直方图 : 不同的桶数 = 0 / 256 ✓

--- 性能对比（各测 20 次取中位数）---
  方案 A 全局原子   :   1.8xxx ms   有效带宽   xx.x GB/s
  方案 B 私有直方图 :   1.3xxx ms   有效带宽   xx.x GB/s
  实测加速比约为 1.3~3 倍（你的机器可能不同）。
```

**这个加速比为什么不是几十倍**？因为方案 A 的时间也**还有一部分花在读数据上**，而读数据这一部分是省不掉的。当原子争用不是绝对瓶颈时，方案 B 的收益就被稀释了。想放大差距，可以：

- 把数据量调小、网格调大（让争用成为主要矛盾）；
- 把 BINS 调大（比如 4096 个桶，shared memory 占用上升）；
- 换成分布更集中的数据（所有线程砸同一个桶）。

**这正是第 4 章要教的思想**：先看瓶颈在哪，再决定优化什么，最后用数据验证收益。

### 2.9 示例 9：Cooperative Groups 网格级归约（`code/lessons/ch03_cooperative/reduce_cg.cu`）

```cpp
__global__ void reduceCooperative(const float* in, float* out, int n) {
    extern __shared__ float s[];                 // 动态共享内存

    cg::grid_group grid = cg::this_grid();
    cg::thread_block block = cg::this_thread_block();

    int tid = threadIdx.x;
    int bid = blockIdx.x;

    // ---- 第 1 步：网格步长累加 ----
    float v = 0.f;
    for (int i = bid * blockDim.x + tid; i < n; i += blockDim.x * gridDim.x) {
        v += in[i];
    }

    // ---- 第 2 步：块内归约（block.sync() 等价于 __syncthreads()）----
    s[tid] = v;
    block.sync();
    for (int stride = blockDim.x >> 1; stride > 0; stride >>= 1) {
        if (tid < stride) s[tid] += s[tid + stride];
        block.sync();
    }

    // ---- 第 3 步：每块交出一个部分和 ----
    if (tid == 0) g_partial[bid] = s[0];

    // ---- 第 4 步：全网格屏障 ----
    // 必须被 grid 内所有线程执行，所以绝对不能出现在任何 if / for 里面
    grid.sync();

    // ---- 第 5 步：0 号块汇总所有部分和 ----
    if (bid == 0) {
        float sum = 0.f;
        for (int b = tid; b < gridDim.x; b += blockDim.x) sum += g_partial[b];
        s[tid] = sum;
        block.sync();
        for (int stride = blockDim.x >> 1; stride > 0; stride >>= 1) {
            if (tid < stride) s[tid] += s[tid + stride];
            block.sync();
        }
        if (tid == 0) *out = s[0];
    }
}
```

启动代码（注意三条硬约束）：

```cpp
// 1) 检查设备支持
int coopSupported = 0;
cudaDeviceGetAttribute(&coopSupported, cudaDevAttrCooperativeLaunch, dev);

// 2) 用 occupancy API 求出「能一次性装下」的最大网格
int blocksPerSm = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&blocksPerSm, reduceCooperative, BLOCK, shmem);
int grid = blocksPerSm * prop.multiProcessorCount;

// 3) 用 cudaLaunchCooperativeKernel 而不是 <<<>>>
void* args[] = {&d_in, &d_out, &n};
cudaLaunchCooperativeKernel((void*)reduceCooperative, dim3(grid), dim3(BLOCK), args, shmem, 0);
```

程序里还演示了 `tiled_partition<32>`：

```cpp
__global__ void tiledPartitionDemo(const float* in, float* out, int n) {
    cg::thread_block block = cg::this_thread_block();
    cg::thread_block_tile<32> tile = cg::tiled_partition<32>(block);

    int i = blockIdx.x * blockDim.x + threadIdx.x;
    float v = (i < n) ? in[i] : 0.f;

    // 与 __shfl_down_sync(FULL_MASK, v, offset) 语义完全相同
    for (int offset = tile.size() / 2; offset > 0; offset >>= 1) {
        v += tile.shfl_down(v, offset);
    }

    int laneInTile = tile.thread_rank();          // 等价于 threadIdx.x & 31
    if (laneInTile == 0) out[i >> 5] = v;         // 每个 warp 写一个结果
}
```

**注意**：`grid.sync()` 的开销远大于 `block.sync()`。程序里打印了耗时和有效带宽，你可以把它和 2.5 节的「两段式归约」比一比 —— 在很多显卡上，**两次 kernel 启动反而比一次 `grid.sync()` 更快**，因为 kernel 边界几乎不花什么额外代价，而网格屏障会把整个 GPU 停下来等齐。

### 2.10 示例 10：流与异步流水线（`code/lessons/ch03_streams/streams.cu`）

```cpp
// 1. 页锁定内存（异步拷贝的前提）
float* h_in = nullptr;
cudaHostAlloc((void**)&h_in, totalBytes, cudaHostAllocDefault);   // 不是 malloc！

// 2. 创建 4 条流
cudaStream_t streams[NSTREAM];
for (int s = 0; s < NSTREAM; ++s) cudaStreamCreate(&streams[s]);

// 3. 基线：默认流上的串行三段式（cudaMemcpy 是同步的）
cudaMemcpy(d_buf, h_in, totalBytes, cudaMemcpyHostToDevice);
scaleKernel<<<gridTotal, BLOCK>>>(d_buf, 2.0f, 1.0f, TOTAL_N);
cudaMemcpy(h_out, d_buf, totalBytes, cudaMemcpyDeviceToHost);

// 4. 多流流水线
for (int s = 0; s < NSTREAM; ++s) {
    float* d_seg = d_buf + (size_t)s * SEG_N;
    // 异步 H2D：立刻返回，实际传输由拷贝引擎后台完成
    cudaMemcpyAsync(d_seg, h_in + (size_t)s * SEG_N, segBytes,
                    cudaMemcpyHostToDevice, streams[s]);
    // 同一个流里的 kernel 会等前面的 H2D 完成才开跑
    scaleKernel<<<gridSeg, BLOCK, 0, streams[s]>>>(d_seg, 2.0f, 1.0f, SEG_N);
    // 同一个流里的 D2H 会等 kernel 完成
    cudaMemcpyAsync(h_out + (size_t)s * SEG_N, d_seg, segBytes,
                    cudaMemcpyDeviceToHost, streams[s]);
}
// 异步 API 只保证「提交」，必须显式同步才知道全部干完
for (int s = 0; s < NSTREAM; ++s) cudaStreamSynchronize(streams[s]);
```

跨流依赖：

```cpp
cudaEvent_t ev;
cudaEventCreateWithFlags(&ev, cudaEventDisableTiming);

scaleKernel<<<gridSeg, BLOCK, 0, streams[0]>>>(d_buf, 1.0f, 0.0f, SEG_N);
cudaEventRecord(ev, streams[0]);          // 在 stream0 的时间线上打一个路标
cudaStreamWaitEvent(streams[1], ev, 0);   // 让 stream1 等这个路标
```

## 3. 代码逐行解析

前面每个示例都配了注释，这一节挑三个最容易踩坑的地方，把「为什么」讲透。

### 3.1 解析：为什么 `__syncthreads()` 不能放进分支

```cpp
if (t < BLOCK / 2) {
    __syncthreads();      // ← 问题出在这里
    out[t] = 1;
} else {
    out[t] = 2;
}
```

逐层拆解：

1. **`__syncthreads()` 的语义是「等块内所有线程」。** 它不是「等这个 warp」。
2. **`if (t < BLOCK/2)` 把块切成了两半。** 256 个线程里，前 128 个（warp0～warp3）会进入 if 分支，后 128 个（warp4～warp7）进入 else。
3. **warp4～warp7 永远执行不到 `__syncthreads()`。** 于是前 128 个线程在屏障上等一个永远不来的集合。
4. **后果是「未定义行为」。** 在 Volta 之前，硬件会让整个 warp 卡住，于是 kernel 挂死（需要 `Ctrl+C`，有时连 `nvidia-smi` 都会短暂无响应）。在 Volta 及以后，由于**独立线程调度**，硬件可以只把「一部分线程」挂住，行为更加不可预测。
5. **注意这不是「可能出错」，而是「一定错」。** 只不过错误的表现形式（挂死 / 结果错 / 看起来正常）取决于硬件。**任何依赖运行结果来验证的调试方式都不可靠，必须靠规则。**

顺便说明：**发散的分支里可以读共享内存、可以写共享内存，只有「屏障」这一步不许发散。** 你需要的是把屏障提到所有线程都会经过的外层。

### 3.2 解析：shuffle 的越界语义，以及为什么前缀和必须过滤

```cpp
__inline__ __device__ float warpInclusiveScan(float v) {
    int lane = threadIdx.x & 31;
    for (int offset = 1; offset < 32; offset <<= 1) {
        float n = __shfl_up_sync(FULL_MASK, v, offset);
        if (lane >= offset) v += n;      // ★ 这一行
    }
    return v;
}
```

逐轮推演（用 4 个 lane 举例，`v` 初值分别为 `a0 a1 a2 a3`）：

| 轮次 | offset | `__shfl_up_sync` 返回 | 过滤后 `v` |
|---|---|---|---|
| 初始 | — | — | `a0 a1 a2 a3` |
| 第 1 轮 | 1 | `a0 a0 a1 a2`（lane0 越界返回自己） | `a0 a0+a1 a1+a2 a2+a3` |
| 第 2 轮 | 2 | `a0 a0 a0 a0+a1` | `a0 a0+a1 a0+a1+a2 a0+..+a3` |

- 第 1 轮 lane0 的 `n` 是**它自己的 `a0`**。如果不过滤，`v` 会变成 `a0 + a0 = 2*a0`，后面全错。
- 第 2 轮 lane1 的 `n` 也是自己的值（`a0+a1`），同样必须过滤。

**记住这条规则**：`__shfl_up_sync` / `__shfl_down_sync` 在源 lane **不存在**时返回**调用者自己的值**。凡是「按位置偏移取值」的算法，都要显式处理越界 lane。

对比一下 `__shfl_xor_sync`：因为 `lane ^ offset` 只要 `offset < 32` 就永远落在 `[0, 32)` 内，**不可能越界**，所以蝶形归约不需要任何 `if`。这也是它比 `shfl_down` 更适合做「全归约」的原因。

### 3.3 解析：直方图为什么要在 shared memory 里做

把两种方案的关键差异列成表：

| 维度 | 方案 A 全局原子 | 方案 B 私有 shared 直方图 |
|---|---|---|
| 每次统计的延迟 | 一次 L2 原子往返（几十～几百周期） | 一次 shared memory 原子（约十几周期） |
| 全局原子操作总次数 | `n`（1600 万次） | `块数 × 桶数`（例如 2560 × 256 ≈ 65 万次） |
| 争用程度 | 256 个桶，平均每个桶被砸 6.5 万次 | 同一 block 内 256 个线程砸 256 个桶 |
| 额外的 shared memory 开销 | 无 | 1 KB / block（会轻微降低占用率） |
| 额外的 `__syncthreads()` | 无 | 2 次 / block |
| 额外清零开销 | 无 | `BINS` 次写 |

**结论依赖数据的形状**：

- 桶数少、数据量大、桶分布集中 → 方案 A 的争用极其严重，方案 B 收益巨大。
- 桶数多（比如 65536 个桶）→ 私有直方图放不进 shared memory，方案 B 不可行，只能回到 A 或做分片。
- 数据量很小 → 方案 B 的两次 `__syncthreads()` 和清零开销反而占主导，可能更慢。

**这正是「优化必须测量」的原因。** 你不能背下结论，你只能背下**方法**：先算清楚两种方案各做了什么、代价在哪，再用计时数据验证。

### 3.4 解析：`atomicInc` 的「环形」语义

```cpp
unsigned int a = atomicInc(&g_ticket, gridDim.x);
```

`atomicInc` 的定义是：

```cpp
old = *addr;
*addr = (old >= val) ? 0 : old + 1;
return old;
```

当 `val = gridDim.x` 时，`old` 从 0 递增到 `gridDim.x - 1`，再下一次就超过等于 `val`，于是回绕到 0。所以**只要在此之前把 `g_ticket` 清零**，每个块拿到的 `a` 就正好是 `0 .. gridDim.x-1` 的一个不重复排列（具体谁拿到谁不保证），拿到 `gridDim.x - 1` 的那个块就是「最后一个交卷的」。

注意两个坑：

1. `atomicInc` 的第二个参数是 `unsigned int`。传 `gridDim.x`（也是 `unsigned int`）没问题，传负数会得到奇怪的结果。
2. **计数器必须每次运行前清零。** 程序里用了一个 `resetTicket<<<1,1>>>()` 的 kernel。忘了清会让第二次运行的结果完全错误。

```bash
# 共享内存竞态（对本章特别有用）
```

## 6. 常见错误与排查

| 错误信息 / 现象 | 原因 | 解决办法 |
|---|---|---|
| 程序挂死，`Ctrl+C` 才退出，`nvidia-smi` 显示 GPU 100% | `__syncthreads()` 被放在发散的分支里，或有线程提前 `return` 了 | 把屏障提到所有线程都经过的外层；把 `if (i < n) return;` 改成谓词化写法 |
| 结果偶尔正确、偶尔错误，反复运行结果不同 | 竞态条件（缺屏障 / 缺 `__threadfence` / 缺原子操作） | 用 `compute-sanitizer --tool racecheck` 定位；检查所有「先写后跨线程读」的地方 |
| 结果和 CPU 对拍差一点，差值不固定 | 浮点累加顺序不确定，正常的舍入误差 | 改用 `double` 累加、分块求和或 Kahan 求和；容差用相对误差而不是绝对误差 |
| `atomicAdd` 编译报错：no instance matches | 对 `double` 使用 `atomicAdd` 但目标架构低于 `sm_60` | 加 `-arch=sm_60` 以上，或使用 `atomicCAS` 手写的 `atomicAddDouble` |
| `__shfl_down_sync` 结果不对，只有部分 lane 对 | 掩码写成具体数值但参与的 lane 与掩码不符 | 全 warp 参与就写 `0xffffffffu`；掩码必须覆盖所有真正执行这条指令的 lane |
| kernel 启动返回 `cudaErrorCooperativeLaunchTooLarge` | 协作启动的网格超过了「一次性驻留」的上限 | 用 `cudaOccupancyMaxActiveBlocksPerMultiprocessor × SM 数` 重新计算网格 |
| `cudaLaunchCooperativeKernel` 返回 `cudaErrorInvalidDeviceFunction` | 设备不支持协作启动 | 先用 `cudaDevAttrCooperativeLaunch` 检查；不支持就改用两次 kernel 启动 |
| `cudaMemcpyAsync` 看起来并没有异步，时间线和同步拷贝一样 | 用的是 `malloc` 的可分页内存 | 改用 `cudaHostAlloc()` / `cudaMallocHost()` 分配页锁定内存，并且不要超过物理内存的一小部分 |
| 多流程序反而更慢了 | 数据段太小，传输时间 < 启动开销；或者设备只有 1 个拷贝引擎 | 增大每段的数据量；检查 `cudaDevAttrAsyncEngineCount` |
| `cudaStreamBeginCapture` 返回错误 | 捕获期间执行了同步操作（`cudaDeviceSynchronize` / `cudaStreamSynchronize` / 同步版 `cudaMemcpy`） | 捕获块里只用异步 API；把校验和日志放到捕获之后 |
| `cudaGraphInstantiate` 参数个数不对 | CUDA 版本差异（12.0 改成三参数版本） | 用 `#if CUDART_VERSION >= 12000` 条件编译 |
| 自旋锁程序跑得极慢，几乎不动 | 大量线程原地空转，把 L2 带宽吃光了 | 加 `__nanosleep()` 退避；或者干脆不要用锁，改用原子操作 / 层级归约 |
| `__activemask()` 拿到的掩码不是 `0xffffffff`，shuffle 结果乱 | 在发散的代码里用了 `__activemask()` | 在控制流分岔之前就把掩码算好并保存；或者直接用 `0xffffffffu` |
| 直方图方案 B 偶尔不对，方案 A 反而对 | 私有直方图的清零或汇总缺了屏障 | 补齐两处 `__syncthreads()`，并用 `racecheck` 验证 |

## 7. 本章小结

### 7.1 要点清单

- **同步的本质是表达「先后关系」**，而不是「让程序变慢」。你没有写同步的地方，硬件有权以任意顺序执行。
- **`__syncthreads()` 有两层语义**：屏障 + 可见性。它的作用范围只有**一个 block**。
- **屏障必须被块内所有线程到达。** 三条铁律：不放在发散分支里、不放在提前 `return` 之后、不放错作用范围。
- **`__syncwarp()` 是 warp 级同步**，CC ≥ 7.0 起必需（因为独立线程调度）。`__activemask()` 结果不可预测，不适合构造 shuffle 掩码。
- **`__threadfence()` 三兄弟只管「自己的写对谁可见」**，不阻塞任何人。跨块交接数据的固定搭配是「写数据 → `__threadfence()` → 原子发布标志」。
- **Warp Shuffle 是寄存器级通信**：四个函数分别对应广播、归约、前缀和、全交换。记住「越界返回自己的值」这条语义，前缀和必须过滤。
- **投票函数一次问遍整个 warp**：`__ballot_sync` 给位图，`__any_sync` / `__all_sync` 给布尔。配合 `__popc` 可以做出排名，是流压缩的核心。
- **原子操作的代价主要在争用，而不是原子本身。** 缓解手段按优先级：层级化 > 分片 > 私有化 > 换算法 > 退避。
- **浮点 `atomicMax` 的位技巧只对非负数成立**；double 原子加在 CC < 6.0 时要用 CAS 自己实现。
- **自旋锁在 GPU 上通常不划算**，而且解锁前必须 `__threadfence()`。
- **块间不能直接同步的根因是「网格不一定能全部驻留」**。出路是拆分 kernel、原子领号，或者 Cooperative Groups。
- **Cooperative Groups 的 `grid.sync()` 有三条硬约束**：设备支持、用 `cudaLaunchCooperativeKernel` 启动、网格能一次性驻留。
- **流的价值在于重叠**：页锁定内存 + `cudaMemcpyAsync` + 多流，把传输和计算叠起来。跨流依赖用事件，不要用同步。
- **CUDA Graphs 省的是启动开销和 kernel 间隙**，不是计算时间。kernel 越长收益越小。

### 7.2 自检问题

**Q1：`__syncthreads()` 和 `__threadfence()` 有什么区别？**

答案要点：`__syncthreads()` 是「集合 + 可见性」，它**强制所有线程停在同一个点**，作用范围是 block；`__threadfence()` 只约束**调用线程自己的写**的可见顺序，**不阻塞任何人**，作用范围可以是 block / device / system 三级。前者用来协调「大家一起往下走」，后者用来协调「我的写要被别人先看到」。

**Q2：写一段代码，用一次 kernel 启动完成整个数组的求和，并说明为什么它是正确的。**

答案要点：见 2.4 节的 `reduceOnePass`。正确性来自三点：(1) 每块把部分和写到全局内存；(2) `__threadfence()` 保证这次写对全设备可见之后才继续；(3) `atomicInc` 原子领号，拿到最后一个号的块必然在所有其他块的写都可见之后才开始读。缺任何一环都可能读到旧值。

**Q3：`__shfl_up_sync(mask, v, 4)` 在 lane 2 上返回什么？**

答案要点：lane 2 - 4 = -2，越界。按语义返回**调用者自己的值**（也就是 lane 2 的 `v`），而不是 0，也不是未定义。所以做前缀和时必须用 `if (lane >= offset)` 把它排除。

**Q4：为什么直方图的方案 B 要用两次 `__syncthreads()`？分别防什么？**

答案要点：第一次在清零之后，防止别的线程读到「还没清零」的旧值就开始做原子加；第二次在统计完成之后、汇总之前，防止还没统计完就往全局累加。

**Q5：`grid.sync()` 和「启动两个 kernel」有什么取舍？**

答案要点：`grid.sync()` 省掉了 kernel 启动开销和中间结果的二次读写，但它要求网格一次性全部驻留，而且屏障本身要让整个 GPU 停下来等齐，网格越大越贵。拆成两个 kernel 更灵活、更稳，代价是启动开销（几微秒）和一次全局内存往返。**多数情况下两个 kernel 更快、更简单。**

**Q6：`cudaMemcpyAsync` 在没有页锁定内存时会怎样？**

答案要点：目标/源是可分页内存时，驱动必须先通过一块内部暂存区中转，这一步**必须同步等待**，于是 `cudaMemcpyAsync` 在语义上退化成一个阻塞调用，多流重叠也就无从谈起。所以异步拷贝的前提是 `cudaHostAlloc` / `cudaMallocHost` 分配的页锁定内存。
